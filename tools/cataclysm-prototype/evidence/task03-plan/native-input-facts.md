## Вердикт и поток

Рекомендуется **один новый узкий игровой `ACTION_*` + родной `string_input_popup` + один долгоживущий семантический координатор за локальным IPC**. Новый action нужен лишь для открытия free-text и передачи намерения; он не становится вторым исполнителем механики. Координатор запускается один раз до CDDA (срок жизни сессии), принимает запросы и обращается к локальному Qwen через уже существующий JS runtime/provider. Игра остаётся единственным писателем `userdir`. Для первой проверки использовать fake coordinator; реальный Qwen только после OK владельца (arch4 verdict §3 п.6).

Точный предлагаемый flow: `main` live loop (`src/main.cpp:883`, карта; файл CBM частичный, строка по snapshot ещё требует проверки) → `game::do_turn` (`src/do_turn.cpp:640-682`) → `game::handle_action` (`src/handle_action.cpp:3164,3195,3220,3381`) → зарегистрированный action через `input_context` (`src/handle_action.cpp:242,272`; `src/action.cpp:479-509`, пример регистрации `:989`) → родной popup (`src/string_input_popup.cpp:383-391,469-508`) → если confirm и непустая строка, собрать **read-only наблюдение** из живого мира → IPC к resident JS coordinator → `runP3TurnStep`/semantic owner формирует предложение → CDDA проверяет применимость и вызывает штатные `avatar_action`/`Character`/EOC/`assign_activity` в том же процессе и action dispatch → CDDA сам двигает часы, NPC, звук и save. Конкретный native dispatch предложений надо спроектировать по уже имеющимся действиям; произвольный «action string» в `look_up_action` не содержит параметров (`src/action.cpp:479-509`).

Граница: JS владеет толкованием намерения и Qwen-конфигурацией; CDDA владеет наблюдаемой физикой, целями, activity, временем и save. IPC отвечает только структурированным предложением; не пишет world/userdir, не дёргает headless native adapter. `p3-boundary.js:982-1004` сейчас `execFile` native на вызов; `p3-runner.js:24-26,60-72` строит именно этот adapter. Их нельзя непосредственно присоединить к curses live loop. Новый resident IPC server и узкий native client — **планируемый, ещё не существующий** шов. В `src` snapshot прямой поиск `curl_easy_init/curl_easy_perform/httplib::/boost::asio/asio::ip::tcp/CURLcode` совпадений не дал; готовый CDDA HTTP client не установлен этим исследованием. Node `fetch` уже используется в `p3-wire-smoke.mjs:202,269`; runtime/provider надо проверить отдельно до кодирования транспорта. Предпочтение для WSL: локальный Unix socket через Node `net` и малый native client, без shell/процесса на реплику. Конкретный C++ socket API/сборочную зависимость нужно source-verify при плане реализации; сейчас это предложение, не подтверждённый CDDA API.

Escape/cancel (`TEXT.QUIT`) возвращает `_canceled` и пустую строку (`src/string_input_popup.cpp:490-499`); confirm возвращает текст (`:500-508`). Пустой ввод, cancel, недоступный coordinator, timeout/плохой ответ: сообщение игроку, без применённых операций и расхода игрового времени; возврат в `handle_action`/`do_turn`, CDDA не завершается. Сетевое ожидание ограничить timeout; на успешном ответе проверить полностью до первого native mutation, чтобы отказ не оставил полумир. Не удерживать второй writer/userdir lock. Цена игрового времени — только успешные native actions/activity; реальное ожидание Qwen не тратит игровые секунды. При ошибке после первой mutation простой rollback не доказан: план должен задать допустимые атомарные границы/частичный результат, не обещать транзакцию.

## Альтернативы

- **Родной EOC input есть**: `set_string_var` + `string_input` (`src/npctalk.cpp:6040-6099,8730`; `doc/JSON/EFFECT_ON_CONDITION.md:3885-3905`) открывает `string_input_popup_imgui`, сохраняет строку в `target_var`; cancel подставляет default. Это удобный прототип free text в CDDA и может быть UI внутри нового action. Сам JSON/EOC не зовёт внешний Qwen и не доставляет обратно произвольный структурированный план; `u_query` (`src/condition.cpp:2537`) — условие UI, не семантический транспорт. Отдельно проверить curses-поведение `string_input_popup_imgui`: source показывает ImGui callback (`src/input_popup.cpp:145-190,335-366`), runtime curses не запускался.
- **Только существующий `ACTION_CHAT`**: `src/npctalk.cpp:1241-1258` уже просит sentence/emote; emote явно «no in-game effect», chat — отдельная семантика и меню. Перехват исказит родной chat. Новый action меньше меняет действующее поведение.
- **Внешний coordinator с file adapter**: `p3-boundary.js:812,951-1004` использует файлы/`execFile`; второй native процесс и writer на тот же `userdir` нарушают живой loop. Допустим лишь после замены на resident IPC + read-only projection без save записей.
- **Прямой native HTTP → Qwen**: в проверенном snapshot готовый client не найден, тогда C++ пришлось бы владеть LLM settings/roles. Дублирует существующий semantic owner; не выбирать без нового доказательства.

`npc_make_sound`/`u_make_sound` зарегистрированы `src/npctalk.cpp:8632`; `f_make_sound` выбирает `speech` и вызывает `sounds::sound` с actor position, volume, текстом (`:6380-6454`). Прямой `sounds::sound(string)` в `src/sounds.cpp:322-344` кладёт событие в очереди; `process_sound_markers` считает слух/расстояние и вызывает `npc::handle_sound` (`:571-665`); `do_turn` обрабатывает markers и sounds (`src/do_turn.cpp:627,634,653,657,742`). Следовательно, для *точного* LLM-текста безопаснее узкий native вызов `sounds::sound` с `sound_t::speech`, не `npc::say` (arch4 verdict §3 п.4); переменную EOC через `translation_or_var` дополнительно проверить на буквальность/теги и escaping. `npc::handle_sound` `src/npctalk.cpp:1544+`; громкость — native модель, не JS фильтр/фиксированное 6.

`ACTION_WAIT` вызывает меню `wait()` → `assign_activity(wait_activity_actor(time_to_wait))` (`src/handle_action.cpp:1119,1262,2821`); `wait_activity_actor::start` ставит `moves_total/left`, `finish` завершает (`src/activity_actor.cpp:13970-13991`), `ACT_WAIT` тип (`src/activity_actor_definitions.h:4135-4160`; `data/json/player_activities.json:242`). Это нативная цена длительности, но **не доказан** способ привязать частично произнесённый текст к прерыванию: actor не хранит реплику, finish лишь сообщает «finish waiting». Для речи план должен сначала проверить прерывание и `moves_left`; ACT_GENERIC_EOC не объявлять готовым решением (arch4 verdict §3 п.4).

## Уточнение: activity hook и curses popup

`src/main.cpp:883` теперь прочитан прямо: `while( !g->do_turn() ) {}`. Для curses использовать именно `string_input_popup`: он создаёт `catacurses::newwin` (`src/string_input_popup.cpp:97-104`) и имеет `query_string` (`:383`); штатный пример — поиск карты (`src/overmap_ui.cpp:1505-1512`). `string_input_popup_imgui` из `set_string_var` — иной UI путь; его пригодность curses остаётся непроверенной, для нового action он не нужен.

Нативный hook завершения **есть**: `player_activity::do_turn` при `moves_left<=0` запускает `type->completion_EOC`, затем `character_finished_activity(..., canceled=false)` (`src/player_activity.cpp:350-363`); `player_activity::canceled` отправляет тот же event с `canceled=true` (`:392-399`), включая путь `Character::cancel_activity` (`src/character.cpp:5393-5395`). Поля события — character/activity/canceled (`src/event.h:331-338`, `doc/JSON/EFFECT_ON_CONDITION.md:1835`). `activity_type` читает `completion_eoc` (`src/activity_type.cpp:101`). Значит отдельный actor/scheduler **не нужен только ради сигнала конца**.

Но `ACT_WAIT` общий: его JSON (`data/json/player_activities.json:242-250`) не содержит `completion_eoc`, `wait_activity_actor::finish` лишь сообщает о завершении и обнуляет activity (`src/activity_actor.cpp:13976-13980`). Готовая композиция «именно эта реплика → ждать → sound лишь при полном завершении → очистить pending при cancel/save/reload» **не доказана**. Общий `completion_eoc` на ACT_WAIT затронет все ожидания; event требует маркер конкретной реплики и защиту от повторения/потери. Для плана: сначала spike с fake репликой через штатный `character_finished_activity`/EOC и проверка exact text, cancel, save/reload; до этого пометить как gap. Новый activity actor не заявлять необходимым и не считать готовым обходом.
