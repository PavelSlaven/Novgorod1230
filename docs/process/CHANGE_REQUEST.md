# Change request (CR)

> Процедура. Норм не создаёт: при конфликте действует AGENTS.md, CONTRACT_INDEX и профильные контракты. Проверено: 2026-09-25, commit 21bd0938.

CR — короткая спецификация задачи **до кода**. Он фиксирует то, что [AGENTS.md](../../AGENTS.md) §18 требует
установить перед изменением: результат, границы, критерии готовности, owner и контракты. CR живёт в GitHub issue
(форма `.github/ISSUE_TEMPLATE/change_request.yml`; работает после merge в default branch). До этого issue
оформляется вручную по тем же полям через `gh issue create`.

Пример оформленного CR: [issue #99](https://github.com/PavelSlaven/Novgorod1230/issues/99) (DOC-01).

## Когда CR нужен

Нужен, если выполняется хотя бы одно:

- затронуто больше одного владельца (пакет, app, tool, каталог данных);
- меняется публичный контракт: schema, operation, API, package export (AGENTS §21);
- меняется persistence: DDL, миграции, transaction, idempotency, replay (AGENTS §23);
- меняется граница code/LLM: authority, prompt, request/plan contract (AGENTS §6–§7);
- создаётся новый модуль (AGENTS §16, §21).

Не нужен для небольшой локальной правки с известным owner: короткий план или сразу работа (AGENTS §18).
Если сомневаетесь — пишите CR: он короче, чем переделка.

## Формат

Не больше одной страницы. Поля — ровно эти, в этом порядке (совпадают с issue-формой):

```markdown
## Цель
<какой наблюдаемый результат нужен и зачем — 1–3 предложения>

## Тип задачи
<строка маршрутизации AGENTS.md: docs-only / governance / нормативный корпус / tooling / gameplay / NPC / spatial /
time / items / persistence / UI / world-catalog / bugfix / release …>

## Уровень качества и допустимый долг
<прототип / рабочее решение / финальное; какой техдолг разрешён и в какой LW он записывается>

## Владельцы и MODULE.md
<authoritative owner каждой изменяемой ответственности и путь к его MODULE.md (AGENTS §15)>

## Context pack
<разделы AGENTS.md; строка CONTRACT_INDEX §8.1 и документы из неё; docs/context/*; ключевые файлы и тесты>

## Не трогать
<файлы, контракты, статусы, чужие PR, которые остаются неизменными>

## Критерии готовности
- <наблюдаемый критерий 1>
- <…>
- unseen-equivalent: <разумный случай, которого нет в задании и тестах, и что для него должно работать
  без нового enum/handler/allowlist (AGENTS §5, §28.9)>

## Проверки
<конкретные команды по docs/context/TESTING.md; полный npm test — только CI>

## Contract Auditor
<да/нет и почему — по триггерам AGENTS §25.1>

## Техдолг
<LW-### из docs/work/LEGACY_WARNINGS.md, которые затронуты, добавляются или закрываются; «нет»>
```

## Как заполнять

- **Цель** — результат, а не список правок. Implementation details не согласуются с человеком (AGENTS §18).
- **Тип задачи** — строка маршрутизации роутера [AGENTS.md](../../AGENTS.md).
- **Уровень качества и допустимый долг** — насколько доводить результат и какой долг разрешён. Разрешённый долг записывается в LEGACY_WARNINGS в том же PR; неразрешённый долг — причина вернуть работу.
- **Владельцы** — по [MODULE_INDEX.md](../../MODULE_INDEX.md), `MODULE.md` и реальным imports/callers, не по памяти
  (AGENTS §15). Одна ответственность — один owner.
- **Context pack** — по шагу 3 [WORKFLOW](WORKFLOW.md). Только то, что реально нужно задаче.
- **Не трогать** — явные границы scope (AGENTS §29: не расширять scope без необходимости). Для защищённых файлов
  (любой `AGENTS.md`) — без явного разрешения администратора в задаче (AGENTS §1.1).
- **Критерии готовности** — проверяемые. Unseen-equivalent случай нужен всегда, когда меняется свободное
  gameplay-поведение (AGENTS §24); для docs/tooling — аналог «новый, не упомянутый в задаче случай, который тоже
  должен ловиться». Пример из #99: новая ссылка на несуществующий путь в любом новом docs-файле роняет тест.
- **Проверки** — минимальный набор затронутой области (AGENTS §24), команды из
  [TESTING](../context/TESTING.md).
- **Contract Auditor** — «да», если сработал любой триггер AGENTS §25.1 (публичная schema, DDL/persistence, LLM
  authority, нормативный документ, статус профиля и т. д.). «Нет» — с доказательством, что public behavior,
  contracts, owner boundary, persistence, LLM authority и active profile status не меняются (AGENTS §25.1).
- **Техдолг** — найти LW по путям задачи через `rg` в [LEGACY_WARNINGS](../work/LEGACY_WARNINGS.md). С известным
  костылём жить без попутного рефакторинга; если он блокирует — отдельный issue и решение владельца.

## Жизненный цикл

1. Автор (владелец или агент по заданию владельца) создаёт issue по форме или `gh issue create`.
2. Существенно разные продуктовые варианты уточняются у владельца до кода (AGENTS §18).
3. Исполнение — по [WORKFLOW](WORKFLOW.md); PR ссылается `Closes #N`.
4. Изменение scope по ходу работы — правка тела issue, а не молчаливое расширение PR.
