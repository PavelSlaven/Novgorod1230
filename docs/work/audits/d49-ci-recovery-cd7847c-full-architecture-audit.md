## Межмодульные проверки, существенные для решения

1. **Occurrence и replay.** `occurrence_ref` входит в candidate identity только для finite extraction, а request identity повторно строится одинаково на этапе preflight/presence. Один operation на один domain step предотвращает неоднозначность для разных извлечений. Added `issue-730-finite-occurrence` tests фиксируют повторное распознавание того же occurrence и distinct steps. Это общий механизм, не отдельный сценарный handler.
2. **Outcome и намерение.** Narrator получает confirmed outcomes отдельно от intent; audit prompt прямо запрещает выводить переход, успех, ответ или предметное использование из намерения. Semantic repair повторно строит целую сцену, сохраняя доказанные положения и порядок, а не переписывает последствия в turn owner.
3. **Наблюдаемая сцена и D158.** `lower-dvina-trace-turn-step-current-scene.js` собирает текущую видимую сцену, пространственно подтверждённых NPC/items, изменения и неопределённости. Narrator/auditor/repair получают соответствующие проекции и общий world/story boundary. Молчание данных не превращается в утверждение отсутствия; справочный WK контекст проецируется отдельно от текущей сцены.
4. **NPC knowledge, имя, activity и held items.** Текущий scene projection сверяет имя с committed introduction/recognition и сохраняет предыдущую player-perception того же NPC; activity observation выдаётся лишь для единственной approved записи активной activity и после проверки требуемых held item templates (`lower-dvina-trace-player-safe-npc-details.js:217–241`). Speech audit проверяет фактические фрагменты по claims и request evidence, оставляя текущую субъективную позицию свободной.
5. **Сохранение сцены и reload.** Изменённый `scene-npcs-readback.js` разрешает текущую позицию через party-owned scene node и сверяет NPC placement на текущий G6, body/version и позицию; нет чтения/перезаписи другого party. Saved integration cases фиксируют opening baseline → первый LOOK → reload → следующий LOOK и held net. Фактический PG run пока не состоялся, поэтому это source/test-contract evidence, не runtime acceptance.
6. **Глобальный successor selection.** Текущий importer требует совпадения байтов approved candidate, manifest hashes и отдельной точной authorization; lineage successor добавляется в общую runtime profile/authoring rows, composition successor переключает Fisher ref на @5 (`owner-import.mjs:80–116,182–194`). В candidate реально перечислены оба land scope (`@1`/template@1 и `@2`/template@2) плюс G4-only `land_d2@1` (`candidate.json:92–110`); @5 наследует activity observation @4, а composition @3 ссылается на @5. Это устраняет глобальную `latest` потерю старой coverage через immutable union, без прямого выбора сценарного профиля в runtime. `approval.json` явно ограничивает решение данными и не разрешает DB import/activation; authorization также ограничена изолированными тестовыми БД.
