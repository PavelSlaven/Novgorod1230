## 26. Git, GitHub и stacked PR

Не создавай commit, branch, push, pull request или merge, если это не входит в поставленную задачу.

Если задача включает публикацию изменений:

- используй одну ветку для одного логического PR;
- не включай unrelated changes;
- перед commit проверь `git status`, diff и профильные tests.

Для stacked PR:

- сначала установи exact base/head каждого затрагиваемого PR;
- shared change должен иметь один источник в самом раннем подходящем parent, а downstream PR должны быть restacked;
- не копируй независимо одно и то же canonical изменение в несколько stacked branches;
- не затягивай изменения более позднего PR в более ранний;
- после изменения parent считай downstream branch потенциально stale до restack;
- конфликт `AGENTS.md` не разрешай «последней версией из дочернего PR»: этот файл меняется только по административному правилу раздела 1.

GitHub CI дополняет локальные проверки, но не заменяет проверки, реально необходимые затронутой области.

### 26.1. Обязательная уборка временных ресурсов

Агент отвечает за временные ресурсы своей задачи. После подтверждённого через GitHub merge PR он самостоятельно завершает уборку без дополнительного запроса разрешения:

- проверяет состояние PR, актуальный `main`, незакоммиченные и untracked файлы, зависимости открытых/stacked PR и использование ресурсов другими задачами;
- останавливает свои временные процессы, серверы и SSH tunnels;
- из другого checkout удаляет больше не нужные worktree/клоны, их `node_modules`, временные файлы, логи и локальные ветки; удалённую ветку удаляет только после проверки, что она не нужна открытому или stacked PR;
- удаляет свои одноразовые тестовые контейнеры вместе с anonymous volumes; named volumes и сети удаляет по точным именам только при подтверждённой принадлежности задаче и отсутствии других потребителей;
- проверяет, что worktree registration, процессы, контейнеры, volumes и временные каталоги действительно убраны, и кратко сообщает результат либо конкретный оставшийся блокер.

Одноразовые тестовые ресурсы освобождаются сразу после прогона, включая ошибку и отмену, а не накапливаются до merge. Cleanup теста должен удалять созданные им данные: одного `docker rm` без удаления anonymous volumes недостаточно. После аварийного прерывания агент проверяет оставшиеся ресурсы своего запуска.

Архивы, ZIP и резервные worktree по умолчанию не создаются. Нужные результаты и контекст задачи заранее сохраняются в соответствующем PR/GitHub; secrets и private traces туда не публикуются. Уникальная незавершённая работа, пользовательские материалы, stash, действующие базы и общие ресурсы не считаются мусором только из-за возраста или статуса `dangling`.

Это постоянное разрешение только на адресное удаление установленных временных ресурсов завершённой задачи. Оно не разрешает merge, удаление чужой/незавершённой работы, общих данных, широкий `prune`, `reset` или `clean`. На Windows перед удалением проверяются абсолютные границы каталогов; junction/symlink удаляется как ссылка, без обхода её целевого каталога. Если ownership или отсутствие потребителей не установлены, такой ресурс сохраняется с конкретным объяснением.

### 26.2. Слияние в интеграционную ветку

Интеграционная ветка — ветка PR, объявленная интеграционной в его описании: ведущий ([WR §18.2](WORKFLOW_RULES.md)) вливает в неё ветки задач до слияния этого PR в `main`. Интеграционная ветка не переписывается. Для каждого слияния в неё (включая слияние `main`):

1. Ветка задачи вливается merge-коммитом `--no-ff`, без squash.
2. До слияния проверяется результат CI текущей головы интеграционной ветки. Пока он красный, в ветку вливается только исправление этой поломки; остальные слияния ждут зелёного CI.
3. На результате слияния, до его публикации, выполняются: быстрые наборы тестов затронутых областей в среде, где они реально исполняются (без ложных пропусков, [WR §24.2](WORKFLOW_RULES.md)); сверка sha256 закреплённых файлов с их pins в затронутых данных; проверки по [WR §24](WORKFLOW_RULES.md) для затронутой области.
4. Изменение кода или данных до слияния проходит независимое ревью и Contract Auditor по [AR §25.1](AUDIT_RULES.md), если его триггер сработал. Вердикт `BLOCK` Contract Auditor снимается только исправлением либо изменением нормы или контракта по их собственной процедуре. Замечание советующего ревью, не являющегося Contract Auditor, ведущий может принять с записанной причиной. Если при слиянии разрешался конфликт в файлах, к которым относится триггер аудита, результат слияния — новый объект аудита.
5. Если изменение затрагивает ход, переход, материализацию, старт партии, промпт или вход LLM-роли, на результате слияния выполняется живой прогон играбельного сценария, и его отчёт ([WR §24.1](WORKFLOW_RULES.md)) прикладывается к PR.
6. Сообщение merge-коммита называет выполненные проверки с результатами, вердикт Contract Auditor с проверенным коммитом и того, кто принял сдачу.
7. Изменение кода или данных сопровождается записью в `CHANGELOG.md` в том же слиянии.

## 27. Защита пользовательской работы и опасные действия

Не перезаписывай и не удаляй изменения пользователя или другого агента.

Не перемещай и не удаляй:

- неизвестные files;
- untracked user materials;
- secrets;
- databases;
- stash;
- незакоммиченные изменения;
- чужие worktree.

Не используй широкие destructive команды:

```text
git clean
git reset --hard
git checkout -- .
git restore .
rm -rf .
Remove-Item -Recurse -Force *
```

Не выполняй без прямого основания:

- force push;
- необратимое удаление данных;
- destructive migration;
- production mutation;
- работу с secrets;
- deployment;
- merge;
- публикацию;
- широкую очистку workspace.

Архивирование локальных материалов выполняется только по отдельному прямому заданию.

Подтверждение администратора обязательно для разрушительных, необратимых, security-sensitive или существенно неоднозначных действий, если на них нет уже действующего прямого разрешения. Адресная уборка собственных временных ресурсов по разделу 26.1 разрешена заранее; защита пользовательских и общих данных сохраняется. Для обычного обратимого действия внутри уже поставленной задачи дополнительное подтверждение не требуется.
