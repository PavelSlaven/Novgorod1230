# Инструкция-памятка по работе с картой G0–G4

## Production/target routing

This compatibility document is a migration source. The completed `versioned production activation cutover` made `spatial_v3_target_map_g0_g4_workflow.txt` together with `spatial_architecture_standard_g0_g6.md` the sole production map workflow.

The approved P12 authoring projection is rooted at `data/world-catalogs/novgorod/spatial-v3/manifest.json`: it has 37 SHA-256-pinned datasets and `data_gaps: []`. Historical P28 evidence did not activate it; release `spatial-v3-production-v1` now owns production without v2 fallback.

## 1. Назначение документа

Настоящая инструкция определяет, как создавать и проверять историческую игровую карту уровней G0–G4 для проекта «Русь XIII век».

## Правило ведения семантического каталога G1

Для каждого региона ведётся единый документ `G1_SEMANTIC_CATALOG.md`, кратко описывающий все созданные G1 и их вложенную структуру G2–G4.

Перед проектированием новой G1 агент обязан прочитать весь актуальный каталог и проверить, не дублирует ли новая ячейка уже существующую по:

* общей функции территории;
* набору и сочетанию G2-зон;
* типам G3-мест;
* структуре G4;
* историческим якорям;
* хозяйственному использованию;
* маршрутам;
* рискам;
* сезонным особенностям;
* игровым возможностям.

После присвоения ячейке статуса `approved_local` в каталог добавляется отдельная запись, содержащая:

```text
G1 ID и координаты;
краткое описание территории;
исторические и археологические якоря;
основную смысловую функцию G1;
перечень G2 с их назначением;
перечень G3, сгруппированный по G2;
краткое описание типов G4 внутри каждого G3;
основные маршруты и граничные выходы;
хозяйственные и природные ресурсы;
риски и сезонные особенности;
основные игровые возможности;
уникальные особенности ячейки;
допустимые сходства с соседними G1;
признаки, которые не следует повторять без отдельного основания.
```

Каталог является обязательным входом этапа проектирования каждой следующей G1.

Совпадение отдельных природных элементов допустимо, поскольку соседние территории могут иметь одинаковые леса, реки, болота и хозяйственные практики. Запрещено необоснованно повторять целиком смысловую композицию ячейки, одинаковую структуру G2–G4, одинаковый набор мест интереса и одинаковую игровую функцию.

Если сходство с ранее созданной G1 обусловлено единым ландшафтом, речным коридором, поселением, дорогой или хозяйственной системой, причина сходства должна быть явно записана в новой записи каталога.


Главная цель работы с картой — не перечислить известные исторические объекты и не построить схему транзитных маршрутов, а создать:

```text
исторически допустимую
+ пространственно связную
+ причинно обоснованную
+ достаточно подробную
+ игровую
модель реальной территории
```

Карта должна позволять игроку:

* свободно перемещаться;
* исследовать территорию;
* выбирать маршруты;
* искать пищу, воду, укрытие и ориентиры;
* заниматься промыслами;
* встречать следы человеческой деятельности;
* взаимодействовать с поселениями и хозяйственными зонами;
* сталкиваться с природными, социальными и правовыми рисками;
* проводить продолжительное игровое время даже внутри одной G1;
* открывать новые места не только по главной дороге или основному сюжету.

Исторические источники определяют ограничения и опорные факты мира, но не являются исчерпывающим каталогом всего, что существовало на территории.

# 2. Основное правило

## 2.1. Исторические места — опорные точки, а не предел карты

Наличие в G1 одного или нескольких исторически засвидетельствованных объектов не означает, что карта должна состоять только из них.

Например, если источники подтверждают:

* город;
* погост;
* монастырь;
* перевоз;
* речной маршрут;
* волок;
* промысловую область;
* поселение;
* место сбора дани;

это означает, что данные объекты должны быть сохранены как исторические якоря.

Но вокруг них всё равно существовали:

* природные зоны;
* хозяйственные территории;
* дороги и тропы;
* берега;
* поля;
* луга;
* леса;
* болота;
* ручьи;
* речные рукава;
* места высадки;
* места водопоя;
* охотничьи участки;
* сезонные маршруты;
* опасные участки;
* места отдыха;
* ресурсные зоны;
* границы землепользования;
* участки, используемые местными жителями;
* устойчивые природные ориентиры.

Они могли не попасть в письменные источники не потому, что их не существовало, а потому, что средневековые документы не создавались для полного картографирования повседневного пространства.

## 2.2. Отсутствие прямого источника не запрещает реконструкцию

При отсутствии прямого источника разрешается создавать достоверную реконструкцию, если она основана на сочетании:

```text
ландшафта
+ гидрографии
+ исторической хозяйственной модели
+ способов передвижения
+ археологии
+ природных ресурсов
+ сезонности
+ социальной организации
+ региональной типологии
```

Такая сущность не должна выдаваться за прямо засвидетельствованный факт.

Она получает соответствующую маркировку:

```text
comparative_reconstruction
regional_typology
toponymically_reconstructed
locally_reconstructed
functional_descriptive
```

## 2.3. Запрет галлюцинаций не означает запрет полноценного мира

Неправильно:

```text
нет источника о конкретной деревне
→ оставить всю ячейку пустой
```

Правильно:

```text
нет источника о конкретной деревне
→ не создавать утверждённую деревню
→ исследовать природную и хозяйственную структуру
→ создать обоснованные зоны, маршруты и устойчивые места
→ отметить реконструкции как реконструкции
```

Неправильно:

```text
неизвестна точная конфигурация русла 1230 года
→ создать один абстрактный речной узел
```

Правильно:

```text
неизвестна точная конфигурация русла
→ создать руслово-пойменную модель допустимой точности
→ включить основное русло, пойму, островные и береговые зоны,
   сезонные переходы и опасности
→ не утверждать точную геометрию отдельных проток
```

# 3. Разделение ответственности редакторских данных, кода и LLM

Код не придумывает канонический мир G0–G4 и не имеет права самостоятельно вводить:

* G2;
* G3;
* G4;
* маршруты;
* поселения;
* названия;
* владельцев;
* хозяйственные причины;
* политические статусы;
* ресурсы;
* исторические связи;
* места интереса.

Эти данные создаются редакторским процессом и утверждаются вместе с источниками, периодом и ревизией.

Runtime-код материализует конкретные G5, NPC, предметы и контейнеры из утверждённых categories, templates, profiles и rules. Он:

* передаёт данные;
* проверяет формат;
* проверяет обязательные поля;
* проверяет ID и ссылки;
* выявляет структурные противоречия;
* проверяет допустимые значения;
* детерминированно выбирает из допустимого candidate set;
* создаёт и сохраняет party instances;
* фиксирует seed, catalog digest и materialization trace;
* блокирует продолжение при ошибке.

Если допустимых данных нет, код обязан остановить этап и зафиксировать gap. Он не должен использовать наиболее вероятное значение, fallback или заглушку.

LLM не создаёт G5, NPC и предметы обычной runtime-сцены. Он может выбирать один переданный option_id/command_token, участвовать в отдельно разрешённой конкретизации key entity, проводить аудит или писать прозу из visible context. Последствия выбора рассчитывает код.

# 4. Иерархия карты

```text
G0 → G1 → G2 → G3 → G4 → G5
```

Настоящий документ регулирует G0–G4.

G5 не хранится как заранее полностью материализованная карта мира. Deterministic-код создаёт его в состоянии партии как конкретную сцену на основании утверждённых профилей G4. При новой игре материализуется только стартовый G4; остальные — при первом фактическом входе.

---

# 5. G0 — историко-географический регион

## 5.1. Назначение

G0 представляет крупный самостоятельный историко-географический регион.

Он задаёт:

* общую территориальную рамку;
* исторический период;
* систему власти;
* политические отношения;
* хозяйственную модель;
* право;
* социальную структуру;
* этнокультурную среду;
* религиозную среду;
* основные торговые и военные направления;
* природные макрозоны;
* соседние G0;
* допустимые региональные шаблоны.

## 5.2. G0 не должен подменять сложную внутреннюю структуру

Внутренние:

* земли;
* волости;
* погосты;
* даннические территории;
* зависимые области;
* спорные зоны;
* зоны влияния;

не должны автоматически становиться отдельными G0.

Они могут быть представлены как:

* субрегионы;
* control zones;
* ethnocultural zones;
* economic zones;
* tributary zones;
* contested zones.

## 5.3. Обязательные данные G0

```text
region_id
historical_horizon
region_type
historical_name
name_status
geographic_extent
subregions
political_structure
control_model
legal_model
economic_model
social_model
religious_model
ethnocultural_model
main_routes
main_waterways
neighbor_regions
source_ids
evidence_status
playability_status
```

## 5.4. Контроль не равен географии

Территория может находиться:

* внутри торгового пространства региона;
* в его даннической сфере;
* в зоне военного влияния;
* в культурном контакте;
* в спорном пограничье;

но не управляться непосредственно.

Допустимые статусы:

```text
core
directly_administered
special_status
dependent
tributary
contested
influence_zone
external
```

Каждый политический статус должен иметь отдельное основание.

# 6. G1 — территория 32×32 км

## 6.1. Назначение

G1 — не точка, не одна локация и не один маршрут.

G1 — полноценная дневная территория размером приблизительно 32×32 км.

Игрок должен иметь возможность:

* пересечь её;
* отклониться от основного пути;
* потеряться;
* провести исследование;
* заниматься промыслом;
* искать безопасный путь;
* находить устойчивые места;
* возвращаться в уже известные участки;
* провести внутри неё несколько игровых дней или значительно больше.

Нормативная модель прямо требует, чтобы G1 имела не только географию, но и ответ на вопрос: почему игроку здесь есть чем заниматься.

## 6.2. G1 не должна быть только транзитным узлом

Недостаточно создать:

```text
вход
→ один коридор
→ выход
```

Полноценная G1 должна содержать:

* несколько вариантов движения;
* основные и локальные маршруты;
* безопасные и опасные участки;
* доступные и труднодоступные зоны;
* хозяйственно используемые пространства;
* природные пространства;
* устойчивые ориентиры;
* места исследования;
* сезонные различия;
* зоны вероятного человеческого присутствия;
* зоны отсутствия постоянного населения;
* причины задержаться или свернуть с маршрута.

## 6.3. Классы G1

Перед проектированием необходимо определить класс:

```text
empty_wild
ordinary_rural
dense_river_road
urban_town
urban_major
water_dominant
border_contested
mixed
```

Класс влияет на ожидаемую плотность, но не устанавливает механическую квоту.

## 6.4. Ориентиры глубины

### Пустая или дикая G1

```text
G2: 5–10 зон
G3: 1–5 устойчивых мест
G4: 3–8 локаций на важное G3
```

### Обычная сельская G1

```text
G2: 8–16 зон
G3: 5–15 мест
G4: 4–10 локаций на место
```

### Плотная речная или дорожная G1

```text
G2: 12–25 зон
G3: 10–30 мест
G4: 5–12 локаций на место
```

### Городская G1

```text
G2: 15–40 зон
G3: 20–80 мест
G4: 5–20 локаций на важное место
```

Кроме того, богатый профиль G1 может включать:

```text
6–12 крупных G2-зон;
20–60 обычных внутренних узлов;
5–20 потенциальных G3;
несколько известных маршрутов;
локальные и неизвестные маршруты;
зоны риска;
хозяйственные зоны;
дикие участки;
места отложенной материализации.
```

Эти числа являются ориентирами масштаба, а не требованием создавать сущности ради количества.

## 6.5. Запрет двух крайностей

Нельзя:

```text
механически набивать ячейку объектами до нормы
```

Но также нельзя:

```text
сокращать ячейку до нескольких узлов,
потому что источники не перечисляют всё пространство
```

Каждое сокращение относительно ожидаемой глубины должно быть обосновано:

* реальным характером территории;
* отсутствием устойчивых пространственных различий;
* малой хозяйственной ёмкостью;
* преобладанием однородной воды;
* природной недоступностью;
* особой исторической ситуацией.

Фраза «нет прямого источника» сама по себе не является достаточным основанием для примитивной структуры.

---

# 7. Даже «пустая» G1 не является пустой

## 7.1. Значение слова «пустая»

`empty_wild` означает:

* отсутствие подтверждённого плотного постоянного населения;
* отсутствие крупного поселения;
* слабую хозяйственную освоенность;
* преобладание природной среды.

Это не означает:

* отсутствие мест;
* отсутствие маршрутов;
* отсутствие ресурсов;
* отсутствие опасностей;
* отсутствие человеческих следов;
* отсутствие игрового содержания.

## 7.2. Что может содержать лесная G1

### Крупные G2

* старый сухой бор;
* влажный еловый лес;
* заболоченная низина;
* речная долина;
* система ручьёв;
* водораздельная гряда;
* гарь или старый ветровал;
* участок лесного промысла;
* пойменный лес;
* труднопроходимая чаща;
* озёрная котловина;
* сезонный зимний путь.

### Устойчивые G3

* брод;
* устье ручья;
* лесное озеро;
* сухая грива среди болота;
* старый буреломный проход;
* удобная переправа;
* участок устойчивого звериного хода;
* место выхода к реке;
* рыболовный плёс;
* солонец;
* ягодная или ореховая зона;
* место старой вырубки;
* участок бортничества;
* сезонный промысловый стан;
* естественное укрытие;
* высокий береговой ориентир;
* волоковый участок;
* опасная топь;
* каменная гряда;
* место слияния ручьёв.

### G4 внутри таких мест

Для брода:

* северный подход;
* южный подход;
* мелководная полоса;
* глубокая промоина;
* участок быстрого течения;
* береговая площадка;
* обходной переход;
* место наблюдения за водой.

Для лесного озера:

* открытый берег;
* заболоченный берег;
* место подхода зверя;
* глубокая часть;
* мелководная заводь;
* сухая площадка;
* исток или сток;
* участок водной растительности.

Для промыслового участка:

* основной рабочий участок;
* место хранения временных снастей;
* подходная тропа;
* зона разделки;
* водный источник;
* безопасная стоянка;
* опасный участок;
* следы прежнего использования.

## 7.3. Места интереса не обязаны быть «достопримечательностями»

Место интереса — это не обязательно:

* руины;
* клад;
* святилище;
* уникальный памятник;
* сюжетная тайна.

Место интересно, если оно создаёт:

* выбор;
* риск;
* ресурс;
* информацию;
* препятствие;
* возможность отдыха;
* возможность промысла;
* возможность наблюдения;
* изменение маршрута;
* сезонную проблему;
* социальное взаимодействие;
* правовой конфликт;
* последствия для дальнейшего движения.

# 8. G2 — крупные внутренние зоны G1

## 8.1. Назначение

G2 разделяет G1 на крупные пространственно и функционально различимые зоны.

G2 отвечает на вопрос:

```text
какая это часть территории
и чем она отличается от соседних частей
```

## 8.2. G2 может быть

* лесным массивом;
* болотной системой;
* речным коридором;
* поймой;
* озёрной зоной;
* системой островов;
* сельскохозяйственной зоной;
* поселенческой зоной;
* дорогой или маршрутным коридором;
* водоразделом;
* промысловой территорией;
* городской частью;
* приграничной полосой;
* береговой зоной;
* зоной сезонной доступности;
* зоной особого контроля.

## 8.3. Каждый G2 должен иметь функцию

Для каждого G2 требуется определить:

```text
почему зона выделена;
какова её география;
как она используется;
как через неё проходят;
что в ней опасно;
что в ней ценно;
кто в ней бывает;
какие G3 она содержит;
как она связана с соседними G2;
как меняется по сезонам.
```

## 8.4. Запрет дублирования G2 и G3

Неправильно:

```text
G2: Речной участок
  → G3: Речной участок
```

Правильно:

```text
G2: Основной речной коридор
  ├─ G3: северный плёс
  ├─ G3: участок мелей
  ├─ G3: излучина
  ├─ G3: место высадки
  └─ G3: зимний переход
```

Если G2 содержит только один G3 с тем же названием и функцией, уровни, вероятно, смешаны.

## 8.5. Связность G2

Каждый G2 должен иметь:

* хотя бы один логичный вход;
* хотя бы один выход либо обоснованный тупик;
* связь с соседними G2;
* условия перехода;
* сезонные ограничения;
* риски навигации;
* физическое основание маршрута.

G2 не должны существовать как независимые карточки без общей пространственной схемы.

---

# 9. G3 — конкретные устойчивые места

## 9.1. Назначение

G3 — конкретное место внутри G2.

G3 отвечает на вопрос:

```text
куда именно может прийти игрок
```

## 9.2. G3 не обязательно является поселением

G3 может быть:

* городом;
* селом;
* деревней;
* погостом;
* монастырём;
* усадьбой;
* перевозом;
* волоком;
* бродом;
* пристанью;
* устьем;
* островом;
* плёсом;
* порогом;
* излучиной;
* полем;
* промысловым станом;
* лесным озером;
* болотной гривой;
* охотничьим участком;
* кладбищем;
* устойчивой стоянкой;
* природным ориентиром;
* сезонно используемым местом.

## 9.3. Для каждого G3 необходимо определить

```text
что это за место;
почему оно устойчиво;
почему оно существует именно здесь;
кто его использует;
постоянно или сезонно оно используется;
кому оно принадлежит или кто его контролирует;
какие ресурсы здесь доступны;
какие риски присутствуют;
какие конфликты возможны;
что игрок может здесь делать;
что здесь делать опасно;
с какими местами оно связано;
какие G4 требуются внутри.
```

## 9.4. Устойчивость G3

G3 должен быть достаточно устойчивым, чтобы:

* его можно было повторно посетить;
* он сохранял пространственную идентичность;
* он не зависел от случайной сцены;
* он мог существовать до появления партии.

Разовый костёр, случайный NPC или след зверя не являются заранее сохранённым G3.

Но место, где регулярно останавливаются путники, может быть G3, даже если конкретная текущая стоянка материализуется позже.

## 9.5. Потенциальные G3

Допускаются места, существование которых исторически и природно вероятно, но точная локализация неизвестна.

Они должны иметь:

```text
spatial_precision
evidence_status
reconstruction_method
limitations
```

Например:

```text
пойменная сухая грива — зона-кандидат
```

Но кандидат не должен автоматически превращаться в:

```text
конкретную деревню с названием и населением
```

---

# 10. G4 — игровые локации внутри G3

## 10.1. Назначение

G4 — минимальный заранее устойчивый пространственный уровень карты мира.

G4 отвечает на вопрос:

```text
в какой части конкретного места находится персонаж
```

## 10.2. G4 может быть

* отдельным строением;
* двором;
* усадебным комплексом;
* участком улицы;
* пристанью;
* береговой площадкой;
* полем;
* лугом;
* кладбищем;
* огородом;
* мастерской;
* складской зоной;
* участком леса;
* болотным проходом;
* местом высадки;
* переходом через воду;
* площадкой промысла;
* опасным участком;
* безопасным укрытием;
* точкой наблюдения.

## 10.3. Внутренние помещения

Помещения не обязательно становятся отдельными G4.

Для здания внутри профиля G4 хранятся:

```text
interior_spaces
interior_connections
entry_points
work_zones
storage_zones
sleeping_zones
heating_zones
lighting_zones
restricted_zones
```

## 10.4. Требование игровой глубины

Важное G3 не должно состоять из одного или двух G4, если внутри него объективно существуют разные:

* подходы;
* функции;
* риски;
* маршруты;
* рабочие зоны;
* безопасные зоны;
* наблюдательные точки;
* способы проникновения;
* сезонные варианты.

Игрок должен иметь возможность действовать внутри G3, а не только «войти» и сразу «выйти».

# 11. Причинная модель территории

Каждый элемент карты должен иметь причину существования.

## 11.1. Природная причина

* вода;
* рельеф;
* почва;
* лес;
* болото;
* берег;
* русло;
* водораздел;
* климат;
* сезонность.

## 11.2. Хозяйственная причина

* земледелие;
* выпас;
* рыболовство;
* охота;
* бортничество;
* лесной промысел;
* ремесло;
* торговля;
* перевоз;
* хранение;
* добыча сырья;
* обслуживание дороги или водного пути.

## 11.3. Социальная причина

* владение;
* общинное пользование;
* зависимость;
* повинность;
* охрана;
* сбор дани;
* религиозная функция;
* погребение;
* сезонная миграция;
* межгрупповой обмен.

## 11.4. Маршрутная причина

* сокращение пути;
* доступ к воде;
* безопасный брод;
* обход болота;
* место высадки;
* волок;
* зимняя переправа;
* участок смены транспорта;
* ориентир;
* место отдыха.

## 11.5. Запрет декоративных объектов

Нельзя добавлять место только потому, что оно:

* выглядит атмосферно;
* создаёт красивую сцену;
* напоминает RPG;
* удобно для сюжета;
* разнообразит таблицу.

Сначала должна существовать причина, затем место.

## 12.1. Передвижение

## 12.3. Выживание

* топливо;

## 12.4. Хозяйство и промысел

* рыболовство;

# 13. Маршруты и граф

## 13.1. Карта — это не список мест

Карта состоит из:

```text
узлов
+ физических связей
+ условий перехода
+ сезонности
+ рисков
+ известности маршрутов
+ граничных выходов
```

## 13.2. Требования к графу

Полноценный граф должен иметь:

* несколько ветвей;
* логичные циклы;
* обходные пути;
* тупиковые места;
* разные условия прохождения;
* альтернативы по сезону;
* связи между соседними G2;
* локальные связи внутри G3;
* переходы между G4;
* согласованные выходы в соседние G1.

Граф, близкий к простой линии или дереву без выбора, допустим только при сильном природном обосновании.

## 13.3. `contains` не является маршрутом

```text
G1 contains G2
G2 contains G3
G3 contains G4
```

— это иерархические связи.

Физическое перемещение требует отдельных рёбер.

## 13.4. Граничные контракты

Для каждого выхода из G1 фиксируются:

```text
from_g1
to_g1
from_node
expected_to_node
route_type
corridor_id
seasonality
access
risk
evidence_status
status
```

Допустимые статусы:

```text
pending_neighbor_confirmation
matched
conflict
blocked
```

# 14. Исторические факты, реконструкции и игровая абстракция

## 14.1. Источниковый факт

Прямо или достаточно надёжно подтверждён:

```text
source_backed
archaeologically_supported
```

## 14.2. Реконструкция

Создана на основании совокупности данных:

```text
comparative_reconstruction
regional_typology
```

## 14.3. Игровая абстракция

Используется только когда необходимо представить реальное явление в игровой модели, но невозможно восстановить его конкретную форму:

```text
gameplay_abstraction
```

Игровая абстракция не должна противоречить исторической среде.

## 14.4. Неизвестность

Если основания недостаточны:

```text
unknown
```

Неизвестность сохраняется явно. Она не должна заменяться наиболее вероятным вариантом.

---

# 15. Названия

Допустимые статусы:

```text
attested_exact
attested_variant
attested_normalized
toponymically_reconstructed
locally_reconstructed
functional_descriptive
unknown
```

## 15.1. Историческое название

Используется только при достаточном источниковом основании.

## 15.2. Реконструированное название

Должно учитывать:

* язык;
* местную топонимическую модель;
* фонетику;
* исторический период;
* известные формы;
* природный или хозяйственный смысл.

## 15.3. Функционально-описательное название

Допустимо для реконструированных природных и хозяйственных мест:

```text
Северный плёс
Береговой выход
Сухая грива
Зимний переход
Нижний болотный проход
```

Оно должно выглядеть как возможное местное обозначение, а не как техническая строка разработчика:

```text
G3_ROUTE_NODE_04
Речная зона номер два
Технический проход
```

# 16. Базовая карта и динамический мир

В G0–G4 не следует заранее хранить:

* конкретных случайных NPC;
* конкретный инвентарь NPC;
* содержимое конкретного контейнера;
* случайные следы;
* конкретную погоду;
* текущие события партии;
* конкретный костёр;
* случайно брошенный предмет;
* конкретное животное, находящееся здесь сейчас.

Вместо этого в authoring layer хранятся:

```text
population_profiles
npc_materialization_rules
item_profiles
container_profiles
property_rules
fauna_profiles
seasonal_rules
g5_anchor_rules
```

Базовая карта задаёт конечный набор того, что код вправе материализовать, где, почему и при каких условиях. Неизвестность не является разрешением добавить новый вариант.

# 17. Рабочий процесс для каждой G1

## Этап 1. Зафиксировать вход

* map revision;
* G1 ID;
* координаты;
* соседние G1;
* утверждённые коридоры;
* источники;
* исторические якоря;
* control status;
* evidence status;
* природную подложку.

## Этап 2. Проверить активацию

Установить, почему G1 включена:

* исторический объект;
* маршрут;
* хозяйственная зона;
* политическое отношение;
* связность;
* внешний переход.

## Этап 3. Исследовать территорию

Отдельно исследовать:

* гидрографию;
* рельеф;
* почвы;
* растительность;
* сезонность;
* расселение;
* археологию;
* хозяйство;
* дороги;
* промыслы;
* власть;
* право;
* этнокультурную среду.

## Этап 4. Построить причинную модель

Ответить:

```text
почему здесь именно такой ландшафт;
почему люди использовали эту территорию;
где было удобно двигаться;
где было опасно;
какие ресурсы привлекали людей;
какие зоны оставались малоосвоенными;
как всё менялось по сезонам.
```

## Этап 5. Спроектировать G2

Не начинать с числа объектов.

Сначала определить крупные различия территории.

## Этап 6. Спроектировать G3

Внутри каждого G2 определить устойчивые конкретные места:

* исторические;
* археологические;
* природные;
* хозяйственные;
* маршрутные;
* реконструированные.

## Этап 7. Спроектировать G4

Для каждого важного G3 определить внутренние игровые локации.

## Этап 8. Построить граф

Проверить:

* входы;
* выходы;
* обходы;
* сезонные связи;
* тупики;
* циклы;
* граничные переходы.

## Этап 9. Создать materialization profiles

Определить допустимые:

* категории людей;
* занятия;
* предметы;
* контейнеры;
* животные;
* ресурсы;
* события;
* следы.

## Этап 10. Провести аудит полноты

Проверить не только историческую правильность, но и игровую насыщенность.

## Этап 11. Провести структурную валидацию

Код проверяет структуру, но не исправляет смысл.

## Этап 12. Выполнить repair

При недостаточной полноте пакет возвращается на отдельный смысловой repair.

## Этап 13. Утвердить

Возможные статусы:

```text
draft
repair_required
approved_local
approved_integrated
blocked
deprecated
```

# 18. Аудит полноты

Пакет не может получить `approved_local`, если он только формально валиден.

Необходимо проверить:

## 18.1. Масштаб

```text
[ ] G1 ощущается как 32×32 км, а не как одна сцена.
[ ] Территория не сведена к одному маршруту.
[ ] Уровни G2, G3 и G4 не смешаны.
```

## 18.2. Богатство

```text
[ ] Есть несколько разных типов пространства.
[ ] Есть места вне главного исторического якоря.
[ ] Есть природные, хозяйственные и маршрутные места.
[ ] Даже дикие зоны имеют устойчивые места интереса.
[ ] Игрок может провести в G1 продолжительное время.
```

## 18.3. Причинность

```text
[ ] Каждый G2 имеет причину выделения.
[ ] Каждый G3 имеет причину существования.
[ ] Каждый G4 имеет функцию.
[ ] Ресурсы соответствуют среде.
[ ] Поселения соответствуют хозяйственной ёмкости.
[ ] Маршруты соответствуют рельефу и воде.
```

## 18.4. Игровая ценность

```text
[ ] Есть выбор маршрута.
[ ] Есть риски.
[ ] Есть ресурсы.
[ ] Есть возможности исследования.
[ ] Есть места остановки.
[ ] Есть сезонные различия.
[ ] Есть причины отклониться от основного пути.
```

## 18.5. Историчность

```text
[ ] Исторические факты имеют источники.
[ ] Реконструкции явно маркированы.
[ ] Нет ложной точности.
[ ] Нет поздних объектов без обоснованной ретроспекции.
[ ] Нет современных административных проекций.
[ ] Нет фантастики.
```

## 18.6. Граф

```text
[ ] Нет осиротевших узлов.
[ ] Есть физические связи, а не только contains.
[ ] Нет бессмысленных дубликатов.
[ ] G2 связаны между собой.
[ ] G3 доступны через реальные маршруты.
[ ] G4 образуют игровую структуру места.
[ ] Границы согласованы или явно ожидают соседа.
```

## 18.7. Данные

```text
[ ] Нет конкретных NPC.
[ ] Нет конкретных случайных предметов.
[ ] Нет G5 в world_base.
[ ] Есть правила материализации.
[ ] Неизвестность сохранена явно.
```

# 19. Признаки примитивной карты

Пакет должен возвращаться в `repair_required`, если обнаружено одно или несколько нарушений:

```text
каждый G2 содержит ровно один одноимённый G3;
каждый G3 содержит 1–2 формальных G4;
вся G1 представляет один транзитный коридор;
исторический объект является единственным содержанием квадрата;
дикая территория не имеет мест интереса;
нет хозяйственных зон;
нет опасных зон;
нет сезонных вариантов;
нет альтернативных маршрутов;
все узлы расположены в одной линейной цепочке;
описания уровней повторяют друг друга;
неизвестность заменена отсутствием структуры;
источники используются как полный перечень всего существовавшего;
формальная валидация подменяет аудит игровой полноты.
```

---

# 20. Признаки чрезмерного или вымышленного наполнения

Пакет также возвращается в `repair_required`, если:

```text
места добавлены только ради количества;
каждому месту присвоено вымышленное историческое название;
созданы поселения без достаточной хозяйственной причины;
созданы дороги без географического основания;
созданы владельцы без правовой модели;
созданы точные границы без источников;
в каждую дикую зону добавлена сюжетная тайна;
созданы руины, клады и святилища ради интереса;
региональная типология выдана за конкретный факт;
все потенциальные места заранее материализованы.
```

Богатство карты достигается не количеством необычных объектов, а глубиной причинно связанных обычных пространств.

---

# 21. Критерий хорошей G1

Хорошая G1 отвечает на все вопросы:

```text
Что это за территория?
Почему она выглядит именно так?
Как через неё проходят?
Какие существуют альтернативные пути?
Где опасно?
Где безопасно?
Какие ресурсы здесь есть?
Кто и зачем использует территорию?
Какие места устойчиво существуют?
Какие места подтверждены?
Какие реконструированы?
Что меняется по сезонам?
Что может узнать игрок?
Чем игрок может здесь заниматься?
Почему ему есть смысл отклониться от основного маршрута?
Может ли он провести здесь несколько дней или больше?
Сможет ли G5-материализатор создать сцены без отсебятины?
```

Если ответы сводятся только к:

```text
здесь проходит река;
игрок может пройти дальше;
```

G1 не завершена.

---

# 22. Изолированный конвейер разработки карты

Работа должна быть разделена на самостоятельные этапы:

```text
InputLoader
→ ResearchBriefBuilder
→ SourceCollector
→ ClaimExtractor
→ ProvenanceAuditor
→ G0/G1 Synthesizer
→ G2 Designer
→ G2 Auditor
→ G3 Designer
→ G3 Auditor
→ G4 Designer
→ G4 Auditor
→ Graph Builder
→ Materialization Profile Builder
→ Historical Auditor
→ Gameplay Completeness Auditor
→ Structural Validator
→ Repairer
→ Approval Builder
→ Staging Writer
```

Каждый этап получает формальный вход, выполняет одну операцию и возвращает формальный результат. Оркестратор только управляет последовательностью и остановкой.

---

# 23. Обязательная готовность G1 к использованию в игре

## 23.1. Основное правило

Заполнение G1 не заканчивается созданием G2–G4, графа, источников и материализационных ограничений.

Ячейка считается завершённой только тогда, когда она:

```text
содержательно заполнена;
прошла исторический и игровой аудит;
импортирована в рабочую world_base;
доступна стартовому и ходовому runtime;
имеет утверждённые стартовые G4;
имеет конкретные правила G5-материализации;
имеет правила материализации NPC;
имеет полный сезонно-временной профиль;
прошла сквозной тест запуска новой игры.
```

Нельзя присваивать G1 статус `approved_local`, если она существует только как staging-пакет, ZIP, набор JSON-файлов или исследовательский каталог, который текущий runtime не может загрузить и использовать.

---

## 23.2. Импорт в `world_base`

В рамках заполнения каждой G1 обязательно выполняются:

```text
подготовка плана импорта;
проверка стабильности ID;
проверка внешних ключей;
проверка source_id;
импорт G1–G4 и графовых связей;
импорт материализационных профилей;
post-import validation;
проверка доступности данных через runtime-запросы;
проверка соответствия импортированного пакета исходному digest.
```

Обязательные артефакты:

```text
world-base-import-plan.json
world-base-import-report.json
post-import-validation.json
runtime-visibility-check.json
```

`post-import-validation.json` должен подтверждать:

```text
G1 существует в world_base;
все G2 имеют правильного родителя;
все G3 имеют правильного родителя;
все G4 имеют правильного родителя;
все физические рёбра ссылаются на существующие узлы;
все source_id разрешаются;
нет осиротевших записей;
нет дублирующихся ID;
нет дублирующихся координат G1;
StartNodeSelector видит разрешённые стартовые G4;
runtime получает актуальную, а не устаревшую ревизию.
```

Если импорт не выполнен или post-import validation не прошёл, статус ячейки остаётся:

```text
draft
```

или:

```text
repair_required
```

Запрещено указывать в `local-approval.json`, что production-импорт не входит в область утверждения, и одновременно присваивать ячейке статус `approved_local`.

---

## 23.3. Утверждённые стартовые G4

Каждая завершённая G1 должна иметь отдельный файл:

```text
start-node-profiles.json
```

В нём определяется, какие G4 могут использоваться как стартовые узлы новой партии.

Для каждого стартового кандидата обязательно указываются:

```text
g4_id;
start_allowed;
reason_for_start;
allowed_seasons;
allowed_date_ranges;
allowed_time_bands;
required_transport;
requires_boat;
requires_horse;
requires_sled;
requires_guide;
requires_local_knowledge;
required_character_statuses;
forbidden_character_statuses;
minimum_survival_conditions;
immediate_hazards;
safe_exit_routes;
temporarily_blocked_routes;
start_difficulty;
start_safety_class;
materialization_profile_id;
```

Стартовый G4 должен отвечать следующим требованиям:

```text
персонаж может физически находиться в нём;
существует хотя бы один доступный выход;
старт не требует неизвестного персонажу действия без причины;
старт не помещает персонажа в немедленно смертельную ситуацию без явной заявки;
требуемый транспорт или проводник присутствует либо не требуется;
сезон и состояние среды допускают нахождение в месте;
социальное положение персонажа совместимо с доступом к месту;
G5 может быть материализован без отсебятины.
```

Нельзя автоматически разрешать старт во всех G4.

Нельзя считать стартовыми:

```text
непроходимый участок;
открытую опасную воду без лодки;
тонкий или неизвестный лёд;
затопленную пойму без безопасного выхода;
закрытую чужую территорию без основания;
археологическую зону только потому, что она исторически интересна;
место, для которого отсутствует G5-профиль.
```

В каждой G1 должен существовать хотя бы один утверждённый стартовый G4.

Если ячейка принципиально не предназначена для начала партии, это должно быть явно записано:

```text
start_allowed_in_g1 = false
```

В таком случае она не может использоваться как стартовая G1, но может быть утверждена для перемещения и дальнейшего исследования.

---

## 23.4. Полные G5-материализационные профили

Каждая G1 должна содержать:

```text
g5-materialization-profiles.json
```

Общие запреты для всех G4 не являются достаточным G5-профилем.

Правила должны задаваться:

```text
для конкретного типа G4;
для группы однотипных G4;
через отдельный override для уникального G4.
```

Для каждого профиля определяются:

```text
profile_id;
profile_version;
profile_digest;
layout_template_ids;
applicable_g4_types;
applicable_g4_ids;
allowed_minilocation_types;
required_minilocation_types;
allowed_anchor_types;
required_anchor_types;
entry_points;
exit_points;
visible_passages;
conditionally_visible_passages;
closed_zones;
restricted_zones;
work_zones;
rest_zones;
storage_zones;
resource_zones;
hazard_zones;
observation_zones;
allowed_npc_slots;
allowed_item_slots;
allowed_container_slots;
lighting_profiles;
weather_variants;
seasonal_variants;
water_level_variants;
ice_variants;
flood_variants;
forbidden_elements;
materialization_limits;
seed_scope;
rng_algorithm_id;
required_profile_ids;
required_rule_ids;
```

Примеры различий:

```text
место высадки
→ берег, вода, линия вытаскивания лодки, сухая площадка, подход к руслу;

лесная гряда
→ сухой участок, кромка леса, укрытие, обзорный ориентир, звериная тропа;

поселенческая зона
→ подход, хозяйственная зона, жилой сектор, граница доступа, место общего пользования;

ледовый переход
→ вход на лёд, проверяемая полоса, опасная промоина, противоположный выход, путь отступления.
```

Кодовый G5-материализатор может создавать только те минилокации, якоря, проходы и зоны, которые разрешены активным профилем выбранного G4. Candidate set канонически сортируется; выбор и причины отсева записываются в trace.

Заявка игрока, удобство сюжета или художественная проза не могут создавать отсутствующий G5-якорь.

---

## 23.5. Правила материализации NPC

Каждая G1 должна иметь отдельный файл:

```text
npc-materialization-rules.json
```

Общего перечня категорий населения недостаточно.

Правила должны связывать конкретные G2, G3, G4 или их типы с утверждёнными региональными справочниками:

```text
region_social_roles;
region_occupations;
npc_archetypes;
name_pools;
language_profiles;
knowledge_profiles;
equipment_profiles;
seasonal_presence;
time_of_day_presence;
route_usage;
access_rights;
control_status;
```

Для каждого правила указываются:

```text
rule_id;
applicable_node_ids;
applicable_node_types;
allowed_social_role_ids;
allowed_occupation_ids;
allowed_npc_archetype_ids;
allowed_name_pool_ids;
group_size_range;
presence_frequency;
allowed_seasons;
allowed_time_bands;
reason_for_presence;
required_activity;
required_route_or_resource;
allowed_equipment_profile_ids;
allowed_knowledge_profile_ids;
access_and_control_rules;
forbidden_combinations;
promotion_conditions;
```

`reason_for_presence` является обязательным.

Допустимые причины:

```text
постоянное проживание;
сезонный промысел;
рыболовство;
охота;
сбор ресурсов;
перевозка;
путешествие;
сбор дани;
служба;
охрана;
обслуживание переправы;
религиозная обязанность;
погребальный обряд;
временная стоянка;
переход по известному маршруту.
```

Нельзя материализовать NPC только потому, что сцене нужен собеседник, противник, торговец или проводник.

В базовом пакете G1 не создаются конкретные NPC. В нём создаются rules/profile sets, по которым deterministic-код причинно материализует конкретных людей и сохраняет их в party database.

---

## 23.6. Предметные и имущественные правила

Для каждого типа G4 должны быть связаны:

```text
item_profiles;
container_profiles;
property_rules;
equipment_profiles;
resource_profiles.
```

Правила должны определять:

```text
какие категории предметов допустимы;
почему они здесь находятся;
кто ими владеет;
кто имеет доступ;
какие контейнеры возможны;
что запрещено;
что зависит от сезона;
что зависит от присутствующих NPC;
что может стать конкретным предметом только в G5.
```

Нельзя завершать G1, если G5-сцена может быть создана, но runtime не способен определить допустимую материальную среду места.

---

## 23.7. Полный сезонно-временной профиль

Каждая G1 должна содержать:

```text
seasonal-start-runtime-profile.json
```

Профиль не фиксирует одну вечную погоду или одну дату. Он задаёт утверждённое пространство допустимых стартовых состояний ячейки.

Обязательные данные:

```text
historical_year_range;
supported_seasons;
supported_date_ranges;
allowed_time_bands;
daylight_rules;
twilight_rules;
night_rules;
allowed_weather_classes;
forbidden_weather_combinations;
temperature_ranges;
wind_profiles;
precipitation_profiles;
visibility_profiles;
water_level_profiles;
river_current_profiles;
ice_state_profiles;
flood_state_profiles;
mud_and_ground_profiles;
route_availability_matrix;
transport_availability_matrix;
seasonal_hazards;
seasonal_resource_changes;
seasonal_npc_presence_changes;
```

Для каждого маршрута должно быть определено:

```text
доступен ли он летом;
доступен ли он зимой;
доступен ли он в ледостав;
доступен ли он в ледоход;
доступен ли он в половодье;
требует ли лодку;
требует ли сани;
требует ли проводника;
какие риски возникают;
какие альтернативы остаются.
```

Точная стартовая рамка партии:

```text
год;
сезон;
дата;
время;
погода;
свет;
состояние воды;
состояние льда;
паводковое состояние;
доступные маршруты;
```

выбирается при создании партии, но только внутри утверждённого профиля G1.

LLM не должна свободно придумывать гидрологическое, сезонное или световое состояние ячейки.

---

## 23.8. Проверочные стартовые сценарии

Для каждой G1, разрешённой для старта, создаётся:

```text
start-runtime-fixtures.json
```

Он должен содержать не менее одного полностью проверенного стартового сценария.

Если ячейка разрешает старт в нескольких принципиально разных сезонах, необходимо создать отдельный fixture для каждого поддерживаемого сезонного режима:

```text
летний;
зимний;
переходный;
паводковый;
ледоставный;
```

Не требуется поддерживать все сезоны.

Допустимо явно ограничить старт:

```text
start_supported_seasons = ["winter"]
```

Но каждый разрешённый сезон должен иметь проверенный сценарий.

Fixture содержит:

```text
историческую рамку;
выбранный G4;
причину выбора;
сезонно-временное состояние;
ожидаемые доступные маршруты;
G5-профиль;
допустимые NPC-категории;
допустимые предметные категории;
ожидаемые риски;
ожидаемое видимое состояние;
запрещённые результаты.
```

---

## 23.9. Сквозная проверка запуска

Перед присвоением `approved_local` необходимо выполнить полный тестовый запуск:

```text
world_base
→ загрузка регионального контекста
→ получение G1
→ получение стартовых G4-кандидатов
→ bounded-выбор StartNodeSelector
→ генерация персонажа
→ кодовая материализация G5
→ кодовая материализация NPC
→ кодовая материализация предметов
→ проверка времени, света и среды
→ формирование карты знаний
→ формирование hidden state
→ формирование visible context
→ генерация стартовой прозы
→ кодовый план записи
→ запись партии
→ повторное чтение партии
→ первый игровой экран
```

Результат фиксируется в:

```text
session-readiness-report.json
```

Обязательные проверки:

```text
StartNodeSelector видит ячейку;
выбранный G4 существует;
G5 использует разрешённый профиль;
materialization trace содержит version pins, seed и catalog digest;
NPC соответствуют правилам G4;
предметы соответствуют профилям места;
сезонность не противоречит маршрутам;
свет соответствует дате и времени;
hidden state не попадает в visible context;
позиция персонажа записана как G1→G2→G3→G4→G5;
партия успешно сохраняется;
партия успешно загружается;
повторный вход не рематериализует G5;
первый ход может быть обработан.
```

Результат должен быть:

```text
PASS
```

или допустимый:

```text
PASS WITH NOTES
```

`PASS WITH NOTES` допускается только при отсутствии функциональных, исторических, структурных и runtime-рисков.

---

## 23.10. Граничные переходы

Для статуса `approved_local` необязательно согласовать все соседние G1, если:

```text
внутренняя карта полностью работоспособна;
существует хотя бы один безопасный внутренний маршрут;
несогласованные выходы явно имеют статус pending_neighbor_confirmation;
runtime не позволяет пройти через неподтверждённый выход;
игроку не показывается несуществующая доступность.
```

Для статуса `approved_integrated` все используемые межъячеечные переходы должны иметь статус:

```text
matched
```

---

## 23.11. Агент критики

Для обычного наполнения G1 без изменения кода используется независимый критик данных.

Он проверяет:

```text
историчность;
причинность;
масштаб;
полноту G2–G4;
игровую насыщенность;
граф;
стартовые G4;
G5-профили;
NPC-правила;
предметные правила;
сезонный профиль;
runtime-готовность;
отсутствие галлюцинаций;
отсутствие примитивизации;
отсутствие смысловых дублей.
```

Агент критики кода вызывается обязательно, если для выполнения требований настоящего раздела изменяются:

```text
схемы;
контракты;
валидаторы;
импорт;
approval logic;
StartNodeSelector;
G5 materializer;
NPC placer;
item placer;
seasonal runtime;
оркестрация;
запись в world_base;
запись в party database;
обработка ошибок;
repair.
```

Сначала выполняются автоматические тесты, затем аудит критика кода.

После `CHANGES REQUIRED` или `REJECT` исправления обязательно проходят повторные тесты и повторный аудит.

---

# 24. Короткая формула

```text
источник фиксирует опорные факты,
но не описывает всю территорию.

исторические якоря встраиваются
в богатую причинную модель среды.

G1 должна содержать не только карту,
но и правила её честного использования.

полная G1 =
историческая модель
+ G2–G4
+ физический граф
+ ресурсы и риски
+ стартовые G4
+ G5-профили
+ NPC-правила
+ предметные правила
+ сезонно-временной профиль
+ импорт в world_base
+ post-import validation
+ сквозной тест новой игры.

staging-пакет не является готовой игровой ячейкой.

G1, которую runtime не видит,
не может считаться утверждённой.

G1, в которой нельзя честно создать первую сцену,
не завершена.

G1 должна быть одновременно:
территорией,
графом,
источником игровых возможностей
и готовым входом в runtime.
```

# 25. Итоговое правило допуска

## 25.1. Статус `approved_local`

G1 может получить статус `approved_local` только при одновременном выполнении всех условий:

### Историческая готовность

```text
[ ] Исторические факты имеют проверяемые источники.
[ ] Реконструкции явно отделены от фактов.
[ ] Нет ложной точности.
[ ] Нет необоснованного переноса поздних объектов.
[ ] Политический статус доказан либо ограничен.
[ ] Исторический аудит завершён.
```

### Пространственная готовность

```text
[ ] Масштаб G1 соответствует территории 32×32 км.
[ ] G2, G3 и G4 имеют разные функции.
[ ] Исторические якоря не заменяют территорию.
[ ] Даже дикие зоны имеют устойчивые места интереса.
[ ] Граф содержит физические маршруты.
[ ] Есть выбор пути, риски, ресурсы и исследование.
[ ] Нет осиротевших узлов и рёбер.
```

### Материализационная готовность

```text
[ ] Для каждого типа G4 существуют G5-профили.
[ ] Разрешены конкретные типы минилокаций и якорей.
[ ] Определены входы, выходы и закрытые зоны.
[ ] Созданы npc-materialization-rules.json.
[ ] NPC-правила связаны с региональными ролями и занятиями.
[ ] Определены item, container и property profiles.
[ ] Конкретные NPC и предметы заранее не создаются.
```

### Стартовая готовность

```text
[ ] Создан start-node-profiles.json.
[ ] В G1 есть хотя бы один разрешённый стартовый G4
    либо ячейка явно запрещена для старта.
[ ] Для стартового G4 определены транспорт, доступ,
    знания, сезонность, риски и безопасные выходы.
[ ] Старт не требует несуществующих объектов или маршрутов.
[ ] Создан хотя бы один проверочный стартовый fixture.
```

### Сезонная готовность

```text
[ ] Создан seasonal-start-runtime-profile.json.
[ ] Определены допустимые сезоны и даты.
[ ] Определены время, свет и видимость.
[ ] Определены погода, вода, лёд и паводок.
[ ] Сезонность связана с доступностью маршрутов.
[ ] Определены транспортные и природные ограничения.
```

### Интеграционная готовность

```text
[ ] Актуальная ревизия импортирована в world_base.
[ ] Import report не содержит ошибок.
[ ] Post-import validation пройдена.
[ ] Runtime получает актуальную ревизию.
[ ] StartNodeSelector видит стартовые G4.
[ ] Все обязательные source_id и FK разрешаются.
[ ] Digest импортированных данных соответствует пакету.
```

### Runtime-готовность

```text
[ ] Полный pipeline новой игры успешно прошёл.
[ ] G5 материализован только из разрешённого профиля.
[ ] NPC и предметы созданы причинно.
[ ] Hidden state отделён от visible context.
[ ] Стартовая позиция сохранена полностью.
[ ] Партия записывается и повторно загружается.
[ ] Первый игровой экран сформирован.
[ ] Первый ход может быть обработан.
[ ] session-readiness-report.json имеет PASS
    или допустимый PASS WITH NOTES.
```

### Каталог и аудит

```text
[ ] Запись добавлена в G1_SEMANTIC_CATALOG.md.
[ ] Проверено отсутствие необоснованного смыслового дубля.
[ ] Структурный validator прошёл.
[ ] Исторический аудитор прошёл.
[ ] Gameplay Completeness Auditor прошёл.
[ ] Критик данных прошёл.
[ ] При изменении кода критик кода вернул PASS
    или допустимый PASS WITH NOTES.
```

Если хотя бы одно обязательное условие не выполнено, G1 не получает `approved_local`.

Допустимые статусы:

```text
draft
repair_required
blocked
```

## 25.2. Статус `approved_integrated`

G1 получает `approved_integrated`, если дополнительно:

```text
[ ] Все используемые переходы в обработанные соседние G1 согласованы.
[ ] Все используемые boundary contracts имеют статус matched.
[ ] Нет конфликтующих продолжений дорог, рек и коридоров.
[ ] Соседние ячейки не дублируют пограничные объекты.
[ ] Runtime может безопасно провести персонажа через границы.
[ ] Возврат из соседней G1 ведёт в правильный узел.
```

## 25.3. Жёсткое итоговое правило

```text
Формально валидная, но примитивная карта не завершена.

Содержательно богатая, но не импортированная карта не завершена.

Импортированная карта без стартовых G4 не завершена.

Карта без конкретных G5-профилей не завершена.

Карта без NPC-, предметных и сезонных правил не завершена.

Карта, на которой не прошёл полный тест новой игры,
не считается пригодной для игровой сессии.

Статус approved_local означает:
ячейка уже может использоваться runtime,
а не только то, что её данные хорошо выглядят в отчёте.
```

## 26. Scoped dependency assertion для materialization

Scoped dependency assertion не является новым состоянием канонической карты и
не изменяет G0–G4 workflow.

```text
canonical G4 row
→ canonical row projection
→ exact base-row digest
→ approved materialization scope assertion
```

Assertion:

- не создаёт новый G4;
- не меняет `graph_nodes.status`;
- не повышает `draft`, `repair_required` или `blocked` до approved;
- не меняет parent chain, координаты, границы, историческую или
  пространственную семантику;
- разрешает использовать exact G4 dependency только внутри одного
  утверждённого materialization scope;
- хранит canonical base-row snapshot и provenance утверждения;
- блокируется, если текущая canonical base row отличается от snapshot.

Scoped assertion не заменяет `approved_local`/`approved_integrated`, профильные
аудиты, source evidence или catalog entry. Она лишь фиксирует, что уже
существующая каноническая dependency была точной на момент утверждения overlay.
