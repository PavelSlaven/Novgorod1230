# Как устроена работа над проектом

> Обзор системы документации и разработки. Норм не создаёт: правила — в [AGENTS.md](../../AGENTS.md) и
> [docs/governance](../governance/README.md), нормы подсистем — по
> [CONTRACT_INDEX](../../data/knowledge-source/corpus/DOCUMENTS/CONTRACT_INDEX.md). Здесь объяснено, зачем система
> устроена так, из чего она состоит и как ею пользоваться. Основа — лекция «Как писать код с нейросетями, не
> сжигая токены» и опыт самого проекта. Проверено: 2026-09-25, commit 21bd0938.

## 1. Главный принцип: минимальный достаточный контекст

Агенту не нужен весь проект. Ему нужен контекст под конкретную задачу: что сделать, где, как, что нельзя трогать
и по какому критерию результат считается правильным.

Лишний контекст вредит:

- модель путается и дорисовывает недостающее;
- каждый запрос дороже, агент думает дольше;
- растёт шанс «заодно улучшить» чужие файлы;
- результат трудно проверить.

Недостающий контекст вредит так же. Агент видит только то, что ему дали:

- не указана архитектура — он придумает свою;
- не указаны версии — выберет сам;
- не указаны готовые хелперы — напишет свои;
- не указаны крайние случаи — проверит только happy path.

Поэтому знания о проекте разложены по отдельным документам, и под задачу загружаются только нужные. С хорошим
контекстом справляется и более дешёвая модель. Если агент пишет не то, чинить надо контекст, а не менять модель
на более дорогую.

В Novgorod1230 этот принцип работает дважды. Игру ведёт слабая локальная LLM, и точный контекст ей подаёт World
Knowledge. Разработку ведут агенты, и точный контекст им подаёт эта система.

## 2. Формула работы

| Шаг | Что делаем | Где в проекте |
|---|---|---|
| 1. Зафиксировать задачу | цель, для кого и зачем, результат, уровень качества | GitHub issue |
| 2. Спецификация до кода | change request: владельцы, context pack, «не трогать», критерии готовности, проверки, допустимый долг | [CHANGE_REQUEST](CHANGE_REQUEST.md), форма `change_request` |
| 3. Собрать нужный контекст | строка маршрутизации роутера → разделы governance, строка CONTRACT_INDEX, `MODULE.md`, карты `docs/context`, LEGACY_WARNINGS | [WORKFLOW](WORKFLOW.md), шаг 3 |
| 4. Короткие итерации | маленький шаг → focused-тест → следующий шаг | [TESTING](../context/TESTING.md) |
| 5. Проверить | детерминированные проверки, CI, ревью каждой задачи, Contract Auditor по триггерам | WR §24, AR §25.1 |
| 6. Зафиксировать | строка CHANGELOG, LW, `Closes #N`, отчёт §29 | [WORKFLOW](WORKFLOW.md), «Завершение» |
| 7. Принять | владелец принимает результат по своим метрикам: плейтест, первый экран, проза | issue этапа |

Финальное решение и приёмка остаются за владельцем.

## 4. Где что живёт: одна истина — одно место

| Что | Где | Кто меняет | Когда читать |
|---|---|---|---|
| правила работы, продуктовая конституция, архитектурные инварианты | `AGENTS.md` (роутер) + `docs/governance/` | только по явному разрешению владельца (§1.1) | роутер — всегда; разделы — по строке маршрутизации |
| нормы подсистем | нормативный корпус; статус — **только** из CONTRACT_INDEX | через [CORPUS_EDIT](CORPUS_EDIT.md) | строка §8.1 индекса для области задачи |
| ответственность модуля и его публичный контракт | `MODULE.md` владельца, [MODULE_INDEX](../../MODULE_INDEX.md) | владелец модуля в задаче | владельцы, которых касается задача |
| факты о проекте: стек, архитектура, БД, крайние случаи, UI, тесты, ссылки | `docs/context/` | по [CONTEXT_DUMP](CONTEXT_DUMP.md) | когда задаче нужен факт |
| процедуры | `docs/process/` | docs-задача | по шагу цикла |
| задача и её спецификация | GitHub issue (CR) | автор задачи; изменение объёма — правкой issue | вход в задачу |
| порядок работ | [CURRENT_SPRINT](../work/CURRENT_SPRINT.md) (выжимка) → issues, milestones | при смене этапа | выбор следующей задачи |
| статус Runtime-этапа | описание PR #98 | исполнитель этапа | Runtime-задачи |
| решения владельца | комментарий в issue или PR; если меняют план — правка плана | тот, кто получил решение, в тот же день | вместе с задачей |
| известные костыли и ловушки | [LEGACY_WARNINGS](../work/LEGACY_WARNINGS.md) + issue `tech_debt` | кто нашёл | `rg` по путям задачи до правки |
| история изменений | `CHANGELOG.md`, `## Unreleased` | каждый PR | по необходимости |
| архитектурные решения | `docs/adr/` | задача, меняющая решение | по необходимости |
| утверждение данных | поля утверждения рядом с данными: кто, когда, путь и commit | проход старшей модели (не автор) или владелец (WR §21.1) | задачи с данными |
| отчёты реальных gameplay runs | [docs/playtests](../playtests/README.md) | исполнитель прогона (WR §24.1) | только нужный run |

Что не является источником истины — WR §2: решение или правило, появившееся в чате, в памяти агента или в переписке
агентов, переносят в нужное место из таблицы. Копии кода `src/` и `legacy/src` тоже не владельцы поведения
(LW-001, LW-003).

## 5. Роли

- **Владелец (PavelSlaven):** замысел игры (PC §9.1), выбор между продуктовыми вариантами, разрешения на правку
  governance, приёмка этапов, решения о production.
- **Исполнитель** (текущий назван в [CURRENT_SPRINT](../work/CURRENT_SPRINT.md)): выполняет задачу по CR. Вопросы, которые нельзя закрыть чтением проекта,
  пишет ревьюеру и ждёт ответа. Свои данные не утверждает (WR §21.1), критерии и проверки приёмки молча не меняет (WR §24.2).
- **Ревьюер-архитектор** (текущий назван в CURRENT_SPRINT): отвечает исполнителю на технические вопросы, ревьюит каждую сданную задачу
  против CR, плана этапа и замысла, готовит следующие CR. Продуктовые, нормативные, необратимые и production-решения
  выносит владельцу.
- **Утверждающий проход:** отдельный проход старшей модели инструмента на высоком reasoning или владелец утверждает данные, собранные другим агентом (WR §21.1).
- **Contract Auditor:** независимый read-only аудит по триггерам AR §25.1.
- **CI:** merge gate; полный `npm test` — в CI, локально только в случаях WR §24.

### Обмен сообщениями исполнителя и ревьюера

Исполнитель и ревьюер переписываются через два файла вне репозитория: `questions.md` пишет исполнитель,
`answers.md` — ревьюер. Это только канал сообщений, а не источник истины.

| Блок | Кто пишет | Что это |
|---|---|---|
| `Q-NNN` | исполнитель | вопрос, помеченный `blocking` или `non-blocking` |
| `A-NNN` | ревьюер | ответ на вопрос |
| `TASK-NNN` | ревьюер | поручение: ссылка на issue с CR и короткие указания |
| `DONE-NNN` | исполнитель | сдача: HEAD, что сделано, какие проверки реально выполнены, строки CHANGELOG и LW |
| `REVIEW-NNN` | ревьюер | `ACCEPTED` или `CHANGES_REQUESTED` с пронумерованными замечаниями |
| `NOTE-NNN` | ревьюер | решение владельца; в тот же день переносится в issue, PR или план |

Пути в сообщениях пишутся через `/`. На границе задачи действующие решения переносятся в репозиторий, а старый
лог архивируется: новая сессия начинает с репозитория, а не с чтения истории переписки.

## 6. Как собирается контекст исполнителя

1. **Старт сессии.** Роутер `AGENTS.md` (≤16 КБ) и личные глобальные правила инструмента. Больше ничего
   обязательного.
2. **Под задачу.** Строки маршрутизации роутера → разделы governance. CONTRACT_INDEX по правилу чтения
   (§1–§3.1, строка §8.1, строки §4–§7 её документов). Из больших контрактов читаются нужные разделы, целиком —
   только редактируемый документ. `MODULE.md` владельцев, нужные карты `docs/context`, `rg` по LEGACY_WARNINGS,
   граф кода (CBM), `npm run knowledge:query` для норм.
3. **Не загружать:** весь корпус; историю прошлых чатов; документы «на всякий случай»; legacy-копии как нормы.
4. **Субагенты:** свежий субагент на подзадачу; разведчик возвращает короткий артефакт (файлы, строки,
   команды, неопределённости), а не пересказ репозитория.

## 7. Проверки: скрипт вместо модели, тест проверяет контракт

- Механическую работу делает детерминированный скрипт, модель нужна там, где требуется суждение (WR §19).
- Критерии готовности и проверки приёмки фиксируются до кода; проверки не подгоняются под реализацию (WR §24.2).
- Провал плейтеста сначала становится падающим регрессионным тестом на уровне хода, потом чинится (WR §22).
- Каждое изменение свободного поведения проверяется unseen-equivalent случаем (PC §5, WR §24).
- Пропущенный тест — не пройденный; проверка, которая не выполнялась, не называется пройденной.

## 8. Симптом → причина → что чинить

| Симптом у агента | Причина | Что чинить |
|---|---|---|
| жжёт токены и пишет не то | нет спецификации | CR до кода |
| перечитывает весь проект | документы не разделены или устарели | карты `docs/context`, строка маршрутизации |
| путает архитектуру, вводит свои паттерны | архитектура и владельцы не описаны | ARCHITECTURE, `MODULE.md` |
| тянет новые библиотеки | стек не зафиксирован | STACK |
| пишет свои хелперы и компоненты | не указано, что уже есть | ARCHITECTURE, UI_KIT |
| тестирует только happy path | нет крайних случаев | EDGE_CASES, unseen-equivalent в CR |
| не понимает задачу | цель и критерии не записаны | CR |
| теряет историю проекта | нет текущего спринта, слишком большой контекст | CURRENT_SPRINT, одна задача — одна сессия |
| «улучшает» костыли или ломается о legacy | долг не записан | LEGACY_WARNINGS |
| пишет сценарный код вместо общего механизма | пример принят за норму, статусы вводят в заблуждение | PC §5, AI §15, статус только из CONTRACT_INDEX |
| «чинит» тест вместо кода | критерии приёмки не зафиксированы до кода | CR, WR §24.2 |

## 9. Как поддерживать порядок

- Нашёл ловушку — запиши в LEGACY_WARNINGS и заведи issue, не чини попутно.
- Изменился факт — поправь карту `docs/context` и обнови штамп «Проверено».
- Появилось решение владельца — перенеси его в issue или PR, а не оставляй в чате или переписке.
- Новый этап или крупный merge — context dump на той ветке, где идёт работа.
- Ссылки в картах и процедурах проверяет `npm run test:docs`, корневые `.md` — `docs:check`.
