# Этап 7. Подбор допустимых NPC-кандидатов

## 1. Назначение этапа

Подбор допустимых NPC-кандидатов — это этап запуска новой партии, который формирует ограниченный список возможных NPC на основе уже выбранной исторической рамки, регионального контекста, стартовых G1–G4 кандидатов и допустимых place templates.

Этот этап не создаёт конкретных NPC партии. Он не пишет NPC в party-базу. Он не даёт им окончательные имена, биографии, секреты, имущество, отношения с игроком или текущие действия в сцене.

Его задача — собрать допустимое NPC-пространство:

```text id="e9jbtv"
региональные social roles
+ региональные occupations
+ NPC archetypes
+ name pools
+ key NPC seeds
+ selected candidate place templates
+ historical_frame
+ time/season/place constraints
→ npc_candidate_set
```

Иначе говоря, этап отвечает на вопрос:

```text id="dmt93u"
Какие типы NPC вообще допустимы рядом с такими стартовыми местами в этой исторической рамке?
```

Он не отвечает на вопрос:

```text id="bxoed9"
Кто именно сейчас стоит перед игроком?
```

## 2. Главное правило этапа

NPC-кандидаты формируются только из базы и уже утверждённых контекстов.

Код не должен создавать NPC.
LLM не должна создавать NPC.
Код и LLM не должны подменять отсутствующие региональные роли “здравым смыслом”.

Допустимый результат этапа:

```json id="j269xi"
{
  "npc_candidate_id": "npc_cand_001",
  "npc_archetype_id": "npc_arch_001",
  "social_role_id": "social_role_001",
  "occupation_id": "occupation_001",
  "name_pool_id": "name_pool_001",
  "allowed_place_template_ids": ["place_template_001"]
}
```

Запрещённый результат этапа:

```json id="bywcns"
{
  "npc_id": "npc_001",
  "name": "Иван",
  "secret": "он скрывает долг",
  "current_action": "чинит упряжь",
  "relationship_to_player": "подозревает игрока"
}
```

Такие данные создаются позже, на этапе материализации стартовой G5-сцены и размещения NPC.

## 3. Место этапа в pipeline

```text id="3pjhxq"
1. Заявка игрока
2. Нормализация заявки
3. Выбор исторической рамки
4. Загрузка регионального контекста из world_base
5. Подбор допустимых стартовых G1–G4 кандидатов
6. Подбор допустимых place templates
7. Подбор допустимых NPC-кандидатов
8. Подбор допустимых предметных профилей
9. Выбор стартового узла
10. Генерация персонажа
11. Материализация G5
12. Размещение стартовых NPC
```

Этап 7 должен идти после place templates, потому что допустимость NPC зависит от типа места.

Например, список возможных NPC для дороги, монастыря, торга, двора, пристани, лесного стана или городской улицы должен отличаться.

## 6. Что считается NPC-кандидатом

NPC-кандидат — это не человек сцены, а допустимая комбинация:

```text id="9cy9tn"
NPC archetype
+ social role
+ occupation
+ place template
+ profile level
+ name pool
+ доступность по времени/сезону
+ ограничения источников
```

Пример:

```json id="1e4m2y"
{
  "npc_candidate_id": "npc_cand_001",
  "profile_level": "background",
  "npc_archetype_id": "npc_arch_worker",
  "social_role_id": "social_role_common_free",
  "occupation_id": "occupation_laborer",
  "name_pool_id": null,
  "allowed_candidate_place_template_link_ids": ["cptl_001"],
  "can_be_named_now": false,
  "can_be_materialized_later": true
}
```

Это означает:

```text id="90x44u"
такой тип NPC допустим для будущей стартовой сцены
```

Это не означает:

```text id="j6w48t"
NPC уже существует в party_npcs
```

## 7. Уровни NPC-кандидатов

### 7.1. Background candidate

Фоновый NPC нужен для видимости сцены: кто находится рядом, кто создаёт бытовой фон, кто может увидеть действие, кто создаёт шум, порядок или напряжение.

На этом этапе background candidate не получает:

* имя;
* скрытую биографию;
* долговременную память;
* полный набор характеристик;
* личный квест;
* секрет;
* конкретные вещи.

Он получает только допустимую связку:

```text id="h0qovw"
archetype + social_role + occupation + place_template + visibility role
```

### 7.2. Scene candidate

Сценический NPC нужен для будущего адресного взаимодействия: разговор, просьба, отказ, свидетельство, доступ, торговля, угроза, помощь, препятствие.

На этом этапе scene candidate ещё не становится конкретным NPC, но должен иметь достаточные основания:

```text id="shpgum"
может находиться в таком месте
может выполнять такую функцию
может быть доступен в это время суток
может знать/контролировать что-то в пределах своей роли
```

### 7.3. Key seed candidate

Ключевой NPC-кандидат возможен только если в базе есть `key_npc_seed` или отдельное правило, разрешающее будущую ключевую материализацию.

На этом этапе key candidate не получает полной биографии. Он только помечается как возможный ключевой NPC для будущего выбора.

Ключевой NPC допустим, если он потенциально связан с:

```text id="ssv4rf"
долговременной памятью
доступом к важному ресурсу
властью над местом
историческим якорем
значимой социальной связью
повторной встречей
долгом, обещанием, конфликтом, зависимостью или последствием
```

Но всё это ещё не создаётся как факт партии.

## 8. Источники данных

### 8.1. `region_social_roles`

Социальные роли региона.

Используются для определения:

```text id="pw7ris"

какой у NPC статус;
кому он подчиняется;
кто может его защищать;
кто может его наказать;
какие у него типичные цели, страхи и ограничения;
какие правила генерации NPC связаны с ролью.
```

Минимальные поля:

```text id="9krlps"

slug
title
summary
status_group
legal_status
wealth_band
typical_fears

who_can_punish_them
relation_to_power
relation_to_religion
npc_generation_rules
game_use
limits
status
confidence
sources
audit_notes
```

### 8.2. `region_occupations`

Профессии и занятия региона.

Используются для определения:

```text id="15orqz"
какие инструменты и ресурсы связаны с занятием;

```

Минимальные поля:

```text id="sv9nf2"
status
confidence
sources
audit_notes
```

Общие или региональные архетипы NPC.

Используются для определения игровой функции NPC-кандидата.

Минимальные поля:


Если `npc_archetypes` в реализации разделены на глобальные и региональные, код должен использовать региональные связки или explicit allowlist.

### 8.4. `npc_name_pools`

Именные пулы региона.

Используются только как источник допустимых имён и прозвищ, если NPC позже будет материализован как именованный.

Минимальные поля:

```text id="6uvna7"

patronymic_rules

confidence
sources
audit_notes
```

На этом этапе имя не выбирается. Только фиксируется, какие name pools допустимы для будущей материализации.

### 8.5. `key_npc_seeds`

Зерна ключевых NPC.

Используются только для кандидатов потенциально ключевого уровня.

Минимальные поля:

```text id="ghymyn"
id
region_id
slug
title
summary
allowed_place_template_ids
allowed_graph_node_ids
social_role_id
occupation_id
npc_archetype_id
historical_anchor_id
availability_period
activation_conditions
game_use
limits
status
confidence
sources
audit_notes
```

Key seed не создаёт NPC автоматически. Он только разрешает будущую материализацию ключевого NPC, если стартовое место и условия подходят.

### 8.6. `candidate_place_template_set`

Используется как ограничение по месту.

NPC-кандидат должен быть совместим хотя бы с одной разрешённой связкой:

```text id="lhx5wt"
candidate_place_template_link_id
place_template_id
node_id
candidate_id
```

Нельзя создавать NPC-кандидатов для типов мест, которых нет в `candidate_place_template_set`.

### 8.7. `historical_frame.clock`

Используется для проверки времени суток.

Примеры:

```text id="8me8gm"
если time_of_day = deep_night,
дневные торговцы, чиновники, школьники, обычный рынок, дневная толпа не должны попадать в allowed candidates без специального night rule.
```

Ночной старт не запрещает NPC. Но он меняет доступность и профиль NPC.

### 8.8. `property_context` и `knowledge_context`

Эти блоки не создают NPC, но уточняют:

```text id="qdb3fh"
какие NPC могут контролировать доступ;
какие NPC могут владеть вещами;
какие NPC могут знать путь;
какие NPC могут быть свидетелями;
какие NPC могут скрывать или искажать информацию.
```

## 9. Алгоритм этапа

### 9.1. Проверить входы

Код проверяет:

```text id="2ihxvb"
historical_frame.audit.pass = true
regional_context_package.audit.pass = true
start_candidate_set.audit.pass = true
candidate_place_template_set.audit.pass = true
region_id задан
year задан
season задан
clock задан
```

Если `candidate_place_template_set.selection_status != ready`, этап не запускается.

### 9.2. Загрузить social roles

```sql id="ez7xhj"
SELECT *
FROM world_base.region_social_roles
WHERE region_id = :region_id
  AND status IN (:allowed_statuses);
```

Если `npc_candidate_policy.require_social_role=true`, отсутствие social roles блокирует этап.

### 9.3. Загрузить occupations

```sql id="b1f78p"
SELECT *
FROM world_base.region_occupations
WHERE region_id = :region_id
  AND status IN (:allowed_statuses);
```

Фильтр по сезону:

```text id="cmx1li"
occupation.seasonal_pattern совместим с historical_frame.calendar.season
или seasonal_pattern пустой / all_seasons
```

### 9.4. Загрузить NPC archetypes

```sql id="0w8ckf"
SELECT *
FROM world_base.npc_archetypes
WHERE (region_id = :region_id OR region_id IS NULL)
  AND status IN (:allowed_statuses);
```

Если в базе есть отдельная региональная связка:

```sql id="vc3etb"
SELECT *
FROM world_base.region_npc_archetypes
WHERE region_id = :region_id
  AND is_allowed = true
  AND status IN (:allowed_statuses);
```

Главное правило: если используется глобальный archetype, он должен быть явно разрешён для региона или совместим через региональные правила.

### 9.5. Загрузить name pools

```sql id="mvt95b"
SELECT *
FROM world_base.npc_name_pools
WHERE region_id = :region_id
  AND status IN (:allowed_statuses);
```

Name pools не создают имена. Они дают будущему этапу список допустимых именований.

### 9.6. Загрузить key NPC seeds

```sql id="a9wnx7"
SELECT *
FROM world_base.key_npc_seeds
WHERE region_id = :region_id
  AND status IN (:allowed_statuses)
  AND (
    availability_start_year IS NULL
    OR availability_start_year <= :year
  )
  AND (
    availability_end_year IS NULL
    OR availability_end_year >= :year
  );
```

Если key seeds отсутствуют, это не блокирует обычный старт. Просто `key_seed_candidate_count = 0`.

### 9.7. Построить индексы

Код строит:

```json id="6dt9ph"
{
  "social_role_by_id": {},
  "occupation_by_id": {},
  "npc_archetype_by_id": {},
  "name_pools_by_role_id": {},
  "name_pools_by_occupation_id": {},
  "key_npc_seed_by_id": {},
  "place_template_links_by_template_id": {},
  "place_template_links_by_candidate_id": {}
}
```

### 9.8. Сопоставить social role ↔ occupation

Код строит допустимые пары:

```text id="w1sfcs"
social_role_id + occupation_id
```

Пара допустима, если:

```text id="bkwjxp"
occupation.required_social_roles пустой
или social_role_id ∈ occupation.required_social_roles
```

Дополнительно проверяются:

```text id="a9k50k"
wealth_band compatibility
legal_status compatibility
gender_age_limits, если есть
mobility compatibility
seasonal_pattern compatibility
```

Если occupation требует роль, которой нет в регионе, такая occupation не используется.

### 9.9. Сопоставить archetype ↔ social role ↔ occupation

NPC archetype допустим, если:

```text id="7rxyr7"
social_role_id ∈ archetype.allowed_social_role_ids
или allowed_social_role_ids пустой и региональные правила не запрещают

occupation_id ∈ archetype.allowed_occupation_ids
или allowed_occupation_ids пустой и occupation_group совместим
```

Если archetype имеет жёсткий список ролей или занятий, выход за список запрещён.

### 9.10. Сопоставить archetype ↔ place template

NPC-кандидат должен быть совместим хотя бы с одним `candidate_place_template_link_id`.

Проверка:

```text id="5qhn9o"
place_template_id ∈ archetype.typical_place_template_ids
или place_template_id ∈ occupation.typical_places
или place_template_id разрешён social_role.npc_generation_rules
или place_template_id разрешён place_generation_rules.npc_generation_rules
```

Если ни одно основание не найдено, кандидат отклоняется.

### 9.11. Проверить время суток

Код сверяет:

```text id="3t3pqa"
historical_frame.clock.time_of_day
archetype availability rules
occupation work rhythm
place access rules
social role movement/access constraints
```

Пример:

```text id="m4m3tb"
day_market_worker + deep_night + no night_exception → reject
gate_guard + night + place has night access → allowed
household_member + deep_night + household place → allowed with warning
traveler + road + night → allowed if route/risk rules permit
```

Нельзя пропускать дневного NPC в ночной старт только потому, что “он мог бы быть там”. Нужно основание.

### 9.12. Проверить сезон

Код сверяет:

```text id="gekc9f"
occupation.seasonal_pattern
archetype seasonal limits
place seasonal rules
route/weather seasonal constraints
```

Если NPC-занятие невозможно в выбранный сезон, кандидат отклоняется.

Если возможно, но с ограничениями, добавляется warning.

### 9.13. Проверить player hard constraints

Из `normalized_request.hard_constraints`:

```text id="xkr0v9"
no_combat_start
no_authority_start
no_religious_start
no_trade_start
no_noble_environment
no_family_start
historical_consistency_required
```

Код не должен художественно интерпретировать constraint, но должен сопоставить его с tags:

```text id="rk7lq5"
archetype_group
social_role.status_group
occupation_group
place_template.place_kind
risk_profile
```

Если hard constraint нарушен, NPC candidate отклоняется.

### 9.14. Проверить name pool

Если NPC-кандидат может стать именованным, нужно найти совместимый name pool:

```text id="y8yrh4"
name_pool.region_id = region_id
name_pool.social_role_ids пустой или содержит social_role_id
name_pool.occupation_ids пустой или содержит occupation_id
name_pool.gender_scope compatible, если gender later constrained
status allowed
```

Если это фоновый безымянный NPC и `allow_unnamed_background_npc=true`, отсутствие name pool не блокирует candidate.

Если это scene/key candidate и имя может понадобиться сразу, отсутствие name pool даёт warning или reject по policy.

### 9.15. Проверить key NPC seeds

Key candidate допустим, если:

```text id="s3czu5"
key_npc_seed.region_id = selected region
year внутри availability_period
seed.social_role_id совместим
seed.occupation_id совместим
seed.npc_archetype_id совместим
seed.allowed_place_template_ids содержит place_template_id
или seed.allowed_graph_node_ids содержит candidate node_id
```

Key seed не создаёт NPC. Он только даёт future materialization permission.

### 9.16. Сформировать NPC candidate

```text id="8mtnkj"
+ place_template_link
+ profile_level
+ name_pool compatibility
+ time/season compatibility
```

## 12. Scoring

Scoring не создаёт NPC. Он только сортирует допустимые комбинации.

Рекомендуемая формула:

```text id="qdj5c3"
score =
  archetype_match_score
+ social_role_match_score
+ occupation_match_score
+ place_template_match_score
+ time_match_score
+ season_match_score
+ name_pool_score
+ source_confidence_score
+ player_request_match_score
- warning_penalty
- weak_basis_penalty
- overpowered_or_implausible_penalty
```

Шкала:

```text id="ofeitv"
90–100 = excellent
70–89 = good
50–69 = usable
30–49 = weak
0–29 = reject
```

## 13. Hard gates

NPC-кандидат отклоняется без LLM, если:

```text id="755dx2"
social_role_id отсутствует в region_social_roles
occupation_id отсутствует в region_occupations, если occupation required
npc_archetype_id отсутствует в npc_archetypes
name_pool отсутствует для named scene/key candidate, если policy требует
record status = rejected
record status = conflict
record.region_id не совпадает с historical_frame.region_id
occupation.required_social_roles не содержит social_role_id
archetype.allowed_social_role_ids не содержит social_role_id при жёстком списке
archetype.allowed_occupation_ids не содержит occupation_id при жёстком списке
archetype/place_template mismatch
occupation/place_template mismatch
time_of_day hard conflict
season hard conflict
player hard constraint conflict
key_npc_seed outside year/region/place limits
source missing при require_sources=true
```

Эти проверки выполняет код. Это не генерация мира, а защита ссылок и ограничений.

## 15. Работа LLM на этом этапе

Базовый этап должен работать без LLM. Главный подбор NPC-кандидатов выполняет код через `world_base` и уже собранные пакеты.

LLM допускается только в четырёх вспомогательных режимах:

1. `NpcCandidateSetCompressor` — сжатие большого списка кандидатов.
2. `NpcCandidateSetAuditor` — смысловой аудит уже собранного списка.
3. `NpcCandidateExplanationWriter` — техническое пояснение для разработчика.
4. `NpcCandidateFormatRepairer` — repair JSON-формата.

LLM запрещено:

* добавлять `npc_candidate_id`;
* добавлять `npc_archetype_id`;
* добавлять `social_role_id`;
* добавлять `occupation_id`;
* выбирать имя;
* создавать конкретного NPC;
* создавать current_action;
* создавать hidden motive;
* создавать relationship_to_player;
* создавать inventory;
* создавать witness facts;
* создавать dialogue;
* создавать scene prose.

## 20. Validation rules

Код обязан проверить:

1. `schema === "npc_candidate_set"`.
2. `version === 1`.
3. `selection_status` входит в enum: `ready`, `empty`, `blocked`, `requires_repair`.
4. Каждый `npc_candidate_id` уникален.
5. Каждый `social_role_id` существует в `region_social_roles`.
6. Каждый `occupation_id` существует в `region_occupations` или null допустим.
7. Каждый `npc_archetype_id` существует в `npc_archetypes`.
8. Каждый `name_pool_id` существует в `npc_name_pools`, если указан.
9. Каждый `key_npc_seed_id` существует в `key_npc_seeds`, если указан.
10. Все records относятся к выбранному `region_id` или являются глобальными archetypes, разрешёнными региональной связкой.
11. Нет records со `status=conflict`.
12. Нет records со `status=rejected`.
13. Если `occupation.required_social_roles` не пуст, `social_role_id` входит в список.
14. Если `archetype.allowed_social_role_ids` не пуст, `social_role_id` входит в список.
15. Если `archetype.allowed_occupation_ids` не пуст, `occupation_id` входит в список.
16. `place_compatibility.allowed_candidate_place_template_link_ids` не пуст.
17. Все candidate_place_template_link_ids существуют в `candidate_place_template_set`.
18. `season_match=true` у allowed-кандидатов.
19. `time_of_day_match=true` у allowed-кандидатов.
20. Hard constraints игрока не нарушены.
21. Background candidate без имени допустим только если `allow_unnamed_background_npc=true`.
22. Scene/key candidate без name pool допустим только если policy разрешает.
23. Key seed candidate имеет valid seed и совместим с годом/местом.
24. Нет `npc_id`.
25. Нет `name`.
26. Нет `current_action`.
27. Нет `hidden_motive`.
28. Нет `relationship_to_player`.
29. Нет `inventory`.
30. Нет `dialogue`.
31. Нет `visible_scene`.
32. Нет `intro_prose`.
33. `source_trace` не пустой, если `require_sources=true`.
34. Все source IDs существуют в `source_records`.
35. `audit.evidence` не пустой.
36. Если `audit.pass=false`, `audit.concerns` не пустой.

## 23. Commit gate этапа

Этап считается успешным, если:

```text id="whkymt"
npc_candidate_set валиден,
есть хотя бы один allowed NPC candidate,
каждый allowed candidate ссылается только на записи world_base,
каждый social_role/occupation/archetype/name_pool/key_seed проходит region/year/season/time filters,
каждый candidate совместим с candidate_place_template_set,
нет материализованных NPC,
нет имён, действий, секретов, инвентаря, отношений и сцены,
audit.pass=true.
```

Если кандидатов нет, pipeline не должен просить LLM “придумать людей рядом”. Он должен:

1. ослабить только soft preferences;
2. вернуться к place template stage;
3. выбрать другой стартовый candidate set;
4. вернуть `blocked`;
5. вернуть `requires_clarification`, если игрок запретил случайную замену;
6. записать `NO_ALLOWED_NPC_CANDIDATES`.
