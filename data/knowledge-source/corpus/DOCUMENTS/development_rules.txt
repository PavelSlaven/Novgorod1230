Код не является автором игрового мира и не имеет права самостоятельно придумывать, дополнять или восстанавливать смысловые данные: персонажей, NPC, места, маршруты, предметы, причины событий, отношения, мотивы, исторические обстоятельства, последствия действий и любые иные факты мира создаёт только LLM в рамках специально определённой процедуры генерации, проверки, аудита и утверждения результата. Код отвечает исключительно за технические операции: получение и передачу данных между этапами, чтение и запись состояния, проверку формата и обязательных полей, контроль ссылочной целостности, выявление противоречий с уже зафиксированными фактами, выполнение утверждённых числовых формул и выдачу случайного значения по явному запросу LLM при бросках d20. Если необходимых смысловых данных нет, код не должен выбирать наиболее вероятный вариант, использовать значение по умолчанию, создавать заглушку, достраивать причинную связь или продолжать обработку так, будто факт существует; он обязан остановить соответствующий этап либо вернуть задачу LLM на генерацию, уточнение или исправление. Любая новая смысловая сущность становится частью мира только после того, как она получена как результат предусмотренного LLM-этапа, прошла необходимые структурные и смысловые проверки и была явно утверждена для записи в состояние партии. Любая процедурная догадка кода о том, что существует в мире, кому что принадлежит, почему произошло событие, как должен поступить NPC или к каким последствиям привело действие, считается нарушением архитектуры проекта.
Правила модульной разработки и построения конвейеров
1. Область применения
Настоящие правила обязательны для всего проекта, включая:
•	создание новой игры;
•	обработку игрового хода;
•	LLM-этапы;
•	аудит и repair-процедуры;
•	работу с базами данных;
•	обновление состояния партии;
•	формирование видимого контекста;
•	генерацию прозы;
•	UI и диагностические инструменты;
•	импорт, экспорт и преобразование данных.
Любая новая функциональность должна проектироваться как набор изолированных модулей с явно определёнными контрактами.
________________________________________
2. Основное правило конвейера
Этапы создания новой игры и обработки базового хода строятся по принципу изолированных блоков.
Каждый блок:
1.	получает строго определённые данные на вход;
2.	работает только с полученными данными;
3.	не обращается к глобальному состоянию;
4.	не зависит от порядка вызова других блоков;
5.	не знает о существовании других этапов;
6.	возвращает строго определённый результат;
7.	не передаёт результат следующему этапу самостоятельно.
Последовательность таких блоков образует конвейер обработки.
входные данные
→ этап A
→ результат A
→ этап B
→ результат B
→ этап C
→ итоговый результат
Связывание этапов, выбор последовательности, остановка конвейера и передача результатов выполняются отдельным оркестратором.
________________________________________
3. Каждая смысловая операция является отдельным этапом
Каждая самостоятельная смысловая операция проекта должна быть оформлена как отдельный этап конвейера.
Нельзя объединять в одном этапе несколько независимых задач только потому, что они выполняются последовательно.
Примеры отдельных операций:
нормализация заявки;
загрузка контекста;
выбор кандидатов;
LLM-генерация;
структурная валидация;
смысловой аудит;
repair;
расчёт времени;
обновление состояния;
формирование плана записи;
запись в базу;
отбор видимого контекста;
генерация прозы;
аудит прозы.
Один этап должен иметь одну основную причину для изменения.
Если изменение требований к одной части функции требует переписывать несвязанную часть, этап разделён неправильно.
________________________________________
4. Контракт этапа
Каждый этап обязан иметь формальный контракт.
Минимальный контракт включает:
идентификатор этапа;
назначение;
тип входных данных;
обязательные входные поля;
необязательные входные поля;
тип результата;
обязательные поля результата;
допустимые ошибки;
запрещённые действия;
побочные эффекты;
условия успешного завершения;
условия остановки конвейера.
Рекомендуемая модель:
type Stage<Input, Output, Error> = {
  execute(input: Input): Promise<Result<Output, Error>>;
};
Этап не должен принимать неструктурированный объект без описанного контракта.
Запрещены интерфейсы вида:
execute(data: any);
execute(context: Record<string, unknown>);
execute(...args: unknown[]);
если структура фактически известна и может быть описана типами или схемой.
________________________________________
5. Изоляция этапов
Этап работает только с теми данными, которые явно переданы ему во входном контракте.
Этапу запрещено:
1.	читать или изменять глобальные переменные;
2.	получать данные из скрытого singleton-состояния;
3.	напрямую читать состояние другого этапа;
4.	обращаться к внутренним данным оркестратора;
5.	рассчитывать на то, что другой этап уже был выполнен;
6.	изменять переданный входной объект;
7.	самостоятельно запускать следующий этап;
8.	самостоятельно принимать решение о продолжении всего конвейера;
9.	скрыто обращаться к базе данных, файловой системе, сети или LLM;
10.	использовать данные, отсутствующие во входном контракте.
Если этапу нужны дополнительные данные, они должны быть:
•	добавлены во входной контракт;
•	получены отдельным этапом;
•	переданы через явно объявленный интерфейс.
________________________________________
6. Внешние зависимости
Внутри этапов запрещены неявные внешние зависимости.
Допустимы только зависимости, которые:
1.	явно объявлены в конструкторе или аргументах функции;
2.	представлены интерфейсом;
3.	могут быть заменены тестовой реализацией;
4.	не раскрывают этапу глобальное состояние проекта.
Пример:
interface LlmClient {
  generate(request: LlmRequest): Promise<LlmResponse>;
}

interface StageRepository {
  load(input: LoadRequest): Promise<LoadResult>;
}
Этап может зависеть от интерфейса, но не должен быть жёстко связан с конкретным провайдером, базой данных, файловой системой или UI.
Запрещено:
import globalDatabase from "../database";
import globalState from "../state";
import providerConfig from "../config";
внутри смыслового этапа, если эти зависимости не являются частью его явного контракта.
________________________________________
7. Чистые и побочные этапы
Этапы разделяются на два типа.
7.1. Чистые этапы
Чистый этап:
•	получает данные;
•	вычисляет результат;
•	не изменяет внешнее состояние;
•	при одинаковом входе возвращает одинаковый результат, кроме специально переданных источников случайности или LLM-ответов.
Примеры:
•	нормализация структуры;
•	валидация;
•	расчёт формулы;
•	подготовка контекста;
•	построение плана записи;
•	фильтрация видимых данных.
7.2. Этапы с побочными эффектами
Этап с побочным эффектом выполняет одну конкретную внешнюю операцию:
•	обращение к LLM;
•	чтение из базы;
•	запись в базу;
•	чтение файла;
•	запись файла;
•	отправка события;
•	получение случайного числа.
Побочные эффекты должны быть вынесены в отдельные этапы или адаптеры.
Один этап записи не должен одновременно:
•	генерировать данные;
•	исправлять их;
•	валидировать смысл;
•	обновлять базу;
•	формировать прозу.
________________________________________
8. Неизменяемость данных
Этап не должен изменять входной объект.
Результатом этапа является новый набор данных.
Запрещено:
input.character.health -= 10;
return input;
Требуется:
return {
  ...input,
  character: {
    ...input.character,
    health: input.character.health - 10,
  },
};
Изменение состояния партии должно проходить через явно сформированный результат или план изменений.
старое состояние
+ утверждённый change set
→ новое состояние
________________________________________
9. Оркестратор
Оркестратор отвечает только за управление конвейером.
Его обязанности:
1.	определить последовательность этапов;
2.	передать результат одного этапа следующему;
3.	проверить статус выполнения;
4.	остановить конвейер при ошибке;
5.	выбрать repair-маршрут;
6.	выполнить повторный запуск этапа;
7.	собрать техническую телеметрию;
8.	зафиксировать итоговый статус конвейера.
Оркестратор не должен:
•	генерировать смысловые сущности;
•	исправлять данные самостоятельно;
•	подставлять отсутствующие факты;
•	выполнять смысловой аудит;
•	изменять результат этапа;
•	содержать игровую механику;
•	дублировать внутреннюю логику модулей.
Короткая формула:
оркестратор управляет выполнением;
этап выполняет одну операцию;
контракт определяет передачу данных.
________________________________________
10. Отсутствие знания о соседних этапах
Никакой этап не должен знать:
•	какой этап выполнялся до него;
•	какой этап будет выполняться после него;
•	под каким номером он находится;
•	сколько всего этапов в конвейере;
•	в каком игровом режиме используется конвейер.
Этап должен быть пригоден для отдельного запуска в тесте или другом конвейере.
Неправильно:
if (context.stage4Completed) {
  runStage5Logic();
}
Правильно:
execute(input: Stage5Input): Stage5Output
Все необходимые результаты предыдущей обработки передаются как обычные входные данные.
________________________________________
11. Разделение ответственности
Каждый модуль отвечает за одну конкретную функциональность.
Примеры корректного разделения:
репозиторий читает и записывает данные;
валидатор проверяет структуру;
аудитор проверяет смысл;
LLM-этап создаёт смысловой результат;
repairer исправляет отклонённый результат;
оркестратор соединяет этапы;
UI отображает утверждённое состояние;
логгер записывает технические события.
Модуль не должен выполнять обязанности другого слоя.
В частности:
•	UI не создаёт игровые факты;
•	валидатор не исправляет результат;
•	база данных не определяет смысл;
•	оркестратор не генерирует мир;
•	код не подменяет отсутствующий ответ LLM;
•	LLM-этап не записывает результат напрямую в базу;
•	репозиторий не принимает смысловые решения.
________________________________________
12. Низкая связанность
Модули должны быть минимально зависимы друг от друга.
Запрещены:
1.	циклические зависимости;
2.	импорт внутренних функций одного этапа другим этапом;
3.	обращение к внутренним полям другого модуля;
4.	общий изменяемый контекст;
5.	зависимость от конкретной реализации провайдера;
6.	копирование логики одного модуля в другой;
7.	неявные зависимости через порядок импорта или запуска.
Взаимодействие допускается только через:
•	типизированные входные и выходные контракты;
•	устойчивые публичные интерфейсы;
•	события;
•	специально определённые порты и адаптеры.
________________________________________
13. Высокая внутренняя связность
Все элементы одного модуля должны работать над одной задачей.
Внутри модуля допустимы:
•	вспомогательные функции;
•	внутренние типы;
•	локальные схемы;
•	внутренние преобразования;
•	специфические ошибки;
•	тестовые фабрики.
Они не должны использоваться другими модулями напрямую, если не являются частью публичного контракта.
Если вспомогательная функция начинает обслуживать несколько несвязанных этапов, её следует вынести в отдельный общий модуль.
________________________________________
14. Инкапсуляция
Внутренняя реализация модуля скрывается.
Другие части проекта должны знать только:
•	публичный интерфейс;
•	входной контракт;
•	выходной контракт;
•	возможные ошибки;
•	гарантии результата.
Запрещено использовать внутренние функции модуля в обход публичного интерфейса.
Рекомендуемая структура:
stage-name/
  index.ts
  stage-name.ts
  contracts.ts
  errors.ts
  internal/
  test/
  README.md
index.ts экспортирует только публичные элементы модуля.

15. Ошибки и остановка конвейера
Этап не должен скрывать ошибку или заменять невалидный результат заглушкой.
При ошибке этап возвращает структурированный результат:
type StageError = {
  code: string;
  message: string;
  details?: unknown;
  retryable: boolean;
  category: "input" | "structural" | "semantic" | "external" | "internal";
};
Запрещено:
•	возвращать пустой объект вместо результата;
•	продолжать конвейер с частично невалидными данными;
•	подставлять фиктивные значения;
•	молча игнорировать обязательные поля;
•	превращать ошибку в успешный результат;
•	самостоятельно придумывать отсутствующие смысловые данные.
Если результат не прошёл проверку:
результат этапа
→ отчёт об ошибках
→ repair-этап
→ повторная проверка
При невозможности исправления конвейер блокируется с явным статусом ошибки.

## 18.1. Обязательная регистрация повторно используемых модулей

Перед созданием нового функционального модуля разработчик обязан проверить актуальную карту модулей, реестр публичных интерфейсов, реестр контрактов и документацию связанных подсистем.

Если требуемая функция уже существует, запрещено создавать её вторую реализацию. Необходимо использовать существующий публичный интерфейс либо расширить существующий модуль, если новая задача находится в пределах его ответственности.

Функциональность должна быть оформлена как отдельный повторно используемый модуль, если выполняется хотя бы одно из условий:

1. одинаковая логика уже требуется более чем в одном месте проекта;
2. её повторное применение предусмотрено утверждённым планом следующего этапа;
3. функция не зависит от конкретного конвейера, региона, G1, партии или пользовательского сценария;
4. функция имеет самостоятельный устойчивый входной и выходной контракт;
5. копирование этой логики в другом месте привело бы к появлению второй реализации одного правила;
6. функция представляет общий валидатор, загрузчик, преобразователь, аудитор, импортёр, построитель плана, фильтр, репозиторий, адаптер или иной инфраструктурный механизм.

Нельзя создавать общий модуль только на основании предположения, что функция когда-нибудь может пригодиться. Повторное использование должно быть подтверждено существующим применением, утверждённым следующим этапом или очевидной независимостью функции от текущего сценария.

При создании повторно используемого модуля в той же задаче обязательно:

```text
создать документацию самого модуля;
описать его назначение и границы ответственности;
зафиксировать публичный интерфейс;
зафиксировать входной и выходной контракты;
описать ошибки и побочные эффекты;
добавить модуль в карту модулей;
добавить его контракты в реестр контрактов;
добавить его публичные функции в реестр публичных интерфейсов;
добавить связанные взаимодействия в карту конвейеров;
добавить документ модуля в общий список и навигацию документации;
указать существующие места использования;
указать, для каких будущих задач модуль предназначен;
добавить тесты повторного использования через публичный интерфейс.
```

В общий список документации добавляются:

```text
название модуля;
путь к модулю;
путь к его документации;
краткое назначение;
публичные функции;
основные входы и результаты;
использующие его конвейеры и подсистемы;
статус модуля;
```

При изменении публичного поведения повторно используемого модуля одновременно обновляются:

```text
документация модуля;
карта модулей;
реестр контрактов;
реестр публичных интерфейсов;
схемы взаимодействия;
общая навигация документации;
регрессионные и контрактные тесты.
```

Короткая формула:

```text
новая задача
→ поиск существующего модуля
→ повторное использование или обоснованное расширение
→ создание нового модуля только при необходимости
→ тесты
→ документация модуля
→ регистрация во всех проектных реестрах
→ использование через публичный интерфейс
```

Незарегистрированный повторно используемый модуль считается незавершённым и не может быть принят в основную кодовую базу.

Создание второй реализации уже зарегистрированной функции без отдельного архитектурного обоснования считается нарушением архитектуры проекта.

19. Обязательная разработка через TDD
Весь новый код и каждое изменение поведения разрабатываются по методологии TDD.
Основной цикл:
Красный → Зелёный → Рефакторинг
19.1. Красный — Red
Сначала создаётся тест, описывающий требуемое поведение.
Тест должен:
•	проверять одно конкретное требование;
•	падать до реализации;
•	показывать ожидаемый контракт;
•	не зависеть от внутренних деталей реализации;
•	содержать понятную причину падения.
Если тест проходит до написания реализации, он не доказывает наличие нового поведения и должен быть пересмотрен.
19.2. Зелёный — Green
После появления падающего теста пишется минимальный код, необходимый для его прохождения.
На этом этапе запрещено:
•	реализовывать дополнительные возможности без тестов;
•	заранее строить сложную архитектуру;
•	менять несвязанные модули;
•	добавлять поведение «на будущее»;
•	исправлять другие проблемы без отдельного теста.
Цель этапа — получить минимальную корректную реализацию требования.
19.3. Рефакторинг — Refactor
После прохождения тестов код улучшается без изменения наблюдаемого поведения.
Допустимые действия:
•	устранение дублирования;
•	разделение ответственности;
•	улучшение имён;
•	выделение интерфейсов;
•	уменьшение связанности;
•	повышение внутренней связности;
•	упрощение функций;
•	удаление мёртвого кода;
•	улучшение структуры модулей.
После каждого рефакторинга весь набор тестов должен оставаться зелёным.
________________________________________
20. Обязательные уровни тестирования
Для каждого этапа должны существовать как минимум:
20.1. Контрактные тесты
Проверяют:
•	обязательные входные поля;
•	обязательные выходные поля;
•	допустимые типы;
•	отказ при нарушении схемы;
•	неизменность входных данных.
20.2. Модульные тесты
Проверяют поведение этапа изолированно.
Все внешние зависимости заменяются тестовыми реализациями.
20.3. Негативные тесты
Проверяют:
•	отсутствующие данные;
•	противоречивые данные;
•	невалидные значения;
•	ошибки внешних сервисов;
•	недопустимые переходы;
•	невозможность скрытого продолжения конвейера.
20.4. Интеграционные тесты
Проверяют взаимодействие нескольких этапов через их публичные контракты.
Интеграционный тест не должен обращаться к внутренним функциям этапов.
20.5. Тесты конвейера
Проверяют:
•	правильный порядок этапов;
•	передачу результатов;
•	остановку при ошибке;
•	запуск repair;
•	отсутствие записи до завершения аудита;
•	невозможность пропуска обязательного gate;
•	сохранение состояния только после полного успеха.
20.6. Регрессионные тесты
Каждая найденная ошибка сначала воспроизводится отдельным падающим тестом.
Только после этого исправляется код.
________________________________________
21. Тестируемость как обязательное свойство
Если модуль трудно тестировать изолированно, это считается архитектурной проблемой.
Признаки нарушения:
•	для теста требуется запуск всего приложения;
•	невозможно заменить базу данных;
•	невозможно заменить LLM-клиент;
•	модуль зависит от глобального времени;
•	модуль напрямую использует случайность;
•	тест требует определённого порядка запуска;
•	изменение одного этапа ломает несвязанные тесты;
•	невозможно создать входные данные без полного состояния партии.
Такие зависимости должны быть вынесены в явные интерфейсы.
________________________________________
22. Работа со временем и случайностью
Текущее время и случайность считаются внешними зависимостями.
Запрещено напрямую вызывать внутри смысловых модулей:
Date.now();
new Date();
Math.random();
Они передаются через интерфейсы:
interface Clock {
  now(): Date;
}

interface RandomSource {
  nextInt(min: number, max: number): number;
}
Это обеспечивает воспроизводимость тестов и повторяемость конвейеров.
________________________________________
23. Работа с LLM
Каждый LLM-вызов является отдельным этапом с формальным контрактом.
LLM-этап обязан получать:
•	роль;
•	задачу;
•	разрешённый контекст;
•	установленные факты;
•	запреты;
•	формат результата;
•	критерии успешности.
LLM-этап не должен:
•	читать глобальное состояние;
•	самостоятельно загружать произвольные данные;
•	записывать результат в базу;
•	запускать repair самого себя;
•	менять контракт результата;
•	скрывать сырой невалидный ответ;
•	продолжать конвейер после провала аудита.
Структурная валидация, смысловой аудит и repair оформляются отдельными этапами.
LLM-генерация
→ структурная валидация
→ смысловой аудит
→ repair при необходимости
→ повторная валидация
→ утверждённый результат
________________________________________
24. Работа с состоянием партии
Смысловые этапы не должны напрямую изменять состояние партии.
Они возвращают один из вариантов:
предлагаемый результат;
набор изменений;
план записи;
события для применения;
новую версию состояния без записи.
Фактическая запись выполняется отдельным этапом только после прохождения всех обязательных проверок.
результат
→ структурная проверка
→ смысловой аудит
→ проверка противоречий
→ план записи
→ атомарная запись
Нельзя частично записывать результаты конвейера до завершения всех обязательных gate-проверок, если для этого не предусмотрена отдельная транзакционная модель восстановления.
________________________________________
25. Запрещённые архитектурные практики
В проекте запрещены:
1.	функции, выполняющие несколько независимых смысловых операций;
2.	скрытое глобальное состояние;
3.	неявные зависимости;
4.	циклические импорты;
5.	прямое изменение входных данных;
6.	автоматические смысловые заглушки;
7.	продолжение конвейера после невалидного результата;
8.	прямое обращение смысловых этапов к базе;
9.	прямое обращение UI к внутреннему состоянию модулей;
10.	объединение генерации, аудита, repair и записи в одном модуле;
11.	код без предварительно написанного теста;
12.	исправление ошибки без регрессионного теста;
13.	изменение публичного контракта без обновления документации;
14.	использование внутренней реализации модуля другими модулями;
15.	создание универсального context, содержащего всё состояние проекта;
16.	передача этапу данных, которые ему не нужны;
17.	зависимость этапа от его номера или положения в конвейере;
18.	бизнес-логика внутри оркестратора;
19.	бизнес-логика внутри репозитория;
20.	смысловые решения внутри валидатора.

26. Критерии готовности модуля
Модуль считается готовым только при одновременном выполнении всех условий:
[ ] перед созданием проверено отсутствие существующего модуля с той же ответственностью;
[ ] повторно используемый модуль добавлен в карту модулей, проектные реестры и общую навигацию документации.
[ ] определена одна ответственность;
[ ] описан публичный интерфейс;
[ ] определён входной контракт;
[ ] определён выходной контракт;
[ ] отсутствуют неявные зависимости;
[ ] отсутствует доступ к глобальному состоянию;
[ ] входные данные не изменяются;
[ ] ошибки возвращаются структурированно;
[ ] написаны падающие тесты до реализации;
[ ] реализован минимальный рабочий код;
[ ] выполнен рефакторинг;
[ ] проходят модульные тесты;
[ ] проходят негативные тесты;
[ ] проходят контрактные тесты;
[ ] обновлена документация модуля;
[ ] обновлена схема взаимодействия;
[ ] модуль можно запустить изолированно;
[ ] модуль не знает о других этапах;
[ ] побочные эффекты явно объявлены;
[ ] отсутствуют смысловые заглушки.
Если хотя бы одно обязательное условие не выполнено, модуль не считается завершённым.

27. Итоговая архитектурная формула
проект
= изолированные модули
+ формальные контракты
+ низкая связанность
+ высокая внутренняя связность
+ явные побочные эффекты
+ отдельный оркестратор
+ полная документация
+ обязательный TDD
этап
= строго определённый вход
+ одна ответственность
+ независимая обработка
+ строго определённый результат
разработка
= падающий тест
→ минимальная реализация
→ проходящий тест
→ безопасный рефакторинг
Любое отклонение от этих правил должно быть явно обосновано и зафиксировано отдельным архитектурным решением.
