## 2. How `cata_test` loads the mod

`--mods` is a comma-separated list of **mod IDs**, not a filesystem path (`tests/test_main.cpp:79-91,368-374`). The runner always appends `test_data` and inserts `dda` if absent (`tests/test_main.cpp:88-91,403-406`). It sets base and user paths, creates a test world with that mod list, applies the world season option, and loads world mod files **once during process initialization** (`tests/test_main.cpp:94-105,136-157`). Thus a test case cannot select a different mod after initialization.

With an empty base path, static data is under `data/` relative to the working directory (`tests/test_main.cpp:103-105`; `src/path_info.cpp:115-132`). Mod discovery scans `data/mods` and `<user-dir>/mods` (`src/path_info.cpp:348-350,404-410`; `src/mod_manager.cpp:181-191`). The CMake test commands use the source directory as their working directory (`tests/CMakeLists.txt:64-69`). A future Linux invocation from the **full source root**, once the mod has been staged as `data/mods/novgorod_dev_world`, is:

```text
./tests/cata_test --mods=novgorod_dev_world "novgorod_yard_master_daily_routine"
```

Catch2 receives the positional test specification through `Catch::Session` (`tests/test_main.cpp:359-398`). The mod ID is `novgorod_dev_world` (`dev-world/modinfo.json:3-8`). A copy already exists in `C:/Users/Slaven/NovgorodNative/game/runtime/data/mods/novgorod_dev_world`, but that is not the test runner's `data/mods` when it runs from the full source root; the test runner's path rules above explain why it must be staged or run with a matching data root. ## 6. Clock and daylight

CDDA treats `calendar::turn_zero` as Greenwich midnight at the vernal equinox and the first day of spring (`src/calendar.cpp:131-139`). Its 91-day-season calendar labels that day March 21 and uses an artificial 364-day year with a 30-day February (`src/calendar.cpp:856-867,875-907`). March 21 to August 20 is 152 days in this calendar. The test can put the **seasonal phase** and local clock at the requested start with:

```cpp
set_time( calendar::turn_zero + 152_days + 7_hours );
```

`set_time` assigns `calendar::turn` and refreshes map light/visibility (`tests/map_helpers_tests.cpp:140-153`). This represents CDDA's August 20 at 07:00; it does not encode the historical Julian year **1230**, because the native solar calculation uses elapsed game days and its own year length (`src/calendar.cpp:131-154,713-720,875-907`). A separate daylight probe may set `calendar::set_location(58.5209888889f, 31.2757888889f)` using the project's coordinates (`src/calendar.h:117-121`; `src/calendar.cpp:738-741`; `calendar_daylight_light_profiles.json:93-97`). The test runner applies the default `SEASON_LENGTH=91` before loading world mod files (`src/options.cpp:2921-2922`; `tests/test_main.cpp:148-157`). The raw static initializer is one day **before** option initialization (`src/calendar.cpp:31`); explicit `calendar::set_season_length(91)` is the same initialized case (`src/calendar.cpp:713-720,734-744`).

Native sunrise and sunset solve for solar altitude `-1°`; the end of civil twilight (`night_time`) solves for `-6°` (`src/calendar.cpp:39-43,317-334`). For a year of `4 × season_length` days, the source takes mean solar longitude `360° × elapsed_days/year`, adds its anomaly and eccentricity terms, rotates by a fixed `23.439279°` obliquity, and obtains right ascension and declination (`src/calendar.cpp:124-166,713-720`). It uses sidereal time and the latitude-based hour-angle equation, first from 12:00 local solar noon and then with one correction iteration (`src/calendar.cpp:169-184,258-315`). Longitude is converted to the corresponding local-time offset in the calculation (`src/calendar.cpp:109-111,268-275,289-290`).

The following minute-rounded results are from a read-only calculation of those source equations, **not** from running CDDA. Its default location is Boston, `42.36° N, 71.06° W` (`src/calendar.cpp:31-32`). The project's profile uses `58.5209888889° N, 31.2757888889° E`, Julian date to historical solar coordinates, and local mean solar time (`calendar_daylight_light_profiles.json:93-97`).

| 1230-08-20 seasonal phase | Sunrise | Sunset | End of civil twilight |
| --- | ---: | ---: | ---: |
| Native default location, default 91-day season | ~05:14 | ~18:51 | ~19:20 |
| Native Novgorod location, default 91-day season | ~04:35 | ~19:29 | ~20:13 |
| Native Novgorod location, explicit 91-day season | ~04:35 | ~19:29 | ~20:13 |
| Project's Julian 1230-08-20 profile | 04:46 | 19:16 | 20:00 |

The project numbers are stored as minute-of-day values 286, 1156, and 1200 (`calendar_daylight_light_profiles.json:99-100,1486-1490`). With Novgorod coordinates, the native estimate is 11 minutes earlier at sunrise and 13 minutes later at sunset and civil dusk. With the unmodified Boston default, it is 28 minutes later at sunrise, 25 minutes earlier at sunset, and 40 minutes earlier at civil dusk. Consequently a test of the approved **05:00–20:00 class window** should use clock hours, not assume native `sunset()` exactly equals the project's 19:16 boundary (`src/npc_class.cpp:439-445`; `src/calendar.cpp:317-324`; `calendar_daylight_light_profiles.json:1486-1490`). If “at sunset” means an exact project boundary, the implementation needs an explicit decision about this model difference before fixing its EOC transition time.
