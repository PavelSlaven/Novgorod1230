## 1. Что обсуждалось и какой подход согласован

**Проблема:** CDDA продвигает игровое время посекундно. Если вызывать LLM-рассказчика за каждую игровую секунду или каждый технический микрошаг, игрок получит поток повторяющейся прозы, а стоимость и задержки сделают игру непригодной.

**Направление решения:** отделить **частоту физического исполнения мира** от **частоты литературного ответа**. Время и действия исполняет CDDA; narration обращается к игроку на осмысленной границе пользовательского решения. При этом в интерфейсе остаётся **отдельное постоянное окно коротких сообщений CDDA**. Оно помогает следить за ходом жизни мира между литературными сценами.

Ни «секунда», ни «сообщение в журнале» сами по себе **не являются обязательным триггером вызова нарратора**.

Согласованные инженерные ограничения:

1. Не делать второй игровой clock, `Narration Scheduler`, периодический `LLM every N seconds` или собственный тиковый движок прозы.
2. Для длительных действий прежде использовать native `player_activity`, движение, проверку доступности, завершение и прерывания CDDA.
3. Сохранять имеющийся `@rus/narration` с его factual commit → player-safe projection → approved prose. Писать художественный ответ из подтверждённой сцены, а не из распарсенного журнала сообщений.
4. Использовать существующий CDDA message log для отдельного окна; минимальный адаптер в UI/engine boundary возможен, **если нативный API не годится напрямую**.
5. Журнал — дополнение для хронологии, **не замена** художественной сцене и не средство обхода её обязательной смысловой приёмки.
6. Не начинать отдельную новую систему диспетчеризации событий, ранжирования «интересности» каждой секунды, дополнительный event bus или банк универсальных фраз.

## 2. Что действительно есть в закреплённом CDDA

### 2.1. Игровая секунда и длинные действия

[`game::do_turn()`](https://github.com/CleverRaven/Cataclysm-DDA/blob/0d8843f1c500052c3e026e3da6f8edaf5e00b626/src/do_turn.cpp#L533-L550) продвигает `calendar::turn` на одну игровую секунду. [`player_activity.cpp`](https://github.com/CleverRaven/Cataclysm-DDA/blob/0d8843f1c500052c3e026e3da6f8edaf5e00b626/src/player_activity.cpp#L242-L259) уже содержит механизм продолжения занятий, основанных на времени или затрате `moves`. Это даёт техническую базу, на которой одно намерение игрока может исполняться много секунд без обязательной генерации прозы между ними.

В upstream есть опция [`TURN_DURATION`](https://github.com/CleverRaven/Cataclysm-DDA/blob/0d8843f1c500052c3e026e3da6f8edaf5e00b626/src/options.cpp#L1712-L1715): значение `0` отключает автоматическое продвижение игровых ходов по реальному времени. Для предлагаемого текстового взаимодействия **ожидание ответа LLM, чтение прозы, работа UI, RAG и сетевые задержки не должны продвигать игровые часы**. Это уже согласовано в [обсуждении времени](./Novgorod1230_Cataclysm_Time_and_Group_Conversation_Discussion_2026-10-18.md). Не объявлять это автоматически обеспеченным в будущей интеграции: конфигурацию и весь путь нужно проверить.

### 2.2. CDDA действительно имеет короткий журнал сообщений

[`src/messages.cpp`](https://github.com/CleverRaven/Cataclysm-DDA/blob/0d8843f1c500052c3e026e3da6f8edaf5e00b626/src/messages.cpp) содержит:

- `Messages::add_msg(...)`: добавление коротких текстовых сообщений;
- `game_message` с `timestamp_in_turns`, типом сообщения и счётчиком `count`;
- `coalesce_messages(...)` и cooldown-логику: повторяющиеся записи могут объединяться или скрываться в боковой панели;
- `Messages::recent_messages(size_t count)`: чтение последних записей как пар **строка времени суток + текст сообщения**;
- `Messages::serialize(...)` / `Messages::deserialize(...)`: сохранение и восстановление native журнала.

Источники: [структура game_message](https://github.com/CleverRaven/Cataclysm-DDA/blob/0d8843f1c500052c3e026e3da6f8edaf5e00b626/src/messages.cpp#L48-L76), [добавление и сворачивание](https://github.com/CleverRaven/Cataclysm-DDA/blob/0d8843f1c500052c3e026e3da6f8edaf5e00b626/src/messages.cpp#L182-L209), [recent_messages](https://github.com/CleverRaven/Cataclysm-DDA/blob/0d8843f1c500052c3e026e3da6f8edaf5e00b626/src/messages.cpp#L362-L376), [публичные методы и сохранение](https://github.com/CleverRaven/Cataclysm-DDA/blob/0d8843f1c500052c3e026e3da6f8edaf5e00b626/src/messages.cpp#L434-L471).

**Ограничение:** `recent_messages` возвращает **готовые текстовые строки**, а не структурированный список авторитетных world-event ID, причин, субъектов и подтверждений восприятия. Сохранение native message log не доказывает готовность общего CDDA + Novgorod checkpoint/replay. Нельзя считать все низкоуровневые `add_msg` автоматически разрешёнными для нашего игрока или использовать эти строки как объективное свидетельство для LLM.

## 3. Когда рассказывать, а когда молчать

Для **целевого прототипа**, не текущего `TurnScreen`:

| Ситуация | Мир и UI | Рассказчик |
| --- | --- | --- |
| Игрок начинает длинный путь/работу | CDDA исполняет действие и продвигает секунды; карта, статус и применимые сообщения обновляются | Не вызывается отдельно на каждую секунду или клетку |
| Длинное действие продолжается без значимого прерывания | Native execution; возможны короткие player-safe сообщения в журнале | Нет промежуточной генерации |
| Действие завершилось, упёрлось в препятствие или вернуло управление | Зафиксировать фактический результат и доступное восприятие | Одна связная сцена для этой границы |
| В процессе возникла опасность/существенное обращение, требующее выбора | CDDA прерывает действие согласно реальным механикам; прошедшее время и частичный результат учитываются | Описать только реально достигнутую границу; не приписывать будущее завершение |
| Игрок просит «осматриваюсь»/«что вокруг?» | Получить актуальную player-safe сцену; длительность решает механический owner, не narrator | Одна новая сцена по запросу, без выдуманного изменения мира |
| Завершился разговор, существенное действие NPC или бой | Сначала фактическая речь/результат, восприятие и согласованное сохранение | Художественное изложение ровно того, что герой мог узнать |

**Не добавлять универсальный таймер прозы каждые 5/10/30 секунд.** Реальные границы — завершение или прерывание уже имеющейся активности и запрос игрока на наблюдение. Если в игре понадобится промежуточная остановка, её источником должно быть конкретное прерывание/восприятие, а не частота вызовов LLM.

Рассказчик **не обязан перечислять** каждый шаг, каждый NPC и каждый `add_msg`. Но он обязан передать существенные для игрока подтверждённые и воспринимаемые события по [активной норме художественной подачи](../../data/knowledge-source/corpus/DOCUMENTS/situational_prose_requirements.md); отдельный журнал **не оправдывает** их пропуск.

## 4. Два уровня информации в интерфейсе

**А. Основная область — рассказчик.** Связная историческая проза о достигнутой границе: положение героя, результат действия, изменение окружения, существенные действия других людей, точная произнесённая речь (если она действительно услышана). Текст создаёт только существующий `@rus/narration` из подтверждённой player-safe проекции.

**Б. Отдельная область — «Журнал событий».** Постоянно доступная краткая хронология, независимая от момента генерации прозы. Предлагаемое отображение — игровое время + короткое native сообщение, где сообщение уже обоснованно доступно игроку. Повторы сворачиваются нативным механизмом, история остаётся просматриваемой.

Журнал помогает игроку держать контекст: время, движение, столкновения, предупреждения и замеченные изменения могут быть видимы даже между литературными ответами. Он не должен открывать debug-сообщения, скрытое состояние, чужие мысли, невидимые NPC или события, о которых персонаж не мог узнать.

**Пример только для иллюстрации желаемого UX; это не реальный игровой прогон и не гарантированные CDDA сообщения:**

| Игровое время | Журнал |
| --- | --- |
| 10:32:04 | Вы начали движение к Торгу. |
| 10:32:21 | Прохожий уступил дорогу. |
| 10:32:40 | Справа слышится окрик. |
| 10:32:58 | Вы добрались до Торга. |

По завершении пути narration мог бы написать **одну** сцену прибытия с уместными подробностями, а не четыре отдельные литературные сцены. Если окрик на 10:32:40 требует срочной реакции, действие **должно остановиться тогда**, и фиктивное прибытие на 10:32:58 нельзя записывать.

Примерные timestamp и тексты выше — вымышленные; основание для каждой реальной записи обязано поступить из актуального подтверждённого исполнения/восприятия.

## 5. Границы источников истины, сохранения и приватности

| Ответственность | Владелец / правило |
| --- | --- |
| Секунды, `moves`, activity, физические прерывания, результат | Native CDDA после согласованного cutover |
| Истина о реально произошедшем и доступности действия | CDDA и соответствующие authoritative domain owners; не journal text |
| Perception, память и разрешённый игроку контекст | Единая player-safe projection; не сырой `Messages::recent_messages` |
| Художественный ответ и его проверка | Существующий `@rus/narration`, после подтверждения/commit |
| Краткие сообщения | Native CDDA message log; адаптер только доставляет/показывает разрешённое |
| Окно журнала и окно прозы | Существующие presentation/UI owners; UI не пересказывает события шаблонами |
| Save/load/replay CDDA + Novgorod | Единый согласованный checkpoint протокол ещё предстоит доказать |

В текущем Novgorod1230 [`packages/narration/MODULE.md`](../../packages/narration/MODULE.md) устанавливает `runNarrationFlow` для `surface: turn`, строгую смысловую проверку и запрет создавать факты в прозе. [`packages/presentation/MODULE.md`](../../packages/presentation/MODULE.md) разрешает обычный `TurnScreen` **только** с approved narration. `FactualTurnDeliveryScreen v1` — ограниченный terminal degraded recovery после определённого отказа проверки, **не универсальный режим «тихого хода»**.

Поэтому **целевой беспрозовый показ промежуточных microsteps пока не является активированной возможностью Novgorod1230 UI**. Для него нужно на этапе прототипа проверить существующие read models и при необходимости явно согласовать минимальный presentation cutover; нельзя обходить требования текущего контракта, называя неподтверждённую прозу журналом.

Если LLM тормозит или отказал, **физическое действие не исполняется повторно**. Отображение журнала возможно после доступного подтверждения native результата; но нельзя выдавать непринятое поколение save за durable state. Повторная загрузка не должна дублировать события и записи. Детали сохранения и adapter lifecycle относятся к P4–P5 [основного плана миграции](./Novgorod1230_Cataclysm_Audit_and_Migration_2026-10-18.md).

## 6. Минимальный путь реализации — без нового engine

1. **Сначала проверить headless-доступ к native сообщениям** в выбранном CDDA host. Подтвердить `Messages::recent_messages`/историю, порядок, время, дубли, фильтрацию и поведение после save/load. Не предполагать, что готовый headless API уже существует.
2. **Сделать только тонкую доставку журнала в имеющийся UI**: read-only, ограниченное количество записей, фильтр player-safe, без отдельного БД/event-log owner. Если нужен небольшой native API для чтения последних сообщений/инкрементов, расширять соответствующий существующий CDDA owner после проверки.
3. **Привязать вызов текущего `@rus/narration` к пользовательской meaningful boundary** — завершение, реальное прерывание или явное описание — вместо посекундного тика. Использовать уже существующий путь factual result → persisted player-safe package → narration; не создавать новый prose scheduler.
4. **Сохранить UI-границу между «продолжающееся действие» и «завершённый narratable ответ»**. Любое изменение `TurnScreen`/процедуры публикации требует отдельного явного P7 решения после прототипа; не подменять корректный экран деградированной factual delivery.
5. **Не генерировать новые механические события из записей журнала**. Если необходимы точные event IDs, источники восприятия или replay provenance, брать их из engine/domain confirmed events в соответствующей подсистеме, а не из локализованного текста.

**Ничего дополнительно не вводить, пока не получен работающий вертикальный срез.** В частности: ни второго event bus, ни универсального классификатора «интересных моментов», ни отдельного таймера narration, ни шаблонной prose fallback системы.

## 7. Что проверить на прототипе

Ниже **критерии будущих тестов**, а не отчёт об их прохождении:

1. Длительное действие занимает, например, 54 реальные **игровые** секунды. CDDA исполняет процесс, UI и разрешённый журнал обновляются; **не запускаются 54 LLM-вызова**. При завершении — один narratable result.
2. На 20-й секунде возникает подлинная угроза. Движение прерывается на фактическом достигнутом месте; elapsed и последствия точны; narration не сообщает об успешном прибытии.
3. Игрок просит описать место: выдаётся одна сцена по текущему восприятию; сама генерация текста, сеть и чтение не продвигают clock.
4. Native сообщения доступны из выбранного host; часть повторов свёрнута; журнал не показывает debug, невидимое или неизвестное герою.
5. Narrator получает только player-safe committed evidence **не из parsed log strings**. Существенное воспринятое событие не теряется из prose только потому, что запись есть в журнале.
6. После save/load/retry нет повторного движения, удвоения elapsed, повторной генерации действий или ложных новых записей; доступность журнала и narration согласована с accepted checkpoint.
7. Если approved narration отсутствует, поведение остаётся в рамках действующей политики доставки; нельзя молча выдавать самодельную прозу или general-purpose factual fallback вместо требуемой проверки.

**Проверки не выполнялись в этой беседе.** Доступность инкрементального headless journal bridge, нагрузка от журнала, cutover `TurnScreen` и cross-store persistence пока **не доказаны**.

## 8. Итог обсуждения

**Одна посекундная симуляция CDDA → много native игровых действий и коротких сообщений → одна литературная сцена на meaningful границу.** Игрок видит отдельно **рассказчика** и **живой журнал сообщений**, который удерживает хронологию без дополнительной LLM-генерации.

Проза остаётся художественным выражением подтверждённого мира, журнал — инструментом наблюдения, CDDA — источником физического исполнения. Не копировать конкурирующие механизмы. Этот документ фиксирует принятое направление, **не изменяет** `AGENTS.md`, governing/ACTIVE нормы, schemas, код или release bindings и **не разрешает** production cutover без проверенного прототипа и соответствующего Contract Audit.
