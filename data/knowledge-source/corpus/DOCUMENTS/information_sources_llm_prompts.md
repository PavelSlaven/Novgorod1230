# Работа с информацией, источниками и промтами LLM

## Нормативная актуализация materialization v2

Этот документ подчинён `code_driven_world_materialization_architecture.md`. Источники и редакторский процесс утверждают категории, шаблоны, профили, правила и исторические факты. Runtime-код материализует конкретные G5/NPC и authored/significant/hidden items и рассчитывает обычные последствия. Active player planner предлагает только следующий строгий step, но не генерирует свободный runtime-state и не пишет в базы.

Допустимые runtime-роли LLM: bounded decision по genuinely closed списку с `option_id` и `command_token`, активный player `turn_step_planner`, player conversation interpreter, NPC conversation responder, revision-15 NPC autonomous decider, генерация персонажа игрока, аудит и проза только из visible context. Любой структурированный ответ проходит профильные JSON Schema, state-version и code-owned admission gates; фактическое последствие всегда рассчитывает код. Player turn-step, NPC conversation и NPC autonomous decision активны; NPC combat decision остаётся `proposed`.

`turn_step_planner` получает только `turn_step_request_v1`: root player action, remaining intent, committed state version, working revision, ordered summaries уже выполненных шагов, actor и текущую player-safe working projection. Он возвращает только `turn_step_plan_v1` для следующего шага. Provider не получает hidden state, SQL, write plan, container contents или объективные сведения вне восприятия персонажа.

Одна planner session принадлежит одному root turn, использует не более восьми внутренних шагов и после каждого применённого результата получает заново построенную player-safe projection. Допускается один structural repair невалидного плана; repair видит исходный request и структурные ошибки, но не новый factual context. Exact registered command обходит planner. Все шаги накапливаются в code-owned draft и фиксируются только единым commit после revalidation.

Conversation interpreter получает только player-safe context и возвращает один
`player_conversation_contribution_plan_v1`. NPC responder получает только
фактически воспринятое сообщение, persisted knowledge/memory самого NPC и
общую boundary; private knowledge, скрытые причины и prompts других NPC ему не
передаются. Слушатель или свидетель может получить perception/received
knowledge без response boundary. Social check сообщает лишь delivery quality
и credibility; ответ NPC остаётся отдельным semantic решением. Conversation
не имеет собственной trigger subsystem и использует общие пять категорий
`self`, `others`, `environment`, `objective`, `communication` с уровнями
`material` и `critical`.

Autonomous decider получает один `npc_action_decision_request_v1` только с
субъективным состоянием самого NPC и возвращает один `npc_step_plan_v1`.
Он не получает hidden state других actor, не назначает factual outcome, RNG,
exact elapsed, body delta или write plan. Один structural repair исправляет
только schema, enum и refs. Код повторно проверяет state version и исполняет
одно ближайшее намерение через зарегистрированных movement, activity, items и
temporal owners. Persisted semantic trace при retry/restart исключает повторный
model call и повторное применение последствия. Combat этим path не активирован.

Для Temporal World v4 security projection является code-owned. Factual
visible package создаётся и сохраняется в atomic commit до narration;
narrator получает только persisted player-safe package после commit. LLM не
создаёт дату, schedule, weather transition, temporal boundary, consequence,
route или отсутствующий candidate. Профильный proposed-норматив:
`temporal_world_and_interruptible_activities.md`.

## Назначение документа

Этот документ описывает, как игра работает с исторической, игровой и технической информацией, как отдельный offline/editorial workflow пополняет базу знаний и обращается к внешним источникам, как сведения проходят через черновой слой, как отделяются факты от слухов и как должны строиться внутренние промты runtime LLM-агентов.

Документ нужен для того, чтобы:

1. снизить расход токенов;
2. уменьшить количество противоречий;
3. повысить историческую связность мира;
4. отделить утверждённые данные от черновых;
5. сохранить возможность пополнения базы во время игры;
6. не превращать LLM в единственный источник истины;
7. сделать последующий ручной аудит базы возможным и удобным.

Главный принцип: **LLM может искать, извлекать, сжимать и применять сведения, но всё новое должно иметь происхождение, статус достоверности и возможность последующей проверки.**

---

# 1. Общая модель информации

Информация в игре делится на несколько слоёв:

1. **проектные правила** — как должна работать игра;
2. **утверждённая база** — проверенные исторические, региональные, бытовые и социальные сведения;
3. **черновая база** — сведения, найденные или созданные во время игры, но ещё не прошедшие ручной аудит;
4. **память партии** — всё значимое, что уже произошло в конкретной игре;
5. **знания персонажа** — то, что персонаж видел, слышал, знает, помнит или предполагает;
6. **скрытое состояние мира** — то, что существует в симуляции, но не известно игроку;
7. **сценический контекст** — минимальный набор данных для текущего хода;
8. **отбракованные сведения** — записи, которые аудит признал ошибочными, нерелевантными или вредными для проекта.

LLM не должна каждый ход заново изобретать XIII век. Она должна получать компактный пакет релевантной информации и действовать внутри заданных ограничений.

---

# 2. Источники истины и приоритеты

Источниками истины считаются:

1. актуальные проектные документы;
2. сохранённое состояние текущей партии;
3. журнал уже произошедших событий;
4. утверждённая база проекта;
5. источники контекста и приоритеты;
6. черновая база;
7. редакторские исторически допустимые гипотезы со статусом `draft`, не доступные runtime до аудита.

При конфликте сведений используется следующий порядок приоритета:

1. проектные документы;
2. сохранённые факты текущей партии;
3. журнал уже произошедших событий;
4. утверждённая база проекта, включая проверенные региональные записи;
5. черновая база со статусом `usable_with_caution`;
6. черновая база со статусом `draft`;
7. утверждённая редактором гипотеза, уже переведённая в допустимую category/template/profile/rule запись.

Черновая база не может отменять проектные правила и уже произошедшие события партии.

LLM не должна менять сохранённые игровые факты ради найденной позднее справки, если эти игровые факты уже стали частью партии и не нарушают правила проекта.

---

# 3. Утверждённая база

Утверждённая база — это сведения, которые прошли ручной аудит и считаются надёжными для проекта.

Она может содержать:

1. сведения об эпохе;
2. сведения о землях и регионах;
3. сведения о крупных городах, путях, реках, переправах, монастырях и торгах;
4. исторические события и личности;
5. социальные роли;
6. бытовые шаблоны;
7. правовые и религиозные ограничения;
8. типовые предметы, оружие, одежду, имущество и товары;
9. типовые риски, конфликты и дорожные ситуации;
10. справки о сезонности, климате и хозяйстве.

Утверждённая база не должна быть художественной прозой. Это нормативный слой, из которого код получает категории, profiles, templates и rules для материализации и расчёта, а LLM — только разрешённый контекст своей роли: closed bounded choice, player-safe `turn_step_planner`, аудит или visible prose.

---

# 4. Черновая база

Черновая база — это сведения, которые были найдены, извлечены, сжаты или сформированы во время игры, но ещё не прошли ручной аудит.

Черновая база нужна для отдельного редакторского enrichment workflow. Она не является runtime fallback: нехватка required historical/category/template/profile/rule record создаёт data gap и блокирует зависимую операцию.

Черновая база может содержать:

1. найденные исторические сведения;
2. краткие справки по местам;
3. сведения о личностях;
4. бытовые детали;
5. торговые, правовые, военные и социальные уточнения;
6. региональные особенности;
7. редакторские гипотезы с явным статусом `draft` и источником рассуждения;
8. сведения, требующие последующей проверки.

Черновая база не должна смешиваться с утверждённой. Любая черновая запись должна иметь статус, источник и дату добавления.

---

# 5. Статусы записей базы

Каждая запись базы должна иметь статус.

## `approved`

Запись проверена и принята в утверждённую базу проекта.

Её можно использовать как надёжную опору.

## `draft`

создано, но не использовать для важных решений;

## `usable_with_caution`

прошло быструю проверку, можно использовать как рабочий фон;

## `needs_review`

Запись требует ручной проверки.

заблокировано для игрового применения, пока человек не посмотрит;

## `conflict`

Запись конфликтует с другой записью, проектным документом или уже установленным фактом партии.

До разрешения конфликта её нельзя использовать как основу для важных решений.

## `rejected`

Запись отклонена.

Она не используется при дальнейшей генерации.

---

# 6. Типы информации по достоверности

## 6.1. Исторический факт

Сведения, которые игра считает твёрдыми в рамках выбранной эпохи и региона.

Примеры:

- существование крупного города;
- наличие княжеской власти;
- важная война или угроза;
- социальные ограничения;
- религиозные нормы;
- известные торговые пути.

Исторический факт нельзя отменять свободной генерацией.

## 6.2. Исторически допустимое допущение

Сведения, которые не обязаны быть точным историческим фактом, но соответствуют эпохе, региону и логике проекта.

Примеры:

- безымянная деревня;
- местный кузнец;
- торговец солью;
- монастырский послушник;
- сторож у переправы;
- мелкий спор из-за долга.

Такие данные можно генерировать, если они не конфликтуют с исторической базой.

## 6.3. Игровой факт

То, что уже произошло в конкретной партии.

Примеры:

- персонаж взял долг;
- NPC пообещал помощь;
- игрок оставил вещь в доме;
- персонаж узнал слух;
- дорога оказалась занесена снегом.

Игровой факт имеет высокий приоритет внутри своей партии.

## 6.4. Знание персонажа

То, что персонаж знает, видел, слышал или считает вероятным.

Знание персонажа может быть неполным, ошибочным или устаревшим. UI, подсказки и проза должны показывать мир через знания персонажа, а не через абсолютную правду базы.

## 6.5. Слух

Информация, которая может быть правдивой, искажённой или ложной.

Слух нельзя подавать как факт. В журнале и промтах он должен маркироваться как слух, мнение, чужие слова или непроверенная информация.

## 6.6. Скрытый факт

Данные, которые существуют в состоянии мира, но не известны персонажу.

Скрытые факты нельзя раскрывать в прозе, UI, подсказках действий или журнале, пока персонаж не получил к ним доступ игровым способом.

---

# 7. Формат записи базы

Запись базы должна быть компактной и пригодной для выборочной подстановки в промт.

Рекомендуемый состав записи:

1. `title` — название;
2. `type` — тип записи;
3. `region` — регион или земля;
4. `period` — период применимости;
5. `summary` — краткое содержание;
6. `game_use` — как использовать в игре;
7. `limits` — ограничения и риски применения;
8. `confidence` — уровень уверенности;
9. `status` — статус проверки;
10. `sources` — источники или происхождение;
11. `created_at` — дата добавления;
12. `used_in` — где запись была использована;
13. `related` — связанные места, NPC, события, темы или предметы;
14. `notes` — комментарии для будущего аудита.

Типы записей могут включать:

1. эпоха;
2. регион;
3. место;
4. историческая личность;
5. событие;
6. социальная роль;
7. занятие;
8. обычай;
9. право;
10. религия;
11. торговля;
12. дорога;
13. предмет;
14. оружие;
15. одежда;
16. пища;
17. риск;
18. слуховой шаблон;
19. бытовая сцена.

---

# 8. Подготовка пополнения базы по сигналу из игры

Runtime игры не пополняет утверждённую базу. Он может зарегистрировать формальный data-gap request. По нему отдельный offline/editorial процесс собирает источники и готовит draft records; импорт в `world_base` выполняется только после проверки, approval и нового version pin.

LLM редакторского процесса имеет право обращаться к внешним источникам. Runtime LLM не использует интернет, чтобы незаметно продолжить ход или материализовать отсутствующий вариант.

Найденные сведения не становятся утверждённой истиной проекта автоматически. Сначала они попадают в черновую базу.

Создание редакторского data-gap задания допустимо, если:

1. в текущей базе нет нужных сведений;
2. требуется уточнить историческое место, личность, событие или регион;
3. игрок явно движется к известному историческому объекту;
4. сцена требует конкретной бытовой, правовой, торговой, военной или религиозной детали;
5. нужно снизить риск грубой исторической ошибки;
6. текущая генерация упирается в нехватку достоверного контекста;
7. создаётся новый региональный или локальный пакет сведений;
8. требуется подготовить справку для будущих сцен.

Даже мелкая декоративная деталь не становится runtime-фактом через свободное допущение. Она либо уже разрешена утверждённым шаблоном/правилом, либо остаётся прозой без state mutation, либо оформляется как data gap.

---

# 9. Использование интернета

Интернет и внешние источники являются допустимым источником черновой базы.

Они могут использоваться:

1. при редакторской подготовке каталога новой игры;
2. при offline-подготовке нового региона;
3. при приближении к известному историческому месту;
4. при появлении исторической личности или силы;
5. при уточнении быта, права, торговли, религии, войны или дорог;
6. при подготовке регионального пакета;
7. при проверке спорной детали;
8. при расширении базы для будущих партий.

Интернет не должен использоваться как бесконтрольный поток сведений. Каждое обращение должно иметь понятную информационную потребность.

---

# 10. Что нельзя делать при обращении к внешним источникам

LLM не должна:

1. бесконтрольно копировать большие фрагменты внешних материалов;
2. превращать найденный текст в художественную прозу без сжатия;
3. считать один случайный источник абсолютной истиной;
4. смешивать сведения из разных эпох без маркировки;
5. выдавать черновую запись за утверждённую базу;
6. раскрывать игроку сведения, которые персонаж не мог знать;
7. ломать уже произошедшие события партии ради найденной справки;
8. использовать современные оценки и термины как внутреннее знание средневекового персонажа;
9. сохранять источник без краткого резюме;
10. добавлять в игровую базу нерелевантные энциклопедические сведения;
11. подменять игровую сцену пересказом справочной статьи;
12. использовать материалы без сохранения происхождения.

---

# 11. Данные для генерации новой игры

Во время runtime-генерации новой игры LLM не обращается к внешним источникам и не пополняет базу. Стартовый pipeline использует только approved snapshots, candidates, profiles и rules, подготовленные до запуска партии.

На старте партии из утверждённых данных формируются:

1. историческая рамка;
2. год и сезон;
3. крупная земля;
4. регион;
5. стартовое место;
6. социальная среда;
7. возможные исторические напряжения;
8. крупные ориентиры;
9. локальные бытовые условия;
10. стартовый набор знаний персонажа.

Если утверждённых данных недостаточно, pipeline создаёт data gap и hard block. Внешний поиск, создание draft-карточек и их проверка принадлежат отдельному offline/editorial workflow; его результаты могут использоваться новой игрой только после явного статуса `approved` и новой версии catalog snapshot.

---

# 12. Data gap во время обычного хода

Во время обычного хода runtime не обращается к внешним источникам и не пополняет candidate set.

Недостаток утверждённых данных создаёт диагностируемый data gap и hard block, если:

1. сцена станет исторически пустой;
2. есть риск грубой ошибки;
3. игрок взаимодействует с известным историческим местом или событием;
4. нужно уточнить важную социальную, правовую, военную или религиозную деталь;
5. игра впервые входит в новый важный регион или крупное место;
6. действие игрока требует знания конкретного исторического контекста.

Локальное допущение не может стать фактом или state mutation. Художественная проза использует только переданный visible context.

# Правило обращения к внешним источникам и кэширования сведений

Игра не должна обращаться к внешним источникам автоматически при каждом ходе.

Обращение к внешним источникам выполняет только отдельный offline/editorial workflow. Его draft не влияет на текущий ход и становится runtime-кандидатом лишь после проверки и статуса approved.

Перед обращением к внешним источникам игра должна проверить:

1. есть ли подходящая запись в утверждённой базе;
2. зарегистрирован ли уже такой data gap или редакторский draft;
3. какие region/period/category constraints должен соблюдать будущий кандидат;
4. не запрашивались ли уже похожие сведения раньше;
5. действительно ли найденная информация нужна для текущей сцены, региона, персонажа, события или будущего контекста партии.

Каждый запрос к внешним источникам должен оформляться как отдельная информационная потребность, а не как свободный поиск.

Минимальная структура такого запроса:

```json
{
  "reason": "почему сведения понадобились",
  "period": "год, сезон или диапазон",
  "region": "земля, область или место",
  "topic": "что именно нужно уточнить",
  "scope": "масштаб запроса: место / регион / событие / личность / быт / право / торговля / война / религия / дорога",
  "max_sources": "ограничение на число источников",
  "cache_key": "ключ для повторного использования результата",
  "result_status": "draft / usable_with_caution / needs_review"
}
```

Если по `cache_key` уже есть подходящая запись, игра должна использовать сохранённое резюме, а не выполнять новый внешний поиск.

Ключ кэша должен строиться из периода, региона, темы и масштаба запроса. Например:

```text
1237_novgorod_winter_road_conditions_region
```

Найденные сведения не должны попадать напрямую в художественную прозу, журнал игрока или знания персонажа. Сначала они должны быть сжаты в компактную карточку черновой базы с указанием источников, уровня уверенности, ограничений применения и статуса проверки.

Повторное обращение offline/editorial workflow к внешним источникам допустимо только если:

1. прежняя запись отсутствует;
2. прежняя запись слишком общая;
3. прежняя запись конфликтует с текущей ситуацией;
4. изменился регион, период или масштаб задачи;
5. игрок взаимодействует с конкретным историческим местом, личностью или событием;
6. есть риск грубой исторической ошибки;
7. разработчик или аудит пометил прежнюю запись как недостаточную.

Агент сцены, агент подсказок действий и агент памяти не должны сами запускать внешний поиск. Они могут только сообщить, что текущего контекста недостаточно. После этого runtime регистрирует data gap; отдельный offline/editorial процесс может подготовить draft, но текущий ход не получает новый вариант автоматически.

Результат внешнего поиска должен быть сохранён так, чтобы его можно было использовать повторно в этой и будущих партиях без нового обращения к интернету.


---

# 13. Пополнение базы и знания персонажа

Найденная во внешнем источнике информация не становится знанием персонажа автоматически.

После отдельного аудита и перевода записи в `approved` она может использоваться:

1. как скрытая опора для генерации мира;
2. как основа для описания среды;
3. как материал для слуха;
4. как знание персонажа, если оно соответствует его роли, происхождению и опыту;
5. как информация, которую персонаж может узнать через NPC, книгу, церковную среду, торговцев, княжеских людей или собственное наблюдение.

Если персонаж не мог знать найденный факт, он не должен видеть его в UI, журнале, подсказках и прозе как прямое знание.

---

# 14. Контекстные пакеты

LLM не должна получать всю базу проекта на каждый ход.

Для каждого запроса должен собираться компактный контекстный пакет.

Контекстный пакет может включать:

1. задачу конкретного LLM-агента;
2. текущую сцену;
3. текущее место;
4. видимых NPC;
5. краткое состояние персонажа;
6. важные события последних ходов;
7. релевантные записи памяти;
8. релевантные знания персонажа;
9. релевантный исторический и региональный контекст;
10. релевантные записи утверждённой базы;
11. ограничения роли и допустимых commands;
12. формат ожидаемого ответа.

В пакет не должны попадать данные, которые не нужны для текущего решения.

---

# 15. Правило минимального контекста

Каждый LLM-запрос должен получать минимальный достаточный контекст.

Нельзя передавать:

1. весь проектный документ, если нужен один раздел;
2. всю историю партии, если достаточно последних событий и активных обязательств;
3. все данные региона, если сцена происходит в одной деревне;
4. скрытые факты, если агент пишет текст от лица восприятия персонажа;
5. raw JSON без необходимости;
6. технические логи в игровые промты;
7. все черновые записи базы без отбора;
8. источники целиком, если достаточно краткой карточки.

Контекст должен быть сжат до полезных смыслов.

---

# 16. Отбор контекста

Перед каждым LLM-запросом игра должна выбирать не всю базу, а только релевантные записи.

Отбор контекста должен:

1. определить текущую информационную потребность;
2. найти релевантные утверждённые записи;
3. исключить draft/conflict/rejected записи из runtime facts и options;
4. отделить знания персонажа от скрытой информации;
5. зарегистрировать data gap, если утверждённых записей недостаточно;
6. собрать компактный пакет для конкретного агента;
7. не передавать лишние документы и справки.

Если релевантных записей нет, runtime возвращает data gap. Агент пополнения базы запускается только вне текущей транзакции хода и не меняет её результат.

---

# 17. Разделение LLM-агентов

Разные задачи должны выполнять разные LLM-агенты или разные режимы промтов.

Один агент не должен одновременно:

1. генерировать художественную прозу;
2. обновлять состояние;
3. проверять историческую достоверность;
4. выбирать подсказки действий;
5. чинить JSON;
6. вести журнал;
7. принимать боевые расчёты;
8. искать источники;
9. пополнять базу.

Разделение агентов снижает риск противоречий и упрощает отладку. 
Offline/editorial агент пополнения базы — специальное исключение, которому разрешены поиск, сжатие и создание черновой карточки, но запрещены участие в текущей runtime-транзакции, проза, последствия хода и изменение партии.

---

# 18. Основные типы LLM-агентов

## 18.1. Агент сцены

Создаёт художественное описание текущей сцены.

Он получает:

1. текущую ситуацию;
2. видимые детали;
3. знания персонажа;
4. краткий исторический контекст;
5. активных NPC;
6. ограничения по тону и стилю.

Он не должен:

1. раскрывать скрытые факты;
2. показывать технические данные;
3. придумывать крупные исторические события без основания;
4. менять состояние персонажа напрямую;
5. решать последствия хода без отдельной логики;
6. превращать справочную информацию в лекцию.

## 18.2. Bounded decision agent

Не рассчитывает последствия и не обновляет состояние. Получает только подписанный закрытый список options, уже отфильтрованный кодом, и возвращает точный `request_id`, `state_version`, `option_id`, `command_token`. Любое дополнительное поле, неизвестная команда, stale policy/state, истёкший срок или нарушенная precondition блокируют результат. Последствие и change set после выбора рассчитывает зарегистрированный code handler.

## 18.3. Агент памяти

Предлагает кандидатов из уже утверждённого visible consequence package. Код проверяет ссылки и решает, какие записи сохранить в журнал, память, обязательства, список людей, мест, имущества или слухов.

Он не должен записывать каждую мелочь. В память попадает только то, что может повлиять на будущую игру.

## 18.4. Агент подсказок действий

Предлагает возможные действия с точки зрения персонажа игрока.

Он получает:

1. текущую прозу;
2. состояние персонажа;
3. социальную роль;
4. видимых NPC;
5. опасности;
6. цели и обязательства;
7. знания персонажа.

Он предлагает не список всех команд, а несколько естественных вариантов поведения: что персонаж мог бы сделать в такой ситуации.

Подсказки не должны раскрывать скрытую информацию.

## 18.5. Агент исторической проверки

Проверяет, не противоречит ли генерация эпохе, региону и уже заданной исторической рамке.

Он не должен переписывать всю сцену. Его задача — находить грубые ошибки и предлагать краткие исправления.

## 18.6. Агент структурирования

Преобразует уже принятое содержание в нужную структуру.

Он не должен добавлять новые события, NPC, предметы или факты. Его задача — аккуратно разложить готовый смысл по нужным разделам.

## 18.7. Агент пополнения базы

Ищет, извлекает, сжимает и оформляет сведения для черновой базы.

Он не пишет художественную сцену и не принимает игровые последствия.

Он получает:

1. вопрос или информационную потребность;
2. период;
3. регион;
4. текущую игровую ситуацию;
5. ограничения проекта;
6. уже имеющиеся записи базы;
7. требуемый формат результата.

Он должен вернуть:

1. краткое резюме найденного;
2. список источников;
3. оценку уверенности;
4. возможные противоречия;
5. компактную карточку для базы;
6. рекомендации по использованию в игре;
7. пометку, требует ли запись ручного аудита.

---

# 19. Общие правила внутренних промтов

Каждый внутренний промт должен явно указывать:

1. роль агента;
2. задачу;
3. источники, которыми агент может пользоваться;
4. что агенту запрещено делать;
5. что считать уже установленным фактом;
6. что считать знанием персонажа;
7. какие данные скрыты от игрока;
8. допустимый объём ответа;
9. формат ответа;
10. критерии успешного результата.

Промт не должен просить LLM «сделать хорошо» без конкретных ограничений.

---

# 20. Запреты для LLM

LLM запрещено:

1. менять уже сохранённые факты партии без явной причины;
2. раскрывать скрытые сведения игроку;
3. выдавать слухи за факты;
4. создавать крупные исторические события без опоры на рамку;
5. переносить современные понятия, поведение и лексику в XIII век без необходимости;
6. превращать каждую сцену в драматическое событие;
7. добавлять новые механики, не описанные в документах;
8. добавлять технические данные в художественную прозу;
9. использовать полный доступ к состоянию мира там, где требуется восприятие персонажа;
10. исправлять игровые правила по собственному усмотрению;
11. объявлять черновые сведения утверждённой истиной;
12. путать знания игрока, знания персонажа и знания симуляции.

---

# 21. Правило неизвестности

Если данных недостаточно, LLM не должна притворяться, что знает точный ответ.

При недостатке данных runtime LLM может только:

1. оставить факт неопределённым в прозе без записи состояния;
2. выбрать один переданный option_id/command_token, если код сформировал bounded request;
3. вернуть формальный data-gap signal;
4. запросить offline/editorial пополнение базы;
5. прекратить смысловую операцию, если required candidate set пуст;
6. не превращать слух, предположение или правдоподобие в runtime-факт.

Неизвестность является нормальной частью игры, особенно если персонаж находится в незнакомом месте.

---

# 22. Правило знаний персонажа

Игровой текст, UI, подсказки и карта должны показывать мир через знания персонажа.

Персонаж может знать:

1. то, что видел сам;
2. то, что ему сказали;
3. то, что соответствует его происхождению, занятию и опыту;
4. то, что общеизвестно в его среде;
5. то, что он может разумно предположить.

Персонаж не должен знать:

1. скрытые мотивы NPC;
2. точное устройство незнакомой местности;
3. правдивость слухов;
4. будущие исторические события;
5. технические данные симуляции;
6. полную карту региона, если он её не изучал;
7. сведения из внешних источников, которые игра нашла для себя, но персонаж не мог узнать.

---

# 23. Карта знаний

Карта в игре является не объективной картой мира, а картой знаний персонажа.

Она может показывать:

1. текущую локацию;
2. места, где персонаж был;
3. известные дороги и направления;
4. предполагаемые пути;
5. места из слухов;
6. крупные известные ориентиры;
7. опасные или сомнительные направления.

Она не должна показывать:

1. все узлы фактического графа мира;
2. скрытые поселения;
3. NPC, которых персонаж не знает;
4. точные связи, которые персонаж не проверял;
5. технические идентификаторы узлов;
6. сведения, найденные LLM в источниках, но не полученные персонажем внутри игры.

---

# 24. Игровая память

Игровая память хранит не всё подряд, а только значимые факты.

В память должны попадать:

1. важные решения игрока;
2. обещания;
3. долги;
4. конфликты;
5. приобретённые или потерянные предметы;
6. новые знания персонажа;
7. новые связи с NPC;
8. посещённые места;
9. слухи;
10. изменения состояния мира, которые могут повлиять на будущее.

В память не должны попадать:

1. декоративные описания без последствий;
2. повторяющиеся бытовые детали;
3. технические сообщения;
4. промежуточные рассуждения LLM;
5. незначимые фразы, если они не изменили ситуацию;
6. черновые источниковые справки, если они не стали знанием персонажа.

---

# 25. Журнал и источники информации

Игровой журнал должен отделять разные типы записей:

1. события;
2. память;
3. обязательства;
4. люди;
5. места;
6. имущество;
7. слухи и исторический фон (только то, что персонаж узнал, услышал или вывел из наблюдений).

Запись в журнале должна по возможности содержать:

1. краткое содержание;
2. дату или момент партии;
3. источник информации внутри мира;
4. статус достоверности;
5. связь с NPC, местом или предметом;
6. признак актуальности.

Слухи, предположения и чужие слова должны быть явно отделены от проверенных фактов.

---

# 26. Журнал источников

Помимо игрового журнала, проект должен вести журнал источников.

Журнал источников нужен не игроку, а разработчику и аудитору базы.

В нём фиксируются:

1. когда была создана запись;
2. почему потребовалось пополнение базы;
3. какой агент запросил сведения;
4. какие источники были использованы;
5. какая краткая запись была создана;
6. где она была использована в игре;
7. какой статус проверки она имеет;
8. есть ли конфликты с другими записями;
9. нужно ли вернуться к записи при ручном аудите.

Журнал источников не должен отображаться в игровом интерфейсе.

---

# 27. Отладка источников и генерации

Отладка должна сохранять информацию о том, какие данные использовались при генерации.

В диагностике можно показывать:

1. какие справочные блоки были выбраны;
2. почему они были выбраны;
3. какой контекст ушёл в LLM;
4. какой агент выполнял задачу;
5. что агент вернул;
6. какие данные были записаны в память;
7. какие записи были добавлены в черновую базу;
8. какие источники использовались;
9. какие ошибки проверки возникли;
10. какие данные были отброшены.

Эта информация не должна попадать в игровой UI.

---

# 28. Ручной аудит базы

Ручной аудит базы проводится отдельно от игрового процесса.

Во время аудита разработчик может:

1. принять черновую запись в утверждённую базу;
2. исправить запись;
3. объединить дубли;
4. понизить уверенность;
5. отклонить запись;
6. пометить конфликт;
7. добавить комментарий;
8. заменить источник;
9. связать запись с другими блоками;
10. запретить дальнейшее использование записи.

Игра должна сохранять достаточно метаданных, чтобы аудит был возможен после партии.

---

# 29. Экономия токенов

Экономия токенов достигается не запретом на интернет и не сокращением качества прозы, а правильной подготовкой и отбором контекста.

Для этого нужно:

1. не передавать всю базу целиком;
2. использовать короткие справочные блоки;
3. выбирать только релевантные записи;
4. хранить краткие резюме старых событий;
5. отделять игровую память от художественного текста;
6. не заставлять LLM повторять уже известные правила;
7. не смешивать несколько задач в одном запросе;
8. не передавать скрытые данные агентам, которым они не нужны;
9. не генерировать заново то, что можно взять из базы;
10. сохранять найденные сведения для будущих партий.

---

# 30. Недопустимая экономия

Нельзя экономить токены за счёт:

1. потери причинно-следственной связности;
2. исчезновения важных событий из памяти;
3. удаления обязательств и долгов;
4. упрощения социальной логики;
5. игнорирования состояния персонажа;
6. потери исторического контекста;
7. смешивания слухов и фактов;
8. раскрытия скрытой информации;
9. отказа от источников там, где без них высок риск грубой ошибки;
10. превращения сцены в пустую универсальную прозу.

---

# 31. Требования к промтам

Промты должны быть короткими, но жёсткими.

Хороший промт:

1. говорит агенту, кто он;
2. даёт конкретную задачу;
3. ограничивает источники;
4. запрещает лишнее;
5. указывает формат ответа;
6. требует учитывать знания персонажа;
7. требует сохранять уже установленные факты;
8. не просит придумывать новые механики;
9. не заставляет агента решать чужую задачу;
10. отделяет утверждённую базу от черновой.

Плохой промт:

1. просит «сгенерировать красиво»;
2. даёт всю базу проекта;
3. смешивает прозу, расчёты и JSON;
4. не отделяет факты от слухов;
5. не говорит, что скрыто от игрока;
6. разрешает LLM исправлять правила;
7. требует одновременно придумать содержание и структурировать его;
8. не указывает, можно ли использовать черновые сведения;
9. не требует сохранять источник найденной информации.

# 32. Минимальная структура промта агента

Внутренний промт агента должен иметь такую структуру:

```md
# Роль

Ты — [тип агента].

# Задача

[конкретная задача]

# Доступные источники

[какие данные можно использовать]

# Уже установленные факты

[факты партии, которые нельзя отменять]

# Знания персонажа

[что персонаж знает и может учитывать]

# Скрытая информация

[что нельзя раскрывать игроку]

# Ограничения

[что запрещено делать]

# Черновая база

[можно ли использовать черновые записи и с какой осторожностью]

# Формат ответа

[требуемый формат]

# Критерии успеха

[как понять, что ответ подходит]
```

# 33. Пример промта агента пополнения базы

```md
Найди и сожми сведения, нужные для текущей игровой ситуации. Не пиши художественную сцену и не принимай игровые последствия.

Можно использовать внешние источники и уже имеющиеся записи базы.

# Ограничения

Не копируй большие фрагменты.
Не смешивай эпохи.
Не выдавай черновую запись за утверждённую.
Не раскрывай сведения персонажу автоматически.
Не добавляй игровые события.

1. Краткое резюме.
2. Источники.
3. Уровень уверенности.
4. Возможные противоречия.
5. Черновая карточка базы.
```

# 34. Пример промта агента сцены

```md
# Роль

Ты — агент сцены исторической текстовой RPG.

Напиши художественное описание текущей сцены через восприятие персонажа.

Художественная проза без JSON и технических комментариев.
```

# 35. Пример промта агента подсказок действий

```md
# Роль

Ты — агент подсказок действий.

# Задача

Предложи несколько естественных действий, которые персонаж мог бы выбрать в текущей ситуации.

# Контекст

Используй текущую прозу, состояние персонажа, социальную роль, знания персонажа, видимых NPC, опасности, цели и обязательства.

Верни 3–5 коротких вариантов действия от лица возможного намерения персонажа.
```

# 36. Главное правило

Runtime LLM не пополняет базу, не обращается к внешним источникам и не использует найденный во время партии материал для текущей сцены или state mutation.

Внешний материал существует только в отдельном offline/editorial workflow как draft с provenance. Он не влияет на активную партию и становится доступным runtime лишь после проверки, нормализации, статуса `approved` и публикации нового version-pinned catalog snapshot.

Игра должна становиться умнее от партии к партии, но не должна терять различие между проверенным знанием, черновым знанием, слухом, игровым фактом и знанием персонажа.
