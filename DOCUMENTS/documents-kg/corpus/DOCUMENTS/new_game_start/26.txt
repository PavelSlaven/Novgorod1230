# ПРИОРИТЕТНАЯ РЕДАКЦИЯ 3 — ИЗОЛИРОВАННЫЙ STAGE 26, PLAYER-SAFE SCREEN И DELIVERY BOUNDARY

Эта редакция имеет приоритет над всеми несовместимыми примерами ниже.

## 0. Архитектурный контракт

Stage 26 — отдельный `isolated_code_and_audit_block`. Он получает только exact `first_game_screen_input`, не читает global context, registry, mutable stage outputs, party DB, world_base, transport или UI framework и возвращает только immutable `stage26_first_game_screen_result`.

Stage 26 ничего не создаёт в мире и не реконструирует committed state. Он детерминированно проецирует уже committed player-safe read model в первый экран, затем пропускает экран через code validation, `FirstScreenSafetyAuditor` и `FirstScreenActionLabelAuditor`.

Provided input/output, caller-provided committed state, готовый screen, готовые audits и обход через параллельный UI payload запрещены во всех окружениях. Для тестов разрешается подменять только role executors; каждый результат проходит реальные validators.

## 0.1. Exact input

```text
first_game_screen_input:
  version/schema/request_id
  stage25_party_commit_approval
  party_start_committed
  committed_public_read_model
  approved_narrator_output
  narrator_output_digest
  narrator_prose_approval
  approved_visible_context
  visible_context_package_digest
  visible_context_approval
  screen_policy
```

`committed_public_read_model` формируется только из Stage 25 live postcommit readback и содержит собственный digest. Stage 20 visible context используется только для проверки provenance и не является fallback-источником данных панелей после commit.

## 0.2. Digest binding

До проекции код повторно вычисляет и сверяет:

```text
postcommit_state_digest
party_start_committed_digest
party_public_state_digest
narrator_output_digest
visible_context_package_digest
first_game_screen_input_digest
```

Stage 25 approval обязан подтверждать `pass=true`, `commit_status=committed`, party/transaction IDs, physical plan digest, postcommit digest, committed/public-state digests и permissions `can_start_stage_26`, `can_show_player_output`, `can_accept_player_input`.

Любой stale/substituted artifact блокирует Stage 26.

## 0.3. Code precheck

До screen projection формируется `first_screen_code_precheck`. Он проверяет:

- exact input schema/version/request ID;
- Stage 25 approval, permissions и digests;
- полную структуру `party_start_committed`;
- party state `ready`, current turn `0`, current position и committed narrator message reference;
- committed public read model schema, party/transaction binding и live-readback provenance;
- narrator output, narrator approval и digest;
- visible context approval и digest;
- неослабляемую screen policy;
- отсутствие forbidden input fields, precommit fallback и synthetic message ID.

При `pass=false` projection и LLM auditors не вызываются.

## 0.4. Deterministic projection

Экран строится только из:

```text
approved narrator prose
committed public position/clock/weather/character labels
committed visible NPC/item/container/exit/cue refs
committed current knowledge map/routes
approved narrator action options
committed player-visible message ID
```

Код не создаёт labels, NPC, items, routes, targets, actions или message IDs. Approved refs и `option_id` сохраняются в output.

## 0.5. Reference and consistency firewall

Код обязан проверить:

- attention refs принадлежат committed player-safe read model;
- action option ID, action kind, target ref и basis refs принадлежат approved inputs;
- action не обещает гарантированный результат и не использует hidden truth;
- known nodes/routes принадлежат committed current knowledge;
- unknown exits не раскрывают destination;
- public position ref совпадает с committed current position;
- public time/light/weather projection совпадает с committed clock projection;
- narrator и visible-context approvals относятся к текущим digests;
- все player-facing строки свободны от raw technical IDs, JSON/debug/audit/source text;
- hidden/private/closed-container/future-event truth не попадает в экран.

Boolean-поля `ui_safety_boundary` вычисляются только по результатам фактических code checks и двух semantic audits; они не выставляются заранее.

## 0.6. Required semantic audits

Успешный Stage 26 обязательно проходит:

```text
FirstScreenSafetyAuditor
FirstScreenActionLabelAuditor
```

Оба аудитора получают только screen, approved narrator/visible artifacts, committed public read model, screen policy и safe reference index. Hidden state, global context, DB handles и полная audit history им не передаются.

`FirstScreenSafetyAuditor` проверяет новые факты, hidden leaks, private motives, closed-container truth, future events, position/time contradiction и technical text.

`FirstScreenActionLabelAuditor` проверяет attention/action labels, risk hints, unknown exits, outcome promises, target substitution, hidden truth и сохранение неопределённости.

## 0.7. Repair and escalation

Разрешены отдельные маршруты:

```text
first_screen_format_repair
first_screen_label_semantic_repair
first_screen_action_label_repair
party_public_read_model_repair
stage25_postcommit_repair
narrator_prose_repair
visible_context_repair
delivery_state_repair
blocked
manual_review
```

Format repair меняет только форму JSON. Semantic repair может менять только presentation labels, но не refs, targets, topology, position, clock, narrator prose, message ID или digests.

Каждый repair заканчивается полным code validation и повтором обоих audits. После исчерпания обычных циклов допускается один senior repair; затем Stage 26 блокируется.

## 0.8. Result bundle and immutability

Успешный Stage 26 возвращает immutable:

```text
stage26_first_game_screen_result:
  pass=true
  input/screen/public-state/narrator/visible/postcommit digests
  first_screen_code_precheck
  first_game_screen
  first_screen_code_validation
  first_screen_safety_audit
  first_screen_action_label_audit
  validation/audit/repair history
  diagnostics
  delivery_permission
```

`screen_digest` вычисляется по каноническому JSON. Доставляться может только тот же frozen screen, который прошёл validation и audits.

Failure возвращается тем же result schema с `pass=false`, failed phase, concerns/evidence, repair route и запрещёнными delivery permissions.

## 0.9. Delivery boundary

Stage 26 только утверждает screen artifact. Доставка выполняется отдельным code-only блоком:

```text
approved Stage 26 result
→ persisted party_first_screen_delivery_attempt
→ transport send
→ client acknowledgement
```

`message_id` берётся только из committed player-visible message record. Synthetic fallback запрещён.

Повторная доставка того же party/message/screen digest идемпотентна и использует тот же delivery attempt binding.

`opening_scene_presented=true` разрешается только после валидного ACK, связанного с party ID, transaction ID, message ID и screen digest. Идентичный повторный ACK идемпотентен; конфликтующий ACK блокируется.

## 0.10. Stage 26 → Stage 27

Stage 27 получает только approved Stage 26 screen, acknowledged delivery и player input с контрактом `intent_not_fact`.

До handoff проверяются:

```text
Stage 26 pass=true
screen_status=ready
screen digest current
delivery attempt acknowledged
ACK matches message/screen/party/transaction
free-text input enabled
input contract=intent_not_fact
selected action option belongs to approved screen
```

Слова игрока передаются как заявка-намерение и не становятся фактом мира до следующего pipeline.

# ПРИОРИТЕТНАЯ РЕДАКЦИЯ 2 — STRICT STAGE 25 → STAGE 26 HANDOFF

Эта редакция имеет приоритет над несовместимыми примерами ниже.

## 0. Архитектурный контракт

Stage 26 запускается только после реального успешного Stage 25 commit и postcommit readback. Синтетический `party_start_committed`, write plan, один `commit_gate_result` или caller-provided party state не являются допустимым основанием для первого экрана.

Exact handoff содержит:

```text
stage25_party_commit_approval
party_start_committed, построенный только из live DB readback
party_public_state, построенный только из committed player-safe read model
approved narrator output
approved narrator audit
visible context package
visible context approval
screen policy
```

`stage25_party_commit_approval` обязан подтверждать:

```text
pass=true
commit_status=committed
party_id
transaction_id
physical_plan_digest
postcommit_state_digest
can_start_stage_26=true
can_show_player_output=true
can_accept_player_input=true
```

До построения экрана код повторно проверяет schema/version/request ID, party/transaction binding, успешный transaction result, `party_postcommit_validation.pass=true`, ready-state, current position, narrator output reference и текущие digests.

Запрещены:

```text
options.partyStartCommitted
options.partyStateAfterCommit
options.currentPositionAfterCommit
options.narratorOutputId
options.partyPublicState
ручной committed state
Stage 24 write plan вместо live state
запуск после dry-run или commit gate без transaction/postcommit
```

При любой ошибке Stage 25 или Stage 25→26 handoff первый экран не создаётся и player-facing output не отправляется.

# Этап 26. Первый игровой экран

## 1. Назначение этапа

Первый игровой экран — это первый player-facing экран после успешного commit стартовой партии.

На этом этапе игрок получает:

* стартовую прозу;
* текущую воспринимаемую позицию;
* время, свет и погодное давление, если они видимы или ощутимы;
* ближайшие видимые NPC;
* ближайшие видимые предметы и контейнеры;
* видимые выходы, проходы и направления;
* безопасные варианты внимания;
* безопасные варианты действия;
* поле свободного ввода для первого хода.

Короткая формула:

```text id="sa6y5f"
party_start_committed
+ approved narrator output
+ visible_context_package
+ safe action options
+ current_position public label
→ first_game_screen
→ player first turn input
```

Главное правило:

```text id="k1l7p7"
Первый экран ничего не создаёт.
Он только показывает игроку уже утверждённое и безопасное для персонажа состояние.
```

## 2. Главное правило этапа

Первый игровой экран не является генератором мира.

Экран не должен:

* добавлять NPC;
* добавлять предметы;
* добавлять новые двери, проходы, маршруты;
* добавлять новые угрозы;
* менять время суток;
* менять погоду;
* менять позицию;
* раскрывать hidden state;
* показывать audit/debug/JSON;
* показывать source trace;
* показывать внутренние IDs, если UI не в debug mode;
* показывать игроку то, что персонаж не знает.

Экран должен:

* отобразить только approved narrator prose;
* отобразить только approved action options;
* отобразить только character-safe current position;
* отобразить только видимые/известные/слышимые элементы;
* принять первый свободный ход игрока;
* передать ход в следующий pipeline как заявку, а не как факт.

## 3. Место этапа в pipeline

```text id="kyy17k"

2. Нормализация заявки
3. Выбор исторической рамки
4. Загрузка регионального контекста
5. Подбор стартовых G1–G4 кандидатов
6. Подбор place templates
7. Подбор NPC-кандидатов
8. Подбор предметных профилей
9. Выбор стартового узла
10. Аудит стартового места
11. Генерация персонажа
12. Аудит персонажа
13. Материализация G5-сцены
14. Аудит G5-сцены
15. Размещение стартовых NPC
16. Размещение стартовых предметов
17. Проверка времени и света
18. Формирование карты знаний персонажа
19. Формирование полного hidden state
20. Формирование visible context package
21. Аудит visible context
22. Генерация стартовой прозы narrator
23. Аудит стартовой прозы narrator

```

Этап 26 не должен запускаться до успешного commit.

```text
party_character_knowledge_maps where is_current=true
+ active party_character_known_*
→ player-safe public read model
→ first_game_screen_input.party_public_state
```

Первый экран не читает `party_character_knowledge_snapshots` как текущее состояние и не реконструирует знания из исходного Stage 18 JSON. Snapshot используется только для аудита и восстановления.

`known_nearby_paths` может показываться в карте/выходах только через записи `party_character_known_routes` с `knowledge_kind=nearby_path` и только после player-safe фильтра.

## 8. Структура первого экрана

### 8.1. Main prose

`main_prose` берётся строго из `approved_narrator_output.prose`.

Правила:

```text id="8s6l45"
не редактировать на UI-слое;
не добавлять вступительные фразы;
не сокращать так, чтобы терялись условия;
не расширять атмосферными деталями;
не менять время/позицию/риски;
не добавлять tutorial text внутрь prose.
```

Если нужен tutorial, он должен быть отдельным UI-block, а не частью narrator prose.

### 8.2. Position panel

`position_panel` показывает публичную позицию.

```json id="hpijw1"
{
  "position_panel": {
    "public_position_label": "У стены закрытого двора, рядом с тёмным проходом",
    "technical_position_hidden": true,
    "debug_position": null
  }
}
```

Правило:

```text id="3ih6zq"
Публичная позиция должна быть понятной игроку, но не раскрывать скрытые узлы карты.
```

Допустимо:

```text id="m8g8c1"
У закрытого ларя, в тёмном углу двора.
У двери, рядом с человеком у стены.
На краю освещённой комнаты.
```

Недопустимо:

```text id="5qr5yz"
G5_ANCHOR_001.
Скрытая зона behind_guarded_door.
Точка рядом с NPC, который скрывает долг.
```

### 8.3. Time panel

`time_panel` показывает только player-safe время.

```json id="btr8nf"
{
  "time_panel": {
    "public_time_label": "глубокая ночь",
    "public_light_label": "темно, видимость ограничена",
    "public_weather_label": "холодно"
  }
}
```

Запрещено менять `clock`.

Если в approved prose ночь, UI не может подписать экран как “день”.

### 8.4. Character panel

`character_panel` показывает краткое состояние персонажа.

```json id="cv86r8"
{
  "character_panel": {
    "public_character_label": "Ты",
    "body_state_summary": [
      "холод",
      "усталость: слабая"
    ],
    "inventory_summary": [
      "при себе только то, что уже утверждено в инвентаре"
    ],
    "warning_badges": [
      "видимость ограничена"
    ]
  }
}
```

Правила:

```text id="6vo5j9"
не показывать скрытые болезни, если персонаж их не ощущает;
не показывать полный numerical stat sheet без UI-режима;
не показывать hidden modifiers;
не показывать неосмотренные предметы в инвентаре;
не смешивать property and inventory.
```

### 8.5. Attention panel

Показывает, на что персонаж может обратить внимание.

Типы attention targets:

```text id="3x2cds"
visible_npc;
visible_item;
visible_container;
visible_exit;
audible_cue;
smell_cue;
body_sensation;
known_context_hint;
uncertain_context;
risk_hint;
```

Формат:

```json id="dbexjp"
{
  "attention_target_id": "attention_001",
  "label": "закрытый ларь у стены",
  "target_type": "visible_container",
  "target_ref": {
    "container_instance_id": "container_001"
  },
  "attention_mode": "inspect | approach | listen | ask | observe | remember | avoid",
  "risk_hint": "medium",
  "certainty": "visible | audible | known | uncertain",
  "must_not_reveal_hidden_truth": true
}
```

### 8.6. Action panel

Показывает безопасные suggested actions.

Формат:

```json id="i3w0di"
{
  "suggested_action_id": "suggested_action_001",
  "label": "Осмотреть закрытый ларь.",
  "action_kind": "inspect",
  "target_ref": {
    "container_instance_id": "container_001"
  },
  "basis": "visible",
  "risk_hint": "medium",
  "will_consume_time": "maybe",
  "requires_resolution_pipeline": true,
  "must_not_reveal_hidden_truth": true
}
```

Action option — это не результат.
Action option — это возможная заявка.

Допустимо:

```text id="g6d9nn"
Осмотреть закрытый ларь.
Заговорить с человеком рядом.
Прислушаться.
Проверить тёмный проход.
Подождать.
```

Недопустимо:

```text id="txmz2u"
Открыть ларь с серебром.
Поговорить с человеком, который тебя подозревает.
Пойти тайным ходом к складу.
Подождать, пока войдёт сторож.
```

### 8.7. Free text input

Свободный ввод — главный способ игры.

Контракт поля ввода:

```text id="mq7kyo"
Игрок вводит намерение, а не факт мира.
```

Если игрок пишет:

```text id="qw8ghd"
Я беру нож со стола.
```

Система трактует это как:

```text id="e883mz"
персонаж пытается взять нож, если такой нож существует, видим, доступен или может быть найден.
```

Не как:

```text id="m9jg1g"
нож точно есть на столе и уже взят.
```

## 9. Карта на первом экране

Карта, если показывается, должна быть картой знаний персонажа.

Показывать можно:

```text id="n0a17k"
текущую известную точку;
видимые выходы;
известные персонажу ближайшие пути;
неизвестные направления как неизвестные;
посещённые узлы;
слуховые ориентиры как слухи;
опасности как известные/видимые/слуховые.
```

Нельзя показывать:

```text id="ya5dns"
полную фактическую карту;
скрытые исторические якоря;
закрытые зоны за дверью;
точный destination unknown exit;
hidden route truth;
NPC offscreen position;
события, которые ещё не проявились.
```

Формат:

```json id="pfbwce"
{
  "map_panel": {
    "enabled": true,
    "map_mode": "character_known_only",
    "current_node": {
      "label": "текущая точка",
      "certainty": "known_current"
    },
    "visible_exits": [
      {
        "label": "тёмный проход",
        "destination": "unknown",
        "certainty": "visible_but_unknown"
      }
    ],
    "known_routes": [],
    "unknown_or_hidden": {
      "show_count": false,
      "show_labels": false
    }
  }
}
```

## 10. Первый экран и первый ход

После показа первого экрана система переходит в состояние:

```text id="0l0ptn"
awaiting_player_input
```

Игрок может:

```text id="s0qwrm"
выбрать предложенное действие;
написать свободное действие;
задать вопрос;
осмотреть объект;
заговорить с NPC;
идти к видимому выходу;
ждать;
проверить знание;
попробовать взаимодействовать с предметом;
ничего не делать.
```

Любой первый ход должен проходить через следующий turn pipeline:

```text id="2j73hq"
player_input
→ normalize_player_intent
→ resolve_against_current_state
→ check_visibility_knowledge_access
→ determine time cost/risk
→ update world/party state
→ build new visible context
→ narrator response
```

Первый ход не должен напрямую менять БД как факт до обработки.

## 11. Что считается корректным первым экраном

Первый экран корректен, если:

```text id="5bv62y"
party_state.ready=true;
commit завершён;
approved narrator prose есть;
narrator_prose_audit.pass=true;
visible_context_audit.pass=true;
current_position существует;
public position label не раскрывает hidden state;
action options ссылаются на approved visible actions;
free text input включён;
hidden state не показан;
raw JSON/audit/source/debug не показаны;
opening_scene_presented ещё не помечен true до фактической доставки.
```

## 12. Delivery acknowledgement

Если UI поддерживает подтверждение доставки, используется двухфазная фиксация показа.

До показа:

```json id="3i6j8z"
{
  "opening_scene_presented": false,
  "player_visible_message_ready": true,
  "awaiting_client_ack": true
}
```

После успешного показа клиентом:

```json id="8zy8bj"
{
  "opening_scene_presented": true,
  "shown_at": "ISO-8601 string",
  "client_ack_id": "string"
}
```

Если клиент не подтвердил показ:

```text id="aoh52h"
не создавать второй старт;
не регенерировать prose;
вернуть тот же approved narrator output по message_id;
не запускать новый world generation.
```

## 13. Idempotency первого экрана

Первый экран должен быть идемпотентным.

Повторный запрос `GET /first-screen` с тем же `party_id` должен вернуть тот же approved screen, если:

```text id="rytfam"
party_state.ready=true;
opening_scene_presented=false или true;
narrator_output_id тот же;
visible_context_snapshot_id тот же;
current_turn_number=0.
```

Нельзя:

```text id="2d07xq"
перегенерировать стартовую прозу;
перегенерировать action options;
создать новый visible context;
создать новых NPC/items;
изменить время;
пометить сцену показанной без client ack, если ack required.
```

## 14. Работа LLM на этапе

Основной этап 26 должен быть code/UI-only.

LLM не нужна для показа первого экрана, потому что:

```text id="5dj4je"
стартовая проза уже создана;
проза уже прошла аудит;
visible context уже утверждён;
action options уже безопасны;
party state уже закоммичен;
UI должен только отобразить данные.
```

LLM допустима только как опциональный safety/formatting auditor до показа, если интерфейс дополнительно агрегирует panels из approved data.

LLM не имеет права:

```text id="r0is87"
переписывать стартовую прозу;
создавать новые action options;
переименовывать NPC/items смыслово;
расширять описание позиции;
скрыто добавлять tutorial как факт мира;
менять current_position;
менять time/weather/light;
добавлять hidden hints сверх approved visible context.
```

## 20. Validation rules

Код проверяет:

1. `first_game_screen.schema === "first_game_screen"`.
2. `version === 1`.
3. `screen_status === "ready"`.
4. `party_start_committed.commit_status === "committed"`.
5. `party_state.status === "ready"`.
6. `party_state.is_ready_for_player === true`.
7. `approved_narrator_output.prose_status === "drafted"`.
8. `narrator_prose_audit.pass === true`.
9. `visible_context_audit.pass === true`.
10. `main_prose === approved_narrator_output.prose`.
11. `position_panel.public_position_label` не пустой.
12. `position_panel` не содержит hidden state.
13. `time_panel` не противоречит committed clock.
14. `attention_panel` ссылается только на approved visible refs.
15. `action_panel.suggested_actions` ссылается только на approved action options.
16. `map_panel.map_mode === "character_known_only"`.
17. `map_panel` не содержит hidden nodes.
18. `free_text_input.enabled === true`.
19. `free_text_input.input_contract === "player_intent_not_world_fact"`.
20. UI не содержит raw JSON.
21. UI не содержит audit/debug/source_trace.
22. UI не содержит private motives.
23. UI не содержит closed container contents.
24. UI не содержит future event timers.
25. UI не содержит unknown true ownership.
26. UI не содержит exact destination for unknown exit.

## 23. First turn input contract

Первый ввод игрока должен сохраняться как намерение.

```json id="2ckztd"
{
  "version": 1,
  "schema": "player_first_turn_input",
  "party_id": "string",
  "turn_number": 1,
  "raw_text": "string",
  "selected_action_option_id": "string | null",
  "input_source": "free_text | suggested_action | mixed",
  "received_at": "ISO-8601 string",
  "interpretation_status": "pending",
  "contract": "intent_not_fact"
}
```

Если игрок выбирает suggested action, система всё равно должна обработать его как заявку.

Пример:

```text id="mwylj9"
Игрок нажал: "Осмотреть закрытый ларь."
```

Это значит:

```text id="t3bek2"
персонаж пытается осмотреть ларь;
нужно проверить видимость, доступ, время, риск, свидетелей и возможное раскрытие hidden state.
```

Не значит:

```text id="zs814b"
ларь автоматически открыт;
содержимое известно;
NPC не заметил;
время не прошло.
```

## 24. Commit gate этапа

Первый экран считается успешно подготовленным, если:

```text id="i1gekb"

party ready;
approved narrator output exists;
narrator prose audit passed;
visible context audit passed;
main prose equals approved prose;
position/time panels match committed state;
action options are safe;
map shows only character-known data;
free text input enabled;
hidden/audit/source/debug absent;
delivery_state ready;
```

После этого экран можно показать игроку.


```text id="swlbbp"
Положение: у закрытого ларя, рядом с тёмным проходом.

- человек неподалёку;

1. Осмотреть закрытый ларь.
```
