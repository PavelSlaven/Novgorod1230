# Этап 11. Генерация персонажа игрока

## 1. Назначение этапа

Генерация персонажа игрока — это LLM-этап, который создаёт первого полноценного субъекта партии: персонажа, через которого игрок будет воспринимать мир и действовать в нём.

На этом этапе LLM создаёт не абстрактный “класс персонажа” и не набор удобных характеристик, а человека внутри уже выбранной исторической, региональной, социальной и пространственной рамки.

Персонаж должен быть связан с:

* выбранным годом;
* сезоном;
* временем суток;
* регионом;
* выбранным стартовым узлом;
* разрешённым типом места;
* социальными ролями региона;
* занятиями региона;
* предметными профилями;
* property rules;
* доступными знаниями;
* телесным состоянием;
* ближайшей причиной действовать.

Короткая формула:

```text
historical_frame
+ selected_start_node
+ start_place_audit
+ regional social roles
+ occupations
+ item/container/property candidates
+ player request
→ player_character_dossier
→ player_character_audit
→ player_character_game_profile
```

## 2. Главное правило этапа

LLM создаёт смысл персонажа. Код не сочиняет биографию, статус, имущество, цели, связи или причины.

Код:

* передаёт утверждённый контекст;
* передаёт candidate sets;
* валидирует JSON;
* проверяет ID, enum, диапазоны и ссылки;
* сохраняет утверждённый результат;
* возвращает результат на repair, если есть ошибка.

LLM:

* создаёт происхождение;
* адаптирует заявку игрока к эпохе;
* выбирает допустимый социальный статус из candidate set;
* выбирает допустимое занятие из candidate set;
* задаёт тело, здоровье, сытость, бодрость;
* задаёт характеристики и навыки;
* задаёт знания персонажа;
* задаёт память, цели, страхи и ограничения;
* выбирает стартовое имущество только из допустимых профилей;
* объясняет, почему персонаж находится в выбранном месте;
* упаковывает результат в игровой профиль.

LLM не имеет права:

* менять выбранный стартовый узел;
* менять год, регион, сезон или время;
* создавать стартовую G5-сцену;
* создавать NPC сверх допустимых NPC-кандидатов;
* создавать предметы вне item_profile_candidate_set;
* давать персонажу знания игрока;
* делать персонажа богатым, вооружённым, свободным или влиятельным без цены и риска;
* создавать современное мышление, права, речь или цели без исторической адаптации.

## 3. Место этапа в pipeline

```text
1. Заявка игрока
2. Нормализация заявки
3. Выбор исторической рамки
4. Загрузка регионального контекста
5. Подбор стартовых G1–G4 кандидатов
6. Подбор place templates
7. Подбор NPC-кандидатов
8. Подбор предметных профилей
9. Выбор стартового узла
10. Аудит выбора стартового места
11. Генерация персонажа игрока
12. Аудит персонажа
13. Материализация стартовой G5-сцены
```

Этап 11 запускается только после успешного `start_place_audit.pass=true`.

## 6. Что LLM создаёт на этом этапе

LLM создаёт следующие смысловые блоки:

1. личность;
2. происхождение;
3. социальный статус;
4. занятие или роль;
5. тело;
6. состояния;
7. характеристики;
8. навыки;
9. знания персонажа;
10. память;
11. цели;
12. страхи;
13. обязанности;
14. стартовую причину;
15. стартовый инвентарь;
16. имущество не при персонаже;
17. доступные, но не принадлежащие ресурсы;
18. ближайшие связи;
19. ограничения;
20. риски.

LLM не создаёт:

* стартовую G5-сцену;
* visible context;
* narrator prose;
* новых регионов;
* новых мест;
* новых place templates;
* новых item profiles;
* новых property rules;
* новых социальных ролей;
* NPC вне candidate set;
* предметы вне item candidate set.

## 7. Адаптация заявки игрока

Заявка игрока является намерением, а не истиной.

Если игрок написал:

```text
хочу быть богатым купцом
```

LLM должна проверить:

* есть ли допустимая социальная роль;
* есть ли допустимое занятие;
* совместимо ли это со стартовым местом;
* допустимо ли стартовое имущество;
* есть ли социальная цена;
* есть ли риски;
* не ломает ли это историческую рамку.

Возможная адаптация:

```text
не самостоятельный богатый купец, а приказчик, младший родственник торгового дома, должник, сопровождающий товар, зависимый работник, человек с чужим поручением или временным доступом к товару
```

Если игрок написал:

```text
случайный персонаж
```

LLM выбирает допустимый статус и занятие из candidate set, а не из общих знаний.

Если игрок написал:

```text
хочу быть воином
```

LLM не обязана давать ему дорогую броню, коня и высокий боевой статус. Она может адаптировать запрос в:

```text
сторож, сопровождающий, бывший ратник, младший дружинный человек, охотник с оружием, зависимый служилый, человек с чужим оружием и риском
```

## 8. Identity

Блок `identity` определяет, как персонажа можно называть и воспринимать.

```json
{
  "identity": {
    "character_id": "player_character_001",
    "display_name": "string",
    "name_status": "known | partial | nickname_only | unknown",
    "gender": "male | female | unknown | not_fixed",
    "age_band": "child | adolescent | young_adult | adult | mature | old",
    "approximate_age": "string",
    "short_description": "string",
    "public_identity": "string",
    "private_identity": "string | null"
  }
}
```

Правила:

* имя должно соответствовать региональным name pools, если они доступны;
* если имя не выбирается, это должно быть оформлено как `unknown` или `nickname_only`;
* возраст должен быть совместим с навыками, телом и статусом;
* публичная идентичность может отличаться от частной, но это должно иметь причину.

## 9. Social status

Социальный статус выбирается из региональных социальных ролей.

```json
{
  "social_status": {
    "social_role_id": "string",
    "status_label": "string",
    "freedom_status": "free | dependent | enslaved | bound | outsider | disputed | unknown",
    "wealth_band": "destitute | poor | modest | comfortable | wealthy | controlled_wealth",
    "local_belonging": "local | near_local | outsider | foreigner | unknown",
    "rights": [],
    "obligations": [],
    "protector_or_guarantor": "string | null",
    "authority_over_character": [],
    "who_can_punish_character": [],
    "social_risks": [],
    "why_status_is_allowed": []
  }
}
```

Статус должен отвечать на вопросы:

* свободен ли персонаж;
* имеет ли он право быть в стартовом месте;
* имеет ли право носить своё имущество;
* кто может его наказать;
* кто может за него поручиться;
* как на него смотрят местные;
* что для него опасно социально.

Статус не является декорацией. Он влияет на доступ, доверие, торговлю, ночлег, право собственности, риск обвинений и реакцию NPC.

## 10. Origin

Происхождение объясняет, почему персонаж стал именно таким.

```json
{
  "origin": {
    "birth_or_home_region": "string | null",
    "home_status": "has_home | no_home | away_from_home | unknown",
    "family_status": "family_nearby | family_elsewhere | orphan | separated | unknown",
    "cultural_environment": "string",
    "language_or_speech_notes": "string | null",
    "usual_life": "string",
    "how_left_home_or_usual_place": "string",
    "why_origin_supports_current_status": "string",
    "unresolved_origin_unknowns": []
  }
}
```

Если происхождение неизвестно, это фиксируется как неизвестность, а не как пустота.

Допустимые причины разрыва с домом:

* сиротство;
* служба;
* долг;
* бедствие;
* плен;
* бегство;
* наказание;
* дорога;
* родственная обязанность;
* торговое поручение;
* сезонная работа;
* болезнь;
* потеря памяти;
* утрата имущества.

## 11. Occupation

Занятие выбирается из регионального `occupation_context`.

```json
{
  "occupation": {
    "occupation_id": "string | null",
    "occupation_label": "string",
    "occupation_group": "string",
    "skill_basis": [],
    "typical_tools_or_items": [],
    "seasonal_notes": [],
    "why_occupation_fits_start_place": "string",
    "why_occupation_fits_social_status": "string"
  }
}
```

Если персонаж без устойчивой профессии, это тоже должно быть оформлено:

```json
{
  "occupation_id": null,
  "occupation_label": "no_stable_occupation",
  "occupation_group": "marginal | dependent | travel | survival",
  "why_no_stable_occupation": "string"
}
```

## 12. Body and state

Тело и состояние разделяются на механический и прозаический слой.

```json
{
  "body": {
    "age_band": "adult",
    "build": "string",
    "visible_marks": [],
    "clothing_summary": "string",
    "health": 100,
    "satiety": 100,
    "vigor": 100,
    "active_conditions": [],
    "condition_causes": [],
    "mechanical_state_modifiers": [],
    "body_prose": "string"
  }
}
```

Правила:

* `health`, `satiety`, `vigor` всегда в диапазоне `0–100`;
* состояние ниже `50` должно иметь причину;
* состояние `0` является критическим;
* активные состояния не должны быть абстрактными: нужна причина и влияние;
* холод, голод, болезнь, рана, усталость, страх, промокание, опьянение и связанность должны фиксироваться отдельно;
* проза тела не должна повторять цифры, а должна описывать ощущение.

## 13. Attributes

Используются шесть характеристик:

```json
{
  "attributes": {
    "strength": 10,
    "agility": 10,
    "endurance": 10,
    "reason": 10,
    "attention": 10,
    "influence": 10,
    "attribute_array_used": [14, 13, 12, 10, 9, 8],
    "attribute_rationale": {}
  }
}
```

Правила баланса:

```text
обычный диапазон: 3–18
большинство людей: 8–13
крепкие и опытные: 14–15
редкие выдающиеся: 16–18
обычный стартовый массив: 14, 13, 12, 10, 9, 8
```

Ограничения:

1. не больше двух характеристик 14+;
2. 16+ только при особом основании;
3. при 15+ нужна слабая сторона 8 или ниже;
4. 17–18 не выдаются при обычной генерации;
5. нельзя делать персонажа универсально сильным;
6. каждая высокая характеристика должна вытекать из биографии, тела или занятий.

```json
    "stealth": {

    },
    "melee": {
      "bonus": 0,
      "basis": "string"
    },
    "ranged": {
      "bonus": 0,
      "basis": "string"
    },
    "craft": {
      "bonus": 0,
      "basis": "string"
    },
    "household": {
      "bonus": 0,
      "basis": "string"
    },
    "survival": {
      "bonus": 0,
      "basis": "string"
    },
    "riding": {
      "bonus": 0,
      "basis": "string"
    },
    "healing": {
      "bonus": 0,
      "basis": "string"
    },
    "observation": {
      "bonus": 0,
      "basis": "string"
    },
    "communication": {
      "bonus": 0,
      "basis": "string"
    },
    "custom_and_law": {
      "bonus": 0,
      "basis": "string"
    }
  }
}
```

Уровни:

```text
+0 — нет опыта
+1 — знаком
+2 — умелый
+3 — опытный
+4 — мастер
```

Ограничения:

1. не больше одного навыка +4;
2. +4 требует биографического основания;
3. не больше двух боевых навыков выше +1 без военной или охотничьей биографии;
4. высокий навык должен вытекать из происхождения, занятия и среды;
5. если навык не связан с жизнью персонажа, максимум +1.

## 15. Knowledge

Знания персонажа отделяются от знаний игрока.

```json
{
  "knowledge": {
    "known_facts": [],
    "known_places": [],
    "known_routes": [],
    "known_people": [],
    "known_authorities": [],
    "rumors": [],
    "mistaken_beliefs": [],
    "unknown_but_player_may_know": [],
    "forbidden_knowledge": [],
    "knowledge_basis": []
  }
}
```

Источники знания персонажа:

* личный опыт;
* место жизни;
* социальный статус;
* занятие;
* слухи;
* приказы;
* рассказы очевидцев;
* торговые разговоры;
* религиозные/военные/административные известия;
* видимые последствия событий.

Запрещено:

* давать точное знание будущего;
* давать полную карту;
* давать скрытые причины событий;
* давать точные маршруты без основания;
* давать знание игрока как знание персонажа.

## 16. Memory

Память нужна для причин, навыков, страхов, долгов и связей.

```json
{
  "memory": {
    "key_memories": [],
    "debts": [],
    "obligations": [],
    "fears": [],
    "shames": [],
    "loyalties": [],
    "unresolved_unknowns": [],
    "memory_limits": []
  }
}
```

Память должна объяснять:

* почему персонаж здесь;
* почему умеет свои навыки;
* почему боится или хочет чего-то;
* откуда вещи;
* кому должен;
* почему не может просто уйти;
* какие факты могут иметь последствия.

Память не должна превращаться в заранее написанную сюжетную рельсу.

## 17. Goals

У персонажа должна быть причина действовать.

```json
{
  "goals": {
    "immediate_need": "string",
    "long_term_desire": "string",
    "fear": "string",
    "obligation": "string | null",
    "reason_to_act_now": "string",
    "consequence_of_inaction": "string",
    "goal_visibility_to_player": "known | partly_known | implicit"
  }
}
```

Ближайшая нужда должна быть сценически применимой:

* еда;
* ночлег;
* безопасность;
* лекарь;
* встреча;
* долг;
* пропавшая вещь;
* приказ;
* дорога;
* поручение;
* бегство;
* объяснение;
* защита;
* возвращение чужого имущества;
* риск бездействия.

## 18. Inventory

Стартовый инвентарь создаётся только из `item_profile_candidate_set`.

```json
{
  "inventory": {
    "carried_items": [
      {
        "character_item_id": "pc_item_001",
        "item_profile_candidate_id": "item_prof_cand_001",
        "item_profile_id": "item_profile_001",
        "title": "string",
        "item_kind": "string",
        "count": 1,
        "weight": 0,
        "size_band": "string",
        "condition": "string",
        "carried_where": "hands | belt | body | pouch | bag | container | strapped | other",
        "quick_access": "immediate | quick | short_action | slow | inaccessible",
        "owner_model": "owned | borrowed | entrusted | stolen | disputed | service | unknown",
        "holder": "player_character",
        "use": "string",
        "movement_hindrance": "none | low | medium | high",
        "hands_occupied": 0,
        "social_or_legal_risk": "none | low | medium | high | severe",
        "property_rule_candidate_id": "string",
        "why_character_has_it": "string"
      }
    ],
    "total_weight": 0,
    "load_category": "light | medium | heavy | extreme",
    "occupied_hands": 0,
    "load_effects": [],
    "inventory_limits": []
  }
}
```

Правила:

* предмет при персонаже должен быть физически при нём;
* вещь в другом месте — имущество, а не инвентарь;
* предмет должен иметь владельца или модель владения;
* чужая вещь может быть при персонаже, но даёт риск;
* дорогой, редкий, опасный или служебный предмет требует причины;
* вес считается вместе с контейнерами;
* быстрый доступ зависит от положения предмета;
* инвентарь не должен быть универсальным набором решений.

## 19. Property and access

```json
{
  "property_and_access": {
    "property_not_carried": [],
    "borrowed_or_entrusted_items": [],
    "disputed_items": [],
    "accessible_resources": [],
    "resources_not_currently_accessible": [],
    "obligations_to_return": [],
    "property_risks": []
  }
}
```

Разделение:

```text
инвентарь = при персонаже
имущество = принадлежит или связано, но не при персонаже
доступ = можно временно использовать без владения
```

Физически нести предмет не значит владеть им.

## 20. Relations

Связи персонажа не обязаны создавать полных NPC, но должны иметь уровень детализации.

```json
{
  "relations": {
    "known_npcs": [
      {
        "relation_id": "rel_001",
        "npc_candidate_id": "npc_cand_001 | null",
        "relation_type": "kin | patron | creditor | debtor | enemy | helper | witness | employer | authority | companion | unknown",
        "detail_level": "background | scene | key_seed",
        "what_they_expect": "string",
        "what_character_expects": "string",
        "risk_or_consequence": "string",
        "must_materialize_later": false
      }
    ],
    "relation_limits": []
  }
}
```

Если связь должна помнить персонажа и влиять на будущие сцены, она должна быть связана с `key_seed` или будущей материализацией ключевого NPC.

Если связь нужна только для общего прошлого, достаточно background relation.

## 21. Start place connection

Главный вопрос:

```text
почему персонаж здесь именно сейчас?
```

```json
{
  "start_place_connection": {
    "selected_candidate_id": "string",
    "selected_node_id": "string",
    "selected_place_template_id": "string",
    "reason_here": "string",
    "right_to_be_here": "yes | no | disputed | temporary | hidden | unknown",
    "arrival_context": "local | working_here | passing_through | brought_here | seeking_help | fleeing | ordered_here | lost | unknown",
    "last_route_id": "string | null",
    "what_character_knows_about_place": [],
    "what_character_does_not_know_about_place": [],
    "why_cannot_ignore_situation": "string"
  }
}
```

Стартовая причина должна быть совместима с:

* выбранным местом;
* временем суток;
* сезоном;
* социальным статусом;
* вещами при персонаже;
* ближайшими целями;
* знаниями персонажа.

## 22. Constraints and risks

```json
{
  "constraints_and_risks": {
    "social_constraints": [],
    "legal_constraints": [],
    "property_constraints": [],
    "health_constraints": [],
    "knowledge_constraints": [],
    "movement_constraints": [],
    "inventory_constraints": [],
    "reputation_constraints": [],
    "immediate_risks": [],
```

Этот блок нужен, чтобы игра давила на персонажа не “сюжетом”, а последствиями статуса, тела, вещей, долгов, знаний и места.

## 23. LLM-работа на этапе

На этом этапе LLM обязательна.

Причина: персонаж является новой смысловой сущностью мира. Код не имеет права создать его процедурно.

LLM-режимы этапа:

1. `PlayerCharacterDossierGenerator` — создаёт смысловой профиль персонажа.
2. `PlayerCharacterDossierAuditor` — проверяет историчность, совместимость, ограничения и отсутствие лишних сущностей.
3. `PlayerCharacterGameProfileShaper` — упаковывает утверждённый dossier в строгий игровой JSON.
4. `PlayerCharacterFormatRepairer` — исправляет только JSON-формат.
5. `PlayerCharacterSemanticRepairer` — чинит смысловые ошибки, сохраняя ядро заявки и выбранную рамку.

## 30. Validation rules

Код обязан проверить:

1. `schema === "player_character_dossier"` или `player_character_game_profile`.
2. `version === 1`.
3. `generation_status` входит в enum.
4. `social_role_id` существует в regional social roles.
5. `occupation_id` существует в regional occupations или null обоснован.
6. Персонаж совместим с selected_start_node.
7. Персонаж совместим с historical_frame region/year/season/clock.
8. Есть причина быть в стартовом месте.
9. Есть immediate_need.
10. Есть consequence_of_inaction.
11. Health/satiety/vigor в диапазоне 0–100.
12. Активные состояния имеют причины.
13. Attributes в диапазоне 3–18.
14. Attributes соблюдают баланс.
15. Skill bonuses в диапазоне 0–4.
16. Skill +4 не больше одного.
17. Высокие навыки имеют basis.
18. Боевые навыки выше +1 не превышают лимит без основания.
19. Inventory items имеют item_profile_candidate_id.
20. Inventory items имеют вес, состояние, расположение, доступность, владельца, держателя, пользу, риск.
21. Inventory не содержит имущество вне доступа.
22. Property_not_carried не используется как доступный inventory.
23. Каждый property_rule_candidate_id существует.
24. Каждый container_profile_candidate_id существует, если указан.
25. Total weight рассчитан.
26. Load category рассчитана.
27. Занятые руки рассчитаны.
28. Персонаж не знает будущих событий.
29. Персонаж не знает скрытых фактов без основания.
30. Relations ссылаются на npc_candidate_set или явно являются abstract background relation.
31. Нет NPC вне candidate set.
32. Нет item вне item_profile_candidate_set.
33. Нет visible_scene.
34. Нет intro_prose.
35. Нет G5/minilocation/anchor.
36. source_trace не пустой, если require_sources=true.
37. `audit_self_check.evidence` не пустой.
38. Если `audit_self_check.pass=false`, concerns не пустой.

## 33. Commit gate этапа

Этап считается успешным, если:

```text
player_character_dossier создан,
аудит персонажа пройден,
game profile сформирован,
персонаж совместим с selected_start_node,
статус и занятие выбраны из базы,
характеристики и навыки валидны,
состояния валидны,
инвентарь отделён от имущества,
вещи имеют профиль, владельца, вес, доступность и риск,
знания персонажа ограничены,
есть причина быть в стартовом месте,
нет visible_scene, intro_prose и G5.
```

Если генерация не проходит, pipeline не должен процедурно “доделывать” персонажа. Он возвращает результат в LLM repair с конкретными ошибками.
