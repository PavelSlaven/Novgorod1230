## Правило post-merge складирования локальных материалов

### 1. Назначение

Локальные временные материалы не удаляются автоматически. После подтверждённого merge результата задачи в канонический `origin/main`, успешного завершения обязательного CI и фиксации evidence агент складирует подтверждённые временные материалы в отдельный архив вне Git checkout.

Для задачи с PR складирование запрещено до подтверждения всех post-merge gates. Для задачи без PR оно выполняется только по отдельному явному указанию пользователя.

Это правило не предоставляет агенту право удалять исходные или архивные материалы. Удаление является отдельной задачей и требует нового явного решения пользователя после самостоятельной проверки точных путей.

Архив размещается по шаблону:

```text
C:\Users\Slaven\Documents\Новгород-archive\<YYYY-MM-DD>__<task>__<merge-SHA>\
```

Архив:

- не включается в Git workspace, Graphify, RAG или другие repository indexers;
- не связывается с checkout через symlink или junction;
- не удаляется автоматически и хранится до отдельного решения пользователя;
- содержит обычное доступное для просмотра дерево файлов, а не единственный непрозрачный контейнер.

Post-merge складирование считается завершённым, когда агент:

1. инвентаризировал локальные изменения;
2. отделил результат задачи от временных материалов;
3. составил и сверил точный манифест кандидатов;
4. получил явное решение пользователя для материалов, созданных не им или имеющих неизвестное происхождение;
5. переместил одобренные материалы в архив с проверкой SHA-256;
6. проверил состояние всех использованных worktree;
7. показал итоговый `git status`;
8. перечислил оставшиеся локальные файлы и причину их сохранения.

Складирование не должно повреждать пользовательские данные, незавершённую работу другого агента, локальную конфигурацию, доказательства выполненных проверок или материалы, необходимые для восстановления проекта.

### 2. Область ответственности агента

Агент самостоятельно складирует только те материалы, которые одновременно удовлетворяют всем условиям:

- были созданы самим агентом в рамках текущей задачи;
- не являются отслеживаемыми файлами Git;
- не содержат уникальных пользовательских данных;
- не нужны для продолжения задачи, аудита, воспроизведения или интеграции;
- не входят в перечень защищённых локальных файлов;
- не принадлежат другому активному worktree или параллельной задаче;
- их назначение и содержимое однозначно установлены.

Неизвестный файл не считается мусором.

Если происхождение, владелец или назначение файла не установлены, агент обязан оставить файл на месте и отметить его как требующий ручного решения. Наличие такого файла в `git status` не является разрешением на его перемещение.

Материал, созданный не текущим агентом, можно складировать только по точному манифесту, явно одобренному пользователем.

### 3. Обязательная инвентаризация перед складированием

Перед складированием агент обязан выполнить из корня основного checkout:

```powershell
git fetch --prune origin
git status --short --branch --untracked-files=all
git ls-files --others --exclude-standard
git ls-files --others -i --exclude-standard
git diff --stat
git diff --cached --stat
git worktree list --porcelain
git stash list
```

Для каждого дополнительного checkout или worktree:

```powershell
git -C "<путь>" status --short --branch --untracked-files=all
git -C "<путь>" diff --stat
git -C "<путь>" diff --cached --stat
git -C "<путь>" branch --show-current
git -C "<путь>" rev-parse HEAD
git -C "<путь>" ls-files --others --exclude-standard
git -C "<путь>" ls-files --others -i --exclude-standard
git -C "<путь>" stash list
```

Агент обязан определить для каждого обнаруженного файла или каталога:

```text
путь;
tracked / untracked / ignored;
создатель или предполагаемый владелец;
задача происхождения;
содержимое и назначение;
есть ли уникальные данные;
есть ли копия в Git, PR, evidence package или резервном хранилище;
решение: оставить на месте / складировать после merge / запросить ручное решение.
```

### 4. Классы локальных материалов

#### 4.1. Защищённые материалы

Защищённые материалы нельзя автоматически перемещать или удалять.

Их складирование допускается только по отдельному явному решению пользователя после проверки содержимого и наличия безопасной копии. Удаление не входит в эту процедуру.

#### 4.2. Воспроизводимые материалы

Воспроизводимые материалы могут быть складированы после merge, если:

- они не содержат ручных изменений;
- известна штатная команда восстановления;
- перемещение не мешает текущей или следующей задаче;
- они не являются отслеживаемой частью репозитория.

К ним обычно относятся dependency caches, локальные индексы, Graphify output, логи и тестовые временные каталоги.

#### 4.3. Материалы текущей задачи

Материалы текущей задачи сохраняются до завершения:

- проверок;
- аудита;
- локального commit;
- push;
- CI;
- интеграции;
- фиксации evidence.

После подтверждённого merge агент складирует ненужные рабочие копии, но сохраняет утверждённый результат и необходимые доказательства.

#### 4.4. Неизвестные материалы

Любой файл, который агент не может уверенно классифицировать, считается защищённым до отдельного решения.

Название `.tmp`, `temp`, `backup`, `old`, `copy`, `review`, `clean` или `test` само по себе не является достаточным основанием для перемещения или удаления.

### 7. Особые правила для generated и Graphify

#### 7.1. `generated/`

Каталог `generated/` нельзя перемещать или удалять целиком.

Сначала необходимо определить, какие его файлы отслеживаются:

```powershell
git ls-files generated
```

Отслеживаемые generated-файлы являются частью репозитория и перемещаются или удаляются только через отдельное изменение проекта.

Игнорируемые generated-файлы можно складировать только после подтверждённого merge и проверки штатной команды воспроизведения.

#### 7.2. `graphify-out/`

`graphify-out/` является локальным воспроизводимым repository graph и обычно игнорируется Git.

Его разрешено складировать и затем пересобрать, если:

- там нет вручную добавленных материалов;
- после merge можно выполнить `repo-intel:ensure` или `graphify` на новом HEAD;
- перемещение не используется для сокрытия stale или failed graph state.

Грязный `graphify-out/` сам по себе не является пользовательским изменением и не должен блокировать анализ.

### 8. Запрещённые команды

Команда `git clean` не используется в процедуре ни для просмотра, ни для удаления. Запрещены все её варианты, а также broad cleanup и сбросы:

```powershell
git clean
git clean -n
git clean -nd
git clean -ndX
git clean -fd
git clean -fdx
git reset --hard
git checkout -- .
git restore .
git restore --staged .
Remove-Item -Recurse -Force *
rd /s /q .
rm -rf .
```

Запрещено использовать broad wildcard deletion в корне репозитория.

Для read-only инвентаризации untracked и ignored материалов используются только `git status` и `git ls-files`, перечисленные в разделе 3.

### 9. Безопасный порядок складирования

Для каждого спорного объекта применяется порядок:

```text
подтверждённый merge канонического PR
→ успешный обязательный CI
→ фиксация evidence
→ инвентаризация
→ проверка Git status
→ проверка содержимого
→ проверка происхождения
→ пользовательское одобрение точного манифеста, если материал создан не текущим агентом
→ SHA-256 исходных файлов
→ точечное перемещение в архив
→ SHA-256 архивных файлов
→ сверка количества файлов, размеров и хешей
→ повторный git status
```

Перед перемещением агент обязан разрешить абсолютные исходный и целевой пути и проверить, что:

- исходный путь находится внутри точного checkout или явно проверенного clone/worktree;
- целевой путь находится внутри `C:\Users\Slaven\Documents\Новгород-archive\`;
- целевой путь находится вне repository root;
- между checkout и архивом нет symlink, junction или другого reparse-point;
- команда не содержит wildcard и использует точный `-LiteralPath`.

Архив задачи должен содержать:

```text
README.md;
MANIFEST.json;
SHA256SUMS.txt;
payload/ с сохранённой относительной структурой.
```

`MANIFEST.json` для каждого объекта фиксирует дату, исходный и архивный пути, Git-класс, владельца, задачу происхождения, основание классификации, решение пользователя, число файлов, суммарный размер и SHA-256 каждого файла. `README.md` содержит точную инструкцию обратного перемещения.

При ошибке перемещения или несовпадении манифеста агент немедленно останавливается, ничего больше не перемещает, сохраняет доступные исходные и архивные экземпляры и сообщает пользователю точные пути. Архив не создаётся внутри Git checkout и не индексируется.

### 10. Складирование worktree и clone

Перед перемещением дополнительного clone или worktree:

```powershell
git -C "<путь>" status --short --branch --untracked-files=all
git -C "<путь>" ls-files --others --exclude-standard
git -C "<путь>" ls-files --others -i --exclude-standard
git -C "<путь>" diff --stat
git -C "<путь>" diff --cached --stat
git -C "<путь>" log --oneline --decorate -10
git -C "<путь>" log --oneline origin/main..HEAD
git -C "<путь>" stash list
```

Remote URL и актуальный канонический `origin/main` проверяются из основного checkout; remote с именем `origin` внутри временного clone сам по себе не считается каноническим.

Если найдено изменение, отсутствующее в каноническом репозитории, перемещение запрещено до его классификации.

Зарегистрированный disposable worktree перемещается так:

```powershell
git worktree move "<исходный-путь>" "<архивный-путь>"
```

`git worktree remove`, `git worktree prune` и ручное удаление `.git/worktrees` в этой процедуре запрещены. Если `git worktree move` невозможна, worktree сохраняется на месте с документированной причиной.

Обычный временный clone перемещается целиком точной файловой командой только после подтверждения:

```text
нет незакоммиченных изменений;
нет уникальных commits;
нет stash;
нет единственных локальных evidence;
remote и branch зафиксированы.
```

### 11. Завершение post-merge складирования

После складирования агент обязан выполнить:

```powershell
git status --short --branch --untracked-files=all
git ls-files --others --exclude-standard
git ls-files --others -i --exclude-standard
git worktree list --porcelain
git diff --check
```

Допустимы два финальных состояния.

#### Чистое состояние

```text
нет modified, staged и untracked файлов;
нет нескладированных временных материалов текущей задачи.
```

#### Документированное локальное состояние

Остались только намеренно сохранённые материалы. Для каждого из них в итоговом отчёте указаны:

```text
путь;
статус Git;
назначение;
владелец;
причина сохранения;
условие будущего решения пользователя.
```

Формулировка «репозиторий грязный» без перечня файлов недостаточна.

Архивы не удаляются автоматически. Условие будущего удаления архива всегда формулируется как отдельное решение пользователя, а не как срок или фоновая задача агента.

### 12. Короткое обязательное правило

```text
Агент складирует только свои подтверждённые временные материалы.

Для задачи с PR складирование выполняется только после merge в канонический
main, успешного CI и фиксации evidence. Для задачи без PR требуется отдельное
явное указание пользователя.

Неизвестный файл считается защищённым.

Git clean не используется. Перед перемещением обязательны read-only
инвентаризация, точный манифест, проверка владельца и содержимого, SHA-256
до и после и точный архивный путь вне checkout.

Tracked-файлы, пользовательские данные, локальная конфигурация, секреты,
базы, evidence, неизвестные материалы и чужая работа автоматически не
перемещаются и не удаляются.

Архив не индексируется и не удаляется без отдельного решения пользователя.
```

## 4. Обязательный Repository Intelligence workflow

Перед прямым grep, file search, GitHub code search, широким чтением репозитория или изменением файлов Codex, Cursor и другие агенты обязаны использовать оба независимых канала:

1. нормативный RAG `@rus/knowledge-source`;
2. отдельный repository graph Graphify.

После реализации единого интерфейса обязательный порядок:

```powershell
npm run repo-intel:ensure
npm run repo-intel:status
npm run repo-intel:query -- --query "конкретная информационная потребность"
```

`repo-intel:ensure` обязателен перед анализом репозитория: он пересобирает локальный Repository Graph, если artifact отсутствует или manifest привязан к другому Git HEAD. Нормативный RAG остаётся отдельным каналом; его `degraded` status не блокирует построение или использование Repository Graph.

Пока единый CLI реализуется в PR №13, обязательный bootstrap-порядок:

```powershell
npm run knowledge:status
npm run knowledge:query -- --query "конкретная информационная потребность"
npm run knowledge:read -- --document-id <document_id>
graphify query "та же конкретная информационная потребность"
```

Если важны зависимости, дополнительно используй `graphify path` и `graphify explain`.

Результат поиска используется для навигации. Обязательные и профильные нормативы после обнаружения читаются полностью. Прямой code search допускается только после двойного поиска и используется для точного изучения реализации, contracts, call sites и tests.

В рабочем `README.md` фиксируй:

- точную информационную потребность;
- выполненные RAG и Graphify queries;
- найденные документы, nodes и paths;
- полностью прочитанные нормативы;
- найденные модули, contracts, call sites и tests;
- readiness, gaps и conflicts.

Для navigation MVP PR №13 hard block — недоступный или invalid knowledge-source, отсутствующий/stale Graphify graph, неправильная версия Graphify либо недоступный обязательный документ. Полное coverage, document indexing и уже существующие semantic gaps пока не являются MVP-gate; они не отменяют более строгие hard blocks materialization и игрового runtime.

Для навигационного MVP PR №13 `degraded` knowledge-source отображается как warning в `repo-intel:status` и `repo-intel:query`; он не отменяет обязательное полное чтение нормативов и не делает Graphify нормативным источником. Это исключение относится только к локальной navigation-команде, а не к materialization, игровому runtime или утверждению нормативной готовности.

## 8. Главный принцип материализации

```text
код не придумывает категории, исторические факты и отсутствующие варианты,
но материализует конкретные экземпляры из утверждённых категорий,
региональных шаблонов, профилей и правил;
LLM принимает ограниченные смысловые решения через формальный протокол команд.
```

Пустой обязательный candidate set создаёт typed data gap и hard block. Запрещены ослабление filters, semantic fallback, заглушки, разумные значения по умолчанию и автоматическое достраивание отсутствующих фактов.

Если candidate set пуст, этап обязан создать типизированный data gap и выполнить hard block. LLM repair в этом случае запрещён.

Repair допускается только для исправления формата, контракта или отклонённого LLM-ответа в пределах неизменённого входа и существующего candidate set.

В bounded decision workflow LLM выбирает только один `option_id` и `command_token` из предоставленного конечного option set. Это ограничение не заменяет отдельные нормативные процедуры генерации персонажа игрока, аудита, разрешённой конкретизации key entity и создания прозы.

## 9. Перед изменением кода

1. Изучи текущую реализацию, public API, contracts, schemas, validators, call sites и tests.
2. Проверь карты модулей и реестры, чтобы не создавать вторую реализацию существующей ответственности.
3. Зафиксируй границы изменения и критерии готовности.
4. Не проводи несвязанный refactoring.
5. Не меняй public contracts, orchestration, DDL или save format без нормативного основания.
6. Работай через TDD: Red → Green → Refactor.

Каждый этап обязан иметь формальный input, output, typed errors и явно объявленные dependencies. Этап не читает hidden global state, не изменяет input, не запускает соседний этап и не выполняет скрытые обращения к DB, filesystem, network или LLM.

### Правило необходимой простоты

Проект является инди-разработкой. Не внедряй корпоративные процессы, многоуровневые согласования, избыточные роли, реестры, доказательные цепочки и сложные release-механизмы без конкретной необходимости.

Если несколько решений одинаково выполняют требования и защищают ключевые инварианты, выбирай самое простое — с минимальным числом сущностей, этапов, зависимостей и проверок.

Дополнительная сложность допустима только для устранения конкретного подтверждённого риска, который нельзя надёжно закрыть более простым способом.

Проверки должны соответствовать риску изменения. Во время разработки выполняются только короткие профильные проверки, необходимые для продолжения работы. Полные тестовые наборы, интеграционные проверки и аудит выполняются после завершения крупного этапа и перед итоговой передачей результата. Запрещено повторно запускать тяжёлые проверки после каждой небольшой правки, если не изменились проверяемые код, контракт, DDL, данные или поведение.

Для документации, метаданных и локальных правок выполняются только относящиеся к ним проверки. Низкорисковые и обратимые ошибки допускается обнаруживать по явным логам во время работы. Это послабление не применяется к повреждению данных, необратимым миграциям, безопасности и нарушениям ключевых инвариантов.

## 10. Оркестрация плановой работы

Если задача состоит из нескольких самостоятельных шагов, одна главная LLM владеет общим планом, единственной веткой и единственным PR.

Для каждого шага фиксируются:

1. цель;
2. входные данные;
3. границы и разрешённые файлы;
4. обязательные нормативы;
5. ожидаемый результат;
6. критерии готовности;
7. tests/checks;
8. необходимость независимого аудита;
9. dependencies;
10. известные ограничения.

Зависимые шаги выполняются последовательно:

```text
план
→ исполнитель
→ tests/checks
→ независимый критик
→ исправления
→ повторные tests
→ повторный аудит
→ финальная приёмка
→ следующий шаг
```

Субагент не изменяет общий план, не создаёт другой PR, не выполняет следующий шаг и не аудитит собственную реализацию.

Создавай субагента только для самостоятельной задачи, которую действительно целесообразно выполнять отдельно. При каждом вызове `spawn_agent` обязательно устанавливай `fork_turns: "none"`; полный контекст родительского диалога не передаётся. Поле `message` должно содержать краткое самостоятельное описание задачи, необходимые входные данные, ограничения и ожидаемый результат. Не создавай отдельных субагентов для мелких последовательных действий, которые проще выполнить в рамках одного этапа.

## Адаптивный выбор модели субагента

Главный агент самостоятельно определяет требуемую модель и уровень reasoning для каждой делегируемой задачи. Выбор производится по фактической сложности, риску и неоднозначности задачи, а не по типу родительской сессии.

Базовая конфигурация субагента:

```text
model: gpt-5.6-terra
model_reasoning_effort: medium
```

Главный агент обязан использовать минимальную конфигурацию, достаточную для надёжного выполнения задачи.

### Terra Low

Используется для полностью определённых механических действий:

* поиск конкретных файлов или символов;
* чтение заданных документов;
* сбор списка вызовов и зависимостей;
* запуск указанных команд;
* форматирование;
* переименование;
* локальное обновление документации;
* подготовка краткого отчёта по уже полученным результатам.

### Terra Medium

Используется по умолчанию для самостоятельных исполнительских задач:

* реализация небольшого изолированного изменения;
* написание или исправление тестов;
* исправление локального дефекта с известной причиной;
* анализ ограниченной подсистемы;
* изменение нескольких тесно связанных файлов;
* проверка соответствия формальному контракту;
* выполнение миграционных или редакторских действий по точной инструкции.

### Terra High

Используется, когда задача остаётся ограниченной, но требует заметного рассуждения:

* поиск причины дефекта в нескольких модулях;
* изменение сложного этапа конвейера;
* проверка нескольких взаимодействующих контрактов;
* анализ конкурентности, транзакций или восстановления после ошибок;
* реализация изменения с несколькими реалистичными вариантами;
* подготовка технического решения в рамках уже принятой архитектуры.

### Sol High

Используется для субагента только при наличии хотя бы одного условия:

* требуется новое архитектурное решение;
* нормативы допускают несколько несовместимых трактовок;
* изменяются границы ответственности подсистем;
* затрагиваются публичные контракты нескольких подсистем;
* изменение связано с риском потери или повреждения данных;
* выполняется независимый аудит критической реализации;
* Terra не смогла выполнить задачу либо вернула обоснованную неоднозначность;
* ошибка после реализации не объясняется доступными данными.

### Запрет необоснованного повышения

Нельзя использовать Sol только потому, что родительский агент работает на Sol или задача содержит много файлов.

Количество файлов, длина документа или продолжительность команды сами по себе не определяют сложность reasoning.

Перед запуском субагента главный агент кратко классифицирует задачу:

```text
complexity: mechanical | standard | complex | critical
risk: low | medium | high
ambiguity: low | medium | high
selected_model:
selected_reasoning_effort:
```

Эта классификация сохраняется только в техническом журнале работы и не требует отдельного согласования с пользователем.

Если более дешёвая конфигурация возвращает структурированный blocker из-за недостаточной определённости, главный агент может повторно назначить ту же задачу более сильной конфигурации. Повышение выполняется на один уровень за раз, кроме задач с изначально критическим риском.

## 11. Проверки и агент-критик

После изменения запускай только реально доступные checks и честно перечисляй фактически выполненные команды.

Набор проверок выбирается по области риска:

- при изменении кода, контрактов, DDL, импорта, игровых данных или поведения выполни профильные tests/checks и полный финальный CI;
- при изменении только документации выполни проверки документации, ссылок и консистентности без PostgreSQL и браузера;
- при изменении только generated metadata проверь штатный генератор, воспроизводимость и отсутствие содержательных изменений;
- полный clean-clone acceptance выполняется один раз для финального функционального кандидата; после него допускается evidence-коммит, не меняющий проверяемый код и данные;
- утверждение данных пересматривается только при изменении содержания, семантики, схемы обязательных полей или правил интерпретации, но не из-за изменения технического digest само по себе.

Один независимый критик проверяет итоговый результат. Отдельный критик для каждой небольшой стадии или служебной правки не требуется. После завершения крупного этапа и перед итоговой передачей выполняются необходимые полные проверки и аудит; тяжёлые проверки не повторяются без изменения соответствующей области.

Агент-критик вызывается по `code_critic_invocation_rule.txt`. При `CHANGES REQUIRED` или `REJECT` обязателен цикл:

```text
исправление
→ повторные tests/checks
→ повторная индексация при изменении code/docs
→ повторный аудит
```

Цикл продолжается до `PASS` или допустимого `PASS WITH NOTES`.

## 12. GitHub и единственный PR

Вся работа одной задачи выполняется в одной локальной ветке и одном PR. Дополнительные PR запрещены.

До push агент обязан локально:

1. завершить реализацию;
2. пересобрать RAG и Graphify artifacts, если изменены индексируемые файлы;
3. выполнить обязательные tests/checks;
4. выполнить аудит;
5. проверить `git status`, `git diff --check` и scope staged files;
6. обновить единый рабочий `README.md`.

Только после этого выполняются local commit и push. GitHub CI является дополнительным подтверждением, а не заменой локальным проверкам.

5. какие local services и databases развернуты;
6. какие tests/checks фактически запущены и их результаты;

## graphify

This project has a knowledge graph at `graphify-out/` with god nodes,
community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or
instructions before doing anything else.

Rules:

- For codebase questions, first run `graphify query "<question>"` when
  `graphify-out/graph.json` exists. Use `graphify path "<A>" "<B>"` for
  relationships and `graphify explain "<concept>"` for focused concepts.
- Dirty `graphify-out/` files are expected after hooks or incremental updates;
  dirty graph files are not a reason to skip Graphify.
- If `graphify-out/wiki/index.md` exists, use it for broad navigation instead
  of raw source browsing.
- Read `graphify-out/GRAPH_REPORT.md` only for broad architecture review or
  when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current.
