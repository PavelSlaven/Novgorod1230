# Этап 16. Размещение стартовых предметов

## 1. Назначение этапа

Размещение стартовых предметов — это этап запуска новой партии, на котором LLM материализует только причинно обоснованные предметы, контейнеры и объектные состояния внутри уже утверждённой G5-сцены.

Этот этап создаёт конкретные предметы партии только в пределах:

* выбранной исторической рамки;
* выбранного региона;
* выбранной G4-локации;
* утверждённых G5-якорей;
* утверждённых NPC;
* допустимых `item_profile_candidates`;
* допустимых `container_profile_candidates`;
* допустимых `property_rule_candidates`;
* правил видимости;
* правил доступа;
* правил владения;
* правил риска.

Короткая формула:

```text id="n91s4h"
g5_scene_graph
+ g5_scene_audit
+ initial_npc_placement
+ item_profile_candidate_set
+ player_character
+ historical_frame
→ initial_item_placement_draft
```

LLM не придумывает предметы “потому что они полезны игроку”. Она материализует только то, что допустимо для места, якоря, владельца, контейнера, сцены и текущей ситуации.

## 2. Главное правило этапа

Предмет появляется только при причинном основании.

Причинное основание может быть:

```text id="s5sdyw"
предмет типичен для выбранного места;
предмет нужен для текущей функции G5-якоря;
предмет связан с уже размещённым NPC;
предмет уже есть у персонажа игрока;
предмет является частью утверждённого контейнера;
предмет является видимым элементом обстановки;
предмет нужен для доступа, риска, свидетелей или препятствия;
предмет связан с property rule;
предмет связан с trade/property/work/social function;
предмет является следом состояния сцены;
```

Не является причинным основанием:

```text id="v7d75c"
игрок хочет предмет;
предмет был бы удобен для решения;
предмет выглядит атмосферно;
предмет нужен для красивого описания;
LLM считает, что он там "должен быть";
предмет нужен для будущего сюжета, которого ещё нет;
```

## 3. Место этапа в pipeline

```text id="icg8lc"
1. Заявка игрока
2. Нормализация заявки
3. Выбор исторической рамки
4. Загрузка регионального контекста
5. Подбор стартовых G1–G4 кандидатов
6. Подбор place templates
7. Подбор NPC-кандидатов
8. Подбор предметных профилей
9. Выбор стартового узла
10. Аудит стартового места
11. Генерация персонажа
12. Аудит персонажа
13. Материализация G5-сцены
14. Аудит G5-сцены
15. Размещение стартовых NPC
16. Размещение стартовых предметов
17. Проверка времени и света
18. Формирование visible context
```

Этап 16 идёт после размещения NPC, потому что часть предметов связана с держателями, владельцами, свидетелями, сторожами, работниками, хозяевами, торговцами или контролёрами доступа.

## 6. Что считается размещением предмета

Размещение предмета — это создание конкретного `item_instance` партии и привязка его к G5-якорю, контейнеру, NPC или персонажу игрока.

Минимальная формула:

```text id="b8hz5u"
item_profile_candidate_id
+ g5_anchor_id или holder_id/container_id
+ property_rule_candidate_id
+ visibility
+ access
+ ownership/holder model
+ causal_basis
→ item_instance
```

Если нет `causal_basis`, предмет не размещается.

## 7. Что считается размещением контейнера

Размещение контейнера — это создание конкретного `container_instance`, который может быть:

```text id="kfw82a"
видимым;
закрытым;
запертым;
скрытым;
чужим;
пустым;
с неизвестным содержимым;
с частично видимым содержимым;
доступным только через действие;
```

Контейнер не означает автоматическое создание содержимого.

Контейнер может существовать без раскрытого содержимого:

```json id="qdcra9"
{
  "container_instance_id": "container_001",
  "content_state": {
    "content_known": false,
    "content_materialized": false,
    "content_must_not_be_generated_until_opened_or_inspected": true
  }
}
```

## 8. Что нельзя создавать

На этом этапе запрещено:

```text id="rl5e82"
создавать предмет из желания игрока;
создавать предмет вне item_profile_candidate_set;
создавать контейнер вне container_profile_candidate_set;
создавать property rule вне property_rule_candidate_set;
заполнять закрытый контейнер без причинного основания;
раскрывать скрытый предмет как видимый;
делать чужой предмет свободно доступным;
делать дорогой/редкий/оружейный/служебный предмет без владельца и риска;
создавать NPC inventory без item profile и holder/property model;
создавать новый G5 anchor для предмета;
менять G5-сцену;
писать visible scene;
писать intro prose;
создавать hidden event;
```

## 9. Источники данных

### 9.1. `item_profile_candidate_set`

Главный allowlist.

Используются:

```text id="q29xai"
item_profile_candidate_id
item_profile_id
item_group
item_kind
rarity
value_band
weight_band
size_band
place_compatibility
social_and_occupation_basis
container_compatibility
property_compatibility
visibility_constraints
materialization_constraints
trade_and_value
season_and_time_compatibility
player_request_match
source_trace
```

Если `item_profile_candidate_id` отсутствует в `item_profile_candidate_set`, предмет не может быть создан.

### 9.2. `container_profile_candidates`

Используются для контейнеров.

Проверяются:

```text id="11tv6b"
container_profile_candidate_id
container_profile_id
container_group
container_kind
capacity_band
mobility
lockability
place_compatibility
access_model
content_policy
visibility_constraints
risk_profile
source_trace
```

Если контейнера нет в candidate set, контейнер не создаётся.

### 9.3. `property_rule_candidates`

Используются для собственности, доступа и риска.

Проверяются:

```text id="vhb307"
property_rule_candidate_id
property_rule_id
ownership_model
holder_model
controller_model
access_model
risk_model
transfer_conditions
source_trace
```

Интерактивный предмет без property rule не должен попадать в сцену.

### 9.4. `g5_scene_graph`

Используются:

```text id="9cxi00"
g5_anchors
g5_edges
player_start_position
visibility_model
access_model
item_materialization_slots
```

Предмет может быть привязан только к существующему anchor, который поддерживает item/container.

Anchor должен иметь:

```text id="hvcex4"
anchor.supports.can_hold_item = true
или anchor.supports.can_hold_container = true
```

Если G5 содержит `item_materialization_slots`, предпочтительно использовать их.

### 9.5. `initial_npc_placement`

Используется для владельцев, держателей, свидетелей и контролёров.

Предмет может быть связан с NPC только если:

```text id="yx5nqf"
npc_instance_id существует
npc создан на этапе NPC placement
npc_resource_hints разрешают связанный item profile
или property rule позволяет этот owner/controller model
```

Нельзя создавать нового NPC как владельца предмета.

### 9.6. `player_character`

Используется для:

```text id="e2di39"
видимости предмета персонажу;
доступности из стартовой позиции;
известности предмета;
права взять предмет;
возможности поднять/нести;
знания о владельце;
социального риска;
проверки, не дублируется ли предмет из инвентаря;
```

Если предмет уже есть в инвентаре персонажа, он не должен повторно появляться в сцене как отдельная новая вещь без причины.

## 10. Алгоритм этапа

### 10.1. Проверить вход

Код проверяет:

```text id="w6z5l6"
g5_scene_audit.pass = true
npc_placement_audit.pass = true или placement_status=empty_allowed
item_profile_candidate_set.selection_status = ready
g5_scene_graph.g5_anchors не пуст
```

Если `item_profile_candidate_set` пуст, но место допускает пустую предметную сцену, этап возвращает `empty_allowed`.

### 10.2. Построить индекс item candidates

Код строит:

```json id="2t9340"
{
  "item_profile_candidate_by_id": {},
  "item_candidates_by_place_template_link_id": {},
  "item_candidates_by_anchor_id": {},
  "item_candidates_by_container_profile": {},
  "item_candidates_by_property_rule": {},
  "item_candidates_by_visibility": {},
  "item_candidates_by_rarity": {}
}
```

### 10.3. Построить индекс контейнеров

```json id="3670e4"
{
  "container_profile_candidate_by_id": {},
  "container_candidates_by_anchor_id": {},
  "container_candidates_by_access_model": {},
  "container_candidates_by_can_hold_item_profile": {}
}
```

### 10.4. Построить индекс property rules

```json id="vafuvo"
{
  "property_rule_candidate_by_id": {},
  "property_rules_by_item_profile_candidate_id": {},
  "property_rules_by_container_profile_candidate_id": {},
  "property_rules_by_anchor_id": {},
  "property_rules_by_npc_controller": {}
}
```

### 10.5. Построить индекс G5 item anchors

```json id="p8g0t8"
{
  "anchors_supporting_item": [],
  "anchors_supporting_container": [],
  "visible_anchor_ids": [],
  "requires_inspection_anchor_ids": [],
  "hidden_anchor_ids": [],
  "locked_anchor_ids": [],
  "permission_required_anchor_ids": [],
  "item_slots_by_anchor_id": {}
}
```

### 10.6. Выбрать предметы по причинному основанию

Для каждого возможного предмета LLM должна указать `causal_basis_type`.

Допустимые типы:

```text id="4in2i7"
place_function
anchor_function
npc_holder
npc_controller
player_inventory_already_existing
container_expected_empty_or_unknown
work_activity
trade_activity
access_obstacle
property_risk
visible_background
searchable_detail
seasonal_need
body_state_need
route_or_travel_need
```

Если предмет имеет `causal_basis_type="player_desire"`, результат невалиден.

### 10.7. Привязать предмет к G5-якорю

Предмет можно разместить только если:

```text id="w1otx1"
anchor_id существует
anchor.supports.can_hold_item=true
anchor belongs to selected G4
visibility/access property compatible
```

Если предмет находится в контейнере, он привязывается к контейнеру, а контейнер — к anchor.

### 10.8. Привязать контейнер к G5-якорю

Контейнер можно разместить только если:

```text id="du7f4f"
container_profile_candidate_id существует
anchor.supports.can_hold_container=true
anchor access state compatible
container access_model compatible
```

Контейнеру обязательно задаются:

```text id="1xyvxw"
физическое размещение;
физическое состояние;
доступ;
видимое содержимое;
известность содержимого;
риск вскрытия;
контролёр доступа;
```

### 10.9. Назначить ownership/holder/controller

Каждый предмет должен иметь три разных слоя:

```text id="4vfgpj"
owner — кому принадлежит;
holder — у кого физически находится;
controller — кто контролирует доступ;
```

Они могут совпадать, но не обязаны.

Пример:

```json id="zbev59"
{
  "owner_model": "household",
  "holder_model": "container",
  "controller_model": "npc_controller"
}
```

Если предмет найденный, чужой, служебный, спорный, заложенный, дорогой или опасный, это должно создавать риск.

### 10.10. Назначить видимость

Видимость предмета должна соответствовать:

```text id="hm3bcr"
G5 visibility;
clock.light_profile;
anchor visibility;
container visibility;
player start position;
item size;
item condition;
hidden/searchable flags;
```

Возможные состояния:

```text id="mqlmje"
visible
visible_on_inspection
audible_or_smell_only
searchable
hidden
known_but_not_seen
in_container_unknown
in_container_partly_visible
inaccessible
```

Если `light_profile=dark`, предмет не может быть ясно видимым без света, близости, крупного размера или особого основания.

### 10.11. Назначить доступ

Доступ предмета должен быть отделён от видимости.

Возможные состояния:

```text id="pp7hve"
free
reachable
permission_required
purchase_required
guarded
locked
hidden
requires_search
requires_tool
requires_force
forbidden
inaccessible
```

Видимый предмет не обязательно доступен.

### 10.12. Назначить риск

Каждый interactable item должен иметь риск:

```text id="bl2quw"
theft_risk
witness_risk
legal_risk
reputation_risk
violence_risk
damage_risk
noise_risk
owner_reaction_risk
```

Если риска нет, это должно быть объяснено.

### 10.13. Назначить состояние

Предмет получает состояние:

```text id="5wa2kl"
new
ordinary
worn
damaged
wet
dirty
broken
spoiled
rusted
cold
hot
empty
full
sealed
locked
unknown
```

Состояние должно быть совместимо с сезоном, временем, местом, хранением и контейнером.

### 10.14. Не раскрывать закрытые контейнеры

Если контейнер закрыт, заперт, скрыт или недоступен:

```text id="u268vx"
content_materialized=false
content_known=false
```

Содержимое может быть:

```text id="oc7rlc"
unknown
partly_visible
audible
smell_detectable
known_by_label
known_to_owner_only
```

Но конкретный список содержимого не создаётся без причинного основания.

### 10.15. Проверить player request

Если игрок просил предмет, LLM не материализует его автоматически.

Допустимые варианты:

```text id="nw3vap"
requested_item_already_allowed_and_causal → можно материализовать
requested_item_profile_exists_but_no_causal_basis → rejected placement
requested_item_profile_not_allowed → rejected placement
requested_item_not_in_profiles → unavailable
```

Результат должен быть зафиксирован:

```json id="gvcvw4"
{
  "player_request_item_handling": {
    "raw_request": "string | null",
    "result": "not_requested | placed_with_causal_basis | rejected_no_basis | rejected_not_allowed | unavailable_profile",
    "evidence": []
  }
}
```

## 16. Работа LLM на этапе

На этом этапе LLM обязательна, потому что размещение конкретных предметов — это смысловая материализация объектов в сцене.

LLM выбирает:

* какие item profiles материализовать;
* какие container profiles материализовать;
* какие property rules применить;
* на какие anchors поставить предметы;
* какие предметы видимы;
* какие предметы требуют осмотра;
* какие предметы скрыты;
* какие контейнеры закрыты;
* что не надо материализовать;
* какие риски возникают при взаимодействии;
* почему каждый предмет находится именно здесь.

LLM не выбирает:

* новые item profiles;
* новые container profiles;
* новые property rules;
* новые G5 anchors;
* новые NPC;
* новые владельческие институты;
* новые события;
* visible prose;
* intro prose.

### 17.1. `InitialItemPlacer`

## 23. Validation rules

Код обязан проверить:

1. `schema === "initial_item_placement_draft"`.
2. `version === 1`.
3. `placement_status` входит в enum.
4. Каждый `item_instance_id` уникален.
5. Каждый `container_instance_id` уникален.
6. Каждый `item_profile_candidate_id` существует.
7. Каждый `item_profile_id` совпадает с candidate.
8. Каждый `container_profile_candidate_id` существует.
9. Каждый `container_profile_id` совпадает с candidate.
10. Каждый `property_rule_candidate_id` существует.
11. Каждый `g5_anchor_id` существует.
12. Anchor belongs to selected G4.
13. Anchor supports item/container.
14. NPC holder exists if used.
15. Player holder exists if used.
16. Каждый item имеет causal_basis_type.
17. `causal_basis_type != player_desire`.
18. Каждый item имеет weight.
19. Каждый item имеет size_band.
20. Каждый item имеет condition.
21. Каждый item имеет visibility_state.
22. Каждый item имеет access_state.
23. Каждый interactable item имеет property_state.
24. Каждый interactable item имеет risk_state.
25. Hidden item не visible_to_player_now.
26. Closed/locked/inaccessible container не имеет materialized contents без basis.
27. Container content state корректно отделён от item instances.
28. Rare/restricted/valuable item имеет owner/controller/risk.
29. Чужой item имеет risk.
30. Disputed item имеет risk.
31. Service/authority/sacred item имеет risk and access restriction.
32. Player inventory item не дублируется как scene item без basis.
33. Нет item outside item_profile_candidate_set.
34. Нет container outside container_profile_candidates.
35. Нет property rule outside property_rule_candidates.
36. Нет new NPC.
37. Нет new G5 anchor.
38. Нет visible_scene.
39. Нет intro_prose.
40. Нет hidden_event.
41. `source_trace` не пустой, если require_source_trace=true.
42. `audit_self_check.evidence` не пустой.
43. Если `audit_self_check.pass=false`, concerns не пустой.

## 26. Commit gate этапа

Этап считается успешным, если:

```text id="pbsmx9"
initial_item_placement_draft валиден,
все предметы выбраны из item_profile_candidate_set,
все контейнеры выбраны из container_profile_candidates,
все property rules выбраны из property_rule_candidates,
все предметы и контейнеры привязаны к существующим G5 anchors/NPC/player/container,
каждый предмет имеет причинное основание,
не создан ни один предмет из желания игрока,
видимость и доступ корректны,
владение и риск заданы,
закрытые контейнеры не раскрыты без основания,
не созданы NPC, G5 anchors, visible_scene или intro_prose,
audit pass=true.
```

Если commit gate не пройден, pipeline не должен переходить к visible context или narrator.
