# Этап 4. Загрузка регионального контекста из `world_base`

## 1. Назначение этапа

Загрузка регионального контекста — это четвёртый этап запуска новой партии. Он получает утверждённую историческую рамку и собирает из `world_base` региональный пакет данных, необходимый для последующего выбора стартовой карты, места, персонажа, NPC, предметов, погоды, маршрутов и G5-сцены.

На этом этапе код не создаёт мир. Он только читает уже утверждённые записи из `world_base`, проверяет их применимость к выбранной исторической рамке и собирает компактный `regional_context_package`.

Этот пакет нужен, чтобы следующие LLM-этапы работали не по общим знаниям модели, а по конкретным разрешённым данным проекта.

Короткая формула:

```text
historical_frame
→ world_base queries
→ regional_context_package
→ regional_context_audit
→ candidate retrieval для стартовой карты
```

## 2. Главное правило этапа

Код достаёт данные. LLM не выбирает и не придумывает региональные правила.

На этом этапе запрещено:

* создавать новую локацию;
* выбирать стартовый G1–G4 узел;
* материализовать G5;
* создавать персонажа игрока;
* создавать NPC;
* создавать предметы;
* создавать стартовое событие;
* писать вводную прозу;
* подменять отсутствующие записи догадками;
* расширять региональную базу через LLM.

Разрешено:

* читать `world_base`;
* фильтровать записи по `region_id`, году, сезону, статусу и источникам;
* собирать допустимые списки;
* отсекать неподходящие записи;
* формировать компактный пакет контекста;
* вызывать LLM только для упаковки/сжатия/аудита уже извлечённых записей, если это нужно;
* возвращать ошибку, если критических данных не хватает.

## 3. Место этапа в pipeline

```text
1. Заявка игрока
2. Нормализация заявки
3. Выбор исторической рамки
4. Загрузка регионального контекста
5. Подбор допустимых стартовых G1–G4 кандидатов
6. Выбор стартового места
7. Генерация персонажа
8. Материализация G5
9. NPC / предметы / visible context / narrator
```

Этап 4 получает `historical_frame` и возвращает `regional_context_package`.

Следующие этапы не должны напрямую обращаться к общей базе “как попало”. Они должны получать от этапа 4 ограниченный пакет разрешённых данных или запрашивать дополнительный контекст через контролируемый `ContextRetriever`.

## 6. Какие данные код должен загрузить

### 6.1. Профиль региона

Назначение: дать базовую идентичность региона и рамки применимости.

Источник:

```text
world_base.regions
```

Минимальные поля:

```text
id
slug
canonical_name
display_name
alt_names
region_type
parent_region_id
period_start_year
period_end_year
summary
geographic_scope
natural_landscape

roads_summary

political_summary
social_summary
economic_summary
game_use
limits
status
confidence
sources
audit_notes
```

Фильтр:

```text
regions.id = historical_frame.region.region_id
year.value BETWEEN period_start_year AND period_end_year
status IN allowed_statuses
```

Выходной блок:

```json id="a17gxr"
{
  "region_identity": {
    "region_id": "string",
    "slug": "string",
    "title": "string",
    "region_type": "string",
    "period": {
      "start_year": 0,
      "end_year": 0
    },
    "summary": "string",
    "geographic_scope": "string",
    "natural_landscape": "string",
    "climate_summary": "string",
    "settlement_logic_summary": "string",
    "game_use": "string",
    "limits": "string",
    "status": "approved | usable_with_caution | draft | needs_review",
    "confidence": "unknown | low | medium_low | medium | medium_high | high",
    "sources": []
  }
}
```

Нельзя выводить из профиля региона конкретную стартовую сцену. Профиль региона — это фон и ограничитель.

### 6.2. Timeline / исторические события / исторические фазы

Назначение: дать политическое и социальное давление выбранного периода.

Источники:

```text

```

Если в конкретной реализации названия таблиц отличаются, обязательна смысловая группа:

```text

исторические якоря карты
политические изменения
кризисы
внешние угрозы
социально-экономическое давление
```

Фильтр:

```text

event_start_year <= selected year
event_end_year >= selected year
status IN allowed_statuses
```

Выходной блок:

```json id="rm8t2f"
{
  "historical_context": {
    "year": 0,
    "active_periods": [],
    "active_events": [],

  }
}
```

Timeline не создаёт событие старта. Он только задаёт фон и ограничения.

## 7. Приоритет статусов

При загрузке код должен применять единый фильтр.

Рекомендуемая политика:

```text
approved → использовать
usable_with_caution → использовать с audit note
draft → не использовать для стартовой партии, если policy не разрешает
needs_review → не использовать для стартовой партии, если policy не разрешает
conflict → запрещено
rejected → запрещено
```

Если критическая группа содержит только `draft` или `needs_review`, этап должен вернуть предупреждение или ошибку, а не молча использовать слабую запись.

## 8. Источники и traceability

Каждая запись, попавшая в `regional_context_package`, должна сохранять:

```text
id
status
confidence
sources
game_use
limits
audit_notes
```

В итоговом пакете должен быть `source_trace`.

```json id="edplwq"
{
  "source_trace": [
    {
      "record_id": "string",
      "table": "string",
      "source_ids": [],
      "supports": [
        "social_context",
        "route_context"
      ],
      "status": "approved",
      "confidence": "medium_high"
    }
  ]
}
```

Если источник отсутствует, а `load_policy.require_sources=true`, запись не должна попадать в основной пакет. Её можно поместить в `missing_or_weak_context`.

## 9. Компактность пакета

`regional_context_package` не должен быть полным дампом `world_base`.

Он должен содержать:

* записи, применимые к выбранному региону;
* записи, применимые к выбранному году;
* записи, применимые к выбранному сезону;
* записи, необходимые следующим этапам;
* краткие поля `summary`, `game_use`, `limits`;
* ID для последующей точной проверки.

Плохо:

```text id="90wtmn"
передать в LLM всю документацию проекта, все регионы, все правила, все графы и все таблицы
```

Хорошо:

```text id="qntotz"
передать только применимые к выбранной рамке записи, плюс source_trace и limits
```

## 10. Что делает код

Код выполняет:

1. принимает `historical_frame`;
2. проверяет `historical_frame.audit.pass=true`;
3. проверяет `region_id`, `year`, `season`, `clock`;
4. собирает список допустимых статусов;
5. делает SQL-запросы к `world_base`;
6. нормализует записи в единый формат;
7. проверяет источники;
8. проверяет `status` и `confidence`;
9. собирает `regional_context_package`;
10. строит `downstream_context_index`;
11. выполняет структурную валидацию;
12. при необходимости запускает LLM-аудит или LLM-сжатие;
13. возвращает пакет следующему этапу.

## 11. Что не делает код

Код не должен:

* создавать смысловые сущности;
* заполнять недостающие правила догадкой;
* выбирать стартовое место без отдельного candidate retrieval;
* создавать NPC из `social_roles`;
* создавать предметы из `item_profiles`;
* превращать `weather_rules` в конкретную погоду;
* превращать `route_templates` в конкретный маршрут;
* превращать `place_templates` в конкретное место;
* писать художественную прозу;
* показывать игроку этот пакет.

## 14. Работа LLM на этом этапе

Базовая версия этапа может работать без LLM. Код сам собирает контекст из `world_base`.

LLM допускается только в трёх вспомогательных подэтапах:

1. `RegionalContextPackShaper` — компактно упаковать извлечённые записи в единый JSON.
2. `RegionalContextAuditor` — проверить полноту, противоречия и отсутствие downstream-сущностей.
3. `RegionalContextRepairer` — исправить только формат или классификацию ошибок, не добавляя новых фактов.

LLM не должна читать всю базу напрямую и не должна делать самостоятельный поиск “по памяти”. Ей передаётся только результат SQL-запросов и уже выбранная историческая рамка.

## 19. Validation rules

После загрузки и возможной LLM-упаковки код обязан проверить:

1. `schema === "regional_context_package"`.
2. `version === 1`.
3. `region_identity.region_id === historical_frame.region.region_id`.
4. Все региональные записи имеют нужный `region_id`.
5. Глобальные шаблоны используются только через региональные связки или явные FK.
6. Все записи имеют допустимый `status`.
7. Нет `status=conflict`.
8. Нет `status=rejected`.
9. `sources` не пустой, если `require_sources=true`.
10. Все `source_id` существуют в `source_records`.
11. Все `confidence` входят в enum.
12. Все `game_use` и `limits` сохранены.
13. Пакет содержит social roles или объясняет отсутствие в `missing_or_weak_context`.
14. Пакет содержит occupations или объясняет отсутствие.
15. Пакет содержит place rules или объясняет отсутствие.
16. Пакет содержит route rules или объясняет отсутствие.
17. Пакет содержит weather/season context или объясняет отсутствие.
18. Пакет содержит item/property context или объясняет отсутствие.
19. Пакет содержит NPC context или объясняет отсутствие.
20. Пакет не содержит конкретных NPC.
21. Пакет не содержит конкретных предметов.
22. Пакет не содержит стартовой позиции.
23. Пакет не содержит G5 anchors.
24. Пакет не содержит `visible_scene`.
25. Пакет не содержит `intro_prose`.
26. `audit.evidence` не пустой.
27. Если `audit.pass=false`, `audit.concerns` не пустой.

```text id="tg0b8g"
нет запрещённых статусов,
все source IDs проверены,
не создано ни одной downstream-сущности,
audit.pass=true.
```

Если критических данных не хватает, pipeline не должен переходить к подбору стартовых G1–G4 кандидатов.

## 23. Передача в следующий этап

Следующий этап получает:

```json id="je1qau"

  "normalized_request": {},
  "historical_frame": {},

  "required_year": 0,
  "required_season": "spring | summer | autumn | winter",

```

Следующий этап обязан выбирать стартовые G1–G4 кандидаты только внутри загруженного регионального контекста и канонического графа `world_base`.

Если следующий этапу нужны дополнительные данные, он должен запросить их через контролируемый `ContextRetriever`, а не дать LLM свободно придумывать недостающий контекст.
