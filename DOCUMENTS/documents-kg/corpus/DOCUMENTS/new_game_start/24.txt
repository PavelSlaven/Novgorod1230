# ПРИОРИТЕТНАЯ РЕДАКЦИЯ 2 — ИЗОЛИРОВАННЫЙ STAGE 24

Эта редакция имеет приоритет над несовместимыми примерами ниже.

## 0. Архитектурный контракт

Stage 24 — обязательный изолированный LLM-блок. Он получает только `party_db_write_plan_input`, не читает global context, registry, lifecycle, базу данных, outputs других этапов или UI и возвращает единый `stage24_party_db_write_plan_result`.

Builder, Auditor, Format Repairer, Router и Senior-роли получают только свои явно определённые payload. Передача им pipeline context или database handle запрещена. Provided `input`, `writePlan`, `audit` и готовый Stage 24 output запрещены во всех окружениях.

Stage 24 не выполняет live-запись. Он только формирует, валидирует, независимо аудирует и утверждает план. Транзакция принадлежит Stage 25.

## 0.1. Exact input

```text
party_db_write_plan_input:
  version
  schema
  request_id
  party_creation_context
  approved_pipeline_outputs
  approved_pipeline_manifest
  party_database_schema
  party_database_schema_digest
  world_base_reference_snapshot
  world_base_reference_digest
  write_policy
```

Обязательны заранее выделенные `party_id` и утверждённый `player_character_id`. Технические fallback ID (`pc_001`, `party_<request_id>`) запрещены.

`party_database_schema` обязан быть полным immutable snapshot с непустыми `tables`, а также `columns`, `foreign_keys`, `unique_constraints`, `check_constraints`, `enum_definitions`, `indexes`, `allowed_operations` и checksum. Пустой schema fallback запрещён.

`world_base_reference_snapshot` содержит только разрешённые read-only ссылки и checksum. Stage 24 не обращается к `world_base` самостоятельно.

`write_policy` включает неослабляемые требования атомарности, idempotency, source trace, rollback, запрета `world_base` mutation, запрета неутверждённых сущностей, точной knowledge projection и digest binding. Caller может только усиливать policy.

## 0.2. Approved pipeline manifest и digest binding

Каждый обязательный upstream artifact связан с:

```text
stage_id
artifact_schema
artifact_digest
approval_stage_id
approval_digest
request_id
```

Stage 24 пересчитывает SHA-256 canonical JSON digests и блокирует отсутствующий, изменённый или не тем audit-ом утверждённый artifact.

Обязательные digests:

```text
party_db_write_plan_input_digest
party_database_schema_digest
world_base_reference_digest
approved_pipeline_manifest_digest
party_db_write_plan_digest
party_db_write_plan_audit_digest
```

Audit обязан ссылаться на точный `party_db_write_plan_digest`. Stage 25 повторно вычисляет все handoff digests.

## 0.3. Code precheck

До любого LLM-вызова код создаёт `party_db_write_plan_code_precheck` и проверяет:

- exact input schema и единый request ID;
- заранее выделенные party/player IDs;
- наличие и успешность обязательных upstream approvals;
- соответствие всех artifact digests manifest-у;
- полноту и checksum party DB schema;
- полноту и checksum world-base reference snapshot;
- наличие и целостность character knowledge write projection;
- утверждённые current position и narrator prose;
- полноту и неослабляемость write policy;
- отсутствие global context, live DB handles и запрещённых полей.

При `precheck.pass=false` Builder и остальные роли не вызываются.

## 0.4. Обязательные роли

```text
PartyDbWritePlanBuilder
PartyDbWritePlanFormatRepairer
PartyDbWritePlanAuditor
PartyDbWritePlanAuditFormatRepairer
PartyDbWritePlanAuditRouter
PartyDbWritePlanSemanticRepairer
SeniorPartyDbWritePlanSemanticRepairer
SeniorPartyDbWritePlanBuilder
SeniorPartyDbWritePlanAuditor
```

Builder и независимый Auditor обязательны. Code validation не заменяет LLM audit, а LLM audit не заменяет code validation.

## 0.5. Plan contract и code validation

`party_db_write_plan` обязан содержать:

```text
version/schema/request_id/plan_status
source and schema digests
transaction
preconditions
write_batches
postconditions
forbidden_writes
derived_indexes
audit_snapshots
rollback_plan
source_trace
knowledge_projection_validation
self_audit
```

Код проверяет:

- atomic transaction, dry-run-first, idempotency и полный rollback;
- реальные таблицы, колонки, operations, enums и ограничения schema snapshot;
- уникальный и ациклический batch graph и корректный write order;
- только утверждённые NPC, item, container, G5 anchor и route/edge IDs;
- точное совпадение current position и player character;
- точное совпадение knowledge projection: hash, counts и record keys, без missing/extra records;
- отсутствие hidden state в player-visible targets;
- запрет записи в `world_base`;
- полный source trace и audit snapshots;
- запрет player-visible output до commit.

Код не выбирает замену для битой ссылки и не создаёт недостающую сущность.

## 0.6. Independent audit

`PartyDbWritePlanAuditor` получает только plan, его digest, approved manifest/outputs, schema snapshots и write policy.

Audit schema: `party_db_write_plan_audit`. Он обязан содержать полный набор checks, непустое evidence, валидные concern codes/severity, точный plan digest и согласованные permissions. Audit не может содержать переписанный plan, hidden state или database handles.

При `pass=true`: concerns пусты, route отсутствует, все commit permissions true.
При `pass=false`: concerns/evidence непусты, permissions false, затем вызывается отдельный Router.

## 0.7. Repair routing и escalation

```text
format error plan
→ PartyDbWritePlanFormatRepairer
→ полный validator
→ новый independent audit

format error audit
→ PartyDbWritePlanAuditFormatRepairer
→ полный audit validator

semantic plan error
→ PartyDbWritePlanAuditRouter
→ PartyDbWritePlanSemanticRepairer
→ полный validator
→ новый independent audit

второй semantic repair
→ SeniorPartyDbWritePlanSemanticRepairer / senior roles
→ полный validator
→ новый independent audit

failed senior repair
→ blocked / manual_review
```

Format и semantic repair не взаимозаменяемы. Код только валидирует выбранный Router-ом route и его совместимость с concerns. Каждый repair обязательно завершается повторным audit; последний неаудированный repair запрещён.

## 0.8. Result bundle

Stage 24 возвращает только:

```text
stage24_party_db_write_plan_result:
  version/schema/request_id/pass
  input/schema/world-base/manifest/plan digests
  party_db_write_plan_code_precheck
  party_db_write_plan
  party_db_write_plan_audit
  repair_route
  generation_history
  audit_history
  repair_history
  diagnostics
  handoff_permission
```

Успешный result bundle immutable и допускается к Stage 25 только если precheck, plan и audit успешны, route отсутствует и все handoff permissions true.

# Этап 24. План записи в party-базу

## 1. Назначение этапа

План записи в party-базу — это этап, на котором LLM/структурирующий агент формирует проверяемый `party_db_write_plan`.

Этот этап не пишет данные в базу напрямую. Он только создаёт план транзакции:

```text
какие записи создать;
какие записи обновить;
какие связи установить;
какие snapshot сохранить;
какие таблицы нельзя трогать;
в каком порядке выполнять операции;
какие проверки выполнить до commit;
как откатить операцию при ошибке.
```

Короткая формула:

```text
approved_pipeline_outputs
+ narrator_prose_audit.pass=true
+ party_database_schema
+ write_policy
→ party_db_write_plan
→ db_write_plan_audit
→ transaction executor
```

Главное правило:

```text
LLM/структурирующий агент формирует только план записи.
Код валидирует план.
Код выполняет транзакцию.
Код не сочиняет новые world facts.
```

Этап должен подготовить запись следующих слоёв:


Запись должна быть атомарной: либо вся стартовая партия фиксируется согласованно, либо ничего не записывается как live-state.

## 6. Главное ограничение

План записи не может создавать новые смыслы.

Разрешено:

```text
переложить уже утверждённые сущности в таблицы;
сформировать insert/update операции;
сформировать связи между уже утверждёнными сущностями;
сформировать snapshot аудитов;
сформировать индексы и служебные derived records;
задать порядок транзакции;
задать rollback;
задать idempotency keys.
```

Запрещено:

```text
создавать новый NPC;
создавать новый предмет;
создавать новый маршрут;
создавать новый G5-якорь;
создавать новое знание персонажа;
создавать новое скрытое событие;
менять narrator prose;
менять hidden state;
менять visible context;
менять current_position;
менять clock/weather/light;
писать в world_base;
писать player-visible output до успешного commit.
```


## 32. Работа LLM/структурирующего агента на этапе

LLM/структурирующий агент допустим, потому что mapping из множества утверждённых pipeline outputs в DB write plan является сложной структурной задачей.

Но роль агента ограничена.

Агент делает:

```text
раскладывает утверждённые сущности по таблицам;

формирует insert/update/snapshot operations;
```

Агент не делает:

```text

не материализует новых NPC;
не материализует новые items;
не меняет hidden state;
не меняет visible context;
не меняет narrator prose;
не пишет SQL напрямую;
не исполняет транзакцию;
не пишет в БД сам.
```

## 41. Commit gate этапа

Этап считается успешным, если:

```text
party_db_write_plan валиден;
все previous audits pass=true;
план атомарный;
idempotency_key есть;
write_order корректный;
rollback_plan есть;
preconditions/postconditions есть;
нет world_base mutation;
нет новых semantic entities;
current_position корректен;
все FK зависимости выполнимы;
hidden state не попадёт в public tables;
player-visible output не выйдет до commit;
source_trace and audit snapshots включены;
self_audit.pass=true.
```

После этого план передаётся в `db_write_plan_audit`.

Если gate не пройден, транзакция не запускается.
