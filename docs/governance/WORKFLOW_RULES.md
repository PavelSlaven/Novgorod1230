# Правила рабочего процесса

> Часть governing-корпуса `AGENTS.md` (см. [AGENTS.md](../../AGENTS.md) §1.3). Защита — AGENTS.md §1.1: менять только по прямому явному запросу администратора. Слова «этот файл», «здесь» и «раздел N» внутри перенесённого текста означают весь governing-корпус. ## 2. Источники истины и порядок инструкций

Для вопроса «что уже реализовано и смержено сейчас» единственный источник истины — GitHub-репозиторий `PavelSlaven/Novgorod1230`, ветка `main`.

Если работа ведётся над конкретным PR или feature branch:

- точный checkout этой ветки является рабочим состоянием текущей задачи;
- `main` остаётся источником глобального смерженного состояния;
- несмёрженный PR не становится новой общей нормой только потому, что его код существует;
- более поздний stacked PR не является источником истины для более раннего PR;
- после изменения родительского PR downstream-ветки потенциально устарели до restack/rebase.

Перед работой заново прочитай актуальный `AGENTS.md` из фактического checkout.

Затем открой [Канонический индекс контрактов](../../data/knowledge-source/corpus/DOCUMENTS/CONTRACT_INDEX.md), чтобы установить статусы документов, applicable active contracts, precedence и обязательные триггеры Contract Auditor.

Если в подкаталоге существует вложенный `AGENTS.md`, прочитай его перед изменением файлов в его области. Вложенный файл может уточнять локальные правила, но не должен молча отменять корневые продуктовые и архитектурные инварианты.

Для конкретной подсистемы дополнительно действуют её:

- `MODULE.md`;
- профильные нормативные документы;
- публичные contracts/schemas;
- код;
- тесты;
- versioned world/scenario profiles и bindings.

Не используй старую копию документа или прошлый контекст разговора вместо актуального состояния репозитория, если ответ зависит от текущего кода.

Всегда различай:

1. уже реализованное production-поведение;
2. proposed/target-поведение;
3. план внедрения;
4. рекомендацию или идею, которая ещё не стала контрактом.

Не создавай рядом с GitHub второй источник истины.

Если `AGENTS.md`, профильный контракт, план и реализация расходятся, не принимай расхождение молча как новую норму. Установи, что является active state, что target state, и где находится конфликт.

## 18. Начало работы над задачей

Работай в текущем локальном checkout, если он находится на ветке задачи или её актуальной базе и не содержит посторонних незакоммиченных изменений.

Если текущий checkout находится на другой ветке, отстаёт от актуальной базы задачи или содержит незакоммиченные изменения пользователя либо другого агента, создай отдельный git worktree от актуальной базы задачи и работай в нём. Исходный checkout и его изменения не трогай (раздел 27). Созданный worktree — временный ресурс задачи по разделу 26.1.

Минимальная обязательная проверка:

```powershell
git status --short --branch
git branch --show-current
```

Перед изменением существующего проекта:

1. определи требуемый результат;
2. определи границы задачи;
3. определи критерии готовности;
4. прочитай непосредственно затрагиваемые файлы;
5. найди их публичные contracts;
6. проследи реальные callers/callees и flow;
7. прочитай существующие профильные tests;
8. прочитай `MODULE.md` и профильные нормативы затронутой области;
9. определи authoritative owner изменяемой ответственности.

Стремись понять задачу с высокой уверенностью, но набирай эту уверенность прежде всего чтением проекта.

Задавай точечные вопросы небольшими группами только если:

- ответ нельзя получить из code/contracts/tests/docs;
- существуют несколько существенно разных продуктовых вариантов;
- выбор заметно изменит пользовательское поведение, public contract, persisted data или архитектуру.

Низкоуровневые implementation details не требуют согласования с человеком.

Явное указание «выбери сам» даёт агенту право выбрать самое простое решение, совместимое с этим файлом и профильным нормативом.

Если задача понятна, приступай без подтверждения.

Для нетривиальной задачи дай короткий план. Для небольшой локальной правки переходи сразу к работе.

Работай непрерывно до завершения задачи либо до реальной блокировки. Не останавливайся ради промежуточного подтверждения обратимого действия, которое явно входит в запрос.

### 18.1. Обязательные навыки `caveman` и `ponytail`

Во всех задачах применяй навык `caveman` в режиме `full`. Во всех задачах разработки применяй навык `ponytail` в режиме `full`. Навыки лежат в `.agents/skills/` и `.claude/skills/`. Отключай их или меняй режим только по явной просьбе пользователя (`stop caveman`, `stop ponytail`, `normal mode`, `caveman lite|full|ultra`, `ponytail lite|full|ultra`).

`caveman` управляет только краткостью общения. Он не является основанием сокращать необходимое исследование, реализацию, проверки или итоговый отчёт по §29.

`ponytail` управляет минимальностью решения. Его правило «shortest working diff» означает минимальное корректное решение всей поставленной задачи (§5, §16), а не минимальное число строк, закрывающее только приведённые примеры.

## 19. Изучение репозитория и инструменты

Не изучай весь репозиторий без необходимости.

По умолчанию используй:

- точечное чтение файлов;
- `rg`;
- imports/callers;
- профильные tests;
- `MODULE.md`.

В каждой нетривиальной задаче разработки используй `codebase-memory-mcp` в режиме Verify (Tier 2).

До реализации:

1. проверь проект и состояние индекса через `list_projects` и `index_status`;
2. найди authoritative owner и зависимости через релевантные `get_architecture`, `search_graph` и `trace_path`;
3. сверь существенные графовые результаты с исходными файлами, contracts и tests.

Перед завершением:

1. вызови `detect_changes` для фактического diff;
2. вызови `check_index_coverage` для всех путей, на которые опираются выводы;
3. перед отрицательным или исчерпывающим выводом дополнительно проверь соответствующий scope через `check_index_coverage`;
4. при skipped, partial, excluded, stale, pending или unknown coverage прочитай или проверь через `rg` указанные файлы и диапазоны напрямую.

Если `codebase-memory-mcp` недоступен в среде исполнения, не имитируй его вызовы и их результаты. Зафиксируй недоступность в итоговом отчёте и устанавливай owners, зависимости и полноту выводов прямым чтением файлов и `rg` по затронутому scope. Недоступность инструмента сама по себе не блокирует задачу.

Граф является навигационным инструментом, а не нормативным источником. `@rus/knowledge-source` остаётся отдельным нормативным каналом; графовый результат не заменяет запрос к нему и чтение исходного canonical document.

Для очевидной локальной задачи с заранее известным owner допустим прямой `rg` и точечное чтение без графа.

Индекс обновляют штатные `auto_index=true` и `auto_watch=true`. Не запускай ручную полную переиндексацию после каждой правки; используй `index_repository` только при отсутствующем или нездоровом индексе либо для немедленной синхронизации после крупного внешнего изменения и в начале спринта. Настройка описана в [codebase-memory-mcp: локальная настройка](../../docs/setup/CODEBASE_MEMORY_MCP.md).

В начале каждого спринта — в первой задаче после открытия нового milestone, выдачи владельцем нового этапа плана или смены трека в `docs/work/CURRENT_SPRINT.md` — до другой работы проверь, актуализируй и затем используй `codebase-memory-mcp`:

1. убедись, что сервер подключён в текущем клиенте, и проверь проект фактического checkout через `list_projects` и `index_status`;
2. один раз синхронизируй индекс через `index_repository`: checkout мог измениться через pull, merge или rebase, пока watcher не работал;
3. если индекс не переходит в `ready` или CBM не запускается, установи причину и устрани её; процессы CBM, запущенные другими клиентами, завершай только с разрешения администратора; если устранить нельзя без выхода за рамки задачи, работай по правилу о недоступности `codebase-memory-mcp` (задача не блокируется), зафиксируй это в отчёте и добавь в открытый issue о CBM (создай его, если такого нет);
4. укажи результат проверки в отчёте первой задачи спринта; дальше используй CBM по правилам этого раздела.

Проверяй версии Node.js, Python, Docker и других инструментов только когда задача от них реально зависит.

Не запускай автоматически:

- installation dependencies;
- Docker services;
- полный repository scan;
- полный test suite;
- benchmark;
- security audit;
- dependency audit;
- ручную полную генерацию индексов без установленной необходимости;
- повторные review loops.

После того как текущий flow, owner, contract и необходимое изменение понятны, прекращай исследование и переходи к реализации.

Не выдумывай:

- файлы;
- API;
- поведение;
- tool availability;
- результаты команд;
- результаты тестов.

## 20. Документация и её владельцы

`AGENTS.md` содержит стабильные правила работы и критические инварианты. Вся промежуточная, профильная, сценарная и release-specific документация должна находиться у соответствующего владельца.

Используй [Канонический индекс контрактов](../../data/knowledge-source/corpus/DOCUMENTS/CONTRACT_INDEX.md), чтобы определить статус документа, applicable contract set и precedence. `llm_documentation_navigation.md` сохранён только как compatibility redirect.

Основные направления:

- общая cross-cutting архитектура и нормативные контракты — `data/knowledge-source/corpus/DOCUMENTS/`;
- граница code/LLM и materialization — `data/knowledge-source/corpus/DOCUMENTS/code_driven_world_materialization_architecture.md`;
- world base, DDL/import/profiles/rules и materialization requirements — `data/knowledge-source/corpus/DOCUMENTS/world_base_materialization_table_requirements.md`;
- active Spatial v3 read-only DB/graph architecture — `data/knowledge-source/corpus/DOCUMENTS/spatial_v3_target_read_only_database_and_graph_architecture.md`; прежний `read_only_database_and_graph_architecture.md` является migration/rollback source;
- schema reference — `infra/world-base/SCHEMA_REFERENCE.md`;
- active G0–G5 authoring workflow — `data/knowledge-source/corpus/DOCUMENTS/spatial_v3_target_map_g0_g4_workflow.txt`; прежний `map_g0_g4_workflow.txt` является migration/rollback source;
- региональная semantic catalog информация — соответствующий `G1_SEMANTIC_CATALOG.md`;
- time/activities/traversal/schedules/temporal boundaries — `data/knowledge-source/corpus/DOCUMENTS/temporal_world_and_interruptible_activities.md`;
- ответственность и public contract конкретного модуля — его `MODULE.md`;
- scenario/world content, profiles, manifests, definitions и bindings — соответствующий каталог `data/world-catalogs/...`;
- DDL и party/world schema — соответствующие `schemas/` и schema docs;
- состояние PR, review findings, validation results и краткоживущие rollout notes — PR/issue/task, а не `AGENTS.md`;
- отдельный implementation plan — только в специально предназначенном plan-документе, если он реально нужен задачей.

Правило раздела 1.2 о release- и scenario-specific сведениях распространяется на общие нормативные контракты и `MODULE.md`. Они описывают общий класс поведения, его владельцев и границы. Номера scenario revision, фазы сценария, production release, конкретные персонажи, предметы и места сценария, а также сведения о том, где поведение фактически активировано, находятся у владельца сценарного каталога, release binding или в PR/task. Общий документ может кратко сослаться на владельца текущей активации, но не формулирует общее поведение через ревизию или фазу конкретного сценария. Текущая узкая активация не является условием общей нормы.

RAG используется для **навигации**, а не как самостоятельный норматив:

```powershell
npm run knowledge:query -- --query "<конкретная нормативная потребность>"
```

После поиска проверяй требование в исходном canonical document.

Не создавай случайные root-level `notes.md`, `review.md`, `evidence.md`, `status.md` и подобные файлы вместо обновления правильного владельца документации.

Не создавай промежуточную документацию вообще, если она не нужна. Но если документация нужна, помещай её в соответствующий раздел, а не в `AGENTS.md`.

Generated artifacts не являются местом для ручного авторинга. Изменяй canonical source и используй предусмотренный generator/check workflow.

Не создавай рабочие README, evidence packages и дополнительные отчёты без прямой необходимости.

Недоступный документ является блокировкой только если без него действительно нельзя корректно выполнить текущую задачу.

## 21. Реализация и изменение контрактов

Перед созданием нового модуля проверь существующие модули и публичные interfaces.

Используй текущий stack и закреплённые версии dependencies.

Не обновляй libraries/toolchain, если это не требуется задачей.

Сохраняй public APIs, formats и persisted contracts, если их изменение не является частью задачи.

Если задача **намеренно** меняет contract/capability:

- меняй существующий owner минимально необходимым образом;
- обновляй реальные consumers;
- не сохраняй старое ограничение через special-case exceptions только потому, что оно существовало раньше;
- не создавай dual path ради невыпущенного internal prototype;
- не принимай implementation narrowing как новый продуктовый инвариант.

Не ослабляй реальные authoritative/security/data-integrity ограничения как случайный workaround.

Не создавай semantic fallback, который маскирует отсутствие обязательных authoritative данных.

## 22. Отладка

При ошибке, регрессии или проблеме производительности:

1. зафиксируй наблюдаемый symptom;
2. воспроизведи его, если практически возможно;
3. проследи реальный execution flow;
4. найди всех существенных callers затрагиваемой ответственности;
5. найди root cause;
6. исправь проблему у правильного owner;
7. добавь минимальный regression test, когда это практически полезно;
8. проверь sibling paths, использующие тот же механизм.

Не правь вслепую до изучения доступных logs, tests и связанного code.

Не ставь одинаковый guard во множество callers, если одна корректная проверка принадлежит shared owner.

Не маскируй дефект:

- catch-all;
- silent ignore;
- безусловным fallback;
- ослаблением фильтра;
- повторным semantic call без причинного основания.

## 24. Тестирование и проверки

Во время работы запускай минимальный набор проверок, относящийся к изменяемому поведению.

Для bug fix по возможности добавляй regression test, который действительно воспроизводит root cause.

После реализации выполни относящиеся к области изменения проверки:

- профильные tests затронутого модуля;
- изменённые contracts/schemas;
- `git diff --check`;
- `npm run architecture:check`, если затронуты архитектурные границы;
- `npm run docs:check`, если изменена canonical документация;
- `npm run knowledge:check`, если изменены knowledge-source документы или их generated artifacts;
- профильные PostgreSQL integration tests, если изменены реальные DDL/persistence semantics.

Не подменяй проверку настоящей DB semantics только mocks, когда сама задача меняет PostgreSQL persistence/DDL.

Во время итерационной разработки используй focused/profile tests, regression tests и остальные проверки, необходимые затронутой области. Полный `npm test` не является обязательным локальным pre-commit/pre-push действием: не запускай его автоматически после каждой правки, перед каждым commit или push либо только потому, что очередная итерация закончена.

Полный `npm test` является обязательным финальным merge gate. Один успешный полный suite должен относиться к exact HEAD, который действительно собираются merge в `main`, либо к соответствующему `merge_group`, если используется GitHub Merge Queue. Merge запрещён, пока этот required check не зелёный.

Предпочтительный владелец финального полного прогона — GitHub CI. Без отдельной причины не дублируй один и тот же полный suite локально непосредственно перед его обязательным запуском в GitHub.

Если после зелёного полного suite изменился HEAD либо изменились code/data/contracts, предыдущий результат считается stale. Новый final exact HEAD должен пройти полный `npm test` заново.

Локальный полный `npm test` допустим только если:

- пользователь прямо потребовал локальный полный прогон;
- GitHub CI недоступен;
- конкретная отладка действительно требует полного suite;
- профильный workflow прямо требует локального полного suite.

Для documentation-only изменения не запускай PostgreSQL, browser или полный integration suite без отдельной причины.

Не создавай огромный test forest для каждого внутреннего helper. Проверяй observable contract и существенные regressions.

Для изменения свободного gameplay behavior добавь или проверь хотя бы один unseen-equivalent case, чтобы тесты не превращались в production whitelist.

Никогда не утверждай, что проверка прошла, если она фактически не выполнялась успешно.

В итоговом отчёте перечисляй только реально выполненные checks и их результаты.

## 29. Завершение задачи

Перед завершением сравни результат с исходной задачей и criteria of done, а не только с зелёными тестами.

Не расширяй scope без необходимости.

Если найдена посторонняя проблема, которая не мешает текущей задаче, не исправляй её попутно. Кратко зафиксируй её в итоговом отчёте или в правильном issue/owner, если это входит в запрос.

Итоговый ответ должен кратко содержать:

1. что изменено;
2. какое поведение реализовано или исправлено;
3. какие проверки фактически выполнены;
4. какие реальные ограничения или блокировки остались.

Не объявляй задачу завершённой, если известная обязательная проверка затронутой области завершилась ошибкой.

Не добавляй в итоговый отчёт гипотетические улучшения «на будущее», если они не нужны текущей задаче.
