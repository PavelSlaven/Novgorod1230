## Как понята задача и источник истины

Игровой путь — один живой CDDA. Родные действие, NPC safety/BT, часы, речь, item identity и `game::save()` остаются владельцами. Novgorod интерпретирует свободное намерение и личное знание, но не исполняет вторую физику. Сохранение — по запросу и каждый игровой час; после crash последнее целое сохранение и честный восстановленный момент. Прочитанный несохранённый прогресс может исчезнуть.

Текущая реализация — exact branch checkout; merged поведение — `origin/main`; новый target — исправленный план среза и решения владельца. Native source — чистый `0d8843f1c500052c3e026e3da6f8edaf5e00b626`, все `src/…` ниже относительно него. Карта `cdda-native-map/INDEX.md` → upstream CBM → исходник/JSON → проверка пробела. Норма из графа не выводится. AGENTS/governance/CONTRACT_INDEX/active contracts не править без отдельного задания; live/durable конфликты сначала рассматривает роль «4».

## Развилки перед кодом

1. Где живёт маленькое ядро принятия save — C++ save completion или launcher: решить на арх-приёмке. В обоих вариантах один live CDDA и одна save-цепочка; никакой заявки в новый процесс на каждом ходе.
2. Достаточны ли native stores для semantic facts: проверить потребителей; один дополнительный save-файл только при конкретном gap. Не оставлять два способа хранить одни NPC данные.
3. Достаточна ли native speech/activity композиция для точного текста и interrupt: сначала проба без модели. Если требуется новый механизм при наличии родного аналога — СТОП, решение распорядителя.
4. Согласование D215/D216 с persisted-only narration/retry нормами до игрового пути. Статус reference-плана не даёт права менять active contracts.
5. #771 решает распорядитель; #772/#773 и sealed protocol пересматриваются после native-first исправлений. Ни старые 27/57/72 вызова, ни прежние repairs автоматически не разрешены новым планом.
