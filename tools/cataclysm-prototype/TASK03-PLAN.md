## Живой вход: предложенный способ доставки

**Предлагаю расширить родной реестр одним action, открыть родной `string_input_popup`, а семантический запрос передавать одному resident Node-процессу по локальному AF_UNIX socket.** Это предложение на OK, реализации нет. CDDA остаётся единственным владельцем/писателем userdir и исполняет результат на своём игровом потоке.

Родные опоры: `src/handle_action.cpp:242,272,3164–3381` (input_context/dispatch), `src/action.cpp:479–509` (action identity), `src/string_input_popup.cpp:383–391,469–508` (ввод, confirm/cancel). Используем их, не пишем новый терминальный редактор или command parser. `ACTION_CHAT` уже имеет sentence/emote (`src/npctalk.cpp:1241–1258`), но emote не меняет мир, а chat имеет собственное меню; перехват ломал бы его смысл. Native EOC `set_string_var/string_input` (`src/npctalk.cpp:6040–6099,8730`) умеет получить строку, но не вызвать внешний semantic owner; его ImGui popup в curses отдельно не проверен. Для первой версии выбирается прямой штатный string_input_popup из action dispatch.

Реальный новый gap — transport к существующему JS semantic/runtime owner. В bounded source search готовый CDDA HTTP/semantic IPC не найден; предел отрицательного вывода указан в [native input facts](evidence/task03-plan/native-input-facts.md). Поэтому предлагается малый POSIX client и Node `net`, а не новая LLM реализация в C++. Перед написанием client проверить сборочные headers/API WSL; это не выдуманный CDDA socket API. Endpoint/IPC-файл расположен вне userdir, coordinator не получает путь к world и не импортирует native process adapter. Если будет найден готовый подходящий native transport — использовать его; новый не строить.

Для цены речи обнаружен родной hook: `character_finished_activity` с `canceled` (`src/player_activity.cpp:350–363,392–399`; `src/event.h:331–338`). Сначала fake-реплика проверяет композицию ACT_WAIT → event/EOC → native sound, включая отмену и save/reload. Общий ACT_WAIT не получает безусловный speech completion: событие связывается только с конкретной pending-репликой в native semantic store. Полная/частичная доставка и очистка ещё не доказаны; если они требуют другого механизма, возвращаемся к распорядителю. Нового actor/scheduler только ради уведомления о конце не нужно. Для curses popup есть native пример `src/overmap_ui.cpp:1505–1512`; `string_input_popup.cpp:97–104` создаёт catacurses window.

Launcher запускает coordinator один раз на сессию, затем curses; при выходе завершает только принадлежащий сессии процесс. На действие нет exec/spawn/новой загрузки мира. Один запрос последовательно: native popup → actor-safe projection из живого CDDA → существующие planner/NPC owners → структурированное предложение → native admission/действие/activity → read-only результат. Семантические факты пишутся тем же native владельцем в global_variables/Creature::values/item_vars; копий snapshot/native_readback в semantic.json штатно нет.

Cancel/empty/ошибка транспорта до исполнения возвращают управление loop без мутаций; вывод ошибки не утверждает успех. Timeout берётся из существующей согласованной role config. Реальное ожидание модели не превращается в игровые секунды. Отказ после уже выполненного native действия не обещает rollback: записывается фактический частичный исход, остающийся в живом мире до save/аварии. Не строить вторую транзакцию или operation ledger. Проза/preview помечены «черновик, не сохранено»; при падении возможен откат прочитанного, как принято D216.

## M2: границы единой save-цепочки

Выбран C++ completion, не IPC к launcher. Родные `mapsharing.cpp:110–171` и `filesystem.cpp:177–186` атомарно записывают один файл; целый набор и fsync directories ими не закрыт — gap уже принят ролью «4». Добавляется только минимальное ядро в точке успешного save; старые 1634 строки coordinator не переносятся в C++ целиком.

`game_save` event до записи не является квитанцией. `.pt` использует void write_to_file (`cata_utility.cpp:318–324`), возможное исключение требуется обработать до объявления успеха/приёма. `save_is_dirty`/false не принимаются.

**Уточнение распорядителю до реализации M2:** дословный текст требует равенства всех вызовов save и попыток приёма, но помещает completion только после успешной `.pt`; dirty/false выходят раньше. Предлагаю проверять «успешные native записи = попытки приёма», а все входы save/dirty/false учитывать отдельно в тесте и требовать для них отсутствие принятия/изменения current.
