# Обязательные правила работы

Этот корневой файл является актуальной точкой входа для любого агента. Расширенная инструкция хранится в `.github/AGENTS.md`; при смысловом расхождении необходимо остановить работу и синхронизировать файлы.

Высший норматив по материализации и разделению ответственности кода/LLM:
[CODE_DRIVEN_WORLD_MATERIALIZATION_ARCHITECTURE.md](data/knowledge-source/corpus/DOCUMENTS/code_driven_world_materialization_architecture.md).

## Обязательный интерфейс RAG для агентов

Для поиска профильных нормативов Codex, Cursor и другие агенты разработки обязаны сначала использовать read-only CLI `@rus/knowledge-source`:

```bash
npm run knowledge:status
npm run knowledge:query -- --query "формулировка информационной потребности"
npm run knowledge:read -- --document-id <document_id>
```

CLI возвращает JSON с `document_id`, статусом, SHA-256 и диапазонами строк. Результат поиска используется только для навигации: обязательные и профильные документы после обнаружения читаются полностью. Прямой поиск по файлам допустим только после RAG-запроса для проверки связанных реализаций либо когда CLI завершился typed failure. Typed failure, stale RAG, semantic blocker или отсутствующий обязательный документ нельзя обходить похожим файлом, legacy-копией или предположением.

Статусы `proposed` и `deprecated` доступны только по явному запросу:

```bash
npm run knowledge:query -- --query "..." --statuses active,proposed
```

## Порядок работы

1. Определи затронутые подсистемы и прочитай их профильные нормативы.
2. Для любой задачи G0–G4 обязательно прочитай [правила работы с картой](data/knowledge-source/corpus/DOCUMENTS/map_g0_g4_workflow.txt) и актуальный региональный каталог (для Новгорода — [G1_SEMANTIC_CATALOG.md](data/world-catalogs/novgorod/G1_SEMANTIC_CATALOG.md)).
3. При изменении структуры графа, узлов, рёбер, координат, полей, импорта или DDL дополнительно прочитай [архитектуру графа](data/knowledge-source/corpus/DOCUMENTS/read_only_database_and_graph_architecture.md), [актуальный справочник схемы базы](infra/world-base/SCHEMA_REFERENCE.md) и [WORLD_BASE_MATERIALIZATION_TABLE_REQUIREMENTS.md](data/knowledge-source/corpus/DOCUMENTS/world_base_materialization_table_requirements.md).
4. Изучи текущую реализацию, контракты, валидаторы, тесты и точки вызова.
5. Сформулируй границы изменения и критерии готовности.
6. Вноси минимальные целевые изменения без несвязанного рефакторинга.
7. Запусти относящиеся тесты, затем предусмотренные полные проверки.
8. При обязательном аудите повторяй цикл исправлений до `PASS` или допустимого `PASS WITH NOTES`.

+## Оркестрация плановой работы через субагентов

Если задача состоит более чем из одного самостоятельного шага, её выполнение организуется одной главной LLM-оркестратором через специализированных субагентов.

### Главная LLM-оркестратор

Главная LLM является единственным владельцем:

* общего плана работы;
* порядка и зависимостей шагов;
* текущего статуса задачи;
* границ каждого шага;
* решений о повторной работе;
* финальной приёмки результата;
* перехода к следующему шагу;
* единственной рабочей ветки и pull request.

Главная LLM не передаёт управление всем планом субагенту и не позволяет субагенту самостоятельно выбирать следующий шаг.

Перед началом исполнения главный агент формирует план, в котором для каждого шага фиксируются:

1. идентификатор и цель;
2. входные данные;
3. затрагиваемые файлы и подсистемы;
4. обязательные нормативные документы;
5. допустимые и запрещённые действия;
6. ожидаемый результат;
7. критерии готовности;
8. обязательные тесты и проверки;
9. необходимость аудита агентом-критиком;
10. зависимости от других шагов.

### Исполнение одного шага

Каждый шаг передаётся отдельному специализированному субагенту-исполнителю с минимально необходимыми полномочиями и контекстом.

Исполнитель получает только контракт текущего шага:

```text
цель
+ границы изменения
+ разрешённые файлы и инструменты
+ обязательные нормативы
+ входные материалы
+ ожидаемый результат
+ критерии готовности
+ обязательные проверки
+ известные ограничения и замечания
```

Субагент-исполнитель обязан самостоятельно прочитать актуальные обязательные и профильные нормативы. Пересказ нормативов главным агентом не заменяет чтение канонических файлов из GitHub `main`.

Исполнителю запрещено:

* изменять общий план;
* расширять область задачи без разрешения главного агента;
* выполнять следующий шаг;
* изменять несвязанные файлы;
* создавать дополнительный pull request;
* скрывать ошибки и неполные проверки;
* самостоятельно объявлять свою работу принятой;
* выполнять аудит собственной реализации;
* исправлять замечания критика без повторных тестов и повторного аудита.

По завершении шага исполнитель возвращает:

1. описание выполненной работы;
2. список изученных файлов;
3. список изменённых файлов;
4. принятые технические решения;
5. фактически запущенные команды и проверки;
6. результаты тестов;
7. известные ограничения, gaps и противоречия;
8. материалы, необходимые для аудита.

### Независимая критика

После завершения реализации и обязательных автоматических проверок главный агент передаёт результат отдельному субагенту-критику `Аудитор кода Русь XIII век`, если аудит требуется по `code_critic_invocation_rule.txt`.

Исполнитель и критик должны быть разными агентами. Критик не изменяет код и не выполняет роль исполнителя.

Критику передаются:

* исходное требование;
* контракт текущего шага;
* применимые нормативные документы;
* полный список связанных изменений;
* изменённый код;
* связанные контракты, схемы и типы;
* тесты и результаты их фактического запуска;
* логи исправляемой ошибки;
* предыдущие замечания аудита, если это повторная проверка.

Аудит отдельного фрагмента запрещён, если корректность зависит от интеграции с другими изменёнными файлами или модулями.

### Цикл исправления

При результате:

```text
CHANGES REQUIRED
```

или:

```text
REJECT
```

главная LLM:

1. не принимает шаг;
2. не переходит к следующему шагу;
3. передаёт все обязательные замечания исполнителю;
4. контролирует внесение исправлений;
5. требует повторного запуска относящихся тестов и проверок;
6. повторно вызывает критика с предыдущим отчётом и новым результатом.

Цикл продолжается до:

```text
PASS
```

или допустимого:

```text
PASS WITH NOTES
```

Главная LLM не может самостоятельно объявить замечание устранённым и не должна незаметно исправлять результат после аудита. Любое изменение после аудита, влияющее на поведение, контракт или архитектуру, повторно проходит проверки и аудит.

### Финальная приёмка шага

Результат критика не заменяет финальную приёмку главным агентом.

После `PASS` или допустимого `PASS WITH NOTES` главная LLM отдельно проверяет:

1. выполнена ли цель шага;
2. соблюдены ли его границы;
3. выполнены ли все критерии готовности;
4. запущены ли обязательные проверки;
5. соответствует ли результат общему плану;
6. не появились ли незапланированные изменения;
7. обновлены ли документация, реестры и итоговый `README.md`;
8. сохранена ли возможность интеграции результата в единственный pull request.

Только после этой проверки главный агент отмечает шаг завершённым и передаёт следующему исполнителю следующий шаг плана.

### Изменение плана

Только главная LLM может изменить общий план.

Изменение плана допускается при обнаружении:

* нормативного конфликта;
* отсутствующей зависимости;
* data gap или hard block;
* неверно определённых границ;
* новой технически подтверждённой зависимости;
* результата аудита, требующего архитектурного изменения.

Любое изменение плана фиксируется в итоговом `README.md` с причиной, затронутыми шагами и влиянием на порядок интеграции.

Субагент не может молча изменить план или превратить локальное решение в новое архитектурное требование.

### Последовательность и параллельность

Зависимые шаги выполняются строго последовательно:

```text
план
→ исполнитель шага
→ тесты и проверки
→ независимый критик
→ исправления при необходимости
→ повторные тесты
→ повторный аудит
→ финальная приёмка главным агентом
→ следующий шаг
```

Параллельно допускаются только независимые исследовательские или read-only задачи либо изменения непересекающихся файлов, если это заранее указано в плане.

Запрещены:

* параллельное изменение одного файла разными агентами;
* одновременное выполнение зависимых шагов;
* начало следующего шага до приёмки предыдущего;
* создание нескольких конкурирующих реализаций одного решения;
* создание дополнительных веток или pull request без отдельного решения главного агента.

### Итоговое правило

```text
главная LLM держит план и принимает результат;
субагент-исполнитель выполняет только один формально заданный шаг;
отдельный субагент-критик независимо проверяет результат;
непринятый шаг возвращается на исправление;
следующий шаг начинается только после тестов, аудита и финальной приёмки.
```

## Приоритет источников

1. `CODE_DRIVEN_WORLD_MATERIALIZATION_ARCHITECTURE.md` для вопросов материализации и границы кода/LLM.
2. Профильный норматив конкретной подсистемы.
3. `data/knowledge-source/corpus/DOCUMENTS/development_rules.txt`.
4. Актуальная схема и формальные контракты.
5. Навигационные документы.
6. Существующая реализация.
7. Комментарии и примеры.

Существующий код не считается нормативом, если он противоречит документации.

## Главный принцип материализации

```text
код не придумывает категории, исторические факты и отсутствующие варианты,
но материализует конкретные экземпляры из утверждённых категорий,
региональных шаблонов, профилей и правил;
LLM принимает ограниченные смысловые решения через формальный протокол команд.
```

Если отсутствуют approved category/template/profile/rule или допустимый candidate set пуст, этап обязан создать типизированный data gap и выполнить hard block. LLM repair в этом случае запрещён. Repair допускается только для исправления формата, контракта или отклонённого LLM-ответа в пределах неизменённого входа и существующего candidate set. Запрещены ослабление фильтра, смысловые fallback, заглушки, «разумные» значения по умолчанию и автоматическое достраивание отсутствующих фактов.

## Архитектурные требования

- Каждый этап имеет формальный вход, выход, ошибки и явно объявленные зависимости.
- Этап не читает скрытое глобальное состояние и не запускает соседние этапы.
- Оркестратор управляет последовательностью, но не изобретает игровые факты.
- Кодовая материализация использует только approved, version-pinned и применимые к региону/периоду/сезону данные.
- В bounded decision workflow LLM выбирает только один `option_id` и `command_token` из предоставленного конечного option set. Это ограничение не заменяет отдельные нормативные процедуры генерации персонажа игрока, аудита, разрешённой конкретизации key entity и создания прозы.
- `world_base` остаётся read-only для runtime; состояние партии записывается атомарно через утверждённый план.
- Скрытое состояние не попадает в visible context, player-facing прозу, UI или диагностику игрока.

## Изменения и проверки

- Не меняй публичные контракты, последовательность этапов, DDL или формат сохранения без нормативного основания.
- Не изменяй входные объекты; формируй новый результат или change set.
- Добавляй или обновляй тесты для нового поведения, ошибок и границ.
- Не заявляй об успехе без фактически выполненных проверок.
- Не удаляй и не перезаписывай несвязанные пользовательские изменения.

## Итоговый отчёт

Укажи изменённые файлы, реализованные требования, фактически запущенные проверки, результат обязательного аудита и оставшиеся ограничения.
