# ПРИОРИТЕТНАЯ РЕДАКЦИЯ 3 — ИЗОЛИРОВАННЫЙ STAGE 25 И REAL-COMMIT BOUNDARY

Эта редакция имеет приоритет над несовместимыми примерами ниже.

## 0. Архитектурный контракт

Stage 25 — единый обязательный `isolated_code_block`. Он получает только exact `commit_gate_input`, не читает global context, registry, mutable stage outputs, UI или LLM-состояние и возвращает только `stage25_party_start_commit_result`.

Stage 25 не создаёт и не исправляет смыслы мира. Он технически проверяет утверждённый Stage 24 plan, материализует physical plan, выполняет обязательный dry-run, применяет тот же physical plan атомарной транзакцией, проверяет postconditions, читает live-state из party-базы и выполняет postcommit validation.

Provided `commit_gate_result`, `transaction_result`, `postcommit_result`, `party_start_committed`, `party_state_after_commit` и готовый Stage 25 output запрещены во всех окружениях. Для тестов разрешается подменять только infrastructure executors; каждый их результат проходит реальные validators.

## 0.1. Exact input

```text
commit_gate_input:
  version/schema/request_id
  party_creation_context
  stage24_result_approval
  party_db_write_plan
  party_database_schema
  world_base_reference_snapshot
  approved_pipeline_manifest
  commit_policy
```

`party_creation_context` обязательно содержит `party_id`, `player_character_id`, `schema_version`, `idempotency_key` и `payload_hash`. `stage24_result_approval` подтверждает Stage 24 pass, plan/schema/world-base/manifest digests и три handoff permissions.

`commit_policy` неослабляема. Обязательны atomic transaction, dry-run, idempotency, schema/FK/enum/constraint/reference validation, rollback, postconditions, postcommit readback, запрет `world_base` mutation, silent repair, partial commit и player output до полного завершения Stage 25.

## 0.2. Полная последовательность

```text
exact input validation
→ stage25_commit_preflight
→ logical plan digest validation
→ isolated physical schema adapter
→ physical plan digest
→ idempotency gate
→ mandatory dry-run exact physical plan
→ strict dry-run result validation
→ commit_gate_result
→ approved atomic transaction exact physical plan
→ postconditions before COMMIT
→ COMMIT
→ live-state readback
→ party_postcommit_validation
→ stage25_party_start_commit_result
→ Stage 26 approval
```

Пропуск transaction, dry-run или postcommit readback запрещён. Отсутствующий executor означает hard block.

## 0.3. Digest binding

Stage 25 повторно вычисляет и проверяет:

```text
party_db_write_plan_digest
party_database_schema_digest
world_base_reference_digest
approved_pipeline_manifest_digest
logical_plan_digest
physical_plan_digest
dry_run_result_digest
transaction_result_digest
postcommit_state_digest
```

Dry-run и commit обязаны использовать один и тот же immutable physical plan и `physical_plan_digest`. Повторный запуск adapter между dry-run и commit запрещён.

## 0.4. Preflight и technical firewall

`stage25_commit_preflight` проверяет:

- exact input и единый request ID;
- party/player IDs, idempotency key и payload hash;
- Stage 24 approval, permissions и digests;
- структуру approved manifest и полноту audit chain;
- актуальный immutable party DB schema snapshot;
- таблицы, колонки, operations, data types, not-null, enum, unique, check и FK constraints;
- source/candidate/graph/G5/NPC/item/container/property/route references;
- current position и player character bindings;
- character knowledge projection hash, counts и record keys;
- hidden/public boundary и запрет `world_base` writes;
- полный batch graph, dependencies, write order, rollback и postconditions;
- наличие idempotency, dry-run, transaction и postcommit executors.

Код не выбирает замену для битой ссылки, не создаёт missing record и не удаляет конфликтующую запись.

## 0.5. Dry-run contract

Dry-run выполняется транзакционно и всегда заканчивается `ROLLBACK`. Его output:

```text
party_write_plan_dry_run_result:
  version/schema/request_id
  physical_write_plan_digest
  pass
  checks
  simulated_batches
  batch_results/row_counts
  constraint_checks
  postcondition_checks
  rollback_completed
  concerns/evidence
```

`pass=false`, неверная schema, digest mismatch, отсутствующий check, пустое evidence или `rollback_completed=false` блокируют commit. Отсутствие exception не считается успехом.

## 0.6. Idempotency

До dry-run Stage 25 проверяет `idempotency_key + payload_hash + party_id`:

```text
new key → continue
same key + same hash + committed → return validated prior committed result
same key + same hash + in_progress → block concurrent run
same key + different hash → hard block
active party with incompatible key/payload → hard block
```

`ON CONFLICT DO NOTHING` не заменяет idempotency validation. Любой zero-row insert/update/upsert анализируется и не считается автоматическим успехом.

## 0.7. Atomic transaction

Transaction executor принимает только `approved_party_transaction_input`, содержащий успешный commit-gate approval и exact physical plan digest. Голый write plan не исполняется.

Порядок:

```text
BEGIN
→ validate exact approved physical plan
→ execute every batch once in validated dependency order
→ validate rowCount and returned IDs
→ execute postconditions
→ final ready batch last
→ COMMIT
```

При любой ошибке до COMMIT выполняется `ROLLBACK`; partial commit запрещён. Postconditions обязательны и выполняются до COMMIT.

## 0.8. Postcommit readback

После COMMIT Stage 25 читает live-state из party-базы по `party_id` и `transaction_id`. Committed state запрещено выводить из write plan или pipeline context.

`party_postcommit_validation` проверяет как минимум:

- party state ready и player output allowed;
- current position, clock и player character;
- anchors/routes/NPC/items/containers against plan;
- current knowledge map, hash и counts;
- visible context и narrator prose digests;
- audit snapshots и source trace;
- hidden/public boundary;
- committed idempotency record.

Postcommit failure возвращает `commit_status=commit_error`, блокирует player output и требует manual recovery; фиктивный `party_start_committed` не создаётся.

## 0.9. Result bundle

Успешный Stage 25 возвращает immutable:

```text
stage25_party_start_commit_result:
  version/schema/request_id/pass=true
  commit_status=committed
  party_id/transaction_id/idempotency_key/payload_hash
  logical/physical/dry-run/transaction/postcommit digests
  commit_preflight
  physical_plan_mapping_report
  dry_run_result
  commit_gate_result
  transaction_result
  postcommit_state
  postcommit_validation
  party_start_committed
  party_public_state
  handoff_permission
```

Failure возвращается тем же schema с `pass=false`, `failed_phase`, `commit_status`, concerns/evidence, rollback status, blocked player output и repair route. Обычный exception не является нормативным Stage 25 output.

## 0.10. Stage 25 → 26

Stage 26 разрешён только при:

```text
Stage 25 result pass=true
commit_status=committed
transaction_result.commit_status=committed
postcommit_validation.pass=true
party_state ready
current position present
player output reference present
all digests current
can_start_stage_26=true
can_show_player_output=true
can_accept_player_input=true
```

`commit_gate_result.pass=true` сам по себе не означает, что партия committed, и не разрешает Stage 26.

# ПРИОРИТЕТНАЯ РЕДАКЦИЯ 2 — STRICT STAGE 24 → STAGE 25 HANDOFF

Эта редакция имеет приоритет над несовместимыми примерами ниже.

## 0. Архитектурный контракт

Stage 25 — code-only commit gate и atomic transaction executor. Он не строит, не исправляет и не переосмысливает Stage 24 plan.

Stage 25 принимает только утверждённый digest-bound Stage 24 result bundle через exact `commit_gate_input`:

```text
request_id
party_creation_context
stage24_result_approval
party_db_write_plan
party_database_schema
world_base_reference_snapshot
approved_pipeline_manifest
commit_policy
```

`stage24_result_approval` обязан подтверждать:

```text
Stage 24 pass=true
party_db_write_plan_digest
party_database_schema_digest
world_base_reference_digest
approved_pipeline_manifest_digest
can_send_to_commit_gate=true
can_execute_transaction=true
can_write_party_snapshots=true
```

## 0.1. Обязательный повторный gate

До dry-run Stage 25 повторно проверяет:

- schema/version/request ID approval и plan;
- Stage 24 permissions;
- SHA-256 digest текущего plan;
- digest и полноту party database schema;
- digest и полноту world-base reference snapshot;
- digest approved pipeline manifest;
- atomic/idempotent transaction contract;
- запрет `world_base` mutation;
- adapter safety и hidden/public boundary;
- наличие dry-run callback.

Несовпадение любого digest означает stale/substituted handoff и блокирует commit.

## 0.2. Dry-run и transaction

Порядок Stage 25:

```text
strict handoff validation
→ physical schema adapter validation
→ mandatory dry-run
→ commit_gate_result.pass=true
→ atomic transaction
→ postconditions
→ party ready
```

При ошибке:

```text
commit_gate_result.pass=false
repair_route.return_to_stage=24
никакой live write
никакой player-visible output
никакой partial commit
```

Stage 25 не создаёт missing FK, не заменяет IDs, не удаляет проблемные records и не исправляет plan. Любая смысловая проблема возвращается в Stage 24 или соответствующий upstream repair route.

# Этап 25. Commit gate

## 1. Назначение этапа

Commit gate — это финальный технический шлюз перед записью стартовой партии в `party`-базу.

На этом этапе код проверяет:

* схемы;
* enum;
* обязательные поля;
* foreign keys;
* source IDs;
* candidate IDs;
* graph node IDs;
* G5 anchor IDs;
* NPC IDs;
* item/container IDs;
* property rule IDs;
* route/edge IDs;
* audit pass flags;
* idempotency;
* запрет записи в `world_base`;
* запрет скрытых данных в player-visible таблицах;
* порядок транзакции;
* возможность rollback.

Только после этого код выполняет атомарную запись стартовой партии.

Короткая формула:

```text id="zwrn84"
party_db_write_plan
+ all_approved_pipeline_outputs
+ party_database_schema
+ FK/index/schema/enum/source/candidate validation
→ commit_gate_result
→ atomic transaction
→ party_start_committed
```

Главный вопрос этапа:

```text id="3q2l7x"
Можно ли безопасно и атомарно записать старт партии в party-базу без новых фактов, битых ссылок, скрытых утечек и противоречий?
```

## 2. Главное правило этапа

Commit gate выполняется кодом.

Код не исправляет смысловые ошибки.
Код не создаёт недостающие сущности.
Код не заменяет отсутствующий ID заглушкой.
Код не выбирает альтернативного NPC, предмет, route или anchor.
Код не меняет narrator prose.
Код не меняет hidden state.
Код не меняет visible context.
Код не меняет write plan по смыслу.

Если проверка провалена, commit блокируется.

Допустимые действия кода при ошибке:

```text id="rvpwlb"
зафиксировать validation issue;
сформировать machine-readable error report;
вернуть pipeline на repair route;
не писать live-state;
не отправлять player-visible output;
не ставить party_state.status=ready.
```

Недопустимые действия:

```text id="tvpekl"
создать missing FK;
заменить candidate_id ближайшим похожим;
переписать enum;
удалить проблемный item/NPC молча;
исправить time/light/position молча;
записать частичную партию;
показать игроку narrator prose до commit;
пометить party ready при ошибке.
```

## 4. Что входит в Commit gate

Commit gate состоит из пяти фаз:

```text id="c1fub2"
1. Preflight validation.
2. Schema/enum validation.
3. Referential integrity validation.
4. Write plan safety validation.
5. Dry-run transaction validation.
```

Только после этого возможен:

```text id="tmzl4u"
6. Atomic commit.
```

## 7. Phase 1: Preflight validation

Preflight проверяет, что commit вообще можно запускать.

Проверяются:

```text id="6hjj66"
commit_gate_input.schema;
commit_gate_input.version;
party_id;
player_character_id;
idempotency_key;
payload_hash;
party_db_write_plan exists;
party_db_write_plan_audit.pass=true;
all required approved_pipeline_outputs exist;
party_database_schema exists;
world_base_reference_snapshot exists;
commit_policy exists.
```

Hard block:

```text id="b1o7yp"
нет party_db_write_plan;
нет party_db_write_plan_audit;
любой обязательный upstream audit pass=false;
party_id пустой;
idempotency_key пустой;
party_database_schema отсутствует.
```

Error codes:

```text id="7fpzus"
COMMIT_GATE_INPUT_SCHEMA_INVALID
```

Код валидирует каждый объект against JSON Schema.

Правила:

```text id="7paz15"

типы должны совпадать;
null разрешён только там, где schema допускает null;
array не должен заменяться строкой;
object не должен заменяться свободным текстом;
date/time должны иметь разрешённый формат;
```

## 28. Роль LLM на этапе

Основной Commit gate — code-only.

LLM не должна решать, прошёл ли commit.
LLM не должна override-ить FK, schema, enum, source ID или candidate ID checks.
LLM не должна “объяснять”, почему битая ссылка допустима.
LLM не должна создавать missing ID.

Опционально LLM можно использовать только после провала code gate:

```text id="5g7ial"
для human-readable diagnostics;
```

## 32. Validation rules для commit_gate_result

Код обязан проверить собственный результат gate:

1. `schema === "commit_gate_result"`.
2. `version === 1`.
3. `pass` boolean.
4. Если `pass=true`, all checks pass.
5. Если `pass=false`, concerns не пустой.
6. Если `pass=false`, evidence не пустой.
7. Если `pass=false`, repair_route заполнен.
8. Если `pass=false`, transaction_permission all false.
9. Если `pass=true`, transaction_permission.can_execute_atomic_commit=true.
10. `commit_execution_plan.transaction_id` заполнен при pass=true.
11. `commit_execution_plan.write_order` совпадает с audited write plan.
12. `evidence` не пустой.
13. Нет LLM-generated override.
14. Нет silent repair marker.
15. Нет player-visible output в gate result.
