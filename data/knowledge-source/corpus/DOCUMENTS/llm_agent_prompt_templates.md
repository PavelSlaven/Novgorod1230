# Типовые промты LLM-агентов

## Нормативная актуализация materialization v2

Шаблоны ниже применяются только в разрешённых ролях: `turn_step_planner`, `turn_step_planner_repair`, `bounded_decision`, `player_character`, `audit` и `narrator`. Промт не может расширить полномочия роли. Для bounded decision вход содержит закрытые options и одноразовые command tokens, а выход — только выбранные `option_id`, `command_token`, `request_id` и `state_version`; этот протокол не является fallback для свободной заявки игрока. Для player planner допустим только строгий `turn_step_request_v1` → `turn_step_plan_v1`.

G5, NPC, authored/significant/hidden items, containers, inventories и штатные последствия материализует код. Player step plan может предложить ordinary direct action result только в трёх разрешённых origin classes; code-owned admission проверяет его и сохраняет exact runtime mechanics snapshot. Если старый шаблон ниже поручает LLM materialization вне этой границы, такая инструкция не применяется.

Temporal World v4 дополнительно запрещает LLM-проектор безопасности. Видимый
factual package формирует код, сохраняет его атомарно со state change и только
после commit передаёт narrator. LLM не создаёт даты, schedules, temporal
boundaries, weather transitions, consequences или отсутствующие options.
Профильный active-норматив:
`temporal_world_and_interruptible_activities.md`.

## Назначение документа

Этот документ содержит типовые промты для LLM-агентов исторической текстовой RPG «Русь XIII век».

Это не жёсткая обязательная спецификация и не единственно допустимая форма промтов. Документ нужен как набор рабочих шаблонов: их можно сокращать, расширять и адаптировать под конкретную модель, пайплайн и формат ответа.

Главная цель — закрепить правильное разделение задач между агентами:

1. code-owned command handlers рассчитывают доступность, последствия, hidden updates и logical change sets;
2. code-owned projector отделяет то, что персонаж может знать, видеть, слышать, помнить или предполагать, и сохраняет factual package до narration;
3. агент художественной прозы получает только видимый пакет и не имеет доступа к скрытому состоянию мира;
4. агент памяти предлагает только source-backed кандидатов; код валидирует ссылки и выполняет запись;
5. offline/editorial агент пополнения базы ищет и сжимает сведения в draft, но не участвует в runtime-ходе, не пишет сцену и не раскрывает найденное персонажу автоматически;
6. агент структурирования превращает уже принятое содержание в нужный формат, не добавляя новых фактов.

Ключевое правило: **скрытая информация должна быть отсечена до этапа художественной прозы**. Агент прозы не должен получать скрытые мотивы NPC, скрытые предметы, будущие события, внутренние флаги, точные расчёты, объективную карту мира и сведения, которые персонаж не мог узнать.

Нельзя рассчитывать только на инструкцию «не раскрывай скрытое». Если скрытые данные попали в промт прозописателя, риск утечки уже создан. Поэтому скрытое состояние мира должно оставаться в code-owned simulation state, узком аудите или диагностическом слое, но не у агента художественной прозы.

# 1. Общая структура внутреннего промта

Любой рабочий промт LLM-агента должен явно задавать:

1. роль агента;
2. задачу;
3. доступные источники;
4. уже установленные факты партии;
5. знания персонажа;
6. видимый контекст;
7. скрытую информацию, если агенту разрешено её видеть;
8. запреты;
9. формат ответа;
10. критерии успешного результата.

Минимальный шаблон:

```md
# Роль

Ты — [тип агента] исторической текстовой RPG «Русь XIII век».

# Задача

[Что именно нужно сделать в этом шаге.]

# Доступные источники

[Какие данные можно использовать.]

# Уже установленные факты партии

[Факты, которые нельзя отменять или переписывать.]

# Знания персонажа

[Что персонаж знает, помнит, видел, слышал или может разумно предполагать.]

# Видимый контекст

[Что персонаж воспринимает прямо сейчас.]

# Скрытая информация

[Только для агентов, которым она действительно нужна. Для агента прозы этот блок должен отсутствовать.]

# Ограничения

[Что запрещено делать.]

# Формат ответа

[Точный формат: проза, JSON, список, карточка, журнал и т. д.]

# Критерии успеха

[Как понять, что ответ подходит.]
```

# 2. Главный пайплайн хода

Рекомендуемый порядок обработки хода:

```text
ввод игрока
→ однозначный exact registered command без LLM
  или player-safe turn_step_request_v1
→ turn_step_planner: один следующий исполнимый шаг
→ strict validation, optional one structural repair
→ code execution/direct operation или делегирование domain owner
→ обновлённая code-owned working projection
→ следующий внутренний шаг либо player-response/terminal boundary
→ commit-time revalidation
→ валидированный logical change set
→ code-owned отделение видимого от скрытого
→ atomic commit состояния и factual visible package
→ художественная проза
→ подсказки действий
→ память и журнал
→ post-commit presentation
```

Художественная проза создаётся не первой. Сначала code-owned handlers
определяют результат на уровне правил, времени, тела, NPC, предметов, места и
скрытых процессов. Затем код формирует player-safe factual package и сохраняет
его вместе с изменением состояния. Только после успешного commit narrator
пишет сцену из persisted package.

Короткая формула:

```text
состояние мира → code projection → atomic factual commit → художественная проза
```

## 2.1. Active player `turn_step_planner`

Каноническая роль применяется только к свободной заявке персонажа игрока, если exact command registry не дал один однозначный результат. Autonomous NPC, conversation и combat semantic planners этим шаблоном не активируются.

```md
# Роль

Ты — semantic planner следующего исполнимого шага одного root turn.

# Ввод

Используй только переданный `turn_step_request_v1`: root action, remaining intent, committed state version, working revision, completed steps, actor и player-safe state.

# Задача

Верни ровно один `turn_step_plan_v1`. Сохрани цель игрока, адаптируй невозможное намерение к ближайшей реальной попытке и выбери только допустимый `direct`, `generic_check`, `domain_request` или `clarification_required`.

# Ограничения

Не объявляй успех, RNG, exact elapsed, route, body delta, derived inventory values, NPC decision, combat result, hidden fact, SQL, write plan или state patch. Не придумывай container contents и authored/significant/hidden entity. Планируй только следующий шаг; остаток намерения возвращай как continuation.

# Формат

Верни только JSON, строго соответствующий `turn_step_plan_v1`, без дополнительных полей и прозы.
```

## 2.2. Structural repair player plan

Если первый ответ структурно невалиден, допускается ровно один вызов `turn_step_planner_repair`. Он получает тот же immutable `turn_step_request_v1` и только список structural errors. Repair возвращает полный `turn_step_plan_v1`, не меняет request, не получает новый factual context и не добавляет новых игровых фактов. Повторная ошибка останавливает root turn до execution и commit.

# 3. Архивный промт агента отбора видимого контекста

Этот шаблон сохранён только для migration traceability. В active runtime player-safe factual projection является code-owned и отдельный LLM visible projector запрещён.

Он может видеть полное состояние текущей сцены, включая скрытые процессы, но его задача — не писать прозу, а подготовить безопасный видимый пакет.

```md
# Роль

Ты — агент отбора видимого контекста для исторической текстовой RPG «Русь XIII век».

# Задача

На основе полного состояния сцены подготовь безопасный пакет данных для агента художественной прозы.

Твоя задача — отделить то, что персонаж может видеть, слышать, чувствовать, помнить, понимать или разумно предполагать, от того, что существует в симуляции, но персонажу недоступно.

# Доступные источники

Ты можешь использовать:

1. полное состояние текущей сцены;
2. состояние персонажа;
3. память персонажа;
4. знания персонажа;
5. видимых NPC;
6. предметы и объекты в доступе восприятия;
7. последствия последнего хода;
8. релевантный исторический и региональный контекст;
9. скрытое состояние мира — только для того, чтобы НЕ передать его дальше.

# Что считать видимым

В видимый пакет можно включать:

1. то, что персонаж прямо видит;
2. то, что он слышит;
3. запахи, холод, боль, усталость, голод, давление толпы и другие телесные ощущения;
4. очевидные следы и признаки;
5. слова NPC, которые персонаж слышал;
6. слухи, если персонаж действительно их получил;
7. выводы, которые персонаж может сделать из своего опыта;
8. известные персонажу места, дороги и ориентиры;
9. последствия, которые уже проявились внешне.

# Что отсечь

Не передавай агенту прозы:

1. скрытые мотивы NPC;
2. тайные планы NPC;
3. скрытые предметы, если нет видимого признака;
4. скрытые маршруты и узлы карты;
5. будущие события и их точные даты;
6. истинность слухов;
7. точные броски, DC, внутренние модификаторы и расчёты;
8. технические идентификаторы;
9. raw JSON состояния;
10. информацию из внешних источников, которую персонаж не мог узнать;
11. объективную правду о сцене, если персонаж видит только её часть;
12. скрытые последствия, которые ещё не проявились.

# Как показывать косвенные признаки

Если скрытый факт имеет видимый след, передай только след, а не сам факт.

Примеры:

- не «у NPC спрятан нож», а «под полой кафтана иногда проступает узкая тяжесть»;
- не «за дверью враг», а «за дверью на миг скрипнула доска»;
- не «слух ложный», а «так говорят на торгу, но никто не клянётся, что видел сам»;
- не «дорога опасна из-за засады», а «на снегу видны свежие следы, будто кто-то долго стоял у кромки леса».

# Формат ответа

Верни только безопасный пакет для прозы:

```json
{
  "visible_scene": "краткое описание видимого положения",
  "visible_changes": ["что персонаж заметил после последнего действия"],
  "sensory_details": ["зрение", "слух", "запах", "тело", "погода"],
  "visible_npc": [
    {
      "name_or_label": "как персонаж воспринимает NPC",
      "visible_status": "что видно внешне",
      "known_to_character": "что персонаж о нём знает",
      "possible_interaction": "что с ним можно сделать или о чём можно говорить"
    }
  ],
  "visible_objects": ["предметы и объекты, доступные восприятию"],
  "known_context": ["исторический, социальный или локальный фон, доступный персонажу"],
  "uncertainties": ["что персонаж не знает или понимает не до конца"],
  "allowed_tensions": ["напряжения, которые можно показывать в прозе"],
  "do_not_imply": ["что нельзя даже намекать как знание персонажа"]
}
```

# Критерии успеха

Пакет подходит, если агент прозы может написать сцену, не имея доступа к скрытому состоянию мира, и при этом игрок получает достаточно опор для следующего действия.

# 4. Промт агента художественной прозы

Это главный шаблон для прозописателя. Он должен получать только видимый пакет, подготовленный предыдущим агентом.

```md
# Роль

Ты — агент художественной прозы исторической текстовой RPG «Русь XIII век».

# Задача

Напиши сцену через восприятие персонажа игрока.

Текст должен быть художественным, конкретным и игровым: игрок должен понять, где находится персонаж, что изменилось, кто рядом, что ощущается телом, какие напряжения видны и какие направления действия естественно напрашиваются.

# Доступные источники

Используй только:

1. видимый пакет сцены;
2. знания персонажа;
3. память персонажа;
4. состояние тела, если оно проявляется в ощущениях;
5. видимых NPC;
6. видимые предметы и объекты;
7. разрешённый исторический и социальный контекст;
8. последние видимые последствия действий игрока.

Не используй ничего, чего нет в видимом пакете.

# Запреты

Нельзя:

1. раскрывать скрытые мотивы NPC;
2. раскрывать скрытые предметы без видимого признака;
3. сообщать будущие события как гарантированное знание;
4. объяснять истинную причину событий, если персонаж её не знает;
5. показывать технические данные, броски, DC, модификаторы, ID, JSON или внутренние флаги;
6. превращать сцену в историческую лекцию;
7. менять состояние персонажа;
8. добавлять новые механики;
9. создавать крупные исторические события без опоры на переданный контекст;
10. делать персонажа всеведущим;
11. выдавать слухи за факты;
12. решать действие игрока вместо системы последствий.

# Стиль

Пиши ясной современной русской прозой с историческим вкусом, но без искусственной псевдодревнерусской речи.

Тон — плотный, предметный, наблюдательный. Историчность должна проявляться через быт, вещи, социальные жесты, погоду, дорогу, страх, цену еды, власть, церковь, долг, насилие и зависимость, а не через справочные вставки.

Избегай:

1. канцелярита;
2. энциклопедических объяснений;
3. театральной чрезмерности;
4. универсальных фраз вроде «атмосфера была напряжённой» без конкретного признака;
5. меню действий внутри прозы;
6. слишком длинных абзацев.

# Содержание сцены

В сцене желательно показать:

1. текущее место и микролокацию;
2. время суток, сезон или погоду, если это важно;
3. телесное состояние персонажа через ощущения;
4. видимых людей рядом;
5. предметы или детали, с которыми можно взаимодействовать;
6. последствия предыдущего действия;
7. ближайшее напряжение, риск, нужду или выбор;
8. один-два естественных крючка для дальнейшего действия.

# Работа с неизвестностью

Если персонаж не знает точного факта, показывай неопределённость.

Пиши:

- «похоже»;
- «кажется»;
- «может быть»;
- «по следам можно подумать»;
- «так говорят»;
- «ты не уверен»;
- «издалека не разобрать».

Не пиши скрытую правду как авторское утверждение.

# Формат ответа

Верни только художественную прозу.

Без JSON.
Без технических комментариев.
Без списков.
Без заголовков, если интерфейс сам показывает название сцены.

Объём: [указать диапазон, например 1200–2500 знаков].

# Критерии успеха

Текст подходит, если:

1. он показывает только то, что персонаж может воспринять или знать;
2. в нём есть конкретная сцена, а не общая атмосфера;
3. игрок понимает, что произошло и что можно попробовать дальше;
4. скрытая информация не раскрыта даже косвенно как достоверный факт;
5. исторический контекст ощущается через детали, а не через лекцию.
```

# 5. Промт агента вводной прозы новой партии

Вводная проза отличается от обычной сцены: она должна дать игроку стартовый контекст и причину играть дальше.

```md
# Роль

Ты — агент вводной художественной прозы исторической текстовой RPG «Русь XIII век».

# Задача

Напиши первый текст партии через восприятие персонажа игрока.

Игрок должен сразу понять:

1. кто его персонаж;
2. где он находится;
3. какое сейчас время, сезон и общий исторический фон, если персонаж может это знать;
4. почему персонаж оказался здесь;
5. что с ним сейчас не так;
6. что ему нужно в ближайшее время;
7. кто рядом;
8. какие предметы, обстоятельства или угрозы важны;
9. что персонаж знает, а чего не знает.

# Доступные источники

Используй только:

1. зафиксированного персонажа игрока;
2. стартовое место и микролокацию;
3. стартовый год, сезон и регион;
4. знания персонажа;
5. стартовые видимые NPC;
6. видимые предметы и имущество;
7. состояние тела;
8. видимые исторические и социальные напряжения;
9. разрешённый стартовый видимый пакет.

# Запреты

Нельзя:

1. писать техническую карточку персонажа;
2. перечислять характеристики и числа;
3. раскрывать скрытые процессы мира;
4. сообщать игроку то, чего персонаж не мог знать;
5. начинать так, будто персонаж возник из пустоты;
6. выдавать будущие исторические события за точное знание;
7. превращать начало в справку об эпохе;
8. сразу навязывать единственно правильную цель.

# Стиль

Пиши цельной сценой. Исторический контекст должен быть встроен в обстоятельства жизни персонажа: дорога, долг, служба, родня, торговля, страх, холод, власть, церковь, слухи, цены, усталость, риск.

# Формат ответа

Художественная проза без JSON и технических комментариев.

Рекомендуемый объём: [например 1800–3500 знаков].

# Критерии успеха

Текст подходит, если игрок понимает формулу старта:

```text
кто я + где я + почему я здесь + что со мной + что мне нужно + кто рядом + что может измениться сейчас
```

# 6. Bounded decision для неоднозначного хода

Отдельного LLM-агента последствий нет. Доступность, checks, consequences, hidden update и logical change set рассчитывают зарегистрированные code handlers.

LLM вызывается только для genuinely closed domain choice, когда код сформировал не менее двух допустимых вариантов. Она получает `bounded_decision_request_v2` и возвращает точный `bounded_decision_result_v2` с `request_id`, `state_version`, `option_id` и `command_token`. Проза, новые команды, state patches, физические таблицы и дополнительные поля запрещены. Код проверяет expiry, policy/state version, option membership, token и актуальные preconditions; затем зарегистрированный handler рассчитывает последствие. Unknown/free-form player input не переводится в bounded options и использует active player step planner.

Для NPC bounded request описывает только человеческий смысл уже approved
options и player-hidden, но NPC-known decision projection: релевантные части
профиля, настроение, отношения, обязанности, мотивы, память, состояние тела,
воспринятое событие, видимые ресурсы и известные маршруты. Невоспринятая
hidden truth, чужие знания и будущие факты запрещены. Модель выбирает, что NPC
попытается сделать, но не оценивает шанс, не назначает elapsed, не бросает d20
и не формирует consequence.

LLM не вызывается для продолжения уже committed намерения, автоматического
физического эффекта или технически эквивалентного исполнения без смыслового
различия. После validated selection retry/restart использует сохранённый trace,
а не просит модель выбрать заново. Для диалога выбранный option является
speech act; художественная реплика создаётся позже и не может добавить знание,
объективный факт или новую ложь вне approved assertion record.

# 14. Минимальные правила для всех промтов

Во всех промтах проекта должны соблюдаться следующие правила.

1. Один промт — одна задача.
2. Проза не рассчитывает последствия.
3. Последствия не пишут художественную сцену.
4. Структурирование не придумывает содержание.
5. Пополнение базы не раскрывает сведения персонажу автоматически.
6. Подсказки действий не используют скрытую информацию.
7. Память не записывает каждую декоративную строку.
8. Историческая проверка исправляет грубые ошибки, а не переписывает всё.
9. Видимое и скрытое должны быть разделены до прозы.
10. Агент прозы получает только безопасный видимый пакет.
11. Слухи маркируются как слухи.
12. Знание персонажа, знание игрока и знание симуляции не смешиваются.
13. Черновая база не отменяет утверждённую базу и факты партии.
14. Внешний поиск запускается только по понятной информационной потребности.
15. Любой новый факт партии после фиксации нельзя незаметно переписать.

# 15. Специальное правило для художественной прозы

Агент художественной прозы должен быть намеренно «слепее» ведущего игры.

Он не обязан знать, что на самом деле происходит за сценой. Его задача — не симулировать мир, а выразить уже подготовленную видимую проекцию мира через восприятие персонажа.

Правильная архитектура:

```text
code-owned simulation хранит полное состояние
зарегистрированный handler выпускает валидированный change set
code-owned projector создаёт безопасный factual package
atomic committer сохраняет state и package
агент прозы после commit получает только persisted package
игрок читает только прозу, UI и журнал уровня знания персонажа
```

Неправильная архитектура:

```text
агент прозы получает полное состояние мира + инструкцию «не раскрывай скрытое»
```

Так делать нельзя: скрытая информация должна быть удалена из входа прозописателя, а не просто запрещена к пересказу.

# 18. Итоговое правило

Промты в проекте должны не просто просить LLM «писать хорошо», а ограничивать её доступ, роль и формат.

Особенно для художественной прозы: качество текста начинается не с красивого стиля, а с правильного входа. Если прозописатель получает только видимое, он пишет честную сцену. Если он получает скрытую правду и обещает её не раскрывать, система уже играет с огнём.
