# Время и точные временные срезы

## Статус и граница миграции

Это target-норматив materialization v3. До P28 active production использует materialization v2; target-текст не разрешает partial activation, dual write или fallback. После активации authoritative game clock имеет exact rational sub-minute precision.

Полный active target amendment Temporal World v4 находится в
`temporal_world_and_interruptible_activities.md`. Этот документ маршрутизирует
target-разработку к `temporal-world-v1` / `4.3.0-target.1`, не активируя
production runtime. `GameTimestamp` хранится как canonical
decimal strings, arithmetic выполняется через `BigInt`, а calendar/daylight —
только version-pinned projection, не второй clock.

## 1. Единственная арифметика времени

`game_timestamp` хранит reduced positive rational sub-minute component. Whole minute — производная граница событий, а не authoritative clock. Каждая time-bearing операция фиксирует exact elapsed rational, world time before/after и clock commit mode.

```text
world_time_after = world_time_before + actual_exact_elapsed
crossed_whole_minute_boundaries = whole_minute_index(after) - whole_minute_index(before)
```

Сложение ассоциативно: разбиение действия на произвольные technical slices даёт тот же final timestamp и total crossed boundaries. Запрещены terminal ceil, minimum minute per step, private rounding carry и authoritative округление.

## 2. Владение часами

`direct_party_clock` обновляет party clock ровно один раз в committed time-bearing result. `shared_root_transport_clock` сохраняет local exact elapsed, но имеет `crossed_whole_minute_boundaries=0`; clock обновляет только root transport interval. Idempotent retry не может продвинуть часы повторно.

Time-bearing result передаёт time system exact elapsed, crossed boundaries, action/segment digest, intensity, factual context и change-set refs. Body, NPC, weather, places, events и timers обновляются ровно один раз на этом boundary; они не пересчитывают terrain или duration.

## 3. Dynamic duration

Authoritative duration для traversal определена только в `formulas.md`; этот документ не дублирует формулу. Все factors/delays положительны, versioned и pinned. Dynamic snapshot захватывается на interval start: timestamp, weather/light/environment, portal/access, carrier/body/load/pace, resolved factors/delays и digest. Будущие conditions не замораживаются route plan.

Каждая additive delay имеет `application_scope` и stable `occurrence_key`. Одна occurrence commit-ится максимум раз; `segment_once` и `step_once` не повторяются в slice, `interval_once` создаётся точным interval recheck. Missing/duplicate identity — `time_delay_occurrence_invalid` hard rejection.

## 4. Activity и traversal

`immediate_action` не двигает time. `timed_activity` и `timed_traversal` хранят exact cumulative/remaining values и append-only attempts/results. Positive sub-minute elapsed двигает exact time даже если crossed whole-minute boundaries равно 0. `blocked_before_progress` имеет zero traversal elapsed; explicit pause/interruption/strand может иметь zero или positive exact elapsed только по committed control outcome.

## 5. Синхронизированный carrier-local slice

При active root transport traversal orchestrator создаёт один atomic slice:

```text
one root interval + zero-or-more carrier-local timed results
→ one shared exact clock update → one change set
```

Root transport — clock owner. Slice заканчивается на earliest root recheck/segment boundary, local completion или explicit synchronized boundary. Все local participants получают то же exact elapsed, capped своим remaining duration. При zero root elapsed local normal result не создаётся; local zero-time допустим только для explicit blocked/paused/failed control outcome. Local outcome не меняет root progress без explicit pinned carrier effect. Independent asynchronous clock advancement запрещено.

## 6. Таймеры и последствия

Exact-timestamp timer сравнивается с exact timestamp; minute-indexed event запускается только на crossed boundary. Every committed time change имеет append-only change set, idempotency record и causal trace. Нет скрытого продвижения часов при смене G-level, endpoint binding, topology resolution, preparation или UI operation.

## 7. Traceability

Target источник: `spatial_architecture_standard_g0_g6.md` §11.2–§11.10. До P28 v2 остаётся active runtime boundary; этот документ — target contract, не заявление о готовой persistence/runtime реализации.

## Время в игре

Время показывает, когда происходит сцена и сколько прошло после действий игрока.

Время нужно для пяти вещей:

1. менять день и часть суток;
2. двигать погоду;
3. обновлять состояние тела;
4. продвигать действия NPC;
5. запускать последствия, которые зависят от ожидания, дороги, сна, работы или событий.

### 1. Уровни времени

В игре используются два уровня времени:

`день + точное время внутри дня`

День отвечает за общий исторический и календарный фон.
Время внутри дня отвечает за текущую сцену: утро, день, вечер, ночь, свет, усталость, доступность NPC, работу мест, дорогу и ожидание.

Короткая формула:

`текущее время = день + время суток`

### 2. Когда время движется

Время проходит после любого действия, которое не мгновенное.

Примеры:

| Действие                                       | Примерное время |
| ---------------------------------------------- | --------------: |
| быстро осмотреться, сказать фразу              |      0–1 минута |
| поговорить, осмотреть предмет, подойти         |       1–5 минут |
| обыскать комнату, спорить, вскрывать, ждать    |      5–30 минут |
| пройти по месту, работать, лечить, торговаться |    30–120 минут |
| спать, ехать, идти между местами               |     часы / день |

Если действие не требует времени, время не меняется.

### 3. Простая формула времени хода

`новое время = старое время + длительность действия`

Длительность выбирается по смыслу действия.
Точность до минуты нужна только в напряжённых сценах: бой, погоня, стража, скрытность, пожар, болезнь, ожидание события.

В обычной сцене достаточно крупных шагов:

`мгновение → несколько минут → полчаса → час → часть суток → день`

### 4. Что пересчитывается после времени

После значимого хода проверяется:

`погода + состояние тела + NPC + место + события`

Минимальная цепочка:

`прошло время → обновить состояния → обновить NPC → проверить события → собрать новую видимую сцену`

### 5. Влияние на состояние тела

Если прошло значимое время, тело может ухудшиться или восстановиться.

Формула:

`новое состояние = старое состояние + восстановление − расход − вред`

Время влияет на состояния только при причине:

| Причина                        | Что меняется                |
| ------------------------------ | --------------------------- |
| долго не ел                    | Сытость падает              |
| долго не пил                   | появляется жажда как активное состояние; при опасном продолжении возможен вред Здоровью |
| долго шёл, работал, не спал    | Бодрость падает             |
| холод, ночь, дождь, ветер      | холод или промокание фиксируются как активные состояния; при опасной среде возможен вред Здоровью |
| сон, еда, вода, отдых, лечение | состояние восстанавливается |
| болезнь, рана, мороз, жара     | возможен вред               |

Если причина не затрагивает состояние, оно не меняется.

### 6. Влияние на NPC

NPC не стоят на месте, пока игрок действует.

После значимого времени NPC могут:

1. продолжить текущее дело;
2. завершить текущее дело;
3. перейти к следующему делу;
4. уйти;
5. прийти;
6. заметить следы или шум;
7. позвать других;
8. изменить отношение;
9. распространить слух;
10. стать недоступными.

Простая формула:

`состояние NPC = прежнее состояние + прошедшее время + событие сцены`

### 7. Влияние на место

Место тоже меняется со временем.

После ожидания, сна, путешествия или возвращения нужно проверить:

1. погоду;
2. свет и время суток;
3. доступность ворот, рынка, переправы, ночлега;
4. движение NPC;
5. слухи;
6. следы;
7. опасность;
8. последствия прежних действий игрока.

Формула:

`состояние места = прежнее состояние + прошедшее время + погода + действия NPC + последствия`

Если игрок вернулся в уже созданное место, оно не создаётся заново. Берётся прежнее состояние и обновляется на прошедшее время.

### 8. События и таймеры

Отложенное событие — это последствие, которое уже имеет причину, но срабатывает не сразу, а после прохождения времени.

Формула:

если текущее время >= время события → событие срабатывает

Отложенное событие должно иметь:

причину — почему оно вообще началось;
условие времени — когда или через сколько оно может сработать;
результат — что меняется в мире после срабатывания.

Примеры в общем виде:

NPC завершает текущее дело и переходит к следующему;
место открывается, закрывается или меняет режим;
состояние тела ухудшается или восстанавливается;
слух, след, тревога или приказ распространяется дальше;
преследование приближается или теряет темп;
погода меняет условия сцены;
голод, жажда, усталость, холод или болезнь дают последствия.

Короткая формула:

причина → ожидание → срабатывание → последствия

Отложенное событие создаётся, когда действие, состояние или внешний процесс уже начались, но их результат должен проявиться позже: ожидание, погоня, болезнь, слух, приказ, закрытие места, смена погоды, движение NPC.
Оно не создаётся «на всякий случай»: нужна конкретная причина, время или условие срабатывания и понятное последствие для персонажа, NPC, места или мира.

### 9. День и часть суток

Смена части суток влияет на сцену.

| Часть суток | Что меняется                                                        |
| ----------- | ------------------------------------------------------------------- |
| Утро        | люди начинают работу, холод после ночи, открываются дворы и рынок   |
| День        | больше свидетелей, активная работа, лучше видимость                 |
| Вечер       | люди возвращаются, закрываются места, растёт осторожность           |
| Ночь        | темнота, холод, меньше людей, выше подозрительность, труднее дорога |

Погода задаётся по частям суток и влияет на тело, дорогу, видимость, звук, следы, огонь, бой и скрытность.

### 10. Короткое правило

После каждого значимого действия игра отвечает на четыре вопроса:

1. **Сколько времени прошло?**
2. **Поменялась ли часть суток или день?**
3. **Что изменилось в теле, NPC, погоде или месте?**
4. **Сработал ли триггер на отложенные события?**

Главная формула:

`время = длительность действия + изменения мира + последствия`

Время не должно двигаться случайно. Оно проходит только из-за действия, ожидания, сна, дороги, работы, лечения, разговора, боя или другого понятного события.
