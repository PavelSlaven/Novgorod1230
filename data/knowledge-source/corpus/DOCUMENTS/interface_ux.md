# Интерфейс и UX

## Статус и граница миграции

Этот документ задаёт **target materialization v3** для player projection.
Принятое историческое P28 evidence не меняло production composition. До
отдельного `versioned production activation cutover` active production
остаётся materialization v2; target UI contract не включает runtime
activation, dual write или v3→v2 fallback. UI читает player-safe projection и
никогда не является источником factual topology, readiness или layout-derived
semantics.

Temporal World v4 требует `VisiblePackagePersistenceEnvelope`: code-owned
projector формирует player-safe factual package до commit, package сохраняется
атомарно со state change, а UI и narrator читают его только после commit.
Narration, layout и browser payload не могут добавить temporal fact,
consequence, schedule, route или hidden candidate.

## 1. Player-safe movement and knowledge projection

Игрок получает intent-oriented movement options, а не скрытые IDs, все factual routes или candidate diagnostics. Каждая видимая опция сообщает только допустимую player-safe цель/направление, наблюдаемые условия, безопасно объяснённую readiness и последствия, которые персонаж может воспринять или знать.

```text
mechanical_readiness = ready | requires_frontier_resolution
                     | requires_preparation | temporarily_blocked | data_gap
knowledge_visibility = visible | hidden | misidentified
```

`ready` может показывать выполнимое намерение, но не обязан раскрывать endpoint chain. `requires_frontier_resolution` и `requires_preparation` показываются как нейтральное ожидание/подготовка без hidden topology, capacities, candidate IDs, internal validators или причины, недоступной персонажу. `temporarily_blocked` показывает наблюдаемое препятствие только в разрешённом knowledge scope. `data_gap` не раскрывает техническую диагностику: игрок видит безопасный отказ или необходимость вернуться к другому действию; полный typed error остаётся в development diagnostics.

`hidden` route, frontier, NPC motive, item slot, exact cost, internal route binding и candidate-set contents не попадают в игровой экран. `misidentified` отображается лишь как belief/слух/неуверенная ориентировка, не как factual correction. Свободный ввод игрока остаётся намерением и не подтверждает существование маршрута или объекта.

## 2. Route, scene and map behavior

Scene view отображает visible G6 и доступные `scene_position` relations только через perception/knowledge projection. Route map отображает известные или наблюдаемые связи, never factual topology by default. Линии, координаты, слои, zoom и визуальная близость — presentation only: они не создают containment, movement edge, distance, route cost или readiness.

Карта может явно показывать неизвестность, неполноту и ошибочное знание, но не может автоматически дорисовывать hidden branch. Отсутствие `visual_map_ready` не блокирует movement/simulation; отсутствие `semantic_ready` не маскируется layout или prose. UI не выводит G7/G8 и не превращает visual anchor в новый G-level.

## 3. Interruption, stranded state and diagnostics boundary

При interruption UI показывает только player-safe состояние: текущую наблюдаемую сцену/anchor, доступные безопасные действия, последствия для персонажа и то, что дальнейшее движение требует нового решения. `stranded` не получает invented nearest endpoint, скрытый teleport или ложную карту; интерфейс сообщает ограничение без раскрытия recovery topology.

Development diagnostics отделены от игрового UI: они могут содержать typed errors, traces, candidate diagnostics и raw payloads только в явном developer context. Ни журнал, ни prose, ни browser payload player-facing слоя не должны их включать. Target traceability: `spatial_architecture_standard_g0_g6.md` §§1.5, 7, 9, 14 и Appendix A §§A.7–A.8.

# Интерфейс и UX

Интерфейс игры обслуживает историческую текстовую RPG-симуляцию XIII века. Игра охватывает период **1230–1250** и строится вокруг свободного ввода игрока, устойчивого состояния мира, исторического давления, памяти персонажа, видимого знания и постепенной материализации окружающей среды.

Интерфейс не является энциклопедией мира, редактором состояния или панелью администратора. Он показывает игроку то, что важно для действия здесь и сейчас: прозу сцены, положение персонажа, телесное состояние, доступные по восприятию сведения, ввод действия, сохранение, журнал памяти, инвентарь при персонаже, карту знаний и отдельную диагностику генерации для разработки.

Главное правило:

```text
игровой UI показывает видимый опыт персонажа
журнал показывает важную память персонажа и партии
диагностика показывает технический процесс разработки
```

Игровой интерфейс не должен смешивать эти три слоя.

## 1. Назначение интерфейса

Интерфейс должен помогать игроку действовать как человек внутри исторической среды, а не как оператор базы данных.

Основные задачи UI:

1. дать понять, что это за игра и в каком историческом диапазоне она происходит;
2. позволить начать новую партию через свободное описание персонажа или ситуации;
3. позволить загрузить существующую партию;
4. сделать прозу сцены главным элементом экрана;
5. показывать только те параметры, которые нужны для решения текущего действия;
6. отделять инвентарь при персонаже от имущества, прав, долгов и доступа;
7. хранить важную информацию в журнале, а не перегружать основной экран;
8. показывать карту только как карту знаний персонажа;
9. предлагать варианты действий через отдельного LLM-агента, не превращая их в жёсткое меню;
10. сохранить и актуализировать отладку создания новой игры отдельно от игрового журнала.

Короткая формула:

```text
UI = проза + видимое состояние + ввод + память + отдельные оверлеи + диагностика разработки
```

## 2. Общие принципы

### Видимое важнее полного

Игрок не должен видеть весь мир, скрытую карту, скрытые мотивы NPC, внутренние флаги, технические контракты, сырые промты или данные, которые персонаж не мог знать.

Показывается:

1. то, что персонаж видит, слышит, чувствует или помнит;
2. то, что персонаж разумно предполагает из опыта, статуса и слухов;
3. то, что уже стало важной памятью партии;
4. то, что нужно для честного выбора действия.

Не показывается:

1. фактическая скрытая карта мира;
2. скрытые причины событий;
3. точные будущие даты и гарантированные исходы;
4. полные профили NPC;
5. скрытые мотивы и технические статусы NPC;
6. все возможные действия сцены как список команд;
7. полный JSON состояния;
8. raw request, raw response, промты и ошибки парсинга в игровом UI.

Короткая формула:

```text
видимое для игрока = восприятие персонажа + память персонажа + доступные слухи + наблюдаемые последствия
```

### Проза главнее панели

Основной экран должен быть читальным экраном. Проза сцены занимает визуальный приоритет. Параметры, карточки, кнопки, подсказки и графы не должны конкурировать с текстом.

Целевое распределение внимания на desktop:

```text
70–80% внимания — проза и ввод
20–30% внимания — краткое состояние, кнопки и оверлеи
```

Если интерфейс начинает выглядеть как таблица управления симулятором, он нарушает задачу игры.

### Игрок действует текстом

Главное действие игрока — свободный ввод. Кнопки и подсказки помогают, но не заменяют самостоятельную формулировку.

Чипы действий не должны быть меню всех разрешённых команд. Они должны быть мягкими подсказками, составленными с точки зрения персонажа и текущей сцены.

### UI не придумывает мир

Интерфейс не создаёт факты, не достраивает правила и не исправляет смысловую логику мира. Он показывает утверждённое игровое состояние, важную память и диагностические сведения, если включён режим разработки.

Короткая формула:

```text
мир создаётся и обновляется игровыми системами
UI читает и показывает доступный игроку слой
```

## 3. Информационные слои

В интерфейсе должно быть четыре разных слоя информации.

### 1. Сценический слой

Это основной экран игры:

1. проза текущей сцены;
2. время, сезон, часть суток;
3. место и ближайшая позиция;
4. короткие телесные состояния;
5. метки тревоги;
6. строка инвентаря при персонаже;
7. свободный ввод;
8. кнопки сохранения, журнала, инвентаря, людей рядом и карты.

### 2. Память партии

Это журнал. Он хранит важные сведения, которые игроку нужно помнить между ходами:

1. события;
2. память персонажа;
3. обязательства;
4. известных людей;
5. известные места и карту знаний;
6. имущество и права;
7. слухи и исторический фон.

### 3. Ситуационные оверлеи

Это отдельные окна поверх основного экрана:

1. инвентарь;
2. люди рядом;
3. подробная карточка состояния;
4. карта знаний;
5. загрузка сохранения;
6. создание новой игры.

Оверлеи не должны разрушать текущую сцену. Они открываются поверх неё и закрываются без потери контекста.

### 4. Диагностика разработки

Это технический слой:

1. процесс создания новой игры;
2. этапы генерации;
3. LLM-вызовы;
4. raw request / raw response;
5. ошибки;
6. JSON-снимки;
7. HTML-артефакты из `data/new-game-process`.

Этот слой не является частью мира и не должен попадать в игровой журнал.

## 4. Стартовое окно

Стартовое окно — первое знакомство игрока с игрой. Оно должно объяснять, что игра является исторической текстовой RPG-симуляцией про мир XIII века, где персонаж действует через свободный ввод, а мир хранит последствия.

Стартовое окно содержит:

1. название игры;
2. короткое пояснение, что действие происходит в исторической среде 1230–1250 годов;
3. пояснение, что игрок описывает желаемого персонажа или стартовую ситуацию свободным текстом;
4. кнопку **Новая игра**;
5. кнопку **Загрузить**.

На первом стартовом экране не должно быть полей имени, класса, региона, года, статуса, характеристик или выбора профиля.

Пример смысла стартового текста:

```text
Историческая текстовая RPG-симуляция XIII века.
Действие партии начинается в пределах 1230–1250 годов.
Игрок описывает человека или ситуацию свободным текстом, а игра адаптирует заявку к эпохе, месту, статусу и обстоятельствам.
```

Короткая формула стартового окна:

```text
объяснение игры + Новая игра + Загрузить
```

## 5. Новая игра

После нажатия **Новая игра** открывается отдельное состояние стартового окна или оверлей создания партии.

В нём должен быть один главный элемент: большое поле свободного описания.

Игрок может написать:

1. кем хочет быть;
2. примерную биографию;
3. желаемый статус;
4. стартовую ситуацию;
5. настроение партии;
6. место или регион, если хочет;
7. год или исторический контекст, если хочет;
8. цель, страх, долг или проблему;
9. только одну фразу;
10. ничего.

Если поле пустое, игра сама создаёт правдоподобного персонажа и стартовую рамку в пределах документов проекта.

Поле свободного описания не является анкетой. В UI не нужно добавлять отдельные поля года, региона, имени, статуса, профессии, происхождения, пола, навыков или имущества.

Заявка игрока считается желанием, а не готовой истиной. UI должен заранее мягко объяснять это:

```text
Опиши персонажа или ситуацию. Можно оставить поле пустым.
Игра сохранит ядро идеи, но приведёт её к эпохе, месту и социальному порядку.
```

После отправки заявки показывается экран создания мира.

## 6. Экран создания мира

Создание новой партии может занимать заметное время. Игрок должен видеть понятный прогресс без технической перегрузки.

Экран создания мира показывает:

1. текущий человеческий этап;
2. краткое объяснение, что сейчас происходит;
3. общий прогресс;
4. аккуратный список этапов;
5. кнопку отмены, если отмена технически поддержана;
6. понятную ошибку, если генерация не завершилась.

Игровой экран создания мира не должен показывать:

1. raw JSON;
2. промты;
3. ответы модели;
4. стеки ошибок;
5. внутренние имена фаз;
6. провайдера и модель, если это не режим разработки.

Человеческие этапы создания новой игры:

1. разбор заявки игрока;
2. выбор исторической рамки;
3. выбор региона и сезона;
4. уточнение исторического давления;
5. создание стартового места;
6. разворачивание локации, минилокации и точки сцены;
7. создание персонажа игрока;
8. связывание персонажа со стартовым местом;
9. создание людей рядом;
10. создание предметного слоя;
11. создание начальных маршрутов и карты знаний;
12. проверка связности и реализма;
13. сохранение партии;
14. подготовка вводной прозы.

Короткая формула:

```text
заявка → рамка → регион → место → персонаж → люди → предметы → карта знаний → проверка → сохранение → проза
```

## 7. Загрузка игры

Кнопка **Загрузить** открывает отдельное окно со списком сохранённых партий.

Для одной партии используется один автослот. Игрок не выбирает ручные слоты и не обязан давать сохранению название.

Карточка сохранения показывает:

1. имя или краткое обозначение персонажа;
2. год и сезон;
3. регион;
4. текущее место;
5. часть суток или игровое время;
6. краткое состояние персонажа;
7. дату последнего сохранения;
8. короткий фрагмент последнего важного события, если он есть.

Кнопка загрузки должна быть простой:

```text
Продолжить
```

Сохранения не должны выглядеть как файловый менеджер. Это каталог партий, а не список технических файлов.

## 8. Основное окно игры

Основное окно игры состоит из пяти зон:

1. верхняя строка контекста;
2. центральная проза;
3. компактная боковая или верхняя панель состояния;
4. блок свободного ввода;
5. кнопки оверлеев и сохранения.

Короткая формула:

```text
основной экран = контекст + проза + краткое состояние + ввод + доступ к памяти
```

### Верхняя строка контекста

Верхняя строка должна быть компактной. Она показывает только то, что помогает понять текущую сцену:

1. год;
2. сезон;
3. часть суток;
4. текущий регион или земля;
5. текущее место;
6. ближайшая сценическая позиция, если она важна;
7. погода или свет, если они влияют на восприятие и действия.

Техническую иерархию позиции полностью показывать не нужно. Игроку достаточно художественно понятного пути:

```text
Новгородская земля · зима 1241 · вечер · погост у реки · двор у ворот
```

### Центральная проза

Проза — главный элемент игры.

Она должна:

1. описывать видимое и слышимое;
2. показывать важные последствия прошлых действий;
3. давать игроку достаточно опор для следующего действия;
4. сохранять исторический тон без псевдосредневековой перегрузки;
5. не подменять восприятие персонажа знаниями рассказчика;
6. не превращаться в отчёт системы.

В прозе должны быть видны возможности действия, но не в виде полного меню. Игрок должен понимать, с кем можно говорить, что можно осмотреть, куда можно двинуться и что выглядит опасным, из самой сцены.

Проза не должна сообщать:

1. скрытые мотивы NPC;
2. скрытые предметы без основания;
3. точные броски и внутренние расчёты;
4. будущие события как гарантированное знание;
5. все варианты решения сцены.

### Компактная панель состояния

Панель состояния не должна занимать много места. Она нужна для быстрого чтения тела и ближайших рисков.

На основном экране показываются базовые состояния новой модели:

1. **Здоровье**;
2. **Сытость**;
3. **Бодрость**.

Дополнительно показываются короткие метки тревоги, если они есть:

1. ранен;
2. мёрзнет;
3. промок;
4. голоден;
5. обессилен;
6. напуган;
7. кровотечение;
8. болен;
9. перегружен;
10. связан;
11. пьян;
12. отравлен.

Подробности активных состояний не раскрываются на основном экране. Они открываются в карточке состояния или в соответствующем разделе журнала.

Короткая формула:

```text
основной экран состояния = Здоровье + Сытость + Бодрость + короткие тревоги
```

### Краткий инвентарь на основном экране

На основном экране инвентарь показывается одной компактной строкой:

```text
в руках / на теле / груз
```

Примеры:

```text
В руках: пусто · На теле: нож, кошель · Груз: лёгкий
```

```text
В руках: факел и мешок · На теле: топор за поясом · Груз: тяжёлый
```

Полный список вещей, контейнеры, владельцы, риски, доступность и вес открываются в отдельном окне инвентаря.

### Кнопки основного экрана

На основном экране должны быть доступны:

1. **Сохранить**;
2. **Журнал**;
3. **Инвентарь**;
4. **Люди рядом**;
5. **Карта** или **Ориентация**;
6. переключатель дневной и ночной темы, если он не вынесен в настройки.

Кнопки должны быть заметными, но не крупнее прозы.

## 9. Свободный ввод игрока

Свободный ввод находится внизу основного экрана и остаётся доступным большую часть времени.

Поле ввода должно поддерживать:

1. короткое действие;
2. длинное описание намерения;
3. разговорную реплику;
4. уточнение способа действия;
5. попытку осмотра;
6. перемещение;
7. ожидание, сон, работу или разговор;
8. несколько предложений, если игрок формулирует сложный план.

Поведение поля:

1. `Enter` отправляет действие;
2. `Shift+Enter` добавляет новую строку;
3. отправка блокируется на время обработки хода;
4. после ошибки текст действия не должен теряться;
5. после клика по подсказке текст вставляется в поле для редактирования, а не выполняется мгновенно.

Короткая формула:

```text
действие игрока = свободный текст + намерение + способ + контекст персонажа
```

## 10. Агент подсказок действий

Старые чипы быстрых действий нужно переосмыслить. Они не должны быть статическим списком вроде «поговорить», «осмотреть», «идти».

Подсказки должен готовить отдельный LLM-агент. Его задача — читать текущий видимый контекст с точки зрения персонажа игрока и предлагать несколько правдоподобных вариантов поведения.

Агент подсказок отвечает не на вопрос:

```text
какие команды вообще доступны игроку
```

а на вопрос:

```text
как этот персонаж мог бы поступить сейчас, учитывая сцену, страхи, статус, память, тело, вещи и ограничения
```

Подсказки должны учитывать:

1. видимую сцену;
2. текущую прозу;
3. положение персонажа;
4. здоровье, сытость и бодрость;
5. активные тревоги;
6. инвентарь при персонаже;
7. социальный статус;
8. память и обязательства;
9. известные риски;
10. характер текущей ситуации;
11. что персонаж знает и чего не знает.

Подсказки не должны:

1. раскрывать скрытую информацию;
2. предлагать оптимальное мета-решение от лица игрока;
3. показывать все возможные действия;
4. подменять свободный ввод;
5. выглядеть как кнопки меню;
6. гарантировать успех;
7. обещать результат, которого персонаж не может знать.

Рекомендуемый формат:

1. 3–6 подсказок;
2. короткий текст действия;
3. мягкая пометка тона или риска;
4. возможность вставить подсказку в поле ввода;
5. возможность обновить подсказки после изменения сцены.

Примеры подсказок:

```text
Тихо спросить у старосты, почему у ворот поставили людей.
Осмотреть следы у саней, не привлекая внимания.
Попросить воды и место у огня, ссылаясь на дорогу и холод.
Не спорить сейчас: отойти к навесу и прислушаться к разговору.
```

Короткая формула:

```text
подсказка = видимый контекст + память персонажа + риск + правдоподобное намерение
```

## 11. Журнал

Журнал — это игровая память партии. Он не является логом всех технических событий и не является дампом состояния.

Журнал открывается отдельным окном или полноэкранным оверлеем. На desktop он может быть широким модальным окном. На мобильном — отдельным полноэкранным экраном.

Журнал должен иметь вкладки:

1. **События**;
2. **Память**;
3. **Обязательства**;
4. **Люди**;
5. **Места**;
6. **Имущество**;
7. **Слухи/история**.

Короткая формула:

```text
журнал = важные события + память + долги + люди + места + имущество + слухи
```

### События

Вкладка **События** хранит важные игровые события в порядке времени.

Запись события должна показывать:

1. когда это произошло в игровом времени;
2. где это произошло;
3. что стало известно персонажу;
4. что изменилось для партии;
5. какие последствия уже видимы;
6. какие вопросы остались открытыми, если персонаж это понимает.

Не нужно писать в журнал каждую строку прозы и каждое техническое обновление. Записываются только события, важные для памяти, последствий, обязательств, отношений, предметов, мест и исторического давления.

### Память

Вкладка **Память** хранит сведения о персонаже:

1. происхождение;
2. статус;
3. привычное занятие;
4. причины оказаться в стартовой ситуации;
5. важные воспоминания;
6. страхи;
7. цели;
8. слабые места;
9. границы знания;
10. то, что персонаж считает правдой;
11. то, в чём он может ошибаться, если это уже оформлено как часть памяти.

Память не должна превращаться в биографическую энциклопедию. Она нужна для принятия решений и для подсказок поведения.

### Обязательства

Вкладка **Обязательства** хранит:

1. долги;
2. обещания;
3. поручения;
4. приказы;
5. угрозы;
6. зависимости;
7. сроки;
8. людей, перед которыми персонаж отвечает;
9. имущество, которое нужно вернуть;
10. последствия бездействия.

Обязательство должно быть связано с человеком, местом, предметом, сроком или риском. Если такой связи нет, это не обязательство, а общая цель.

### Люди

Вкладка **Люди** показывает известных персонажу людей и группы.

Для каждого человека показывается только наблюдаемая и известная информация:

1. имя или способ обращения;
2. роль;
3. статус, если персонаж его знает;
4. последнее известное место;
5. последнее видимое занятие;
6. отношение к персонажу, если оно проявилось;
7. долг, просьба, конфликт или связь;
8. что персонаж знает точно;
9. что слышал как слух;
10. что остаётся неизвестным.

Нельзя показывать:

1. скрытые мотивы;
2. внутренний профиль NPC;
3. технический уровень NPC;
4. истинный статус, если персонаж его не знает;
5. будущие действия NPC;
6. скрытые ресурсы и тайные связи.

### Места

Вкладка **Места** содержит карту знаний персонажа и список известных мест.

Она показывает:

1. текущую локацию персонажа;
2. известные места;
3. известные маршруты;
4. примерные направления;
5. слухи о местах и дорогах;
6. ложные или сомнительные сведения, если персонаж так их воспринимает;
7. последние посещения;
8. важные риски дорог;
9. сезонные ограничения, если персонаж о них знает.

Фактическая скрытая карта мира не показывается.

### Имущество

Вкладка **Имущество** отделена от инвентаря.

Здесь показывается то, что связано с персонажем, но не находится при нём физически:

1. дом;
2. скот;
3. лодка;
4. товар;
5. инструмент не при персонаже;
6. залог;
7. долг;
8. имущество у других людей;
9. право доступа;
10. спорное имущество;
11. чужая вещь, которую нужно вернуть;
12. имущество семьи, хозяина, службы или общины.

Для каждого объекта важно показывать:

1. где он находится;
2. кому принадлежит;
3. кто фактически держит;
4. имеет ли персонаж право пользоваться;
5. какой есть риск;
6. как это связано с обязательствами.

Короткая формула:

```text
имущество = право + связь + место хранения + держатель + доступ + риск
```

### Слухи/история

Вкладка **Слухи/история** показывает историческое давление так, как его может знать персонаж.

Можно показывать:

1. слухи;
2. тревожные признаки;
3. приказы;
4. движение людей;
5. рост цен;
6. закрытые дороги;
7. страх местных;
8. последствия войны, власти, походов, сбора, налогов или набегов;
9. имена исторических личностей, если персонаж мог о них слышать;
10. примерные фазы событий через видимые признаки.

Нельзя показывать:

1. точные будущие даты;
2. скрытые причины;
3. гарантированные исходы;
4. знание рассказчика, недоступное персонажу;
5. полную историческую справку без связи с партией.

## 12. Инвентарь

Инвентарь открывается отдельным оверлеем. В основной боковой панели остаётся только краткая строка.

Инвентарь — это предметы, которые персонаж физически несёт при себе и может использовать в текущей сцене.

Inventory panel v1 получает готовую visible-only projection от code. Она показывает руки,
на теле, equipment, quick/primary container, external load, total mass, load category и
hands; не показывает internal IDs, raw trace, audit diagnostics, hidden owner или
unknown contents закрытого контейнера. UI не пересчитывает packing, массу, hands или
access. Имущество вне physical placement path не выводится как «при себе».

Короткая формула:

```text
инвентарь = предметы при персонаже
имущество ≠ инвентарь
```

Окно инвентаря должно показывать:

1. что в руках;
2. что на теле или за поясом;
3. что в сумке, мешке, кошеле или другом контейнере;
4. что можно быстро достать;
5. что требует времени, открытия или поиска;
6. что занимает руки;
7. общий груз;
8. уровень нагрузки;
9. состояние значимых предметов;
10. владельца или спорность владения;
11. риск использования, продажи, показа или присвоения;
12. вещи, которые связаны с обязательствами.

Окно инвентаря не должно показывать имущество, лежащее дома, у родни, в лодке, на складе, у другого человека или в другом месте. Такие вещи показываются в журнале во вкладке **Имущество**.

### Группировка инвентаря

Рекомендуемая структура окна:

1. **В руках** — используется сразу, занимает руки.
2. **На теле / за поясом** — быстро достать.
3. **В контейнерах** — мешки, кошели, футляры и содержимое.
4. **Одежда и снаряжение** — надето, защищает, греет, мешает или создаёт статус.
5. **Риск и право** — чужие, служебные, спорные, заметные или опасные вещи.
6. **Нагрузка** — вес, уровень груза, влияние на движение.

Если предмет недоступен в текущей сцене, он не должен выглядеть как готовая кнопка действия.

## 13. Люди рядом

Список людей рядом лучше скрыть под отдельную кнопку и открывать оверлеем. Он не должен занимать постоянное место на главном экране.

Основной способ понять, с кем можно взаимодействовать, — проза сцены. Оверлей **Люди рядом** нужен как вспомогательная память восприятия, а не как меню диалогов.

Оверлей показывает только наблюдаемое:

1. кто виден рядом;
2. как персонаж может его назвать;
3. где он находится относительно сцены;
4. чем занят;
5. видимое настроение или состояние;
6. может ли заметить действия персонажа;
7. связан ли с текущим порядком, угрозой или просьбой;
8. что уже известно из разговора или памяти.

Оверлей не должен показывать:

1. скрытые мотивы;
2. истинные цели;
3. полный профиль;
4. технический статус;
5. все возможные реплики;
6. гарантированную реакцию.

Короткая формула:

```text
люди рядом = видимые участники сцены + их занятие + их наблюдаемая роль + риск свидетеля
```

## 14. Карта и ориентация

Карта игры показывается как граф знаний персонажа, а не как фактическая карта мира.

Игроку можно показывать:

1. текущую локацию;
2. известные места;
3. посещённые маршруты;
4. известные дороги;
5. примерные направления;
6. слухи о путях;
7. сомнительные сведения;
8. сезонные ограничения, если персонаж о них знает.

Игроку нельзя показывать:

1. скрытые узлы;
2. маршруты, о которых персонаж не знает;
3. точную фактическую географию, если персонаж её не знает;
4. будущие безопасные пути;
5. скрытые опасности как гарантированную информацию.

Короткая формула:

```text
карта в UI = карта знаний персонажа + текущая локация + известность путей
```

### Ориентация на основном экране

На основном экране достаточно краткого блока **Ориентация**:

1. текущая локация;
2. откуда персонаж пришёл;
3. 2–4 видимых или известных направления;
4. короткий риск, если он очевиден персонажу;
5. кнопка открытия большой карты в журнале.

### Большая карта в журнале

Большая карта находится во вкладке **Места** или открывается из неё.

Требования к читаемости графа:

1. текущая локация должна быть явно выделена;
2. известные, слуховые и сомнительные пути должны различаться визуально;
3. надписи не должны наезжать друг на друга;
4. длинные подписи должны сокращаться с возможностью увидеть полное название при наведении или раскрытии;
5. граф должен поддерживать масштабирование и перетаскивание;
6. при большом числе узлов карта должна группировать дальние места;
7. узлы разных масштабов не должны смешиваться в нечитаемую кашу;
8. минилокации не нужно показывать на большой региональной карте, если они перегружают схему;
9. карта должна сохранять читаемость на мобильном экране;
10. неизвестные фактические узлы не должны появляться даже серыми заглушками.

Рекомендуемая логика масштаба:

```text
сцена → минилокации и проходы
место → локации внутри места
регион → известные места и дороги
дальний путь → направления, слухи и пройденные маршруты
```

## 15. Состояние персонажа и карточка подробностей

Основной экран показывает только краткое состояние.

Подробная карточка состояния открывается отдельно и показывает:

1. Здоровье;
2. Сытость;
3. Бодрость;
4. активные состояния;
5. причины активных состояний, если персонаж их понимает;
6. видимые последствия;
7. ограничения действий;
8. текущие телесные ощущения;
9. что может ухудшить состояние;
10. что может помочь, если персонаж это знает.

Карточка не должна показывать скрытые численные расчёты, если игроку достаточно понятного описания. Формулы и внутренние проверки остаются в документах и диагностике, а не в игровом UI.

## 16. Сохранение

Кнопка **Сохранить** сохраняет текущую партию в её единственный автослот.

Не нужно открывать отдельное окно ручного выбора слота. После сохранения достаточно короткого статуса:

```text
Сохранено
```

или

```text
Не удалось сохранить: причина
```

Карточка партии в списке загрузки обновляется автоматически.

Короткая формула:

```text
одна партия = один автослот
```

## 17. Визуальный стиль

Интерфейс должен быть историчным по ощущению, но не театрально-псевдосредневековым.

Нужны две темы:

1. **дневная**;
2. **ночная**.

### Ночная тема

Ночная тема подходит для длительного чтения в темноте.

Она может использовать:

1. тёмный фон;
2. тёплый текст;
3. приглушённые линии;
4. мягкие золотистые или охристые акценты;
5. тёмное дерево, железо, кожа или копоть как визуальные ассоциации;
6. слабое свечение активных элементов.

### Дневная тема

Дневная тема должна быть светлой, но не белой канцелярской.

Она может использовать:

1. оттенки пергамента, бересты, льна или светлого дерева;
2. тёмно-коричневый или почти чёрный текст;
3. мягкие охристые акценты;
4. тонкие линии, напоминающие чернила;
5. аккуратные кнопки без яркого современного пластика.

### Значки и кнопки

Значки должны быть красивыми, но функциональными.

Подходящие мотивы:

1. печать;
2. свиток;
3. берестяная грамота;
4. мешок;
5. нож;
6. очаг;
7. дорога;
8. узел верёвки;
9. колокол;
10. свеча;
11. щит;
12. ключ;
13. след;
14. рука;
15. карта.

Значки не должны превращать UI в фэнтезийную панель заклинаний. Их задача — быстро отличать журнал, инвентарь, карту, людей, состояние, сохранение и тему.

### Шрифты и плотность

Шрифт должен быть аккуратным и небольшим, но читаемым.

Рекомендации:

1. основной прозаический текст — чуть крупнее служебного UI;
2. служебные подписи — компактные;
3. заголовки — выразительные, но не огромные;
4. межстрочный интервал прозы должен облегчать чтение;
5. декоративный шрифт допустим только в заголовках и коротких метках;
6. длинная проза не должна набираться трудночитаемым декоративным шрифтом.

Короткая формула стиля:

```text
исторический вкус + читабельность + компактность > декоративность
```

## 18. Адаптивность

Интерфейс должен быть адаптивным.

### Desktop

На широком экране:

1. проза занимает центр;
2. ввод находится внизу;
3. краткое состояние может быть справа;
4. журнал, инвентарь, люди и карта открываются оверлеями;
5. подсказки действий находятся рядом с вводом или под прозой.

### Tablet

На среднем экране:

1. боковая панель сворачивается;
2. состояние переходит в компактную верхнюю или нижнюю строку;
3. кнопки оверлеев группируются;
4. проза остаётся главным элементом;
5. поле ввода остаётся доступным без прокрутки, если возможно.

### Mobile

На узком экране:

1. интерфейс становится одноколоночным;
2. проза идёт первой;
3. краткое состояние сворачивается в компактную строку или кнопку;
4. ввод закрепляется внизу или легко возвращается после прокрутки;
5. журнал, инвентарь, карта и люди рядом открываются полноэкранными оверлеями;
6. большие графы карты получают отдельный режим просмотра;
7. кнопки должны быть достаточно крупными для касания;
8. текст не должен требовать горизонтальной прокрутки.

Короткая формула:

```text
на малом экране всё, кроме прозы и ввода, становится оверлеем
```

## 19. Диагностика и `data/new-game-process`

Отладку создания новой игры нужно сохранить и актуализировать под новые документы.

Диагностика должна быть отделена от игрового интерфейса. Игрок в обычном режиме не видит промты, raw JSON, внутренние этапы, ошибки парсинга и технические снимки.

Диагностика доступна через:

1. dev/debug-кнопку;
2. отдельный диагностический drawer;
3. HTML-артефакты в `data/new-game-process`;
4. режим разработки.

Короткая формула:

```text
игровой журнал ≠ технический журнал генерации
```

### Назначение HTML-артефактов

HTML-артефакт создания новой игры нужен разработчику, чтобы понять:

1. где остановился процесс;
2. какой этап дал ошибку;
3. какие данные были переданы;
4. что вернула модель;
5. какие проверки не прошли;
6. что было сохранено;
7. насколько итог соответствует документам.

Артефакт может показывать техническую информацию, которую нельзя показывать в игровом UI.

### Этапы, которые должны быть отражены в диагностике

Диагностика новой игры должна соответствовать актуальной логике документов:

1. **Заявка игрока** — свободное описание или пустой ввод.
2. **Историческая рамка** — год, сезон, регион, общий исторический фон.
3. **Региональный контур** — активный регион, соседние регионы, дороги, власть, хозяйство, страхи, слухи.
4. **Исторический слой** — события, личности, фазы, локальные признаки, границы знания персонажа.
5. **Стартовое место** — функция места, владельцы или держатели, доступ, риски, связь с регионом.
6. **Локация, минилокация и точка сцены** — точное сценическое положение персонажа.
7. **Сцена** — погода, свет, звуки, движение людей, настроение места, видимые следы.
8. **Персонаж игрока** — статус, происхождение, тело, характеристики, навыки, причина быть здесь.
9. **Память и знания персонажа** — что знает, что слышал, чего не знает, в чём может ошибаться.
10. **Импульс действия** — ближайшая нужда, страх, долг, внешнее давление, риск бездействия.
11. **NPC рядом** — фоновые, сценические и ключевые NPC с нужной глубиной.
12. **Предметы, инвентарь и имущество** — предметы при персонаже, доступ, владельцы, риски, имущество вне инвентаря.
13. **Маршруты и карта знаний** — текущая позиция, известные пути, слухи о путях, обратные маршруты, дальний курс при необходимости.
14. **Скрытые процессы** — то, что есть в мире, но не видно игроку.
15. **Проверка связности** — историчность, причинность, отсутствие дублей, согласованность места, персонажа, предметов и NPC.
16. **Сохранение партии** — фиксация стартового состояния и автокаталога.
17. **Видимое состояние** — слой, который можно передать рассказчику и UI.
18. **Вводная проза** — стартовый текст, написанный только из видимого состояния.

### Что должен показывать артефакт

HTML-артефакт должен содержать:

1. статус: success или error;
2. время создания;
3. длительность;
4. общий прогресс;
5. список этапов;
6. последний успешный этап;
7. этап ошибки;
8. понятное сообщение ошибки;
9. технические детали по раскрытию;
10. список LLM-вызовов;
11. request / response по каждому вызову;
12. итоговый снимок процесса;
13. кнопку копирования JSON;
14. различие между предупреждением, повтором, ошибкой и успешным этапом.

### Что нельзя делать с диагностикой

Нельзя:

1. смешивать технический журнал с игровым журналом;
2. показывать raw JSON в обычном игровом режиме;
3. превращать ошибки генерации в игровую прозу;
4. незаметно подставлять заглушку вместо проваленного этапа;
5. скрывать причину ошибки в HTML-артефакте;
6. оставлять старые этапы, которые больше не соответствуют документам;
7. показывать игроку сведения, которые персонаж не должен знать.

## 20. Что нельзя делать в UI

Нельзя:

1. делать стартовую анкету с множеством обязательных полей;
2. показывать старую модель параметров как целевую;
3. держать полный инвентарь в боковой панели;
4. смешивать инвентарь и имущество;
5. показывать полный профиль NPC рядом с прозой;
6. раскрывать скрытые мотивы NPC;
7. показывать фактическую карту мира вместо карты знаний персонажа;
8. делать граф карты нечитаемым из-за наезжающих подписей;
9. превращать подсказки действий в жёсткое меню команд;
10. выполнять подсказку сразу без возможности редактирования;
11. показывать техническую диагностику в игровом журнале;
12. сообщать будущие исторические события как точное знание персонажа;
13. перегружать основной экран таблицами, JSON, формулами и административными данными;
14. делать яркую современную RPG-панель, которая конфликтует с исторической прозой;
15. жертвовать читаемостью ради декоративного средневекового стиля.

## 21. Короткие формулы

```text
UI = проза + видимый контекст + краткое состояние + свободный ввод + память
```

```text
старт = объяснение игры + Новая игра + Загрузить
```

```text
новая игра = свободное описание игрока → создание мира → вводная проза
```

```text
основное окно = верхний контекст + проза + состояние + ввод + кнопки оверлеев
```

```text
состояние на главном экране = Здоровье + Сытость + Бодрость + метки тревоги
```

```text
инвентарь на главном экране = в руках / на теле / груз
```

```text
инвентарь = предметы при персонаже
имущество ≠ инвентарь
```

```text
журнал = события + память + обязательства + люди + места + имущество + слухи/история
```

```text
карта в UI = карта знаний персонажа + текущая локация + известные пути
```

```text
подсказка действия = видимый контекст + память персонажа + правдоподобное поведение + риск
```

```text
игровой журнал ≠ технический журнал генерации
```

```text
одна партия = один автослот
```

## 22. Главное правило

Интерфейс должен держать игрока внутри восприятия персонажа.

Он показывает прозу, память, тело, вещи при себе, известных людей, известные места и слухи так, чтобы игрок мог принять честное решение свободным текстом.

Всё, что является скрытой реальностью мира, внутренней логикой NPC, техническим состоянием генерации, raw JSON, промтом, ошибкой модели или будущим знанием, должно быть отделено от игрового UI и доступно только через диагностику разработки, если это нужно.

Главная формула:

```text
хороший UI = меньше админки + больше сцены + честная память + видимые ограничения персонажа
```
