# Как устроена работа над проектом

> Обзор системы документации и разработки. Норм не создаёт: правила — в [AGENTS.md](../../AGENTS.md) и
> [docs/governance](../governance/README.md), нормы подсистем — по
> [CONTRACT_INDEX](../../data/knowledge-source/corpus/DOCUMENTS/CONTRACT_INDEX.md). Здесь объяснено, зачем система
> устроена так, из чего она состоит и как ею пользоваться. Основа — лекция «Как писать код с нейросетями, не
> сжигая токены» и опыт самого проекта. Проверено: 2026-09-28, commit 3fd78c1f.

## 1. Главный принцип: минимальный достаточный контекст

Агенту не нужен весь проект. Ему нужен контекст под конкретную задачу: что сделать, где, как, что нельзя трогать
и по какому критерию результат считается правильным.

Лишний контекст вредит:

- модель путается и дорисовывает недостающее;
- каждый запрос дороже, агент думает дольше;
- растёт шанс «заодно улучшить» чужие файлы;
- результат трудно проверить.

Недостающий контекст вредит так же. Агент видит только то, что ему дали:

- не указана архитектура — он придумает свою;
- не указаны версии — выберет сам;
- не указаны готовые хелперы — напишет свои;
- не указаны крайние случаи — проверит только happy path.

Поэтому знания о проекте разложены по отдельным документам, и под задачу загружаются только нужные. С хорошим
контекстом справляется и более дешёвая модель. Если агент пишет не то, чинить надо контекст, а не менять модель
на более дорогую.

В Novgorod1230 этот принцип работает дважды. Игру ведёт слабая локальная LLM, и точный контекст ей подаёт World
Knowledge. Разработку ведут агенты, и точный контекст им подаёт эта система.

## 2. Формула работы

| Шаг | Что делаем | Где в проекте |
|---|---|---|
| 1. Зафиксировать задачу | цель, для кого и зачем, результат, уровень качества | GitHub issue |
| 2. Спецификация до кода | change request: владельцы, context pack, «не трогать», критерии готовности, проверки, допустимый долг | [CHANGE_REQUEST](CHANGE_REQUEST.md), форма `change_request` |
| 3. Собрать нужный контекст | строка маршрутизации роутера → разделы governance, строка CONTRACT_INDEX, `MODULE.md`, карты `docs/context`, LEGACY_WARNINGS | [WORKFLOW](WORKFLOW.md), шаг 3 |
| 4. Короткие итерации | маленький шаг → focused-тест → следующий шаг | [TESTING](../context/TESTING.md) |
| 5. Проверить | детерминированные проверки, CI, ревью каждой задачи, Contract Auditor по триггерам | WR §24, AR §25.1 |
| 6. Зафиксировать | строка CHANGELOG, LW, `Closes #N`, отчёт §29 | [WORKFLOW](WORKFLOW.md), «Завершение» |
| 7. Принять | владелец принимает результат по своим метрикам: плейтест, первый экран, проза | issue этапа |

Финальное решение и приёмка остаются за владельцем.

## 5. Роли и исполнители

- **Владелец (PavelSlaven):** замысел игры (PC §9.1), выбор между продуктовыми вариантами, разрешения на правку
  governance, приёмка этапов, решения о production. Сливает PR, только при зелёном CI.
- **Ревьюер-архитектор** — Claude Code со старшей моделью на машине владельца (текущий назван в
  [CURRENT_SPRINT](../work/CURRENT_SPRINT.md)). Ставит задачи и пишет CR. Одобряет планы исполнителей там, где это
  требует режим задачи (5.1). Ревьюит каждую сдачу против CR, плана этапа и замысла. Коммитит за Codex, переносит
  ветки на GitHub (10.4) и открывает PR. Утверждающие проходы и Contract Auditor запускает отдельной старшей
  моделью. Продуктовые, нормативные, необратимые и production-решения выносит владельцу.
- **Исполнители** работают по CR, каждый в своей ветке (решение владельца D31,
  [#133](https://github.com/PavelSlaven/Novgorod1230/issues/133#issuecomment-5866721387)). Кто какую задачу ведёт
  сейчас — [CURRENT_SPRINT](../work/CURRENT_SPRINT.md).

  | Исполнитель | Модели | Что делает | Ветка |
  |---|---|---|---|
  | Cursor | только Composer: `composer-2.5`, для механики `composer-2.5-fast` | код Runtime; вливает ветки других исполнителей кода в PR #98 | `codex/live-world-runtime` (PR #98) |
  | Codex, данные | ведущая `gpt-5.6-sol`, субагенты `gpt-6-luna`; `gpt-6-sol` не используется | данные игровой базы | `data/game-base-v1-*`, PR в main |
  | Codex, исследования | те же | выписки из книг, черновики данных, разведка кода и черновики дизайна, тесты без правки кода | без ветки или `fleet/<id>` |
  | младшие исполнители Claude | Sonnet | отдельные CR кода | `fleet/<id>` или своя ветка от PR #98 |

  Вопрос, который нельзя закрыть чтением проекта, исполнитель пишет ревьюеру и ждёт ответа. Свои данные не
  утверждает (WR §21.1), критерии и проверки приёмки молча не меняет (WR §24.2).
- **Утверждающий проход:** отдельный проход старшей модели инструмента на высоком reasoning или владелец утверждает данные, собранные другим агентом (WR §21.1).
- **Contract Auditor:** независимый read-only аудит по триггерам AR §25.1.
- **CI:** merge gate; полный `npm test` — в CI, локально только в случаях WR §24.

**Модель — под задачу**, а не старшая по умолчанию (решение владельца 2026-09-26): механика — младшие модели на
низком reasoning; исполнение — средние; старшая модель — только короткие проходы: утверждение данных, Contract
Auditor, архитектурная эскалация. Каждая подзадача — свежий субагент.

### 5.1. План до работы и режимы задач

Основание — решение владельца D31 ([#133](https://github.com/PavelSlaven/Novgorod1230/issues/133#issuecomment-5866721387)):
каждый исполнитель до работы присылает план и начинает после OK. Режимы задач ниже — уточнение владельца
2026-09-28.

До правок исполнитель присылает план: как понял задачу, где источник истины, что изменит, чем проверит, развилки,
объём. Работает только после подтверждения; при смене подхода — новый план. Без плана — только механические шаги,
продиктованные дословно. Свой аудит — не больше одного круга на сдачу: если исполнитель второй раз обходит то же
самое, он останавливается и задаёт вопрос.

| Режим | Задачи | План одобряет | Ревьюер проверяет |
|---|---|---|---|
| «План у ревьюера» | код, меняющий контракты, схему БД, промпты LLM или границы владельцев; утверждение данных | ревьюер | план и каждую сдачу |
| «Ведёт sol» | исследования, черновики данных, тесты без правки кода, разведка только на чтение | ведущая модель исполнителя (у Codex — `gpt-5.6-sol`, работу делают субагенты `gpt-6-luna`) | итоговую сдачу |

Режим задачи ревьюер пишет в её задании.

### 5.2. Обмен сообщениями исполнителя и ревьюера

Исполнитель и ревьюер переписываются через файлы задачи вне репозитория (10.1): `questions.md` пишет исполнитель,
`answers.md` — ревьюер, `progress.md` — журнал хода исполнителя, одна строка на этап. Это только канал сообщений,
а не источник истины.

Каждое сообщение — блок с заголовком `## <ТИП>-<задача>[-<шаг>] | <время> | <кратко>`.

| Блок | Кто пишет | Что это |
|---|---|---|
| `PLAN-…` | исполнитель | план до работы, 5–10 строк |
| `PLAN-OK-…` | ревьюер или ведущая модель (5.1) | план подтверждён, возможно с поправками |
| `Q-…` | исполнитель | вопрос, помеченный `blocking` или `non-blocking` |
| `A-…` | ревьюер | ответ на вопрос |
| `TASK-…` | ревьюер | поручение: ссылка на issue с CR и короткие указания |
| `DONE-…` | исполнитель | сдача: HEAD, что сделано, какие проверки реально выполнены, строки CHANGELOG и LW |
| `REVIEW-…` | ревьюер | `ACCEPTED` или `CHANGES_REQUESTED` с пронумерованными замечаниями |
| `NOTE-…` | ревьюер | решение владельца (в тот же день переносится в issue, PR или план) или указание вне цикла, например влить ветку |

Пути в сообщениях пишутся через `/`. На границе задачи действующие решения переносятся в репозиторий, а старый
лог архивируется: новая сессия начинает с репозитория, а не с чтения истории переписки.

## 6. Как собирается контекст исполнителя

1. **Старт сессии.** Роутер `AGENTS.md` (≤16 КБ) и личные глобальные правила инструмента. Исполнитель на servak
   дополнительно получает `RULES.md` и задание (10.2). Больше ничего обязательного.
2. **Под задачу.** Строки маршрутизации роутера → разделы governance. CONTRACT_INDEX по правилу чтения
   (§1–§3.1, строка §8.1, строки §4–§7 её документов). Из больших контрактов читаются нужные разделы, целиком —
   только редактируемый документ. `MODULE.md` владельцев, нужные карты `docs/context`, `rg` по LEGACY_WARNINGS,
   граф кода (CBM), `npm run knowledge:query` для норм.
3. **Не загружать:** весь корпус; историю прошлых чатов; документы «на всякий случай»; legacy-копии как нормы.
4. **Субагенты:** свежий субагент на подзадачу; разведчик возвращает короткий артефакт (файлы, строки,
   команды, неопределённости), а не пересказ репозитория.

## 7. Проверки: скрипт вместо модели, тест проверяет контракт

- Механическую работу делает детерминированный скрипт, модель нужна там, где требуется суждение (WR §19).
- Критерии готовности и проверки приёмки фиксируются до кода; проверки не подгоняются под реализацию (WR §24.2).
- Провал плейтеста сначала становится падающим регрессионным тестом на уровне хода, потом чинится (WR §22).
- Каждое изменение свободного поведения проверяется unseen-equivalent случаем (PC §5, WR §24).
- Пропущенный тест — не пройденный; проверка, которая не выполнялась, не называется пройденной.

## 8. Симптом → причина → что чинить

| Симптом у агента | Причина | Что чинить |
|---|---|---|
| жжёт токены и пишет не то | нет спецификации | CR до кода |
| перечитывает весь проект | документы не разделены или устарели | карты `docs/context`, строка маршрутизации |
| путает архитектуру, вводит свои паттерны | архитектура и владельцы не описаны | ARCHITECTURE, `MODULE.md` |
| тянет новые библиотеки | стек не зафиксирован | STACK |
| пишет свои хелперы и компоненты | не указано, что уже есть | ARCHITECTURE, UI_KIT |
| тестирует только happy path | нет крайних случаев | EDGE_CASES, unseen-equivalent в CR |
| не понимает задачу | цель и критерии не записаны | CR |
| теряет историю проекта | нет текущего спринта, слишком большой контекст | CURRENT_SPRINT, одна задача — одна сессия |
| «улучшает» костыли или ломается о legacy | долг не записан | LEGACY_WARNINGS |
| пишет сценарный код вместо общего механизма | пример принят за норму, статусы вводят в заблуждение | PC §5, AI §15, статус только из CONTRACT_INDEX |
| «чинит» тест вместо кода | критерии приёмки не зафиксированы до кода | CR, WR §24.2 |

## 9. Как поддерживать порядок

- Нашёл ловушку — запиши в LEGACY_WARNINGS и заведи issue, не чини попутно.
- Изменился факт — поправь карту `docs/context` и обнови штамп «Проверено».
- Появилось решение владельца — перенеси его в issue или PR, а не оставляй в чате или переписке.
- Новый этап или крупный merge — context dump на той ветке, где идёт работа.
- **Ревьюер проверяет порядок в документах на границе каждой задачи:**
  - в сдаче есть строки CHANGELOG и LW;
  - [CURRENT_SPRINT](../work/CURRENT_SPRINT.md) обновлён, если сменились порядок задач или исполнители;
  - план этапа обновлён в ветке PR #98, если он изменился;
  - решения владельца перенесены в issue в тот же день;
  - этот документ обновлён, если изменился сам процесс: исполнители, площадка, правила обмена.
- Ссылки в картах и процедурах проверяет `npm run test:docs`, корневые `.md` — `docs:check`.

## 10. Рабочая площадка: servak и машина владельца

Тяжёлая работа идёт на **servak** — сервере владельца (64 потока, 251 ГБ памяти; доступ `ssh servak`). Там
работают исполнители, тесты с PostgreSQL и исследования. Машина владельца остаётся для игры владельца, приёмки и
отправки веток на GitHub.

Инструменты флота (`fleet`, `pg-slot`, `RULES.md`) живут на servak, а не в репозитории. Их устройство описано в
этом разделе; меняется устройство — меняется и раздел.

### 10.1. Что где лежит на servak

Всё наше — только в `/srv/novgorod-work/`. Остальное на сервере принадлежит владельцу и не трогается: сервисы
моделей, библиотека, веб-сервисы.

| Путь в `/srv/novgorod-work/` | Что |
|---|---|
| `fleet/bin/fleet` | запуск и учёт исполнителей |
| `fleet/RULES.md` | правила для исполнителей на servak; каждый получает их при первом запуске |
| `fleet/bin/pg-slot` | запуск теста с PostgreSQL в одном из двух слотов; если оба заняты, ждёт |
| `fleet/tasks/<id>/` | задача: `TASK.md`, `questions.md`, `answers.md`, `progress.md`, логи запусков `runs/`, `task.env` |
| `worktrees/<id>` | рабочая копия задачи кода: ветка задачи и свой `npm ci` |
| `worktrees/ref-pr98`, `worktrees/ref-gamebase` | эталонные копии только для чтения: ветка PR #98 и закреплённый коммит игровой базы |
| `data/books/` | индекс библиотеки для исследований, выписки `evidence/`, инструкция сборщика `scripts/COLLECTOR_BRIEF.md` |
| `prose-test/` | стенд прозаического теста (10.6) |

Основной клон репозитория на servak — `/root/Novgorod1230`; рабочие копии задач — его worktree.

### 10.2. Как ревьюер ведёт задачу

1. `fleet new <id> <claude|codex|cursor> <модель> <reasoning> <code|research> [база]` создаёт задачу. Для кода —
   рабочую копию на ветке `fleet/<id>` от базы; по умолчанию база — `codex/live-world-runtime`.
2. Ревьюер пишет `TASK.md`: ссылка на issue (CR), режим (5.1), рамки, что сдать.
3. `fleet run <id>`: первый запуск получает `RULES.md` и `TASK.md`, следующие продолжают сессию исполнителя.
4. Ревьюер следит за `fleet heads` — последним заголовком каждой задачи. Отвечает в `answers.md` и снова
   запускает `fleet run <id>`.

Каждый запуск идёт в systemd scope с квотой CPU и памяти. Одновременно — до 3 исполнителей Claude, 10 Codex и
2 Cursor; у сессии Codex — до 8 субагентов `gpt-6-luna`. Точные значения — в `fleet/bin/fleet`. Сеть из песочницы
Codex закрыта. Задаче, которой нужен локальный Qwen владельца, ревьюер открывает её строкой `NET=1` в `task.env`.

### 10.3. Правила исполнителей на servak

Кратко; полный текст — `fleet/RULES.md`.

- План до работы (5.1), заголовки сообщений (5.2), журнал `progress.md`.
- **Без фоновых команд.** Исполнитель работает без интерфейса: когда он остановится, его никто не разбудит.
  Длинные прогоны — в переднем плане, с таймаутом до 30 минут.
- Нельзя push, rebase, reset, `git clean` и другие широкие destructive-команды.
- **Codex не пишет в git:** его песочница держит `.git` только для чтения. Ветку заранее создаёт ревьюер, он же
  коммитит после ревью. Claude и Cursor коммитят сами.
- **Тесты с PostgreSQL — только через `pg-slot`.** На servak Docker с AppArmor блокирует unix-сокеты PostgreSQL.
  Поэтому тестовая обвязка при `NOVGOROD_TEST_DOCKER_APPARMOR_UNCONFINED=1` запускает контейнеры с
  `apparmor=unconfined`. Переменную выставляют сами `fleet` и `pg-slot`.
- Сервисы владельца не трогать; локальную модель владельца вызывать только как клиент.
- Ключи API и другие секреты не печатать, не копировать и не логировать.
- Не заявлять проверку, которая не выполнялась.
- Субагенты — только младшие модели из раздела 5.

### 10.4. Git: ветки и перенос на GitHub

- Токен GitHub на servak — только для чтения. Ветку после ревью переносит ревьюер со своей машины:
  `git fetch ssh://servak/root/Novgorod1230 <ветка>`, затем `git push origin FETCH_HEAD:refs/heads/<ветка>`.
- **Код:** ветка от `codex/live-world-runtime`. Её вливает в PR #98 Cursor обычным merge по `NOTE` ревьюера,
  rebase запрещён (D31).
- **Данные игровой базы:** ветка от линии game-base, PR в main. Runtime импортирует данные по закреплённому
  коммиту через существующий P12-импортёр (D31).
- Merge в main делает только владелец и только при зелёном CI.

### 10.5. Путь данных игровой базы

1. **Выписки.** Исследовательская задача собирает цитаты из книг библиотеки по `COLLECTOR_BRIEF.md`. Скрипт
   сверяет каждую цитату с полнотекстовым индексом; результат — `data/books/evidence/<группа>.csv`.
2. **Черновик** (`candidate`) — Codex по выпискам. Чего нет в источниках, то помечается пробелом, а не
   заполняется выдумкой.
3. **Детерминированные проверки:** build и check профилей с `--self-test`, валидатор мест, построчный diff и
   counts.
4. **Проверка содержания:** раунды проверки — отдельная старшая модель на группу данных; результат — раздел
   `VERIFICATION` рядом с данными.
5. **Утверждение** — отдельный проход, не автор данных (WR §21.1); запись утверждения — рядом с данными.
6. **PR в main**, merge владельцем, импорт в Runtime по закреплённому коммиту.

### 10.6. Прозаический тест

Проверяет, хватает ли данных игровой базы, чтобы слабая локальная модель писала сцену без выдумок. Писатель —
локальный Qwen владельца, судьи — слепые проходы Claude по калибровочной рубрике. Порог —
[#158](https://github.com/PavelSlaven/Novgorod1230/issues/158#issuecomment-5857929393). Стенд — `prose-test/` на
servak.
