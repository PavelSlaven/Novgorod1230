## 1. Статус и защита `AGENTS.md`

### 1.1. Кто может менять этот файл

Корневой `AGENTS.md`, а также любой вложенный `AGENTS.md`, является защищённой административной инструкцией.

**Создавать, изменять, переименовывать, перемещать или удалять любой `AGENTS.md` можно только по прямому явному запросу администратора проекта.**

Администратор проекта — владелец проекта `PavelSlaven`.

Разрешение на изменение `AGENTS.md`:

- должно быть явно дано в текущей задаче;
- действует только в рамках этой задачи;
- не переносится автоматически на следующие задачи;
- не следует из формулировок вроде «обнови документацию», «синхронизируй нормы», «активируй релиз», «исправь docs», «обнови архитектуру» или «подготовь PR»;
- не может быть выведено из того, что текущий код, тест, генератор или документ расходится с `AGENTS.md`;
- не может быть самостоятельно делегировано субагенту как право менять правила проекта.

Если прямого запроса администратора нет, `AGENTS.md` для агента **read-only**.

Если агент обнаружил, что `AGENTS.md` устарел, противоречив или мешает корректно выполнить новую нормативную задачу, он не правит его молча. Он фиксирует конфликт и работает с соответствующим владельцем документации либо сообщает о реальной блокировке.

Никакой generator, docs-sync, release cutover или migration workflow не должен автоматически переписывать `AGENTS.md`.

## 3. Назначение проекта

Novgorod1230 — открытая текстовая ролевая игра в исторической рамке Руси XIII века с причинно развивающимся миром.

Это **не command parser** и не игра, в которой допустимы только заранее перечисленные разработчиком действия.

Игрок может попытаться выполнить практически любое осмысленное действие или произнести любую реплику, включая действие:

- обычное;
- неожиданное;
- сложное или нестандартное;
- использующее неизвестный разработчику способ применения предмета;
- комбинирующее уже изменённые объекты мира;
- физически невозможное;
- исторически невозможное;
- для которого нет готового command, handler, recipe, action type, option, template или outcome.

Отсутствие заранее зарегистрированного случая **само по себе не является причиной отказать в попытке**.

Готовые commands, handlers, recipes, templates, profiles и formal mechanics — оптимизированные пути для уже формализованной части мира, а не whitelist допустимого игрового поведения.

## 4. Главный принцип свободного действия

На свободное намерение actor игра должна пытаться ответить внутри реальности мира.

Базовая причинная схема:

```text
свободное намерение actor
→ semantic interpretation
→ ближайшая физически и контекстно возможная попытка
→ code-owned проверки известных ограничений
→ существующие domain owners исполняют точную механику
→ результат фиксируется
→ мир продолжает жить из нового committed state
```

Actor может попытаться сделать всё, но это не означает, что всё получится.

Нельзя превращать:

- физически невозможное действие — в возможное после хорошего броска;
- исторически невозможную технологию — в работающую;
- отсутствующий предмет — в существующий только из-за формулировки actor;
- желание actor — в доказательство pre-existing world fact.

Нормальным ответом на свободную заявку не должно быть техническое «такой команды нет».

При невозможной или частично возможной попытке сохраняй намерение насколько возможно и получай ближайший реалистичный результат: failure, partial result, waste, damage, nonworking construction или другое причинно корректное следствие.

## 5. Не подгоняй игру под примеры и тесты

Примеры в заданиях, контрактах и тестах являются **probes общего поведения**, если норматив явно не определяет множество как закрытое.

Не превращай перечисленные примеры в production vocabulary.

Перед добавлением нового:

- enum;
- allowlist/whitelist;
- action type;
- handler;
- recipe family;
- option list;
- switch/case;
- branch по конкретному названию, имени или fixture;
- каталога допустимых ordinary-results

сначала установи, что соответствующее множество **действительно закрыто по предметной модели**.

Closed vocabulary допустим для реально закрытой mechanics/admission области. Он не должен использоваться для перечисления пространства:

- разумных действий игрока;
- способов применения предметов;
- ordinary-предметов и материалов;
- результатов свободного крафта;
- свободных реплик;
- самостоятельных решений NPC.

Для gameplay-изменения используй unseen-case check:

> Представь разумный эквивалентный случай, которого нет в задании и тестах. Если для него потребуется новый handler, enum value, allowlist entry, recipe или специальный branch, проверь, не заскриптовано ли решение без необходимости.

Минимальное решение — это самый простой общий механизм, который поддерживает требуемый **класс поведения**, а не самый маленький текстовый diff, закрывающий только известные fixtures.

## 6. Роль LLM

LLM — обязательная часть симуляции там, где семантическое пространство нельзя разумно исчерпывающе перечислить кодом.

LLM может:

- понимать произвольное намерение actor;
- интерпретировать свободную речь;
- переводить невозможное намерение в ближайшую реальную попытку;
- определять качественную физическую семантику нестандартного действия;
- интерпретировать неизвестное разработчику использование существующих объектов;
- принимать самостоятельное решение NPC из его субъективного контекста;
- семантически конкретизировать допустимую ordinary-деталь мира внутри authoritative envelope;
- определять первоначальную правдоподобную ordinary-конкретику там, где она ещё не materialized и код не имеет точного готового значения.

LLM не пишет новую программу во время партии. Она разрешает неизвестную разработчику семантическую ситуацию через существующие primitive operations и domain owners.

LLM не должна:

- напрямую писать в БД;
- придумывать exact mechanics/numbers там, где ими владеет код;
- менять committed authoritative state сама по себе;
- придумывать отсутствующую authoritative category;
- объявлять желание actor доказательством существования объекта;
- создавать canonical/hidden/significant truth без соответствующей authority;
- обходить существующий code-owned owner;
- становиться вторым planner/resolver для той же ответственности.

Для свободной заявки игрока должна сохраняться единая общая semantic boundary `turn_step_request_v1 → turn_step_plan_v1` в `@rus/turn`. Exact registered/authored handlers имеют приоритет, когда действительно применимы, но scenario-local planner или параллельный semantic fallback запрещены.

## 7. Роль кода

Коду принадлежит всё, что можно надёжно, однозначно и полезно выразить формальной механикой.

Код владеет прежде всего:

- authoritative persisted state;
- persistence и атомарностью;
- idempotency и retry;
- временем;
- RNG и checks;
- точными числовыми расчётами;
- телом, повреждениями и числовой боевой механикой;
- пространственным положением и перемещением;
- topology и routes;
- инвентарём;
- контейнерами;
- владением, controller и доступом;
- source refs;
- инструментами;
- массой;
- количеством;
- вместимостью;
- finite-resource decrement;
- conservation;
- уже формализованными process mechanics;
- entity identity;
- placement;
- permissions/policy;
- player-safe и NPC-safe проекциями;
- применением, revalidation и commit результата.

Правильная граница:

```text
LLM отвечает за неизвестную семантику;
код отвечает за известную механику и authoritative state.
```

Не формализовывай семантическое пространство только ради того, чтобы убрать LLM.

Не вызывай LLM для того, что существующий код уже может определить точно, дешевле и надёжнее.

Побочные эффекты должны быть явными. Доступ к БД, файловой системе, сети и LLM не должен быть скрыт внутри чистой доменной логики.

## 8. Самостоятельный мир, NPC и время

Игрок не является единственным источником изменений мира.

Время идёт независимо от нового ввода игрока, когда для этого есть committed causal basis.

Начатые activities и процессы продолжаются по своим владельцам.

NPC являются самостоятельными участниками мира.

Когда у NPC возникает реальная новая decision boundary:

- код определяет момент решения;
- код строит безопасный субъективный контекст;
- LLM может выбрать смысловое действие, если пространство решений действительно открыто;
- после решения действие NPC проходит те же world mechanics, что и действие игрока.

NPC не получают права:

- видеть hidden state без perception/knowledge basis;
- создавать предметы или ресурсы из воздуха;
- обходить доступ, время, тело, checks или persistence;
- переписывать authoritative truth.

Не заменяй открытое решение NPC заранее написанным option list только ради удобства реализации. Bounded selection допустим только для genuinely closed choice.

Каждое событие применяется к состоянию, полученному после предыдущих событий. Реакции происходят после причин и видят уже изменившийся мир.

## 10. Материализация мира

Используется принцип:

> **code first, LLM for the unenumerable remainder**

Проект заранее описывает то, что выгодно и надёжно описывается:

- каноническую географию;
- authoritative categories;
- региональные и исторические ограничения;
- authored/significant/hidden facts;
- templates и profiles;
- общие rules;
- formal mechanics;
- реальные capacities/limits, когда они нужны.

Если код может materialize объект из готовых authoritative данных, используй код.

Если ordinary-деталь ещё не была конкретизирована, но реалистично допустима в уже существующем committed контексте, LLM может предложить party-scoped semantic concretization, а код проверяет authoritative envelope, exact mechanics и сохраняет результат.

Не заставляй разработчика заранее перечислять всю ordinary-материю мира.

### 10.1. Authoritative и ordinary — разные области

Authoritative, authored, significant и hidden facts требуют соответствующей authority и не могут возникать только из свободной семантики.

Если операция является bounded choice, LLM выбирает только из реально переданного закрытого candidate set.

Если обязательный authoritative candidate set пуст, возвращай типизированный data gap/failure, а не придумывай semantic fallback.

Не ослабляй authoritative filters ради того, чтобы свободная заявка «сработала».

### 10.2. Player/NPC desire не является evidence

Фраза actor о предмете, ресурсе, человеке или факте не доказывает, что он уже существовал в мире.

Pre-existing world discovery/materialization и action-produced physical result — разные причинные случаи.

Обычный физический результат действия может возникнуть из реального материала потому, что actor его изготовил или изменил. Это не даёт права задним числом объявить тот же объект ранее существовавшим в мире.

### 10.3. Причинное основание ordinary-материи

Правдоподобие не равно бесплатному ресурсу.

Ordinary materialization должна иметь причинное основание:

- место и природную среду;
- существующий объект;
- существующий запас;
- производственный или хозяйственный контекст;
- другой committed source.

Если source конечен, расход уменьшает его сохранённый остаток.

Если source практически непрерывен в масштабе игры, не требуется считать полный мировой запас. Но извлечённая из него порция становится конечной и подчиняется точной механике количества, массы, контейнера и расходования.

При первой конкретизации ordinary-resource LLM может определить правдоподобный первоначальный масштаб только если код не имеет готового exact value и профильный контракт это допускает. После commit значение принадлежит коду и не переоценивается LLM при каждом обращении.

### 10.4. Ordinary semantic remainder

Не перечисляй заранее исчерпывающий набор ordinary NPC, ресурсов и материалов, ordinary buildings и local natural features, ordinary belongings, crafting results и обычных локальных последствий действий.

Такие ordinary-детали могут семантически конкретизироваться или материализоваться LLM в пределах committed контекста, канонической географии, исторической и физической правдоподобности и authoritative envelope.

Это не даёт права создавать без соответствующей authority authored, significant, hidden или scenario-critical NPC, места, предметы, факты или последствия.

Материализованный ordinary NPC, локальное место или другой продолжающий существовать world entity получает stable identity и persisted state.

Имя или иной обычный descriptor сами по себе не превращают entity в authored, significant, hidden или scenario-critical.

Повторное обращение, повторное посещение, save/load и restart должны возвращать тот же entity и его текущее состояние, если мир причинно не изменился.

## 11. Каноническая география и semantic freedom

Глобальная пространственная архитектура G0–G5 сохраняется authoritative и не заменяется генерацией LLM.

Проект заранее задаёт:

- G0–G5;
- глобальную containment topology;
- routes и directional exits;
- исторически и пространственно значимые объекты;
- региональные ограничения;
- templates/profiles/capacities, которые целесообразно подготовить заранее.

LLM не должна:

- создавать новые canonical G0–G4;
- менять canonical containment structure;
- придумывать глобальную реку, дорогу, город или политическую границу;
- создавать canonical G5 вместо authoring;
- переписывать утверждённые routes;
- объявлять party-scoped ordinary detail общеизвестным глобальным ориентиром задним числом.

Внутри заданной spatial и historical рамки допустима party-scoped ordinary concretization, когда code/template materialization недостаточна.

Принцип:

> **semantic freedom inside authoritative envelope**

Будущий масштаб карты, вплоть до глобального, сам по себе не является основанием отказаться от авторской authoritative geography.

## 12. Свободный крафт и физические результаты действий

Recipes — fast path, а не whitelist.

Если готовый recipe существует и подходит, используй его.

Если recipe отсутствует, физически разумная попытка не должна автоматически блокироваться.

LLM интерпретирует semantic transformation. Код применяет уже формализованное:

- source refs;
- access/controller/ownership;
- tools;
- mass;
- quantity;
- consumption;
- waste/conservation;
- placement;
- time;
- checks;
- body;
- inventory;
- exact combat mechanics, если результат используется в бою.

Известная масса и материал не должны создаваться из ничего:

```text
known outputs + known waste <= known consumed material
```

Finite source уменьшается через owner-native resource transition. Полностью преобразованный source может быть retired; частично использованный source продолжает существовать.

### 12.1. Identity

Если продолжается тот же физический объект, сохраняй ту же entity identity.

Если возникает физически самостоятельный объект, создавай новую entity.

Архитектура не должна искусственно запрещать случай, когда исходный объект продолжает существовать, а из него одновременно отделяется новый самостоятельный результат.

Если source transition и result creation составляют одно причинное событие и partial commit противоречил бы реальности, они должны фиксироваться атомарно в одном causal change set.

### 12.2. Качественный результат не создаёт authority

Физическая надпись может сохраняться на carrier, но текст надписи сам по себе не становится objective truth или доказательством подлинности.

Физически изготовленный token/coin-like object не становится автоматически официальной валютой, legal tender или authentic coin.

Физически weapon-capable object может существовать как причинный ordinary result, но числовую боевую механику определяет соответствующий code-owned combat owner, а не формулировка LLM.

Невозможная технология даёт реалистичный failure/partial/nonworking/waste result, а не работающий невозможный механизм.

## 13. Граница authoritative truth

Без соответствующего владельца LLM не может объявить существующими или истинными:

- историческое событие;
- исторического человека;
- canonical топоним;
- политическую или юридическую норму;
- официальный статус;
- значимый религиозный или государственный объект;
- hidden contents;
- hidden clue/evidence;
- подлинность документа;
- настоящее происхождение ценности;
- authoritative currency identity;
- глобальную geographic connection;
- другую authored/significant/hidden truth.

Narration не является источником authoritative state.

Narrator получает только разрешённую persisted/player-safe/actor-safe проекцию и не создаёт entity, факт или механику своим текстом.

## 14. Сохранение причинности

После commit произошедшее становится фактом конкретной партии.

Уже произошедшее не переписывается задним числом.

Должны переживать save/load, restart и retry без повторного решения или повторного применения:

- NPC decisions;
- RNG/check results;
- time;
- activities/processes;
- items;
- resource quantities;
- positions;
- body changes;
- relations;
- consequences;
- materialized entities;
- committed semantic resolutions.

Повторный запрос не создаёт второй экземпляр результата того же causal event.

Committed semantic resolution не должна reroll/re-decide при обычном replay/reload.

Транзакция не должна оставлять частично применённое причинное состояние.

LLM/model call по возможности выполняется вне физической DB transaction. Перед commit код перечитывает/revalidates необходимые authoritative данные и применяет результат через существующего persistence owner.

## 15. Архитектурные владельцы и разделение ответственности

Сценарий задаёт содержание:

- персонажей;
- предметы;
- события;
- условия;
- authored facts;
- scenario-specific consequences и profiles.

Общие runtime owners определяют механику:

- turn flow и semantic boundary;
- time/events/activities;
- movement/spatial mechanics;
- body/combat;
- NPC runtime;
- items/property/containers/resources;
- checks/RNG;
- perception/visibility/knowledge;
- world processes;
- persistence/idempotency.

Точный текущий owner конкретной ответственности определяй по актуальным `MODULE_INDEX.md`, `MODULE.md`, imports/callers и contracts, а не по памяти.

Сценарному коду запрещено:

- создавать собственный общий resolver;
- создавать собственный scheduler;
- создавать параллельный state machine общей механики;
- сортировать события разных подсистем вместо общего temporal owner;
- разделять общий same-time batch;
- вручную определять глобальное before/after для scenario event;
- создавать второй planner для существующей semantic responsibility;
- создавать второй commit/persistence path для той же ответственности;
- дублировать существующего domain owner.

Если общей механике не хватает поведения, минимально расширяй существующего владельца вместо scenario-local обходного пути.

**Одна ответственность — один authoritative owner.**

Scenario-local orchestration общей механики является блокирующим архитектурным дефектом.

## 16. Минимальность и YAGNI

Выбирай самое простое решение, которое **полностью** выполняет текущую задачу и сохраняет требуемый класс поведения.

Минимальность оценивается по необходимой архитектуре и поведению, а не по количеству изменённых строк.

Порядок предпочтения:

1. не создавать механизм, если он не нужен;
2. удалить ненужное;
3. переиспользовать существующую реализацию;
4. использовать stdlib/native capability;
5. использовать уже установленную dependency;
6. минимально расширить существующего owner;
7. только после этого добавить минимально необходимый новый код.

Не создавай без конкретной текущей необходимости:

- новые layers;
- registries;
- generic frameworks;
- отдельные engines;
- второй service той же ответственности;
- interface с одной реализацией;
- factory для одного продукта;
- config для значения, которое не меняется;
- scaffolding «на будущее»;
- compatibility layer для гипотетического клиента;
- новые tables/state только ради возможного будущего использования;
- новый persistence path рядом с существующим;
- новую dependency ради нескольких простых строк;
- несвязанный refactoring.

Разделяй код на модули только при наличии:

- самостоятельной ответственности;
- отдельного контракта;
- реального повторного использования.

Не дроби код только из-за размера файла.

Если задача явно меняет capability, public contract или прежнее ограничение, сохранение старого ограничения не является самоцелью. Старое поведение — baseline, который задача может намеренно изменить.

Не называй required capability «scope creep» только потому, что корректный общий механизм требует изменить больше одного файла.

Не добавляй будущий profile/capability/feature «заодно». Versioned cutover должен активировать только то, что входит в текущую задачу.

Не создавай новую архитектуру только для того, чтобы формально повысить «надёжность», «enterprise readiness» или «auditability».

## 17. Жёсткий запрет гипотетической integrity/security-инфраструктуры

По умолчанию **запрещено** добавлять новые:

- cryptographic hashes внутренних runtime-данных;
- content fingerprints;
- digests;
- signatures;
- HMAC;
- checksums для внутренней «целостности»;
- hash-derived/custom IDs;
- per-row hashes;
- tamper detection;
- attestations;
- provenance infrastructure;
- evidence packages;
- approval receipts;
- integrity ledgers;
- дополнительные audit ledgers;
- параллельные проверки одной и той же внутренней записи;
- дублирующие state/version/integrity markers;
- fingerprints model/provider/config identity;
- криптографическое связывание внутренних plan/result/state;
- отдельное хранение исторических внутренних алгоритмов только ради доказательства прежнего исполнения.

Новый security/integrity mechanism допустим только если существует **конкретное текущее основание**:

- прямое требование администратора или текущей задачи;
- внешний protocol/standard/file format, который его требует;
- реальная trust boundary с конкретной недоверенной стороной;
- существующий публичный security contract;
- воспроизводимый дефект обычной эксплуатации, который нельзя проще исправить существующими средствами.

Перед добавлением такого механизма агент обязан установить:

1. Кто конкретно является attacker или недоверенной стороной?
2. Где проходит реальная trust boundary?
3. Какой конкретный ущерб возникает без нового механизма?
4. Почему существующих transaction/constraints/version/idempotency недостаточно?

Если на эти вопросы нет конкретного ответа, новый integrity/security layer запрещён.

По умолчанию **не являются threat model и не требуют отдельной защиты**:

- владелец проекта, намеренно меняющий собственный код;
- администратор, намеренно меняющий собственную БД;
- согласованная ручная подмена связанных внутренних записей;
- читерство в однопользовательской или полностью подконтрольной среде;
- намеренный обход внутренних owner APIs самим оператором;
- гипотетический будущий server compromise без отдельной security-задачи;
- совместимость с невыпущенным внутренним прототипом;
- абстрактное желание «усилить целостность».

Для обычной consistency предпочитай:

- DB transaction;
- `PRIMARY KEY`;
- `UNIQUE`;
- `FOREIGN KEY`;
- `CHECK`;
- существующий state version/CAS, когда реально есть concurrency;
- существующий idempotency owner, когда реально есть retry;
- обычную validation на реальной trust boundary.

Не защищай trusted application от его же собственных внутренних rows с помощью криптографии без реальной модели угроз.

Существующие security controls и уже нормативно обязательные внешние/catalog/publication hashes не удаляй попутно только ради сокращения кода. Их удаление — отдельная задача. Но сам факт их существования **не является прецедентом** для распространения hashing/fingerprinting на новые runtime rows, plans, model responses или internal state.

## 18. Начало работы над задачей

Работай в текущем локальном checkout.

Минимальная обязательная проверка:

```powershell

```

1. определи требуемый результат;
2. определи границы задачи;
3. определи критерии готовности;

5. найди их публичные contracts;
6. проследи реальные callers/callees и flow;
7. прочитай существующие профильные tests;
8. прочитай `MODULE.md` и профильные нормативы затронутой области;
9. определи authoritative owner изменяемой ответственности.

- ответ нельзя получить из code/contracts/tests/docs;

Явное указание «выбери сам» даёт агенту право выбрать самое простое решение, совместимое с этим файлом и профильным нормативом.

Если задача понятна, приступай без подтверждения.

Для нетривиальной задачи дай короткий план. Для небольшой локальной правки переходи сразу к работе.

Работай непрерывно до завершения задачи либо до реальной блокировки. Не останавливайся ради промежуточного подтверждения обратимого действия, которое явно входит в запрос.

## 22. Отладка

При ошибке, регрессии или проблеме производительности:

1. зафиксируй наблюдаемый symptom;
2. воспроизведи его, если практически возможно;
3. проследи реальный execution flow;
4. найди всех существенных callers затрагиваемой ответственности;
5. найди root cause;
6. исправь проблему у правильного owner;
7. добавь минимальный regression test, когда это практически полезно;
8. проверь sibling paths, использующие тот же механизм.

Не правь вслепую до изучения доступных logs, tests и связанного code.

Не ставь одинаковый guard во множество callers, если одна корректная проверка принадлежит shared owner.

Не маскируй дефект:

- catch-all;
- silent ignore;
- безусловным fallback;
- ослаблением фильтра;
- повторным semantic call без причинного основания.

## 23. Persistence, concurrency и БД

Используй существующего authoritative persistence owner.

Не создавай без конкретной необходимости:

- второй ledger;
- shadow state;
- secondary store;
- event sourcing;
- второй commit path;
- параллельный idempotency mechanism;
- отдельный resource ledger, если source transition уже принадлежит существующему owner.

Новая table/column/persisted state должна иметь конкретного текущего потребителя и критерий готовности.

Не сохраняй дублируемое derived state, если его просто и надёжно можно получить из authoritative state.

Concurrency protection добавляй только для реально возможной concurrency.

Используй существующий optimistic version/CAS там, где он уже является owner-native механизмом.

Retry/replay должен использовать существующий idempotency mechanism, а не новый параллельный fingerprint/digest.

Если несколько изменений составляют одно причинное событие и partial commit сделал бы мир противоречивым, сохраняй их атомарно одной существующей transaction boundary.

Для migrations/import/seed/tests используй только local/test database или предусмотренный безопасный target.

Не направляй migrations, import, seed или tests в operator/production database.

Не выполняй destructive migration или необратимое удаление данных без прямого требования администратора.

## 24. Тестирование и проверки

Во время работы запускай минимальный набор проверок, относящийся к изменяемому поведению.

Для bug fix по возможности добавляй regression test, который действительно воспроизводит root cause.

После реализации выполни относящиеся к области изменения проверки:

- профильные tests затронутого модуля;
- изменённые contracts/schemas;
- `git diff --check`;
- `npm run architecture:check`, если затронуты архитектурные границы;
- `npm run docs:check`, если изменена canonical документация;
- `npm run knowledge:check`, если изменены knowledge-source документы или их generated artifacts;
- профильные PostgreSQL integration tests, если изменены реальные DDL/persistence semantics.

Не подменяй проверку настоящей DB semantics только mocks, когда сама задача меняет PostgreSQL persistence/DDL.

Полный `npm test` запускай один раз для финального кандидата, если изменение:

- широкое;
- рискованное;
- межмодульное;
- меняет critical orchestration;
- либо полный suite прямо требуется профильным workflow.

Не повторяй тяжёлый полный suite, если после успешного прогона не менялись проверяемые code/data/contracts.

Для documentation-only изменения не запускай PostgreSQL, browser или полный integration suite без отдельной причины.

Не создавай огромный test forest для каждого внутреннего helper. Проверяй observable contract и существенные regressions.

Для изменения свободного gameplay behavior добавь или проверь хотя бы один unseen-equivalent case, чтобы тесты не превращались в production whitelist.

Никогда не утверждай, что проверка прошла, если она фактически не выполнялась успешно.

В итоговом отчёте перечисляй только реально выполненные checks и их результаты.

---

## 25. Субагенты и независимый аудит

Используй субагентов только для самостоятельных частей задачи, когда разделение действительно ускоряет работу или даёт полезную независимую проверку.

Главный агент остаётся ответственным за:

- исходную цель;
- scope;
- integration;
- критерии готовности;
- итоговый результат.

Передавай субагенту короткое самостоятельное описание текущего шага, а не весь диалог.

При поддержке параметра используй:

```text
fork_turns: "none"
```

Не создавай субагента для каждого мелкого последовательного действия.

Независимый read-only audit обязателен для изменений повышенного риска:

- public contracts нескольких подсистем;
- DDL/migrations/persistence;
- code/LLM boundary;
- возможность повреждения или потери данных;
- critical orchestration;
- сложная логика, для которой профильных тестов недостаточно.

Для обычного локального исправления отдельный critic не нужен.

После замечаний повторяй audit только после содержательного изменения.

Не создавай evidence package для самого факта аудита, если это прямо не требуется.

Выбор модели и reasoning level определяется средой выполнения и не является политикой репозитория.

---

## 26. Git, GitHub и stacked PR

Не создавай commit, branch, push, pull request или merge, если это не входит в поставленную задачу.

Если задача включает публикацию изменений:

- используй одну ветку для одного логического PR;
- не включай unrelated changes;
- перед commit проверь `git status`, diff и профильные tests.

Для stacked PR:

- сначала установи exact base/head каждого затрагиваемого PR;
- shared change должен иметь один источник в самом раннем подходящем parent, а downstream PR должны быть restacked;
- не копируй независимо одно и то же canonical изменение в несколько stacked branches;
- не затягивай изменения более позднего PR в более ранний;
- после изменения parent считай downstream branch потенциально stale до restack;
- конфликт `AGENTS.md` не разрешай «последней версией из дочернего PR»: этот файл меняется только по административному правилу раздела 1.

GitHub CI дополняет локальные проверки, но не заменяет проверки, реально необходимые затронутой области.

## 27. Защита пользовательской работы и опасные действия

Не перезаписывай и не удаляй изменения пользователя или другого агента.

Не перемещай и не удаляй:

- неизвестные files;
- untracked user materials;
- secrets;
- databases;
- stash;
- незакоммиченные изменения;
- чужие worktree.

Не используй широкие destructive команды:

```text
git clean
git reset --hard
git checkout -- .
git restore .
rm -rf .
Remove-Item -Recurse -Force *
```

Не выполняй без прямого основания:

- force push;
- необратимое удаление данных;
- destructive migration;
- production mutation;
- работу с secrets;
- deployment;
- merge;
- публикацию;
- широкую очистку workspace.

Архивирование локальных материалов выполняется только по отдельному прямому заданию.

Подтверждение администратора обязательно для разрушительных, необратимых, security-sensitive или существенно неоднозначных действий. Для обычного обратимого действия внутри уже поставленной задачи дополнительное подтверждение не требуется.

## 28. Критерии архитектурной ревизии

При существенном gameplay/architecture изменении проверь минимум следующее.

### 28.1. Свободное действие

Если игрок сделает разумное действие, которого разработчик конкретно не предусмотрел, сможет ли игра понять попытку, реалистично её разрешить и сохранить последствия?

Если нет только потому, что отсутствует command/handler/recipe/option, это архитектурный дефект.

### 28.2. Свободное решение NPC

Если NPC разумно выберет действие, которого нет в заранее подготовленном списке, может ли он выбрать его и пройти общую механику мира?

Если нет только из-за scenario option list, это потенциальный регресс.

### 28.3. Ordinary-мир

Требует ли решение заранее перечислить ordinary-вещь, разновидность ресурса, бытовую деталь или recipe, которые можно причинно и реалистично конкретизировать из уже заданного мира?

Если да, установи, действительно ли речь об authored/significant/hidden truth. Если нет — вероятно создан лишний whitelist.

### 28.4. Authoritative envelope

Не получила ли LLM возможность изменять canonical geography, topology, history, hidden truth, exact mechanics или persisted authority?

Если получила — semantic boundary слишком широкая.

### 28.5. Code first

Не вызывается ли LLM для того, что существующий код уже может решить точно?

Если вызывается — сохрани code-owned path.

### 28.6. Persistence

После commit воспроизводится ли тот же мир без повторного RNG, decision, materialization или повторного применения action?

Если нет — изменение не готово.

### 28.7. Identity и причинность

Сохраняется ли identity того же физического объекта и создаётся ли новая entity только когда действительно возникает самостоятельный объект?

Может ли один causal change set атомарно сохранить source transition и возникший result?

### 28.8. Простота

Можно ли выполнить текущий criterion of done расширением существующего owner и меньшим количеством entities/state/checks?

Если да — выбирай более простой вариант.

### 28.9. Anti-scripted check

Работает ли один разумный unseen-equivalent case без нового enum/handler/allowlist entry?

Если нет — проверь, не зашит ли конкретный fixture вместо общего поведения.

### 28.10. Anti-integrity-bloat check

Можно ли назвать реального attacker/trust boundary или конкретный normal-use defect, который требует нового digest/fingerprint/hash/ledger?

Если нет — такой механизм не должен появляться.

## 29. Завершение задачи

Перед завершением сравни результат с исходной задачей и criteria of done, а не только с зелёными тестами.

Не расширяй scope без необходимости.

Если найдена посторонняя проблема, которая не мешает текущей задаче, не исправляй её попутно. Кратко зафиксируй её в итоговом отчёте или в правильном issue/owner, если это входит в запрос.

Итоговый ответ должен кратко содержать:

1. что изменено;
2. какое поведение реализовано или исправлено;
3. какие проверки фактически выполнены;
4. какие реальные ограничения или блокировки остались.

Не объявляй задачу завершённой, если известная обязательная проверка затронутой области завершилась ошибкой.

Не добавляй в итоговый отчёт гипотетические улучшения «на будущее», если они не нужны текущей задаче.

## 30. Краткая формула проекта

Если требуется выбрать между двумя подходами, сохраняй следующую иерархию:

```text
свободная причинная игра
→ semantic freedom inside authoritative envelope
→ code first for exact mechanics
→ LLM for the unenumerable remainder
→ один owner на ответственность
→ committed world не переписывается
→ simplest complete general mechanism
→ никакой гипотетической инфраструктуры
```

Если решение технически аккуратно, но превращает игру в набор заранее перечисленных случаев, создаёт второй owner или добавляет integrity/security machinery без реальной необходимости, оно противоречит архитектуре проекта.
