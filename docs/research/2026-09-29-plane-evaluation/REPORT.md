# Оценка Plane вместо файловых мостов
> Движок: не относится.
> Даты: 2026-09-29 — 2026-09-29.
> Источник отчёта: запись памяти memory/plane-evaluation.md

## Вопрос

Можно ли заменить файловые мосты Plane Community Edition и как обеспечить сохранность рабочих файлов, если сами агенты получают доступ к Plane.

## Метод

Владелец предложил рассмотреть Plane вместо текстовых файловых мостов. Оценка сочетала проверку сценария рабочего процесса, ревьюера Opus и самостоятельное чтение исходного кода Community Edition на ветке master. В записи также отдельно отмечено, что документация Plane может описывать платные редакции и опережать возможности CE ([source-memory.md](source-memory.md):11,14).

## Ход

Владелец предложил развернуть Plane только на servak, без облачного сервиса. В записи описаны проверка прав, API, MCP, удаления, вебхуков и эксплуатации, а затем предложение использовать Plane как окно для владельца, синхронизируемое с файловой системой. На момент записи решение о пилоте оставалось открытым ([source-memory.md](source-memory.md):11,13-31).

## Результаты

В Community Edition были обнаружены три роли: Admin, Member и Guest. Contributor, Commenter, настраиваемые роли, Workspace Admin, журналы аудита, OAuth-приложения и Plane AI относились к платным возможностям ([source-memory.md](source-memory.md):14).

Любой участник проекта, включая Guest, мог редактировать и удалять комментарии других участников: endpoint комментариев использовал `ProjectLitePermission`, проверявший только членство в проекте. API-ключ имел все права своего пользователя; выпустить ключ только для чтения было нельзя ([source-memory.md](source-memory.md):15-16).

MCP-сервер предлагал 30 инструментов. Удаление было действием внутри инструмента, поэтому клиентский список разрешённых инструментов не мог исключить его ([source-memory.md](source-memory.md):17).

Удаление было мягким; окончательное стирание происходило через 60 дней по умолчанию, с настройкой через переменную окружения. Журнал активности сохранял старый текст изменённого комментария, но не удалённого ([source-memory.md](source-memory.md):18).

Вебхуки работали на уровне workspace: после 5 неудачных повторов вебхук отключался, а пропущенные события терялись. Получатели на localhost и в частной сети блокировались, если их не внесли в соответствующие списки разрешённых адресов ([source-memory.md](source-memory.md):19).

Лимит API составлял 60 запросов в минуту на ключ. Для запуска требовалось 13 контейнеров; конкурентность Celery по умолчанию равнялась числу ядер. На servak с 64 ядрами её требовалось ограничивать вручную. В записи также отмечены известные поломки обновлений в 2026 году ([source-memory.md](source-memory.md):20-21).

Текущий файловый мост работал с агентами от root; `fleet/tasks` не находился под git, а правило «только добавлять» технически не обеспечивалось ([source-memory.md](source-memory.md):23).

В записи предложено оставить файлы источником истины, дать Plane роль доски для владельца и зеркалировать туда файлы детерминированным sync-ботом. Агентам при этом не выдавать ключи Plane. Для защиты файлов предлагалось настроить автоматические git-коммиты и `chattr +a`; полную замену файлового моста рассматривать лишь через прокси без операции удаления ([source-memory.md](source-memory.md):25-29).

## Выводы

Автор записи рекомендовал использовать Plane как обзорную доску владельца с файловым sync-ботом, сохраняя файлы источником истины. Для полной замены моста предлагался только прокси, не предоставляющий удаление. Решение о пилоте ещё ожидало владельца ([source-memory.md](source-memory.md):25-31).

## Решения владельца
