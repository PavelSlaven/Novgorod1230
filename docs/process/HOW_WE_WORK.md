# Как устроена работа над проектом

> Обзор системы документации и разработки. Норм не создаёт: правила — в [AGENTS.md](../../AGENTS.md) и
> [docs/governance](../governance/README.md), нормы подсистем — по
> [CONTRACT_INDEX](../../data/knowledge-source/corpus/DOCUMENTS/CONTRACT_INDEX.md). Здесь объяснено, зачем система
> устроена так, из чего она состоит и как ею пользоваться. Основа — лекция «Как писать код с нейросетями, не
> сжигая токены» и опыт самого проекта. Проверено: 2026-09-30, commit 46732203.

## 1. Главный принцип: минимальный достаточный контекст

Агенту не нужен весь проект. Ему нужен контекст под конкретную задачу: что сделать, где, как, что нельзя трогать
и по какому критерию результат считается правильным.

Лишний контекст вредит:

- модель путается и дорисовывает недостающее;
- каждый запрос дороже, агент думает дольше;
- растёт шанс «заодно улучшить» чужие файлы;
- результат трудно проверить.

Недостающий контекст вредит так же. Агент видит только то, что ему дали:

- не указана архитектура — он придумает свою;
- не указаны версии — выберет сам;
- не указаны готовые хелперы — напишет свои;
- не указаны крайние случаи — проверит только happy path.

Поэтому знания о проекте разложены по отдельным документам, и под задачу загружаются только нужные. С хорошим
контекстом справляется и более дешёвая модель. Если агент пишет не то, чинить надо контекст, а не менять модель
на более дорогую.

В Novgorod1230 этот принцип работает дважды. Игру ведёт слабая локальная LLM, и точный контекст ей подаёт World
Knowledge. Разработку ведут агенты, и точный контекст им подаёт эта система.

## 2. Формула работы

| Шаг | Что делаем | Где в проекте |
|---|---|---|
| 1. Зафиксировать задачу | цель, для кого и зачем, результат, уровень качества | GitHub issue |
| 2. Спецификация до кода | change request: владельцы, context pack, «не трогать», критерии готовности, проверки, допустимый долг | [CHANGE_REQUEST](CHANGE_REQUEST.md), форма `change_request` |
| 2а. Проверить гипотезу стендом | если решение опирается на поведение нейросети или на формулу из данных — маленькая проверка вне игры на локальной модели до плана реализации | раздел 11 |
| 3. Собрать нужный контекст | строка маршрутизации роутера → разделы governance, строка CONTRACT_INDEX, `MODULE.md`, карты `docs/context`, LEGACY_WARNINGS | [WORKFLOW](WORKFLOW.md), шаг 3 |
| 4. Короткие итерации | маленький шаг → focused-тест → следующий шаг | [TESTING](../context/TESTING.md) |
| 5. Проверить | детерминированные проверки, CI, ревью каждой задачи, Contract Auditor по триггерам | WR §24, AR §25.1 |
| 6. Зафиксировать | строка CHANGELOG, LW, `Closes #N`, отчёт §29 | [WORKFLOW](WORKFLOW.md), «Завершение» |
| 7. Принять | владелец принимает результат по своим метрикам: плейтест, первый экран, проза | issue этапа |

Финальное решение и приёмка остаются за владельцем.

## 5. Роли и исполнители

- **Владелец (PavelSlaven):** замысел игры (PC §9.1), выбор между продуктовыми вариантами, разрешения на правку
  governance, приёмка этапов и решения о production. По D58 ведущий исполнитель сливает нужные изменения кода,
  docs и данных после обязательных проверок; governance остаётся за владельцем и защищён правилом §1.1.
- **Ревьюер-архитектор** — Claude Code со старшей моделью на машине владельца (текущий назван в
  [CURRENT_SPRINT](../work/CURRENT_SPRINT.md)). Ставит задачи и пишет CR. Одобряет планы исполнителей там, где это
  требует режим задачи (5.1). Ревьюит каждую сдачу против CR, плана этапа и замысла. Коммитит за Codex, переносит
  ветки на GitHub (10.4) и открывает PR. Утверждающие проходы и Contract Auditor запускает отдельной старшей
  моделью. Продуктовые, нормативные, необратимые и production-решения выносит владельцу.
- **Исполнители** работают по CR, каждый в своей ветке (решение владельца D31,
  [#133](https://github.com/PavelSlaven/Novgorod1230/issues/133#issuecomment-5866721387)). Кто какую задачу ведёт
  сейчас — [CURRENT_SPRINT](../work/CURRENT_SPRINT.md).

  | Исполнитель | Модели | Что делает | Ветка |
  |---|---|---|---|
  | Cursor | только Composer: `composer-2.5`; `composer-2.5-fast` — только по явному указанию ревьюера (D48) | код Runtime параллельно с Claude (D49); не тесты, контракты и БД | `codex/live-world-runtime` (PR #98) |
  | Codex, данные | `gpt-6.1-sol` и `gpt-6-sol` — план и короткое суждение; работу делает `gpt-6-luna` (D48, D50, D57); Codex CLI — не ниже 0.159.2 | данные игровой базы | `data/game-base-v1-*`, PR в main |
  | Codex, исследования | те же | выписки из книг, черновики данных, разведка кода и черновики дизайна, тесты без правки кода | без ветки или `fleet/<id>` |
  | младшие исполнители Claude | Sonnet | отдельные CR кода, runtime-задачи среза D49 | `fleet/<id>` или своя ветка от PR #98 |

  Если Cursor ещё раз ослабляет тест ради зелёного, задача переходит к Claude (D47). Runtime-задачи идут параллельно
  на разных исполнителях с чёткими границами файлов и владельцев (D49); изменения в PR #98 вливаются после ответа
  точки D55 и обязательных проверок по 5.3.

  Вопрос, который нельзя закрыть чтением проекта, исполнитель пишет ревьюеру и ждёт ответа. Свои данные не
  утверждает (WR §21.1), критерии и проверки приёмки молча не меняет (WR §24.2).
- **Утверждающий проход:** отдельный проход старшей модели инструмента на высоком reasoning или владелец утверждает данные, собранные другим агентом (WR §21.1).
- **Contract Auditor:** независимый read-only аудит по триггерам AR §25.1.
- **CI:** merge gate; полный `npm test` — в CI, локально только в случаях WR §24.

**Модель — под задачу**, а не старшая по умолчанию (решение владельца 2026-09-26): механика — младшие модели на
низком reasoning; исполнение — средние; старшая модель — только короткие проходы: утверждение данных, Contract
Auditor, архитектурная эскалация. Каждая подзадача — свежий субагент.

### 5.1. План до работы и режимы задач

Основание — решение владельца D31 ([#133](https://github.com/PavelSlaven/Novgorod1230/issues/133#issuecomment-5866721387)):
каждый исполнитель до работы присылает план и начинает после OK. Режимы задач ниже — уточнение владельца
2026-09-28. Норма плана исполнителя под ведущим — [WR §18.2](../governance/WORKFLOW_RULES.md).

До правок исполнитель присылает план: как понял задачу, где источник истины, что изменит, чем проверит, развилки,
объём. Работает только после подтверждения; при смене подхода — новый план. Без плана — только механические шаги,
продиктованные дословно. Свой аудит — не больше одного круга на сдачу: если исполнитель второй раз обходит то же
самое, он останавливается и задаёт вопрос.

| Режим | Задачи | План одобряет | Ревьюер проверяет |
|---|---|---|---|
| «План у ревьюера» | код, меняющий контракты, схему БД, промпты LLM или границы владельцев; утверждение данных | ревьюер | план и каждую сдачу |
| «Ведёт sol» | исследования, черновики данных, тесты без правки кода, разведка только на чтение | ведущая модель исполнителя (у Codex — `gpt-6.1-sol` или `gpt-6-sol` ведёт план и короткое суждение, работу делают субагенты `gpt-6-luna`) | итоговую сдачу |

Режим задачи ревьюер пишет в её задании. Модельный стенд в любом режиме запускается только после плана стенда
и явного разрешения ревьюера ([WR §24.3](../governance/WORKFLOW_RULES.md)); одобрение ведущей модели
исполнителя его не заменяет. Задачи, которые меняют промпт или вход LLM-роли, всегда идут в режиме «План у ревьюера».

### 5.2. Обмен сообщениями исполнителя и ревьюера

Исполнитель и ревьюер переписываются через файлы задачи вне репозитория (10.1): `questions.md` пишет исполнитель,
`answers.md` — ревьюер, `progress.md` — журнал хода исполнителя, одна строка на этап. Это только канал сообщений,
а не источник истины.

Каждое сообщение — блок с заголовком `## <ТИП>-<задача>[-<шаг>] | <время> | <кратко>`.

| Блок | Кто пишет | Что это |
|---|---|---|
| `PLAN-…` | исполнитель | план до работы, 5–10 строк |
| `PLAN-OK-…` | ревьюер или ведущая модель (5.1) | план подтверждён, возможно с поправками |
| `Q-…` | исполнитель | вопрос, помеченный `blocking` или `non-blocking` |
| `A-…` | ревьюер | ответ на вопрос |
| `TASK-…` | ревьюер | поручение: ссылка на issue с CR и короткие указания |
| `DONE-…` | исполнитель | сдача: HEAD, что сделано, какие проверки реально выполнены, строки CHANGELOG и LW |
| `REVIEW-…` | ревьюер | `ACCEPTED` или `CHANGES_REQUESTED` с пронумерованными замечаниями |
| `NOTE-…` | ревьюер | решение владельца (в тот же день переносится в issue, PR или план) или указание вне цикла, например влить ветку |

Пути в сообщениях пишутся через `/`. На границе задачи действующие решения переносятся в репозиторий, а старый
лог архивируется: новая сессия начинает с репозитория, а не с чтения истории переписки.

### 5.3. Кто что сливает и что показывается владельцу

Норма слияния в интеграционную ветку (merge без rebase, проверки на результате слияния, живой прогон, след
проверок в merge-коммите) — [GS §26.2](../governance/GIT_SAFETY_RULES.md).

- **Слияние по D58:** ведущий исполнитель сливает изменения, которые считает нужными, кроме governance. Для данных
  игровой базы нужны одобрение независимого прохода Opus (`approve` или `approve_with_limits`) и зелёный CI; если в PR
  влита свежая main и пересобраны generated-файлы, дельта пересборки — новое непроверенное содержимое: перед merge её проверяет
  короткий проход Opus, лишнее откатывается. PR #98 вливается в main только при играбельном срезе D49.
- **Governance** — только по прямому запросу администратора проекта; `AGENTS.md` и `docs/governance/*` защищены §1.1.
- **Перед слиянием в PR #98** ведущий отправляет пакет сдачи кода/данных ChatGPT-точке D55 и дожидается её ответа.
  Тесты и проход Opus идут параллельно; ведущий проверяет находки точки. Точка — дополнительный рецензент, не
  утверждающий: требуемые независимое утверждение и Contract Auditor выполняются отдельно.
- **Сначала показать владельцу.** Результаты исследований и подборок (каталоги, наборы правил, «топ-N»), а также
  новые правила процесса не публикуются в docs, issue и PR и не запускают следующую работу, пока владелец их не
  увидел и не сказал OK. Фильтр аудиторов и критиков показ владельцу не заменяет.

## 6. Как собирается контекст исполнителя

1. **Старт сессии.** Роутер `AGENTS.md` (≤16 КБ) и личные глобальные правила инструмента. Исполнитель на servak
   дополнительно получает `RULES.md` и задание (10.2). Больше ничего обязательного.
2. **Под задачу.** Строки маршрутизации роутера → разделы governance. CONTRACT_INDEX по правилу чтения
   (§1–§3.1, строка §8.1, строки §4–§7 её документов). Из больших контрактов читаются нужные разделы, целиком —
   только редактируемый документ. `MODULE.md` владельцев, нужные карты `docs/context`, `rg` по LEGACY_WARNINGS,
   граф кода (CBM), `npm run knowledge:query` для норм.
3. **Не загружать:** весь корпус; историю прошлых чатов; документы «на всякий случай»; legacy-копии как нормы.
4. **Субагенты:** свежий субагент на подзадачу; разведчик возвращает короткий артефакт (файлы, строки,
   команды, неопределённости), а не пересказ репозитория.

## 7. Проверки: скрипт вместо модели, тест проверяет контракт

- Механическую работу делает детерминированный скрипт, модель нужна там, где требуется суждение (WR §19).
- Критерии готовности и проверки приёмки фиксируются до кода; проверки не подгоняются под реализацию (WR §24.2).
- Провал плейтеста сначала становится падающим регрессионным тестом на уровне хода, потом чинится (WR §22).
- Каждое изменение свободного поведения проверяется unseen-equivalent случаем (PC §5, WR §24).
- Пропущенный тест — не пройденный; проверка, которая не выполнялась, не называется пройденной.
- Гипотеза о поведении нейросети проверяется стендом до кода (раздел 11), а не сборкой игры после.

## 8. Симптом → причина → что чинить

| Симптом у агента | Причина | Что чинить |
|---|---|---|
| жжёт токены и пишет не то | нет спецификации | CR до кода |
| перечитывает весь проект | документы не разделены или устарели | карты `docs/context`, строка маршрутизации |
| путает архитектуру, вводит свои паттерны | архитектура и владельцы не описаны | ARCHITECTURE, `MODULE.md` |
| тянет новые библиотеки | стек не зафиксирован | STACK |
| пишет свои хелперы и компоненты | не указано, что уже есть | ARCHITECTURE, UI_KIT |
| тестирует только happy path | нет крайних случаев | EDGE_CASES, unseen-equivalent в CR |
| не понимает задачу | цель и критерии не записаны | CR |
| теряет историю проекта | нет текущего спринта, слишком большой контекст | CURRENT_SPRINT, одна задача — одна сессия |
| «улучшает» костыли или ломается о legacy | долг не записан | LEGACY_WARNINGS |
| пишет сценарный код вместо общего механизма | пример принят за норму, статусы вводят в заблуждение | PC §5, AI §15, статус только из CONTRACT_INDEX |
| «чинит» тест вместо кода | критерии приёмки не зафиксированы до кода | CR, WR §24.2 |

## 9. Как поддерживать порядок

- Нашёл ловушку — запиши в LEGACY_WARNINGS и заведи issue, не чини попутно.
- Изменился факт — поправь карту `docs/context` и обнови штамп «Проверено».
- Появилось решение владельца — перенеси его в issue или PR, а не оставляй в чате или переписке.
- Новый этап или крупный merge — context dump на той ветке, где идёт работа.
- **Ревьюер проверяет порядок в документах на границе каждой задачи:**
  - в сдаче есть строки CHANGELOG и LW;
  - [CURRENT_SPRINT](../work/CURRENT_SPRINT.md) обновлён, если сменились порядок задач или исполнители;
  - план этапа обновлён в ветке PR #98, если он изменился;
  - решения владельца перенесены в issue в тот же день;
  - этот документ обновлён, если изменился сам процесс: исполнители, площадка, правила обмена.
- Размер файла не порог: файл делится по ответственности, а не по числу строк — [MODULE_RULES](../architecture/MODULE_RULES.md), п. 7, AI §16. Ревьюер не просит деления «до N строк».
- Ссылки в картах и процедурах проверяет `npm run test:docs`, корневые `.md` — `docs:check`.

## 10. Рабочая площадка: servak и машина владельца

Тяжёлая работа идёт на **servak** — сервере владельца (64 потока, 251 ГБ памяти; доступ `ssh servak`). Там
работают исполнители, тесты с PostgreSQL и исследования. Машина владельца остаётся для игры владельца, приёмки и
отправки веток на GitHub.

Инструменты флота (`fleet`, `pg-slot`, `RULES.md`) живут на servak, а не в репозитории. Их устройство описано в
этом разделе; меняется устройство — меняется и раздел.

### 10.1. Что где лежит на servak

Всё наше — только в `/srv/novgorod-work/`. Остальное на сервере принадлежит владельцу и не трогается: сервисы
моделей, библиотека, веб-сервисы.

| Путь в `/srv/novgorod-work/` | Что |
|---|---|
| `fleet/bin/fleet` | запуск и учёт исполнителей |
| `fleet/RULES.md` | правила для исполнителей на servak; каждый получает их при первом запуске |
| `fleet/bin/pg-slot` | запуск теста с PostgreSQL в одном из четырёх слотов; если все заняты, ждёт |
| `fleet/bin/pg-request` | запрос Codex на тест с PostgreSQL через очередь флота |
| `fleet/tasks/<id>/` | задача: `TASK.md`, `questions.md`, `answers.md`, `progress.md`, логи запусков `runs/`, `task.env` |
| `worktrees/<id>` | рабочая копия задачи кода: ветка задачи и свой `npm ci` |
| `worktrees/ref-pr98`, `worktrees/ref-gamebase` | эталонные копии только для чтения: ветка PR #98 и закреплённый коммит игровой базы |
| `data/books/` | индекс библиотеки для исследований, выписки `evidence/`, инструкция сборщика `scripts/COLLECTOR_BRIEF.md` |
| `prose-test/` | стенд прозаического теста (10.6) |

Основной клон репозитория на servak — `/root/Novgorod1230`; рабочие копии задач — его worktree.

### 10.2. Как ревьюер ведёт задачу

1. `fleet new <id> <claude|codex|cursor> <модель> <reasoning> <code|research> [база]` создаёт задачу. Для кода —
   рабочую копию на ветке `fleet/<id>` от базы; по умолчанию база — `codex/live-world-runtime`.
2. Ревьюер пишет `TASK.md`: ссылка на issue (CR), режим (5.1), рамки, что сдать.
3. `fleet run <id>`: первый запуск получает `RULES.md` и `TASK.md`, следующие продолжают сессию исполнителя.
4. Ревьюер следит за `fleet heads` — последним заголовком каждой задачи. Отвечает в `answers.md` и снова
   запускает `fleet run <id>`.

Каждый запуск идёт в systemd scope с квотой CPU и памяти. Одновременно — до 4 исполнителей Claude, 18 Codex и
2 Cursor; у сессии Codex — до 16 субагентов `gpt-6-luna` на втором аккаунте и до 8 на основном. Fleet задаёт значение конкретного прогона. Сеть из песочницы
Codex закрыта. Задаче, которой нужен локальный Qwen владельца, ревьюер открывает её строкой `NET=1` в `task.env`.

### 10.3. Правила исполнителей на servak

Кратко; полный текст — `fleet/RULES.md`.

- План до работы (5.1), заголовки сообщений (5.2), журнал `progress.md`.
- **Без фоновых команд.** Исполнитель работает без интерфейса: когда он остановится, его никто не разбудит.
  Длинные прогоны — в переднем плане, с таймаутом до 30 минут.
- Нельзя push, rebase, reset, `git clean` и другие широкие destructive-команды.
- **Codex не пишет в git:** его песочница держит `.git` только для чтения. Ветку заранее создаёт ревьюер, он же
  коммитит после ревью. Claude и Cursor коммитят сами.
- **Тесты Codex с PostgreSQL запрашиваются через `pg-request`;** клиент передаёт относительный путь тестового файла, а исполнитель флота запускает его через `pg-slot` в одном из четырёх слотов. Например: `/srv/novgorod-work/fleet/bin/pg-request test/spatial-v3/target-canonical-start-postgres-acceptance.js`. Для прочих исполнителей — через `pg-slot`. На servak Docker с AppArmor блокирует unix-сокеты PostgreSQL.
  Поэтому тестовая обвязка при `NOVGOROD_TEST_DOCKER_APPARMOR_UNCONFINED=1` запускает контейнеры с
  `apparmor=unconfined`. Переменную выставляют сами `fleet` и `pg-slot`.
- Сервисы владельца не трогать; локальную модель владельца вызывать только как клиент.
- Ключи API и другие секреты не печатать, не копировать и не логировать.
- Не заявлять проверку, которая не выполнялась.
- Субагенты — только младшие модели из раздела 5.

### 10.4. Git: ветки и перенос на GitHub

- Токен GitHub на servak — только для чтения. Ветку после ревью переносит ревьюер со своей машины:
  `git fetch ssh://servak/root/Novgorod1230 <ветка>`, затем `git push origin FETCH_HEAD:refs/heads/<ветка>`.
- **Код:** ветка от `codex/live-world-runtime`; ведущий вливает нужные изменения в PR #98 после ответа точки D55
  и обязательных проверок (5.3). Обычный merge, rebase запрещён (D31, D47).
- **Данные игровой базы:** ветка от линии game-base, PR в main. Runtime импортирует данные по закреплённому
  коммиту через существующий P12-импортёр (D31).
- Merge в main: ведущий исполнитель — по D58 и 5.3; governance — только по прямому запросу администратора (§1.1).

### 10.5. Путь данных игровой базы

1. **Выписки.** Исследовательская задача собирает цитаты из книг библиотеки по `COLLECTOR_BRIEF.md`. Скрипт
   сверяет каждую цитату с полнотекстовым индексом; результат — `data/books/evidence/<группа>.csv`.
2. **Черновик** (`candidate`) — Codex по выпискам. Чего нет в источниках, то помечается пробелом, а не
   заполняется выдумкой.
3. **Детерминированные проверки:** build и check профилей с `--self-test`, валидатор мест, построчный diff и
   counts.
4. **Проверка содержания:** раунды проверки — отдельная старшая модель на группу данных; результат — раздел
   `VERIFICATION` рядом с данными.
5. **Утверждение** — отдельный проход, не автор данных (WR §21.1); запись утверждения — рядом с данными.
6. **PR в main**, слияние ведущим по 5.3, импорт в Runtime по закреплённому коммиту.

### 10.6. Прозаический тест

Проверяет, хватает ли данных игровой базы, чтобы слабая локальная модель писала сцену без выдумок. Писатель —
локальный Qwen владельца, судьи — слепые проходы Claude по калибровочной рубрике. Порог —
[#158](https://github.com/PavelSlaven/Novgorod1230/issues/158#issuecomment-5857929393). Стенд — `prose-test/` на

### 10.8. Правила процесса D48–D58

Приняты владельцем 2026-09-29–2026-10-01 (D48–D58). Инструменты для правил 1–5 (очередь продолжения, две модели Codex, `reason-dupes`,
`test-guard`, `fleet say`, гейт в `fleet new`) вводятся задачей `fleet-tools`; до её слияния правила действуют как договорённость
ревьюера и исполнителей, а `fleet/RULES.md` — источник текста для исполнителей.

1. **Записки ревьюера во время прогона не теряются.** Записка, пришедшая пока задача идёт, ставит флаг; после
   прогона `fleet` сам запускает задачу с указанием прочитать новые ответы (очередь продолжения). Исполнитель
   перечитывает `answers.md` перед `DONE`.
2. **Модели Codex:** `gpt-6.1-sol` и `gpt-6-sol` ведут план и короткое суждение; объёмную работу по умолчанию
   выполняют субагенты `gpt-6-luna` «армией». Codex CLI — не ниже 0.159.2; Sonnet — только где Codex не может,
   Opus — для утверждения и Contract Auditor; Codex не делает GitHub review (D52). Luna — до 16 субагентов на acct2
   и до 8 на основном аккаунте;
   fleet задаёт число конкретного прогона. Если суммарный вход сессии Codex разросся (порог порядка 150M
   токенов), следующий прогон начинается свежей сессией с передачей.
3. **Дешёвая проверка перед Opus:** скрипт шаблонных причин `reason-dupes` и сторож тестов `test-guard` (снятые
   assert, `catch {}`, skip, заявленные «pass» без лога). Проход Opus — после них, один на сдачу.
4. **Время в заголовке блока ставит `fleet say`**, а не модель, для обеих сторон.
5. **Гейт авторинга данных:** авторинг по пункту не запускается, пока по нему открыт вопрос владельца или идёт
   архитектурный разбор.

6. **Расход Codex и Cursor (D52, D54):** планируй ровный расход Codex почти до 0% остатка к сбросу окна или более
   раннему истечению банковского сброса. Второй аккаунт Codex — без кредитов: новые прогоны разрешены до 90%
   пятичасового окна и до 98% недельного; сторож останавливает идущие на 95% и 99% соответственно. На основном
   аккаунте кредиты расходуются только после включённого лимита, автопополнение выключено. Владелец использует
   банковский сброс, когда недельное окно исчерпано и до обычного сброса больше двух суток, иначе — накануне
   истечения; ведущий учитывает оба аккаунта в `fleet/resets.tsv`. Для Cursor ведётся месячный пул Composer;
   on-demand не используется, fleet не запускает новые прогоны с 98% пула.
7. **Рецензент D55:** до слияния изменения в PR #98 ведущий передаёт пакет сдачи кода/данных ChatGPT-точке и ждёт
   ответа. Тесты и Opus идут параллельно; ведущий разбирает замечания точки. Она не заменяет Opus: утверждение и
   Contract Auditor остаются за ним.
8. **PostgreSQL (D57):** Codex запрашивает PG-прогон через `/srv/novgorod-work/fleet/bin/pg-request`, передавая
   относительный путь теста, например `/srv/novgorod-work/fleet/bin/pg-request test/spatial-v3/target-canonical-start-postgres-acceptance.js`. Флот исполняет запрос через
   `pg-slot`; доступно четыре слота. Песочница Codex не меняется.
9. **Вечерний разбор (D57):** предложения каждого разбора собираются в одно GitHub issue с меткой
   `evening-review`; issue создаёт сам разбор, ведущий отслеживает его и ведёт дальнейшую работу.
10. **Слияние (D58):** ведущий сливает нужные изменения кода, docs и данных после обязательных проверок; governance
    остаётся за владельцем и требует прямого запроса администратора.

Правило о причинном решении анахронизмов — [PRODUCT_CONSTITUTION §4 и §9.1](../governance/PRODUCT_CONSTITUTION.md);
страховка эпохи для NPC (речь, знания, поведение) — решение D60 в [#133](https://github.com/PavelSlaven/Novgorod1230/issues/133#issuecomment-5928266458) и нормы [PRODUCT_CONSTITUTION §8–9](../governance/PRODUCT_CONSTITUTION.md). Здесь они не пересказываются.

Контекст ревьюера: чат не открывается заново ежедневно; в конце задачи, когда ничего не висит в полёте и состояние
записано в handoff, ревьюер сообщает владельцу «точка для compact», и владелец запускает `/compact` (D48). Так
цепочка процесса сохраняет память о целом.

Вечерний разбор — постоянная плановая задача приложения (ежедневно 21:07), а не сессионный cron. Он сверяет лимиты,
сделанное за день, план (в том числе живой прогон среза D49), документацию и предложения по процессу. Результат —
`evening-reviews/<дата>.md`, краткий отчёт владельцу и одно issue с меткой `evening-review` со всеми предложениями.
Разбор не правит репозиторий, мост флота и память.

## 11. Стенд: проверка гипотезы до сборки игры

Решение владельца D41 ([#133](https://github.com/PavelSlaven/Novgorod1230/issues/133)): проверка стендом обязательна.
Норма — [WR §24.3](../governance/WORKFLOW_RULES.md): стенд запускается только после плана стенда и явного
разрешения ведущего (решение D83, в мостах флота — блоки `BENCH-PLAN` и `BENCH-OK`); параметры роли берутся с
фактического запроса production-кода. Изменение промпта или входа роли сдаётся с полным захваченным запросом —
[WR §24.4](../governance/WORKFLOW_RULES.md).

**Стенд** — маленькая и быстрая проверка гипотезы **вне игры**. Работает без сервера, БД, сборки и живого мира, на
**настоящей локальной модели** с теми же параметрами, что в игре. Отвечает на вопрос «сработает ли идея» за минуты,
до того как на неё потрачены недели кода.

Образцы:
- прозаический тест данных — хватает ли пакета, чтобы слабая модель написала сцену без выдумок (#158, раздел 10.6);
- стенд свойств вещей — как лучше проставлять свойства новой вещи (#178, комментарий от 2026-09-28). На нём
  выяснилось, что нейросеть хорошо выбирает из закрытых списков, но плохо держит числа и физику. Это определило
  архитектуру до строчки кода.

### 11.1. Когда стенд обязателен

До плана реализации, если выполняется хотя бы одно:

1. **Решение опирается на поведение нейросети** — что она выберет, поймёт, различит или напишет:
   - граница код и нейросеть;
   - промпты;
   - схемы запросов и ответов;
   - закрытые списки, из которых модель выбирает;
   - описания, по которым планировщик понимает действие;
   - что рассказчик или NPC сделают с пакетом данных.
2. **Меняется промпт, формат пакета для модели, сама модель или её параметры** (температура, шаблон, размер
   контекста). Стенд здесь — проверка на регрессию: прежний набор случаев до и после.
3. **Меняются данные, которые получают рассказчик или NPC** — хватает ли данных, нет ли противоречий. Это
   прозаический тест.
4. **Код считает из данных или ответа модели** — массы, вероятности наличия, распределения облика, сложности
   проверок. Проверка — на выборке или симуляцией без модели: например 1000 бросков профиля или масса по геометрии
   на 15 вещах.
5. **В CR или плане есть допущение, редакторское число или фраза «это сделает код» / «это сделает нейросеть».**
   Каждое такое место — кандидат: рядом ссылка на стенд или пометка «не проверено». Урок стенда свойств:
   предполагали код, вышел гибрид.
6. **Вводится гейт процесса или у него меняется модель** — проверяющий данных, правщик, Contract Auditor,
   самопроверка ведущей модели. Стенд — подложенные ошибки: ловит ли гейт и согласен ли сам с собой при повторе.

**Не нужен:**
- детерминированный код, который целиком покрыт тестами;
- правка документов;
- механический перенос утверждённых данных.

В поле CR «Стенд» тогда пишется «не нужен» и почему.

Стенд уместен и сверх обязательного: когда есть два подхода и спор решается опытом быстрее, чем обсуждением.

### 11.2. Как устроен стенд

- **Мал и быстр.** Минуты, а не часы. Только то, что проверяет гипотезу. Вспомогательные словари стенда
  редакционные и живут вне репозитория.
- **Настоящая модель.** Локальная модель игры (сейчас Qwen владельца на servak) как клиент, с игровыми
  параметрами. Ключ не печатается и не логируется.
- **Фиксированный набор случаев.** Не меньше 10–15. Обязательно обычные, необычные и провокационные: анахронизм,
  противоречие, крайний размер, двусмысленное название. Для текстов — по 3 образца на случай: модель
  недетерминирована.
- **Варианты рядом.** Если есть выбор решения, прогоняются оба на одном наборе. Если меряется улучшение, в набор
  входит якорь — прошлый вариант под теми же судьями, потому что судьи дрейфуют между прогонами.
- **Оценка — сначала скриптом:** формат, словари, диапазоны, согласованность чисел. Суждение модели — только там,
  где скрипт не может: слепые судьи, по 3 на текст, по одной рубрике.
- **Честный вывод.** Что сработало, что нет, где промахнулся сам стенд. Промахи стенда отделяются от промахов
  идеи: в стенде свойств масса гребня ошиблась из-за грубой геометрии стенда, а не нейросети.
- **Сначала — работает ли рычаг.** Перед сравнением значений параметра проверить, что он доходит до тела запроса и
  меняет ответ сервера. Разведка стендов нашла три рычага, которые не работали как задумано: таймаут хода, бюджет
  контекста, уровень рассуждений.
- **Порог переносится только через якорь.** Порог судей на новый пул судей, новую модель судьи или новую пару
  писателей переносится после прогона одних и тех же якорных текстов через старый и новый пул.
- **Задержка — попутно.** Каждый стенд на модели меряет p50/p95, число вызовов и починок. Общий каркас —
  `/srv/novgorod-work/benches/_lib` (вызов с игровыми параметрами, замер), а не свой под каждый стенд.
- **Отрицательный вывод пересматривается**, когда меняется соседнее звено: стиль запроса, модель, выборка.

### 11.3. Где что лежит

- **Код и данные стенда** — на servak, в `/srv/novgorod-work/benches/<имя>/`, с `README.md`: гипотеза, как
  перезапустить, ссылка на отчёт. Исключения: стенд прозы в `/srv/novgorod-work/prose-test`, стенд свойств в
  `/srv/novgorod-work/prop-bench`.
- **Результат** — комментарием в issue или CR того решения, которое стенд проверял: цифры, выводы, что это меняет в
  решении. Ссылка на него — в поле CR «Стенд».
- **В репозиторий** стенд переносится только тогда, когда становится постоянной проверкой production-пути — у
  правильного владельца и с тестом.
- **Каталог стендов** — [#181](https://github.com/PavelSlaven/Novgorod1230/issues/181): где стенд нужен по ближайшим
  задачам, с гипотезами, вариантами и приоритетами. Сделанный стенд отмечается там ссылкой на результат.

### 11.4. Чем стенд не является

Стенд проверяет идею, а не готовую игру. Приёмка по-прежнему — живой прогон через сервер и отчёт по WR §24.1.
Хороший результат стенда — повод реализовать, а не замена проверки реализации. Ревьюер не одобряет план
реализации без результата стенда, если стенд обязателен по 11.1.

Стенд, который нашёл ошибку детерминированного кода, заканчивается issue и регрессионным тестом у владельца, а не
отчётом стенда.

### 11.5. Типовые вопросы стенда

Двадцать категорий из каталога [#181](https://github.com/PavelSlaven/Novgorod1230/issues/181). Помогают не пропустить
стенд при разборе CR.

- **Нейросеть:**
  - разделение труда код/нейросеть;
  - пределы локальной модели, включая регистр эпохи и дословное копирование;
  - форма подачи пакета: язык инструкции, JSON против текста ситуации, порядок сообщений;
  - модель и параметры под задачу;
  - работает ли рычаг на этом деплое.
- **Игрок и мир:**
  - разнообразие формулировок игрока;
  - попытки сломать правила и инъекции, в том числе через данные мира;
  - согласованность на нескольких шагах;
  - характер, речь и пределы знаний NPC;
  - схлопывание разнообразия: разные места и NPC звучат одинаково;
  - рассказ против состояния, которым владеет код: время, изменения мира;
  - понятность для игрока: подписи вариантов, причины провала, сообщения о сбое;
  - доступ к знаниям и утечки.
- **Числа и нагрузка:**
  - баланс симуляцией без модели: запасы, сложности проверок, бюджет игрового дня;
  - стоимость и скорость хода, нагрузка servak;
  - масштаб мира: фоновые процессы и NPC вне сцены.
- **Проверяющие:**
  - проверка проверяющих, включая гейты процесса;
  - дрейф калибровки судей и порогов;
  - сбои и починка;
  - поиск знаний (WK).
