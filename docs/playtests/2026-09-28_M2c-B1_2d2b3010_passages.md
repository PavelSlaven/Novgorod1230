## Findings

- **"Occupied" refusal — verified live, twice** (this run and one earlier run with the
  same seeding fix but a different exploration order): destination occupancy is
  computed once by the movement-admission owner, surfaces identically in the
  planner-visible snapshot and is narrated as an ordinary blocked action, never a raw
  error. This matches the CR #160 criterion and the already-committed unit tests
  (`apps/game-server/test/lower-dvina-trace-phase-2-services-block-plan.test.js`,
  commit `b164a8df`).
- **Free-text pass-target phrase ("иду к руслу") — NOT reached live in this run.**
  The directional exit ("Продолжить путь — выход 1") never reached `clear` visibility
  admission within the exploration budget (up to 10 local-edge and up to 8
  exit-directed turns tried across two strategies), so `pass_target_description` never
  had a chance to replace the neutral ordinal label
  (`spatial-v3-current-visibility-provider.js`'s `readExitDisclosure` only resolves it
  when `visibilityByExit.get(exit.id) === 'clear'`). Submitting the exit's own label
  verbatim did not change position or reveal new state, matching a **pre-existing,
  already-documented symptom** in an unrelated earlier playtest report,
  `docs/playtests/2026-09-24_m2c-v17-generated-g5-movement-blocked_7708.md`: submitting
  `Продолжить путь — выход N` verbatim there also returned `movement: null` with
  unchanged position, filed as `Q-051`, dated four days before this run. I did not
  independently re-diagnose that gap (out of scope for CR #160's own code, and the
  underlying pass-target-description mechanism is already proven correct in isolation
  by this CR's own unit tests against real approved catalog data — see commit
  `2d2b3010`'s tests in `spatial-v3-current-visibility-provider.test.js`). This is a
  live-run gap, not a code defect in this CR's changes.
- **`tools/local-play` is Windows-only** (`local-postgres.js`'s `defaultBinaries()`
  requires `process.platform === 'win32'`), confirmed unusable on this Linux stand,
  independent of the earlier AppArmor finding — recorded as a stand limitation per
  A-B1-02.
- No leftover Docker containers or tracked/untracked file changes remained after
  cleanup (`docker ps -a`, `git status` both checked clean).
