# Генерация мира и ходы

## Статус и граница миграции

Этот документ задаёт active materialization v3 для генерации мира и ходов.
Завершённый `versioned production activation cutover` сделал Spatial v3 sole
production owner; v2 сохранён только как explicit migration/rollback source.
Lower Dvina Trace revision 13
дополнительно активировал единственную player semantic boundary
`turn_step_request_v1` → `turn_step_plan_v1`. Partial activation, dual write,
scenario-local player planner и v3→v2 runtime fallback запрещены.

Temporal execution дополнительно регулирует active target-норматив
`temporal_world_and_interruptible_activities.md`. Ход применяет event-driven
earliest boundary, deterministic same-time cascade и ровно одного clock owner.
Factual visible package сохраняется вместе с change set; художественная проза
создаётся только после успешного commit.

## 1. Target spatial vocabulary and player projection

В target модели вопросы масштаба разделены строго:

```text
G0 = историко-географический регион
G1 = территориальная ячейка
G2 = крупная зона ячейки
G3 = устойчивое конкретное место
G4 = крупная часть места
G5 = конкретная локальная локация или комплекс
G6 = непосредственно разыгрываемое пространство
scene_position = устойчивая позиция внутри G6
```

Старые слова `place`, `location`, `minilocation` и `anchor` не являются новыми уровнями и не могут заменять typed refs. Player-facing описание может использовать естественные слова, но factual position хранится только через утверждённый endpoint и соответствующий G6/`scene_position`. UI-координаты, проза и предполагаемое направление не являются factual topology.

## 2. New-game, materialization and scene preparation

New-game фиксирует только утверждённые входы: историческую рамку, canonical G0–G5, factual endpoint, персонажа и необходимые pinned versions/digests. Если required candidate set пуст, binding неоднозначен или отсутствует approved cost/topology, результатом является typed data gap и hard block; nearest/first-row/name-based/LLM fallback запрещены.

`world_base` target-владельцем canonical G0–G5, route topology, templates и profiles. Party state владеет ограниченно generated G5 из approved G4 expansion profile, G6, `scene_position`, динамическими instances и append-only последствиями. Generated G5 создаётся только через конкретный open frontier, конечные approved candidates и capacity; код не создаёт G1–G4 или исторические факты во время хода.

Подготовка G6, NPC, authored/significant/hidden items, containers и slots возвращает proposal/report из существующих templates/profiles/rules. Единственный commit component применяет утверждённый write set атомарно. Для каждого такого экземпляра нужен approved slot/candidate и причинная связь; свободный текст игрока или LLM не расширяет этот набор. Ordinary direct action result регулируется отдельной player-turn границей раздела 3 и не является fallback materialization. Повторная preparation использует idempotency/trace, а не создаёт второй baseline.

## 3. Expansion and turn boundary

Path query отделён от resolution/preparation: option с `requires_frontier_resolution` или `requires_preparation` не executable, не перемещает персонажа и не двигает время. Только новый запрос после отдельного commit может вернуть `ready` option с полными steps. Ход исполняет только `immediate_action`, `timed_activity` или `timed_traversal`; смена G-ancestor, endpoint binding и подготовка не добавляют скрытого времени.

Обработка player turn имеет два входных пути:

```text
одна exact registered command → code fast path без LLM
иначе → player-safe turn_step_request_v1
       → strict turn_step_plan_v1 для следующего шага
       → code-owned execution / domain delegation
       → обновлённая working projection
       → continuation либо player-response/terminal boundary
       → единый atomic commit → persisted visible package → narration
```

Player planner не создаёт factual topology, routes, endpoints, G5/G6, NPC/item slots, hidden facts или write patch. Direct `create_entity` допускается только для `direct_partition`, `ambient_ordinary` и `crafted`: код проверяет доступный origin, ordinary allowlist, refs, placement и inventory invariants и сохраняет exact runtime mechanics snapshot конкретного экземпляра. Authored/significant/hidden предметы и container contents остаются code-owned candidate materialization.

Внутренние LLM-шаги работают с code-owned player-safe working projection, ограничены восемью шагами и не являются temporal scheduler. Перед commit код повторно проверяет committed state version. Bounded decision сохраняется только для genuinely closed choices. NPC conversation semantic contract активен для Lower Dvina Trace revision 14 через общий `npc_decision_signal_v1 → npc_decision_boundary_v1`; production v5 активирует также autonomous Phase 7: «Отдых у огня» длится 30 минут, boundary Жданко возникает на +25, actor-step получает фактически зарегистрированные domain operations и применяется на том же timestamp, после чего общий temporal owner продолжает интервал до +30 из обновлённой working projection. Execution, persistence и visibility остаются code-owned; combat semantic resolution остаётся `proposed`. Target traceability: `turn_step_llm_contract.md`, `npc_conversation_mode_contract.md`, `npc_autonomous_decision_contract.md` и `spatial_architecture_standard_g0_g6.md` §§1–2, 5–6, 9–10, 12, 14–16.

# Генерация мира и ходы

Мир игры должен генерироваться не как готовая энциклопедия всей Руси, а как слой за слоем материализуемая историческая среда. Сначала создаётся достаточный стартовый узел партии, затем мир расширяется только там, где игрок, персонаж, время, дорога, слухи, NPC или последствия действительно к нему прикасаются.

Главное правило materialization v2:

```text
Редакторские данные утверждают категории, шаблоны, профили, правила и историю.
Код материализует и изменяет конкретные экземпляры только из утверждённых вариантов.
LLM принимает bounded decisions, создаёт персонажа игрока, аудит и прозу.
```

Код не является автором категорий или истории и не создаёт отсутствующие варианты. Он является единственным штатным materializer G5, NPC, предметов, контейнеров и code-only последствий. Все выборы выполняются из активных profile/rule records детерминированным versioned RNG и сохраняются с trace. Этот раздел и `code_driven_world_materialization_architecture.md` заменяют все более узкие формулировки ниже, приписывающие LLM создание runtime-экземпляров.

Если LLM не отвечает, возвращает невалидный результат или результат не проходит проверку, нельзя незаметно ставить заглушку. Нужно вернуть этап на доработку, передать причины ошибки и повторить генерацию или упаковку данных. Сложные вещи лучше разделять на несколько связанных этапов: рамка, регион, место, персонаж, NPC, предметы, скрытые процессы, проверка, сохранение, проза.

Игра охватывает период 1230–1250. Доступные регионы описаны в `world_regions.txt`. Этот список задаёт допустимую региональную сетку и опорный историко-географический контур. Конкретный год партии уточняет власть, войны, дороги, риски, слухи, доступность мест, историческое давление и локальные последствия.

## 1. Основные сущности мира

### Регион

Регион — большая историко-географическая зона из `world_regions.txt`.

Он задаёт:

1. климат;
2. сезонные ограничения;
3. власть;
4. право и обычай;
5. дороги и водные пути;
6. экономику;
7. соседей;
8. войны и внешнее давление;
9. бытовую культуру;
10. общий исторический фон.

Регион не является полной картой всех поселений. Он задаёт рамку, внутри которой создаются конкретные места.

### Место

Место — конкретный устойчивый узел мира внутри региона.

Примеры:

1. город;
2. посад;
3. погост;
4. село;
5. монастырь;
6. двор;
7. постоялый двор;
8. переправа;
9. брод;
10. пристань;
11. лесной стан;
12. застава;
13. торг;
14. зимовье;
15. конкретный участок дороги или берега, если он стал значимым узлом.

Место имеет имя или устойчивое описание, владельцев или держателей, функцию, связи с дорогами, историю, правила доступа и значение для окружающих.

Место отвечает на вопрос:

```text
что это за узел мира и зачем он существует
```

### Локация

Локация — часть места, доступная как отдельная игровая зона.

Примеры:

1. двор перед воротами;
2. берег у переправы;
3. изба хозяина;
4. сени;
5. горница;
6. амбар;
7. конюшня;
8. пристань;
9. дорога у въезда;
10. торг;
11. церковный двор;
12. участок леса у тропы;
13. навес у саней.

Локация отвечает на вопрос:

```text
в какой зоне места сейчас можно действовать
```

### Минилокация

Минилокация — точная сценическая зона внутри локации.

Примеры:

1. у двери;
2. у печи;
3. за телегой;
4. под навесом;
5. у костра;
6. возле сундука;
7. у ворот;
8. рядом с мостками;
9. в тени стены;
10. за столом.

Минилокация нужна, чтобы понимать, кто рядом, что можно достать, кто видит действие, сколько времени нужно на перемещение внутри сцены и какие объекты доступны физически.

### Точка сцены / якорь

Точка сцены, или якорь, — ближайшая опорная точка относительно персонажа.

Примеры:

1. дверь;
2. колодец;
3. мостки;
4. сундук;
5. костёр;
6. повозка;
7. лавка;
8. ворота;
9. лодка;
10. тело раненого;
11. запертый ларь.

Якорь нужен не для художественного украшения, а для честной обработки доступа, видимости, скрытности, угрозы, предметов и движения внутри сцены.

### Позиция персонажа

Положение персонажа определяется не координатами, а устойчивой иерархией места.

Формула позиции:

```text
позиция = регион → место → локация → минилокация → точка сцены
```

Минимально текущая позиция хранится как отдельная часть состояния партии:

```text
current_position:
  region_id
  place_id
  location_id
  minilocation_id
  anchor_id
  last_route_id
```

Где:

1. `region_id` — текущий регион;
2. `place_id` — конкретное место;
3. `location_id` — зона внутри места;
4. `minilocation_id` — точная сценическая зона;
5. `anchor_id` — ближайшая опорная точка;
6. `last_route_id` — путь, по которому персонаж сюда пришёл.

Позиция хранится технически, но игроку показывается художественно:

```text
Ты стоишь во дворе постоялого двора, под навесом у конюшни. За воротами темнеет дорога к реке.
```

Положение персонажа нельзя хранить только в прозе. Иначе система не сможет честно вернуть персонажа в уже посещённое место, обработать дальний курс, проверить видимость, доступ к предметам, маршруты и последствия движения.

## 2. Историческая рамка

Эпоха задаётся в начале партии как жёсткая историческая рамка:

1. год;
2. сезон;
3. регион;
4. власть;
5. войны;
6. право;
7. быт;
8. материальная культура;
9. дороги и сезонные пути;
10. границы знания персонажа;
11. крупные исторические события и личности, если они релевантны региону и году.

Дальше каждый новый факт LLM обязана сверять с этой рамкой.

Исторические реальные места и персонажи используются, когда действие касается крупных известных узлов:

1. князей;
2. посадников;
3. городов;
4. монастырей;
5. битв;
6. торговых путей;
7. известных политических событий;
8. крупных родов, властей и войск.

Их нельзя свободно менять, убивать, переносить, делать случайно доступными или подгонять под удобство сцены.

Локальные места и персонажи материализуются кодом из утверждённых региональных categories, templates, profiles и rules:

1. дворники;
2. перевозчики;
3. смерды;
4. купцы;
5. старосты;
6. сторожа;
7. слуги;
8. дружинники низшего уровня;
9. малые дворы;
10. безымянные деревни;
11. локальные конфликты;
12. слухи;
13. долги;
14. бытовые происшествия.

Они не объявляются «реальными историческими», но каждый экземпляр обязан иметь approved causal basis, revision/region/period scope и materialization trace. LLM не добавляет отсутствующий локальный вариант во время партии.

По ходу партии код применяет известный исторический контур и утверждённые региональные варианты. Если источник или required candidate не зафиксирован, система не создаёт неизвестную сущность: она регистрирует data gap и блокирует зависимую операцию.

### Исторические события

Историческое событие не наступает внезапно. Оно входит в партию через фазы:

```text
фон → предвестники → нарастание → удар → последствия
```

Фаза события хранится как:

```text
фаза события = примерная дата + признаки + влияние + отложенные события
```

Персонаж не должен получать точное знание будущего события, если не мог его знать. Можно показывать слухи, тревогу, косвенные признаки, распоряжения, движение людей, рост цен, страх, закрытые дороги или изменение поведения NPC. Нельзя сообщать точную будущую дату, скрытую причину и гарантированный исход как знание персонажа.

Если событие уже существует в состоянии партии, нельзя создавать его дубль под другим названием. Нужно использовать существующее событие, уточнять фазу и показывать локальные проявления.

Короткая формула:

```text
исторический слой = события + личности + регионы + фазы + видимое знание
```

## 3. Видимое, скрытое и ещё не созданное

В мире различаются три состояния информации.

### Видимое

Видимое — то, что персонаж сейчас может видеть, слышать, чувствовать, помнить, понимать или разумно предполагать.

Видимое может попасть в прозу.

### Скрытое

Скрытое — то, что уже существует в партии, но персонаж этого не видит или не понимает.

Примеры:

1. тайный мотив NPC;
2. предмет в закрытом сундуке;
3. человек за дверью;
4. уже начавшийся слух;
5. долг, о котором персонаж не знает;
6. отложенное событие;
7. опасность на дороге, о которой есть только косвенные признаки.

Скрытое не может свободно меняться ради удобного ответа. Если оно уже создано, оно имеет приоритет над новой выдумкой.

### Ещё не материализованное

Ещё не материализованное — часть мира, которую система пока не создала подробно.

Это не значит, что там ничего нет. Но это также не значит, что можно создать любой удобный объект. Новая деталь должна пройти проверку:

```text
правдоподобие → необходимость → связь с регионом и местом → влияние на старые факты → фиксация
```

После фиксации новая деталь становится фактом партии и не может быть незаметно переписана.

## 4. Карта мира

Карта игры — не точная географическая сетка, а граф сохранённых мест и связей.

```text
карта = сохранённые узлы + маршруты + известность путей + журнал движения + исторические якоря
```

Узел может быть регионом, местом, локацией, минилокацией или точкой сцены.

Связь может быть дорогой, тропой, проходом, воротами, дверью, рекой, бродом, переправой, зимником, лесной просекой, берегом или иным маршрутом.

Каждый созданный узел получает постоянный идентификатор и не пересоздаётся при возвращении.

Для маршрута фиксируются:

```text
route:
  id
  from_id
  to_id
  scale
  type
  base_time
  access
  conditions
  risk
  known_to_character
  known_to_player
  seasonal_rule
  reverse_route_id
  last_used_at
```

Маршрут не обязан быть известен персонажу. Игрок может знать, что в реальной истории где-то был город, но персонаж не получает это знание автоматически.

## 5. Материализация мира

Мир расширяется кольцами.

Когда игрок действует внутри сцены, детализируется текущая минилокация и ближайшие объекты.

Когда игрок переходит внутри места, детализируются соседние локации.

Когда игрок выходит из места, детализируются дороги, подходы, промежуточные зоны, погода, риск и время.

Когда игрок идёт по известному маршруту, используется маршрут.

Когда игрок держит направление без конкретного маршрута, используется дальний курс.

Когда игрок спрашивает слухи, детализируется слуховой слой.

Когда игрок вступает в отношения, детализируется социальная сеть.

Когда игрок касается исторической реальности, уточняется исторический слой.

Дальние части мира остаются грубыми, пока не нужны. Не надо заранее подробно создавать все города, всех бояр, все дороги, все семьи и все события региона. Достаточно иметь исторически правдоподобный контур и материализовать детали по мере приближения партии.

## 6. Дальний курс

Если игрок задаёт не конкретное место, а направление — «иду на север», «держусь востока», «иду вниз по реке», «иду прочь от деревни» — система создаёт дальний курс.

Дальний курс не является обычным переходом между уже известными узлами.

Короткая формула:

```text
дальний курс = старт + направление + способ движения + прогресс + отклонение + уверенность + ориентиры + риск + исторические якоря + последствия
```

Для дальнего курса учитываются:

1. стартовая позиция;
2. направление;
3. способ движения;
4. время пути;
5. сезон;
6. погода;
7. состояние персонажа;
8. груз и снаряжение;
9. знание местности;
10. видимые ориентиры;
11. риск заблудиться;
12. исторические и хозяйственные якоря в направлении движения.

Исторический якорь — это не гарантированная точка прибытия. Он не притягивает персонажа автоматически. Но если в направлении движения есть крупная историческая, хозяйственная или дорожная реальность, LLM не должна заменять её пустотой без причины.

Персонаж не может бесконечно идти в одном направлении и оставаться рядом со стартовой точкой. После достаточного прогресса он должен прийти к одному из результатов:

1. выйти к известному или новому маршруту;
2. достигнуть природного препятствия;
3. выйти к хозяйственному следу;
4. попасть в промежуточную зону;
5. приблизиться к историческому или локальному якорю;
6. заблудиться;
7. вернуться к следам прежнего пути;
8. столкнуться с риском, погодой, людьми, зверьём, усталостью или нехваткой припасов.

## 7. В начале партии

### 1. Определяется историческая рамка

Код нормализует ввод игрока и строит закрытый набор совместимых historical-frame options из утверждённых записей. Единственный вариант выбирается кодом; при нескольких вариантах LLM возвращает только подписанный `option_id` через bounded decision protocol.

Это отвечает на вопрос:

```text
в каком времени и в какой большой исторической зоне начинается партия
```

Код не придумывает категории, историю и отсутствующие варианты. Он нормализует ввод игрока, выбирает утверждённые candidates, материализует instances, рассчитывает последствия и сохраняет прошедший gates результат.

Если игрок не указал год или регион, код формирует варианты только в пределах утверждённых периодов и регионов. Отсутствие допустимого варианта блокирует Stage 3; свободный выбор или внешний исторический факт LLM не принимается.

### 2. Отделяется общее от конкретного

Общий мир содержит широкие сведения о регионе, эпохе, соседях, дорогах, власти, хозяйстве, обычаях, войнах, слухах и рисках.

Но это ещё не факты конкретной партии.

Конкретная партия начинается только там, где выбраны:

1. стартовое место;
2. стартовая локация;
3. минилокация;
4. точка сцены;
5. персонаж игрока;
6. люди рядом;
7. предметы рядом;
8. текущее время;
9. текущая ситуация;
10. начальные напряжения.

### 3. Создаётся активный регион

Редакторский каталог задаёт регион и G0–G4; код выбирает утверждённый стартовый контур.

Активный регион должен включать:

1. природу;
2. климат;
3. сезонные ограничения;
4. дороги и водные пути;
5. экономику;
6. власть;
7. право;
8. социальные нормы;
9. соседние земли;
10. внешнее давление;
11. исторические события и личности, если они релевантны году и месту;
12. основные слухи и страхи.

Регион должен быть достаточно подробным, чтобы ограничивать и направлять игру, но не превращаться в энциклопедию всех поселений, людей и событий.

### 4. Создаются соседние регионы в виде контуров

Соседние регионы нужны не для немедленной игры, а чтобы мир не был изолированной комнатой.

У соседей должны быть:

1. направления;
2. связи;
3. торговое или военное давление;
4. слухи;
5. потенциальные маршруты;
6. примерное отношение к активному региону.

Подробно соседние регионы раскрываются только тогда, когда партия к ним приближается.

### 5. Уточняется исторический слой

Код выбирает только утверждённую историческую рамку, привязанную к региону, периоду и источникам. При нескольких допустимых рамках LLM возвращает только option_id/command_token; события, личности и слухи не создаются во время runtime.

Для каждого релевантного исторического события задаются:

1. причина;
2. участники;
3. регион влияния;
4. примерное время;
5. текущая фаза;
6. локальные признаки;
7. возможные отложенные события;
8. что персонаж может знать;
9. что персонаж не может знать.

Исторический слой должен создавать давление мира, а не рельсы сюжета.

### 6. Выбирается стартовое место

Стартовое место — конкретный узел мира внутри региона.

Код материализует стартовое место из утверждённого place template и выбранной команды:

1. что это за место;
2. зачем оно существует;
3. кто его держит;
4. кто через него проходит;
5. чем там занимаются;
6. какие правила действуют;
7. какие конфликты накопились;
8. какие дороги или проходы с ним связаны;
9. какие сезонные условия важны;
10. почему это место подходит для начала партии.

Стартовое место не должно быть произвольной сценической декорацией. Оно должно быть связано с регионом, дорогами, хозяйством, властью и текущим временем.

### 7. Место разворачивается в локации

Код материализует G5 внутри стартового G4 из утверждённого G4 materialization profile.

Для каждой важной локации задаются:

1. назначение;
2. доступность;
3. видимые объекты;
4. люди или группы;
5. проходы;
6. закрытые зоны;
7. возможные риски;
8. связь с другими локациями.

Не нужно создавать все внутренние зоны сразу с полной детализацией. Достаточно активной локации и ближайших зон, к которым персонаж может обратиться в первых ходах.

### 8. Создаётся минилокация и точка сцены

Для стартовой сцены обязательно задаются:

```text
location_id
minilocation_id
anchor_id
```

Код выбирает стартовый anchor из утверждённых G5 slot rules; LLM не создаёт и не размещает anchor:

1. у двери;
2. у ворот;
3. у костра;
4. возле саней;
5. под навесом;
6. у стола;
7. на берегу;
8. в сенях;
9. на дороге у въезда;
10. рядом с конкретным предметом или NPC.

Это нужно для честной обработки первых действий: идти, брать, говорить, прятаться, осматриваться, атаковать, убегать, искать, слушать.

### 9. Создаётся текущее состояние активной сцены

Текущее состояние сцены включает:

1. погоду;
2. время суток;
3. свет;
4. грязь, снег, холод, жару, дождь, ветер или иные условия;
5. звуки;
6. запахи;
7. движение людей;
8. доступность дороги;
9. опасность;
10. порядок;
11. дефицит;
12. настроение места;
13. видимые следы;
14. текущую позицию персонажа.

Состояние сцены становится фактом партии после проверки.

### 10. Создаётся персонаж игрока

На этом этапе вызывается отдельная процедура «Генерация персонажа игрока».

Персонаж создаётся внутри уже заданной стартовой рамки:

```text
год + сезон + регион + место + локация + минилокация + точка сцены + текущее время
```

LLM создаёт персонажа как человека, связанного с эпохой, местом и обстоятельствами, а не как абстрактную камеру наблюдения.

Результат генерации персонажа должен включать:

1. социальное положение;
2. происхождение;
3. тело и состояния;
4. характеристики и навыки;
5. знания и карту знаний;
6. память;
7. цели и страхи;
8. имущество и инвентарь;
9. долги и зависимости;
10. связи;
11. стартовую позицию;
12. причину находиться здесь.

### 11. Связываются персонаж и место

Старт должен объяснять, почему именно этот человек оказался именно в этом месте, в этой локации и именно сейчас.

Связка может строиться через:

1. работу;
2. дорогу;
3. долг;
4. бегство;
5. болезнь;
6. приказ;
7. поиск;
8. наказание;
9. родню;
10. угрозу;
11. службу;
12. торговлю;
13. плен;
14. случай, который уже имеет правдоподобную причину.

Без этой связки игрок не понимает, кто он, зачем он здесь и почему ему важно происходящее.

### 12. Создаются люди вокруг

Код материализует NPC и группы рядом с персонажем из региональных profile sets; уровни `background|scene|key` определяют полноту, а не автора экземпляра.

Используются три уровня:

1. фоновый NPC;
2. сценический NPC;
3. ключевой NPC.

Фоновые NPC нужны для видимости сцены: кто рядом, что делает, кто может заметить действие, кто создаёт шум, порядок или угрозу.

Сценические NPC нужны для текущего взаимодействия: разговор, торговля, отказ, помощь, проверка, конфликт, угроза, спор, свидетельство.

Ключевые NPC нужны для долговременных последствий: память, долг, обещание, конфликт, зависимость, тайна, ресурс, доступ или повторная встреча.

Уровень NPC определяется не количеством текста, а тем, сколько состояния игра обязана помнить о нём для честных последствий.

### 13. Создаётся предметный слой

Код материализует предметный слой активной сцены из item/container/property profiles и causal rules.

Он включает:

1. видимые вещи;
2. владельцев вещей;
3. держателей вещей;
4. контейнеры;
5. закрытые места;
6. следы;
7. инструменты;
8. пищу;
9. оружие;
10. одежду;
11. животных;
12. источники света;
13. проходы;
14. преграды;
15. вещи персонажа;
16. чужое имущество;
17. вещи с социальным или правовым риском.

Предметы не должны появляться задним числом только потому, что игрок их попросил.

Если значимый контейнер, тайник, закрытая комната, амбар, сундук, мешок, повозка или склад уже стал частью активной сцены, его содержимое должно быть либо зафиксировано заранее, либо создано как правдоподобный профиль места до результата действия.

Нельзя сначала позволить игроку открыть сундук, а потом свободно придумывать, что в нём было, если сундук уже был значимым объектом партии.

Предметный слой должен учитывать:

1. видимость;
2. доступ;
3. владельца;
4. держателя;
5. вес;
6. состояние;
7. социальный риск;
8. занятые руки;
9. возможность быстро достать предмет;
10. влияние на нагрузку;
11. право владения;
12. риск обвинения, кражи, наказания или подозрения.

### 14. Создаются скрытые и неизвестные слои

Часть мира уже существует, но персонаж её не видит.

Часть мира пока неизвестна даже системе и будет материализована позже.

Эти состояния нужно различать:

```text
не видно ≠ можно придумать что угодно
ещё не создано ≠ этого точно нет
```

Скрытые слои могут включать:

1. мотивы NPC;
2. тайники;
3. скрытые предметы;
4. закрытые помещения;
5. слухи в движении;
6. угрозы;
7. отложенные события;
8. планы NPC;
9. исторические процессы;
10. следы, которые персонаж ещё не заметил.

Скрытое не показывается игроку напрямую. Оно проявляется через следы, слухи, реакции людей, последствия, прямое наблюдение или успешные действия персонажа.

### 15. Создаются начальные напряжения

LLM задаёт начальные напряжения, из-за которых мир уже движется.

Примеры:

1. долг;
2. ожидание;
3. непогода;
4. спор;
5. голод;
6. угроза;
7. чужие люди;
8. задержка;
9. слух;
10. болезнь;
11. приказ;
12. приближающееся событие;
13. закрывающаяся дорога;
14. пропажа;
15. чужая вещь при персонаже;
16. необходимость принять решение.

Если напряжение должно проявиться позже, оно сохраняется как отложенное событие.

Отложенное событие должно иметь:

```text
причина
условие срабатывания
примерное время или триггер
результат
кого или что затрагивает
что будет видно персонажу
```

Мир должен начать двигаться независимо от игрока, а не ждать его как декорация.

### 16. Всё проверяется на согласованность

Code validators проверяют, а LLM может проводить только отдельный аудит без права менять артефакт:

1. год;
2. регион;
3. сезон;
4. власть;
5. право;
6. социальные роли;
7. исторические события;
8. предметы;
9. дороги;
10. карту;
11. текущую позицию;
12. память персонажа;
13. карту знаний персонажа;
14. знания NPC;
15. скрытые слои;
16. видимую сцену;
17. имущество и владельцев;
18. доступность локаций;
19. состояние тела;
20. начальные напряжения.

Они не должны противоречить друг другу.

Код выполняет формальные и доменные проверки, материализует instances и рассчитывает последствия по утверждённым правилам. LLM проводит только явно назначенный аудит либо выбирает один вариант bounded decision; код проверяет ответ и сохраняет change set.

### 17. Факты партии фиксируются

После проверки старт становится реальностью этой партии.

Код записывает состояние:

1. историческую рамку;
2. активный регион;
3. соседние регионы в виде контуров;
4. исторические события и личности;
5. место;
6. локации;
7. минилокацию;
8. точку сцены;
9. `current_position`;
10. персонажа игрока;
11. NPC и группы;
12. предметы;
13. владельцев и держателей вещей;
14. погоду;
15. время;
16. маршруты;
17. известные и неизвестные персонажу пути;
18. угрозы;
19. слухи;
20. долги;
21. скрытые процессы;
22. отложенные события;
23. журнал стартовой фиксации.

Дальше рассказчик не должен переизобретать место, людей, вещи и условия.

### 18. Собирается видимое состояние

LLM получает только то, что персонаж может видеть, слышать, чувствовать, помнить, понимать или разумно предполагать.

Скрытые мотивы, тайные вещи, будущие события и объективная карта мира не показываются игроку и не должны попадать в прозу как знание персонажа.

Видимое состояние включает:

1. где персонаж находится в понятной для игрока форме;
2. что происходит сейчас;
3. кто рядом;
4. что видно;
5. какие предметы доступны взгляду;
6. какая погода и свет;
7. что персонаж ощущает телом;
8. что он помнит о своём положении;
9. какие очевидные действия доступны;
10. какие опасности или напряжения заметны.

### 19. Пишется начальная проза

LLM-рассказчик пишет первый текст только из утверждённого видимого состояния.

Проза должна объяснить:

1. кто персонаж;
2. где он;
3. почему он здесь;
4. что с ним не так, если есть проблема;
5. что происходит;
6. что видно;
7. кто рядом;
8. какая погода;
9. что настораживает;
10. какие очевидные действия доступны.

Рассказчик не создаёт новые факты. Он только формулирует уже проверенную сцену.

## 8. По ходу партии

### 1. Каждый ход начинается с текущего состояния

Ход начинается не с новой фантазии, а с уже зафиксированного состояния партии.

Code-owned обработчик загружает релевантные данные:

1. историческая рамка;
2. активный регион;
3. текущее место;
4. текущая локация;
5. минилокация;
6. точка сцены;
7. `current_position`;
8. текущее время;
9. погода;
10. персонаж игрока;
11. числовые состояния персонажа;
12. активные состояния;
13. характеристики и навыки;
14. инвентарь и снаряжение;
15. нагрузка;
16. карта знаний персонажа;
17. известные персонажу маршруты;
18. люди рядом;
19. профили NPC нужного уровня;
20. видимые предметы;
21. скрытые предметы активной сцены, если они нужны для проверки;
22. долги;
23. слухи;
24. угрозы;
25. отложенные события;
26. скрытые процессы, если они могут повлиять на последствия;
27. журнал последних изменений.

Ни одна LLM не получает этот полный пакет. Bounded-decision agent видит только закрытые options и необходимые visible reasons; narrator получает только audited visible context. Скрытые данные остаются у кода и узких audit gates.

### 2. Понимается намерение игрока

Код сохраняет слова игрока как намерение и сопоставляет их с зарегистрированными command handlers. Если подходит несколько команд, LLM выбирает только из закрытого списка; её ответ не становится фактом мира.

Типовые намерения:

1. осмотреться;
2. идти;
3. бежать;
4. говорить;
5. спрашивать;
6. искать;
7. брать;
8. использовать предмет;
9. нападать;
10. защищаться;
11. ждать;
12. торговаться;
13. лгать;
14. вспоминать;
15. работать;
16. прятаться;
17. слушать;
18. следить;
19. лечить;
20. есть;
21. спать;
22. договариваться;
23. нарушать порядок;
24. двигаться по маршруту;
25. держать дальний курс.

Если действие неоднозначно, code-owned command registry формирует закрытый набор допустимых трактовок. LLM может выбрать только один предложенный `option_id`; при пустом наборе действие блокируется, а свободная трактовка не принимается.

### 3. Выбирается подсистема обработки

После определения намерения зарегистрированный кодовый handler направляет действие в нужную игровую логику.

```text
если действие — перемещение → используется система перемещения
если действие — бой → используется боевая система
если действие — предмет → используется система предметов, имущества и инвентаря
если действие — разговор, просьба, торг, обман или угроза → используется профиль NPC и социальная логика
если действие занимает время → используется система времени
если действие затрагивает тело → обновляются состояния
если действие касается оружия или брони → учитываются снаряжение, право ношения, вес и социальный риск
если действие касается исторической реальности → проверяется исторический слой
если действие касается скрытого знания → проверяется карта знаний персонажа и доступные источники
```

Это не отдельная новая механика, а порядок выбора уже существующих правил.

### 4. Проверяется доступность действия

Кодовый handler проверяет по сохранённому состоянию, может ли персонаж это сделать физически, социально и по ситуации.

Нужно проверить:

1. видит ли персонаж объект;
2. знает ли он дорогу;
3. находится ли объект в пределах доступа;
4. свободны ли руки;
5. хватает ли сил и бодрости;
6. не мешают ли раны, голод, усталость, холод, страх или груз;
7. есть ли право входить, брать, говорить, требовать, носить оружие;
8. кто может заметить действие;
9. не мешает ли погода;
10. не закрыт ли проход;
11. не противоречит ли действие уже созданным фактам;
12. не требует ли действие времени, проверки или риска.

Заявка игрока — повод проверить мир, а не переписать его.

### 5. Мир не подстраивается под желание игрока автоматически

Если игрок хочет найти предмет, встретить человека, получить помощь, узнать слух или попасть в закрытое место, код сначала проверяет сохранённое состояние и approved rules. При допустимой неоднозначности он может запросить у LLM bounded decision, где каждый вариант уже содержит проверенные actor/target, preconditions, cost, known risks, visible reason и state version. LLM не отвечает на вопросы ниже свободным payload; их рассчитывает код:

1. существует ли это уже;
2. могло ли это быть здесь заранее;
3. кто владеет этим;
4. кто имеет доступ;
5. почему это не было видно раньше;
6. какой риск создаёт действие;
7. не ломает ли это старые факты;
8. нужно ли создавать новую деталь или отказать.

Удобный ответ не имеет приоритета над уже созданной реальностью партии.

### 6. Используется уже созданный фрагмент мира

Если нужный фрагмент уже создан, используется он.

Приоритет имеют:

1. уже существующие NPC;
2. предметы;
3. маршруты;
4. контейнеры;
5. владельцы;
6. слухи;
7. обязанности;
8. скрытые факты;
9. старые решения;
10. журнал изменений;
11. состояние посещённых мест.

Их нельзя заменить более удобной версией ради текущего ответа.

### 7. Новый фрагмент материализуется осторожно

Если фрагмент мира ещё не создан, он создаётся только там, где это естественно.

Допустимые основания:

1. соседняя зона;
2. дорога;
3. двор;
4. знакомый человек;
5. содержимое правдоподобного места;
6. локальный слух;
7. предмет, который логично мог быть здесь заранее;
8. обычный NPC для этого места;
9. след уже существующего события;
10. промежуточный узел маршрута.

Новая деталь должна вытекать из:

1. региона;
2. года;
3. сезона;
4. места;
5. локации;
6. статуса персонажа;
7. хозяйства;
8. социальной логики;
9. уже существующих фактов.

После материализации новая деталь проходит проверку и фиксируется.

### 8. Неизвестность не равна свободной выдумке

Если предмет, человек, дорога или слух не были описаны, это не доказывает, что их нет.

Но и не разрешает создать удобный ответ.

Порядок такой:

```text
проверить approved category/profile/rule → проверить applicability и необходимость → материализовать допустимый instance или hard block → зафиксировать trace
```

Если утверждённой исторической детали или допустимого варианта нет, runtime регистрирует data gap и не создаёт факт, локальную версию знания или слух. Слух может быть материализован только из отдельной approved rumor category/profile/rule; внешнее пополнение выполняется offline/editorial workflow.

### 9. NPC действуют от своих причин

NPC не ждут игрока как декорации.

У них есть:

1. работа;
2. страхи;
3. интересы;
4. обязанности;
5. отношение к власти;
6. память;
7. ближайшие планы;
8. ограничения;
9. доступ к ресурсам;
10. способность видеть, слышать и реагировать.

NPC могут помогать, мешать, лгать, уходить, звать других, торговаться, молчать, бояться, сопротивляться, подчиняться старшему или действовать против игрока.

Если фоновый NPC вступает в адресное взаимодействие, влияет на сцену или должен оставить последствия, его профиль повышается до сценического или ключевого.

### 10. Время и мир движутся независимо

Если игрок ждёт, спорит, идёт, спит, ищет, работает, сражается, лечится, торгуется или тратит время иначе, меняется время.

После значимого действия применяется цепочка:

```text
действие → длительность → новое время → состояния тела → NPC → место → события → видимая сцена
```

Проверяется:

1. сколько времени прошло;
2. сменилась ли часть суток;
3. изменилась ли погода;
4. изменились ли сытость, бодрость, здоровье или активные состояния;
5. что сделали NPC;
6. изменилось ли место;
7. сработали ли отложенные события;
8. появились ли видимые последствия.

Скрытые процессы могут двигаться даже тогда, когда игрок их не видит.

### 11. Последствия считаются до прозы

Сначала код применяет handler выбранной команды, повторно проверяет preconditions и рассчитывает формальный change set.

Нужно проверить:

1. кто услышал;
2. кто увидел;
3. кто понял;
4. кто ошибся;
5. что переместилось;
6. что потеряно;
7. что найдено;
8. кто разозлился;
9. что стало известно;
10. что испортилось;
11. что стало опаснее;
12. сколько времени прошло;
13. какие состояния изменились;
14. какие маршруты открылись или закрылись;
15. какие отношения изменились;
16. какие отложенные события появились или сработали.

Проза пишется только после этого.

### 12. Проверки и риск

Если действие спорное, опасное или результат не очевиден, нужна проверка.

Общая формула проверки:

```text
d20 + бонус характеристики + бонус навыка + модификатор состояния + модификатор предмета/снаряжения + обстоятельства >= сложность
```

Проверка не отменяет реальность сцены. Даже успех должен учитывать тело, время, свидетелей, закон, владельцев вещей, погоду, вес, расстояние, состояние предметов и последствия.

Если действие невозможно по фактам мира, проверка не назначается. Нельзя броском открыть то, чего физически нет, убедить того, кто не может согласиться, или пройти через место, к которому нет доступа без нового события.

### 13. Новые факты проходят проверку

Перед сохранением code validators и независимый audit gate проверяют, не нарушают ли новые факты:

1. историю;
2. год;
3. регион;
4. сезон;
5. социальный порядок;
6. физику места;
7. карту;
8. маршруты;
9. уже созданные связи;
10. скрытые факты;
11. владельцев вещей;
12. состояние предметов;
13. доступность локаций;
14. границы знания персонажа;
15. память NPC;
16. время и отложенные события.

Если противоречие найдено, факт не сохраняется. Код возвращает формальный validation failure и repair route к утверждённым данным; LLM не вправе свободно переписывать факт или превращать его в слух. Ошибка, ложное знание, непонимание персонажа и нерешённая неопределённость допустимы только как заранее определённые типы состояния с approved source reference.

### 14. Изменения фиксируются в состоянии партии

Только проверенные изменения становятся фактами.

Фиксироваться могут:

1. новое положение персонажа;
2. изменённое время;
3. состояние тела;
4. активные эффекты;
5. отношения;
6. предметы;
7. владельцы и держатели;
8. раны;
9. слухи;
10. обещания;
11. долги;
12. смерть;
13. пропажа;
14. открытая или закрытая дверь;
15. найденный след;
16. новая доступная зона;
17. новый или изменённый маршрут;
18. повышение профиля NPC;
19. отложенное событие;
20. изменение исторической фазы;
21. изменение знания персонажа.

Код записывает эти изменения и не сочиняет их сам.

### 15. Скрытые процессы обновляются

Не всё должно показываться игроку.

Скрыто могут измениться:

1. движение NPC;
2. распространение слуха;
3. приближение угрозы;
4. ухудшение погоды;
5. изменение фазы исторического события;
6. рост подозрения;
7. решение старшего NPC;
8. перемещение предмета владельцем;
9. закрытие доступа;
10. ухудшение болезни;
11. подготовка засады;
12. уход свидетеля.

Игрок узнаёт об этом только через видимые последствия, следы, слухи, реакции людей или прямое наблюдение.

### 16. Обновляется журнал изменений

После хода сохраняется внутренний журнал изменений.

Журнал нужен не для UI, а для памяти мира и защиты от переписывания фактов.

В журнале фиксируется:

1. что изменилось;
2. почему изменилось;
3. когда изменилось;
4. кто видел;
5. кто знает;
6. что стало известно персонажу;
7. что осталось скрытым;
8. какие новые факты созданы;
9. какие отложенные события запущены;
10. какие проверки были важны для результата.

Журнал помогает LLM не переизобретать старые факты и не менять прошлое без причины.

### 17. После каждого хода собирается видимое состояние

Игрок видит не всю базу мира, а только актуальную сцену.

Видимое состояние отвечает на вопросы:

1. где персонаж находится;
2. что теперь перед ним;
3. кто рядом;
4. что изменилось;
5. что он понял;
6. что мог услышать;
7. что может попробовать дальше;
8. что мешает;
9. что угрожает;
10. что требует решения.

Скрытые мотивы, будущие события, объективная карта мира и тайные процессы не раскрываются в прозе без основания.

### 18. Рассказчик пишет только из видимого состояния

LLM-рассказчик не добавляет новые предметы, тайные мотивы, спасительные выходы, скрытых свидетелей, внезапных помощников и удобные совпадения.

Его задача — ясно и выразительно описать уже утверждённую сцену.

Порядок ответа:

```text
сначала последствия и состояние мира → потом видимое состояние → потом проза
```

Игровой ответ должен быть не «что красиво написать», а «что реально могло произойти в этом мире с этим персонажем в этой ситуации».

## 9. Особые случаи хода

### Перемещение

Если игрок перемещается, используется система перемещения.

Нужно определить:

1. текущую позицию;
2. цель или направление;
3. известен ли маршрут;
4. есть ли доступ;
5. сколько времени нужно;
6. нужен ли риск;
7. как расходуются состояния;
8. что делают NPC;
9. сработали ли события;
10. какая новая сцена видна.

Если игрок возвращается назад, используется `last_route_id` или сохранённый маршрут, а не новая генерация старого места.

### Осмотр и поиск

Если игрок осматривается или ищет, код проверяет видимость, расстояние, свет, занятость рук, состояние персонажа, скрытые предметы, признаки и утверждённые правила места.

Осмотр не создаёт предмет из воздуха. Он может раскрыть уже видимое, заметить признак скрытого, уточнить материализованный слой или честно показать отсутствие заметного результата.

### Предметы и имущество

Если игрок берёт, использует, прячет, отдаёт, продаёт, ломает или чинит предмет, код проверяет:

1. где предмет;
2. видит ли его персонаж;
3. может ли достать;
4. кто владелец;
5. кто держатель;
6. заметят ли действие;
7. сколько предмет весит;
8. в каком он состоянии;
9. какие руки заняты;
10. какой социальный или правовой риск возникает;
11. меняется ли инвентарь или только имущественная связь.

Недоступное имущество не считается инвентарём.

### Разговор и социальное действие

Если игрок говорит, просит, угрожает, торгуется, врёт или давит статусом, LLM использует профиль NPC и социальную логику.

Проверяется:

1. знает ли NPC персонажа;
2. считает ли своим или чужим;
3. чего NPC хочет;
4. чего боится;
5. кому подчиняется;
6. что может дать или запретить;
7. что знает;
8. что скрывает;
9. кто слышит разговор;
10. какие последствия будут у согласия или отказа.

NPC не обязан быть полезным. Его поведение должно вытекать из статуса, страха, интереса, долга, памяти и ситуации.

### Бой и насилие

Если игрок нападает, защищается, угрожает оружием или участвует в драке, используется боевая система.

До прозы проверяются:

1. дистанция;
2. оружие;
3. броня;
4. руки;
5. состояние тела;
6. вес и нагрузка;
7. видимость;
8. свидетели;
9. социальный риск;
10. возможность побега;
11. время;
12. травмы;
13. последствия для NPC, места и закона.

Бой не должен существовать отдельно от мира. После боя меняются свидетели, кровь, шум, страх, отношения, право, слухи, раны, предметы и доступность места.

### Время, ожидание, сон и работа

Если действие занимает время, используется система времени.

Короткая формула:

```text
время = длительность действия + изменения мира + последствия
```

После времени обновляются:

1. состояния персонажа;
2. NPC;
3. место;
4. погода;
5. отложенные события;
6. исторические фазы, если они связаны с текущим временем;
7. видимая сцена.

### Историческая реальность

Если игрок касается крупного исторического узла, код проверяет pinned historical layer и его период применимости; LLM может лишь аудитировать уже собранный source-backed package.

Нельзя:

1. произвольно менять известную историческую личность;
2. переносить событие без причины;
3. давать персонажу знание будущего;
4. создавать дубль существующего события;
5. делать крупную личность случайно доступной;
6. менять политическую реальность ради удобной сцены.

Можно:

1. показать локальные последствия;
2. слухи;
3. страх;
4. распоряжения;
5. движение людей;
6. изменение цен;
7. закрытые дороги;
8. бытовое влияние большой истории на маленьких людей.

## 10. Сохранение состояния партии

Состояние партии должно хранить не всю возможную Русь, а всё, что уже стало фактом этой партии.

Минимально сохраняются:

```text
party_state:
  historical_frame
  active_region
  neighboring_region_outlines
  historical_layer
  world_graph
  current_position
  player_character
  character_knowledge_map
  known_routes
  active_place
  active_location
  active_scene_state
  npcs
  npc_groups
  items
  containers
  ownership
  inventory
  equipment
  weather
  time
  visible_state
  hidden_state
  deferred_events
  rumors
  debts
  threats
  recent_changes_log
```

Не все поля обязаны быть одинаково подробными. Подробность зависит от близости к партии и вероятности взаимодействия.

Главное — сохранить утверждённые факты так, чтобы следующие ходы не пересоздавали мир заново.

## 11. Проверка перед прозой

Перед каждой игровой прозой LLM должна ответить на внутренние вопросы:

1. Где сейчас персонаж по `current_position`?
2. Что персонаж реально видит?
3. Что он может знать, а что не может?
4. Какие факты уже сохранены и имеют приоритет?
5. Что изменилось после действия?
6. Сколько времени прошло?
7. Изменились ли состояния тела?
8. Кто из NPC заметил действие?
9. Какие предметы переместились, появились в видимости или стали недоступны?
10. Какие маршруты открылись, закрылись или изменились?
11. Сработали ли отложенные события?
12. Не нарушены ли история, право, социальная логика и карта?
13. Что надо сохранить до текста?
14. Что можно показать игроку?
15. Что должно остаться скрытым?

Только после этого пишется художественный ответ.

## 12. Запреты

Нельзя:

1. создавать мир заново при каждом ходе;
2. хранить позицию персонажа только в прозе;
3. подменять неизвестность удобной выдумкой;
4. создавать предметы по желанию игрока без проверки;
5. менять владельца, если уже был зафиксирован другой владелец;
6. делать скрытое знание видимым без источника;
7. давать персонажу знание будущих исторических событий;
8. создавать дубль исторического события;
9. превращать всех NPC в полные профили без причины;
10. оставлять NPC декорациями, если прошло значимое время;
11. двигать время без причины;
12. не двигать время, если действие явно требует времени;
13. писать прозу до расчёта последствий;
14. исправлять провал LLM заглушкой;
15. заменять уже созданное место более удобной версией;
16. бесконечно продолжать дальний курс без прогресса, ориентира, препятствия, события или переходной зоны;
17. выдавать объективную карту мира как знание персонажа;
18. забывать вес, доступ, владельца и социальный риск предметов;
19. отделять бой, предметы, NPC и время от последствий мира;
20. сохранять противоречивые факты без явной пометки.

## 13. Короткие формулы

```text
мир = историческая рамка + активный регион + сохранённые места + NPC + предметы + маршруты + скрытые процессы + время
```

```text
старт партии = рамка + регион + место + позиция + персонаж + NPC + предметы + напряжения + проверка + фиксация + видимая проза
```

```text
позиция = регион → место → локация → минилокация → точка сцены
```

```text
карта = сохранённые узлы + связи + известность путей + журнал движения + исторические якоря
```

```text
ход = состояние партии + намерение игрока + проверка доступности + подсистема + последствия + фиксация + видимое состояние + проза
```

```text
материализация = правдоподобие + необходимость + связь с миром + проверка противоречий + сохранение
```

```text
время хода = длительность → состояния → NPC → место → события → видимая сцена
```

```text
историческое событие = причина + участники + место + время + фазы + последствия + доступное знание
```

```text
дальний курс = направление + прогресс + отклонение + ориентиры + исторические якоря + последствия
```

```text
видимое состояние = восприятие персонажа + память персонажа + понятные признаки + доступные действия
```

## 14. Главное правило

Мир сначала проверяет, потом отвечает.

Игровой ответ должен рождаться не из желания красиво продолжить текст, а из вопроса:

```text
что реально могло произойти в этом мире с этим персонажем в этой ситуации
```

Код рассчитывает факты, материализацию и последствия, валидирует и фиксирует состояние. LLM выбирает только из закрытых команд, когда это явно требует policy, и формулирует прозу из visible context. Проза идёт последней.
